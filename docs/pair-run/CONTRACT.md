# 接口契约（改动要带 `--contract-change` 并当场留决策）

> **这是整套机制的承重墙。** 两个角色都可以落笔,但改它的那次交接要带
> `--contract-change` 并当场留决策;本轮**不**要求对方签字确认,
> 换来的观测量是 `report` 里的契约变更频率 —— 异常了就该收紧。
>
> 两个 agent 从不交谈,只通过这份契约对齐。契约含糊 → tester 测
> `login() -> token`,dev 写 `authenticate() -> Session`,两边各自都"对",
> 合起来是废的。
>
> 规则:**没写进这份文件的东西,tester 不许断言。**
> 反过来也成立:**这份文件只描述从外面看得见的东西**,不规定怎么实现。
>
> **第三轮的主题是「文档与代码的关系」**,两节(开工前复查把原计划的
> 「副产物路径」一节删了 —— `ignore_paths` 已经做到它要的事)。
> 简报那三节是前两轮的产物,已全部落地并有测试守着 —— 留在这里是为了
> 不被改坏,不是本轮工作项。

## 已经落地的部分（不是本轮工作项，写在这里是为了不被改坏）

`status` 在**轮到当前角色时**写 `.pair/.last-brief.md`,**覆盖式**。
文件开头恒为:

```
# 回合简报

- 角色: tester
- 工作项: W1 [feature]
- 阶段: spec
- 测试: GREEN
```

第 1 行固定 `# 回合简报`;第 2 行空;第 3–6 行是四个 `- <字段>: <值>`
(**半角冒号 + 一个空格**),顺序固定。取值:`角色` 为 `tester`/`dev`;
`工作项` 为 `<ID> [<类型>]`,无进行中工作项时写 `(无)`;`阶段` 为
`idle`/`spec`/`impl`/`review-impl`/`review-test`;`测试` 只有 `GREEN`/`RED`。

## 简报的记忆段落

- 依据: 人类定稿

**这一节是 P1-4 存在的理由。** 当前落盘的四行头部里没有"这一回合 agent
读到了哪条决策",而那正是它要留下的凭据。

### `.pair/.last-brief.md` 的记忆段落

**位置** 紧跟头部四行之后:先一个空行,然后是记忆段落。文件仍以一个换行结束。

**内容** 与 `status` 注入到终端的记忆内容**逐字一致**,但**只要内容本身** ——
终端上包着它的两条 `=` 分隔线与「你不在场时留下的东西」那行标题
**不写进简报**。

一份带记忆段落的完整示例（逐字节精确）:

```
# 回合简报

- 角色: tester
- 工作项: W1 [feature]
- 阶段: spec
- 测试: GREEN

--- 本工作项笔记 (docs/pair-run/notes/W1.md) ---
这一项试过直接改 X,不行,因为 Y。
--- 相关决策 (docs/pair-run/DECISIONS.md) ---
## W1 — 某条结论
- 理由: ……
- 已否决: ……
- 影响路径: `a.py`
```

**什么算「有记忆内容」** 只要 `status` 向终端注入了记忆块就算有 ——
**包括**有工作项但还没写笔记时那段「本工作项还没有笔记」的提示。
它是 agent 实际读到的东西,照写进简报。

**没有记忆内容时** 记忆段落连同**它前面那个空行**一起省略,文件就是四行
头部加一个末尾换行。按上面这条判据,这只出现在:**没有进行中的工作项、
且没有影响路径相干的决策条目**(典型是 `idle`)。

上面「已经落地的部分」里那个示例带着 `工作项: W1 [feature]`,
**不能拿它当「没有记忆内容」的基准** —— 那个组合按现状不可达。

**`status` 提前结束时** 终端没有打印记忆注入(例如 PLAN 里的工作项已全部
完成、`status` 提前收尾那一次),简报**同样没有记忆段落**。
「同一次取值」优先于「轮到自己就写」—— 简报要复现的是终端当次真的打印了
什么,不是"本该打印什么"。

**截断** 注入到终端的内容本身若已被截断(笔记尾部截断、决策条数与字符上限),
简报写的就是**截断之后**的那份 —— 简报要复现的是"agent 实际读到了什么",
不是"文件里原本有什么"。

**不是自己回合时** 不写,**也不清空**:该文件的内容与修改时间都不得变化。
上一次的简报要留着给人类看。

**不做** 不为简报单独计算记忆内容。简报与终端必须来自同一次取值 ——
两处各算一遍,就有了两个可能不一致的答案,而这一节的全部意义是"可对质"。

## 简报的降级与忽略

- 依据: 人类定稿

它是可观测性,不是门禁。**不许因为写简报失败而让 `status` 失败。**
(承诺范围见下面的「边界」:只兜 `OSError`。宽泛地吞掉一切异常会把实现里的
真 bug 一起吞掉,那与"可对质"的目的相反。)

### 写入失败时的 `status`

**行为** 写 `.pair/.last-brief.md` 抛 `OSError` 时,`status` 继续正常执行。

**输出** 标准输出多出**恰好一行**,以 `[简报]` 开头。

**退出码** 与不写简报时**完全相同**。

**其余输出** 完全不受影响:头部、阶段简报、记忆注入,逐字节与成功时一致。

**边界** 只兜 `OSError`(含 `PermissionError`、`IsADirectoryError`、
`OSError(ENOSPC)` 等子类)。其他异常不在这一节的承诺范围内。

### `init` 之后的 `.gitignore`

**行为** 在一个全新项目上跑完 `pair.py init` 之后,该项目根目录的
`.gitignore` 里含有 `.pair/.last-brief.md` 这一行。

**幂等** 重复跑 `init` 不会重复追加该行。

**边界** 只管 `init` 铺设的新项目。**存量项目的 `.gitignore` 不在此列** ——
它在仓库根,不属于任何角色的可写路径,由人类处理。

**不做** 不因为该行缺失而拒绝任何操作。这一条只描述 `init` 的产物。

# 第三轮:文档与代码的关系

> 前两轮的四次卡顿全部出在这里,一次都不是简报本身的问题。
> 两节的共同点:**它们描述的都是"仓库自己检查自己"的行为**,
> 不是协议对 agent 的约束。

## 路径归属的可见性

- 依据: 人类定稿

**背景** 这一节覆盖**两个时机** —— 开工前把缺口摆出来,以及真正撞上时
说清楚。边界有两个缺口,都只在第 N 个回合突然发作:按 `roles` 对
`git ls-files` 实算,**有文件不属于任何角色也没被冻结**(孤儿);
而 `ignore_paths` 里的文件**完全不受边界保护**(它的 `continue` 落在
角色与阶段判断之前),却没有任何地方把这件事摆给人看。
前两轮三次卡顿都出自前者。

孤儿的具体条数是快照,**不写进契约,也不许被断言** —— 起草时实测 33 个,
`8cf6552` 划归之后归零。要断言的是行为,不是那一轮的数字。

### `verify-setup` 的孤儿清单

**行为** `verify-setup` 对**被 git 跟踪的**每个文件判断归属。不落在
角色路径、共享路径、冻结路径、`ignore_paths`、**记忆层路径**
(`notes_dir` 与 `decisions_file`)里的,算**孤儿**。

**为什么记忆层要排除** 它被排除在前四类之外**不是配置疏忽,是
`verify-setup` 自己强制的**:落进任一角色路径、落进冻结路径、落进
`shared_paths`,三种情况本节所在的同一条命令都会 `bad()`,而放进
`ignore_paths` 等于把记忆层从边界保护里摘出去。不排除它,这条警告
**没有任何一种消除方式** —— 开箱即有、结构上不可能清零的警告,
几次之后就没人看了,真出现新孤儿时它淹在里面。

**输出** 有孤儿时打印一段警告:第一行含"孤儿"二字与孤儿总数,随后逐行
列出文件路径。**超过 10 个时只列前 10 行**,再补一行说明**还剩多少个
没列出**(总数减 10,不是总数)。

**不阻断** 这是**警告**,不是拒绝。存量项目接入时必然有大量孤儿,
阻断会让它根本进不来。`verify-setup` 的退出码不受孤儿影响。

**边界** 只看 `git ls-files`。未被跟踪的文件不算孤儿 —— 它们本来就不在
协议的管辖范围里。

### `ignore_paths` 的覆盖清单

**行为** 同一次 `verify-setup` 里,另外打印 `ignore_paths` 覆盖了哪些
**被 git 跟踪的**文件。

**输出** 有覆盖时打印一段:首行含"不受边界保护"与文件总数,随后逐行列出。
**同样超过 10 个只列前 10 行**,并补一行**还剩多少个没列出**(口径与上一节
相同)。同样是警告,不影响退出码。

**两段的先后顺序不作规定** —— 不许断言谁先谁后,和「`[简报]` 那一行的位置
不作规定」是同一个手法。

**为什么要打印它** `ignore_paths` 里的文件任何角色、任何阶段都能写 ——
这是它的用途(副产物就该这样),但"哪些文件已经不受保护"必须是人类
**看得见的决定**,而不是藏在配置里的一行。

### 越界拒绝时要说明孤儿

**行为** `handoff` 因写权限边界拒绝交接时,若越界的文件是**孤儿**
(判据与上面那一节**逐字相同**,不是"不属于任何角色"那个更宽的说法),
拒绝文案中除了原有的越界说明,还要指出该文件不属于任何角色、需要人类划归。

**末尾那句要跟着变** 原文案末尾是一句总结:"请撤销这些改动后重试。"
越界项里**有**孤儿时,这句话必须改成分情况的说法 —— 额外讲明其中有几个
不属于任何角色、多半不是你改的,应当先找人类划归,**不要直接撤销**。
越界项里**没有**孤儿时,末尾维持原样。

**为什么连末尾一起改** 开工前的警告与真正撞上的时刻相隔几十个回合。
前两轮实测:拒绝文案说的是"请撤销这些改动后重试",而那个文件是人类刚改的 ——
agent 照做就会撤销掉不是它写的东西。**只在中间加一句提示、末尾却留着一句
相反的指令,agent 照样照后者做**,这一节就白写了。

**不做** 不自动划归、不修改 `.pair/config.json`。**谁能写什么是人类的
决定**,脚本只负责让缺口可见。

## 文档里的代码引用

- 依据: 人类定稿

**背景** 起草时实测全部引用:绝大多数能定位到封闭 `def`/`class`,少数落在
模块级,**真正需要行号的 0 处**。行号是写作时手边有,不是内容需要 ——
而它每次插行都漂,前两轮为此烧掉两次异议与两次人类手工介入。
(同样地,处数是快照,不写死、不许断言。)

### 引用形式

**行为** 规范性文档里引用源码位置时,形式为 `` `<路径>#<符号>` ``。

**`<路径>`** 是**仓库相对路径**(如 `tests/conformance/harness.py`)。
裸文件名(`harness.py`)只在该文件名在仓库里**唯一**时才允许 ——
本仓库有 3 个 `__init__.py`,裸名解析不到唯一文件。

**`<符号>`** 是目标文件里 `def` / `class` / 模块级赋值的名字,
**包括类内方法与嵌套函数**(`pair.py` 里 `bad`、`put`、`warn` 等 6 个
嵌套函数都是文档实际指向过的东西)。

**重名必须限定** 同一个名字在该文件里出现多次时,必须写成
`<外层>.<内层>`(`Result.text`、`cmd_init.put`)。裸写重名符号时
一致性检查**失败**,并列出它在该文件里的所有候选 ——
`harness.py` 里 `run` / `git` / `read` / `exists` / `cleanup` / `__init__`
各有两处,裸名等于抽签。这与本契约既有的「小节标题重名即歧义」是同一手法。

**检查** 引用的符号在目标文件里不存在时,一致性检查**失败**,
并列出"哪份文档、引用了哪个文件的哪个符号"。

**旧形式被拒** `` `<路径>:<行号>` `` 与区间形式 `` `<路径>:<行号>-<行号>` ``
在规范性文档里**都不再允许**,一致性检查失败并指出应改成哪个符号
(取**起始行**所在的封闭符号;嵌套时取**最内层**那个)。

**历史快照豁免** 形如 `` `<路径>:<行号>@<sha>` ``(区间同理)的引用
**不参与检查**。运行报告(`dogfood-run-*.md`)与"已解决"留档记的是**当时**
的状态,把它们改写成指向当前代码的符号等于篡改历史记录;而若那个符号后来
被删,报告还会无端变红。这个形式与契约既有的 `考古观察@<sha>` 是同一个
手法,不新造概念。**不校验那个 sha 在不在本地仓库** —— 浅克隆会让它无端
变红,而这一条的目的正是**不去碰**历史记录。

**什么不算引用** 两类,**只有这两类**:

1. **```` ``` ```` 围栏代码块里的内容。** 讲解引用形式、粘贴失败输出的
   文档要靠它。
2. **目标 `.py` 文件在仓库里不存在。** `rules.md` 与 `troubleshooting.md`
   拿 `src/auth.py:42` 举例,那是虚构项目,没有符号可迁移。
   现有一致性检查已经在用这个判据(只认得出被引文件里的文件名),
   不新造概念。

**行内代码算引用。** `` `<路径>#<符号>` `` 外面那对反引号**就是**引用的
规定形式 —— 把行内代码整类豁免掉,等于所有引用都不算引用,这条检查恒真。
起草时那句「代码块与行内代码里的示例不算引用」想说的是上面第 1、2 类,
落到纸上把整条检查写没了,现予更正。

**扫描范围** 现有一致性检查的 `NORMATIVE` **全集,含
`improvements.md`**。**这个范围叫「扫描范围」,不叫「规范性文档」** ——
后者在第四轮有一个更大的定义(见「第四轮」开头的术语一节),两者差 5 份文件。
本节说的是前者。它是提案文档,在别的检查里被 `PROPOSALS` 摘出去过,
但**行号引用这一类不摘** —— 现有代码已经表过态:「提案文档也算:它的行号
引用同样指向**当前**的代码」。本仓库七成以上的行号引用在它里面,摘掉等于
迁移收益去掉七成。

**边界** 只管 `.py` 文件的引用。

**不做** 不检查符号内部的位置。符号粒度不够时,用文字描述补充
(如"`cmd_handoff` 里跑全量套件那一段"),那是给人读的,不参与判定。

# 第四轮:文档改动的授权与留痕

> 前三轮每一轮开工,人类都要手抄一次 PLAN 与契约 —— 而它给的授权其实是
> "定方向",不是"当打字员"。这两节要把这件事反过来:**agent 可以落笔,
> 但必须留下谁改的、为什么改、依据是什么。**

## 术语:「规范性文档」与「扫描范围」不是一回事

- 依据: 人类定稿

本轮两节都要判断"这次改动碰没碰规范性文档",而仓库里已经有一个近义的范围
(`test_docs_consistency.py` 的 `NORMATIVE`)。**两者不等,实算差 18 份**,
不点破就是同一个词两个外延 —— 第三轮开工前审查已经因为这类含糊报过一次。

**「规范性文档」(本轮两节用的定义)** = **所有 `.md`**,除去记忆层
(`notes_dir` 与 `decisions_file`)、评审目录(`shared_paths`)、
以及 **`ignore_paths` 与协议自己写的日志**。

后两类是人类在第四轮收尾时裁决补上的:`ignore_paths` 里的是副产物,
它连写权限边界都不受,再要求为它写一句理由是两套口径;协议日志里
只有 `.pair/.last-brief.md` 是 `.md`,而它进了 `.gitignore`、
在 `git status` 里从不出现 —— 写明它豁免是为了让实现与契约一致,
不是为了改变行为。

**判定用的是本回合改动的那批文件,不是 `git ls-files`。** 本回合**新建**的
`.md` 在检查那一刻还没入库 —— 照 `git ls-files` 判,**新写一份规范性文档
就完全逃过这条要求**,而新增文档恰恰最该说明为什么。判据要和写权限边界
用同一批数据(`git status --porcelain`,它包含未跟踪文件)。

**这是一个闭合定义,不是枚举** —— 新加的 `.md` 默认落在范围内,而不是默认
漏掉。第一版写成枚举(`docs/` 下的 + README + INSTALL + skill 的),实算
**漏掉 13 份**,其中包括 `AGENTS.md`、`CLAUDE.md`、`CONVENTIONS.md`、
`GEMINI.md`、`.github/copilot-instructions.md` —— **正是告诉每个 agent
"这是结对项目"的那批入口文件**,也正是 ADR-022 那次 sweep 漏掉过的同一批。
W4 刚用 33 个孤儿证明过枚举会漏,同一轮里不该再造一个枚举。

按这个定义算,当前仓库 64 份被跟踪的 `.md` 里有 **35 份**在范围内,
**含 `docs/pair-run/PLAN.md` 与 `docs/pair-run/CONTRACT.md`**,
也含 `examples/` 下随包分发的样板文档(它们是分发物,改了同样该有理由)。

**「扫描范围」(「文档里的代码引用」那一节用的)** = `NORMATIVE`(17 份)。
规范性文档是 35 份,少掉的 18 份里最要紧的是:`docs/pair-run/PLAN.md`、
`docs/pair-run/CONTRACT.md`、`references/` 下的 `brownfield.md` /
`contract-templates.md` / `documents.md`,以及 `AGENTS.md`、`CLAUDE.md`
这批入口文件。

**这个差是既成事实,不是本轮要消除的东西。** 符号引用检查扫不到那 18 份
(其中 `PLAN.md`、`CONTRACT.md` 与 `references/` 下三份是规范性内容,
其余多为入口文件与 `examples/` 下的样板),是一个独立的缺口 ——
**开放条目 16**;本轮只负责**不再用同一个词指两件事**。

## 文档改动要带理由

- 依据: 人类定稿

**背景** 归属其实已经有了,但依据不是 `git blame` —— 两个 agent 共用同一个
git 身份,`git log --author` 分不出谁是谁。**唯一的归属证据是 `handoff`
写进提交正文的 `role=<角色> phase=… item=…` 那一行**,它由脚本写入而非
agent 自述,可靠。缺的是**理由与文档的绑定**:一次交接可能改了实现加三份
文档,而说明只有提交标题那一句。

### `--doc-reason`

**行为** 本回合的改动里若含**规范性文档**,`handoff` 要求
`--doc-reason "<为什么改>"`,缺了就拒绝交接。

**范围** 按上面「术语」一节的**规范性文档**。
**过程文档豁免** —— 笔记与评审记录本身就是理由,再要一句说明是纯噪音。

**留痕** `--doc-reason` 的内容进提交正文,与 `--allow-deletion` /
`--no-decision` / `--drafter` 同一手法:**不是放行,是强制留痕**。

**判据取 `handoff` 校验那一刻的改动,不是提交内容** 说"回合开始时的工作区"
是不准确的 —— 全仓没有任何一处在回合开始时快照工作区,照那句话去实现会去找一个
不存在的快照点。准确的说法是 **`handoff` 开头 `changed_entries()` 抓到的那一批,
即 `tick_plan_item` 写入之前**(实测:`changed_entries` 在写权限边界校验之前,
`tick_plan_item` 在其后一百多行)。理由是 `handoff` 完成一个工作项时会
自己去 `PLAN.md` 里勾选那一项(`tick_plan_item`),而那次写入发生在写权限
边界校验**之后**。若按"这次提交里含哪些文件"判定,**每一次完成工作项的交接
都会被要求 `--doc-reason`**,而那个改动根本不是 agent 做的。
所以判据必须是回合开始时 `git status` 看到的那批改动。

**不做** 不校验理由写得好不好。脚本查得了"有没有写",查不了"写得对不对"
—— 后者靠对方评审。

### 路线图与计划的**改写**要有依据

**行为** 改动落在 `docs/improvements.md` 上时,分两种:

- **纯追加**(该文件本次改动的**删除行数为 0**)—— 只要 `--doc-reason`
- **有改写**(删除行数 > 0)—— 还要 `--basis "<依据>"`,否则拒绝

**`PLAN.md` 与 `CONTRACT.md` 不走这条分叉,走「冻结文件改成带声明才放行」
那一节。** 那一节对它们的要求是**无条件**的:任何改动(追加也算)都要
`--contract-change`,不带就在写权限边界那一步直接拒绝 —— 走不到本节的
追加/改写分叉。第一版把这两份文件也列在上面,那半句**对它们不可达**:
照它写用例,会写出一条"往 `PLAN.md` 追加、只给 `--doc-reason` 应当通过"的
断言,而实现必然拒绝。`--basis` 因此只作用于 `docs/improvements.md`。

**为什么要分** 路线图的新条目往往是审查中发现的待办。一刀切会让"记录一个
发现"也要先走一遍重流程,**路线图就变成不能记录发现的死文档**。

**判据** `git diff --numstat HEAD -- <文件>` 的删除行数。**必须比 HEAD,
不能用不带参数的 `git diff`** —— 后者只看未暂存的改动,agent 只要在
`handoff` 之前先 `git add` 自己那几个文件,删除行数就变成 0、直接绕过
`--basis`。(`handoff` 自己的 `git add -A` 发生在全部校验**之后**,
所以校验那一刻工作区通常是未暂存的 —— 但"通常"不是防护。)
未跟踪的新文件在 `HEAD` 里没有对应物,删除行数为 0,按纯追加处理,这是对的。
这有先例 ——
`DECISIONS.md` 的追加式检查判的是同一件事,只是那里能靠"只在末尾追加"
用 `startswith`,而路线图的新条目会插在中间,所以改用删除行数。

**`--basis` 要指向一个仓库里真实存在的路径**,不是一句散文。写
`docs/reviews/W7-review-test.md`、`docs/pair-run/DECISIONS.md` 这类**产物**,
而不是"因为我觉得更好"。

**判据是路径真实性,不是 `LOCATION_RE`。** 后者的正则是
`([\w./\-]+):(\d+)` —— **要求带行号**,而上面两个例子都不带,
拿它当判据会把契约自己举的例子全部判成不合格。允许带行号(`…md:12`),
但不强制。

**但"复用 `_known_path`"这句话不完整,要补三条,否则实现方只能猜。**
`_known_path(ref, known)` 是**谓词**,只回答"这个字符串是不是一个真路径";
它全仓唯一的调用处喂给它的是 `LOCATION_RE.group(1)`,**抽取那一步是
`LOCATION_RE` 干的,而这里正好不能用它**。所以:

- **抽取**:按空白切开 `--basis`,逐个候选去问 `_known_path`,**至少命中一个
  就算合格** —— 即**包含匹配,不是整串匹配**。`--basis "见
  docs/reviews/W7-review-test.md 的第二节"` 必须通过,那是人会自然写出来的形式。
- **行号后缀**:候选带 `:数字` 后缀时先剥掉再问,剥不出就按原样问。
- **`known` 集合**:`tracked_files(root) | {本回合改动的路径}`,与既有调用处
  逐字相同。**依据往往就是这一回合刚写的那份评审记录**,只用 `tracked_files`
  会让第一个真实用例就被拒。

**为什么要这一条**:`--doc-reason` 与 `--basis` 若都只要求非空,两者的效果
**完全一样**,叠在一起只是让人多打一行字。要求指向产物之后它们才真的不同 ——
一个是"为什么",一个是"凭什么",而后者可被对方点开核对。

**仍然不校验那份产物的内容**,只校验路径存在。"内容站不站得住"靠对方评审。
等 `discuss` 阶段落地后再收紧成"必须指向一份提案产物"。

## 冻结文件改成带声明才放行

- 依据: 人类定稿

**背景** 前三轮的实测:限制没有产生安全,只产生了**一次无法核对的代笔** ——
第三轮契约定稿由 dev 执行,它自己在 `DECISIONS.md` 里写下"tester 无法从
仓库里分辨这次改动是人类定稿还是 dev 迁就自己的实现"。而人类那一侧同样
别扭:`SETUP` 条目记着"`依据: 人类定稿` 记的是**授权定稿**,不是**逐条
通读**"。

### `PLAN.md` 与 `CONTRACT.md` 的冻结改成「带声明才放行」

**行为** 这两份文件**仍然留在 `frozen_paths` 里**,配置一个字都不用改。
`handoff` 的冻结路径拒绝分支加一个豁免:**改动落在 `plan_file` 或
`contract_file` 上、且带了 `--contract-change "<依据>"` 时放行**;
不带就照旧拒绝。

**"放行"是指跳过写权限边界里的全部三道判定,不是只跳过冻结那一道。**
只 `continue` 掉冻结分支,下一行就是越界判定 —— 实算 `writable_paths`,
这两份文件在 **spec / impl / review-impl / review-test / idle 五个阶段
全部不在 `allowed` 里**(`dev` 的 `docs/*.md` 不含子目录,`tester` 只有
`tests/conformance/**`)。豁免完照样被拒,只是拒绝理由从"冻结"换成"越界"。
所以豁免要同时跳过**冻结、越界、`scope`** 三处,逐字写进实现。

**并且孤儿判据里要排除 `plan_file` 与 `contract_file`。** 否则这两份文件
既不属于任何角色、也不在共享/冻结(已豁免)/`ignore_paths` 里,按「路径归属的
可见性」那一节的判据**它们就是孤儿**:`verify-setup` 每次都会报,而越界文案
会对着一份 agent 刚刚合法改过的文件说「不属于任何角色,多半不是你改的,
先找人类划归,不要直接撤销」—— **协议主动给出与事实相反的指令**,正是那一节
写下来要消灭的东西。这两份文件是**故意**不属于任何角色的,和记忆层同一个道理,
排除法也同一个手法。

**只豁免这两份,其余冻结路径一律不放行。** `frozen_paths` 里还有 `.pair`
与 `.claude` —— `.pair/enforcer.py` 是本轮的裁判,一个旗标就能改判官,
这条防护会整个塌掉。豁免必须按 `plan_file` / `contract_file` 这两个**配置键**
点名,不能写成"带了旗标就能改冻结路径"。

**为什么不改成划归角色(第一版的写法,已否决)** 实算过两条路都堵死:
`docs/pair-run/PLAN.md` 不匹配任何一个现有角色模式(`docs/*.md` 不含子目录),
移出 `frozen_paths` 就**立刻变成孤儿**;而划归给某一方,**另一方就永远改不了
契约**,可契约变更本该双方都能发起 —— P1-9 的目的只实现一半。并进
`shared_paths` 更不行:那个键被异议举证、评审文件命名、打回的位置引用、
范围豁免、记忆层隔离检查等多处依赖,"改了契约"会被算成"异议落到纸面"。
真正通用的解法是**第三个路径类别**(双方都能写、但要带声明),而它和
P0-7 推迟的 `artifact_paths`、P0-5 会需要的 `proposal_paths` 是同一类问题的
三个实例,**值得一起设计,不该在本轮各造一个**。本节因此走最小可行:
不新增配置键,只在既有的冻结拒绝分支上开一个按键名点名的口子。

**强制留决策** 带 `--contract-change` 的那次交接,**必须**同时在
`DECISIONS.md` 追加一条,否则拒绝。

**这是一条新检查,不是"复用已有强制"。** 现有那条("契约在工作项期间变过
就必须留决策")的实际触发点是 `target == "DONE"`,拿的是 `claim` 时记下的
`contract_sha` 去比 —— 它**确实能在工作项完成时抓到中途的契约变更**,
但抓不到"改动发生的那一刻"。W9 要的是后者,所以自己加一条,
和既有那条并存、互不替代。

**不要拿"`idle` 期间改契约它一次都不触发"当理由** —— 实跑过,`idle` 状态下
`handoff` 根本起不来(「还没有认领工作项,没有可交接的回合」),**新检查在
`idle` 期间同样一次都不会触发**。两条的真实差别只有一个:抓改动发生的那次
交接,还是抓 `target == "DONE"` 那一次。那个差别本身足够支撑新加一条;
写上那半句,读的人会以为新检查堵上了 `idle` 这个口子。

**`plan_file` / `contract_file` 上不再叠 `--basis`** 改这两份文件时,
`--contract-change` **取代** `--basis`,只需再带一个 `--doc-reason`。
理由用的是「文档改动要带理由」那一节自己写下的判据:两个都只要求非空的旗标,
效果完全一样,叠在一起只是让人多打一行字。`--basis` 与 `--contract-change`
恰好都收「依据」、恰好都只落在这两份文件上 —— 那条判据当时没有回头用在
`--contract-change` 上,现在补上。**校验强度取高的那一档**:
`--contract-change` 同样要按 `--basis` 的三条抽取规则指向真实路径。

于是一次 `PLAN.md` 改写要带的是**两个**旗标(`--doc-reason` + `--contract-change`),
不是三个。

**声明进提交正文** 与 `--drafter` 同一手法。对方在 `inbox` 里必然看到。

**两份文件的标题要跟着改** `PLAN.md` 现在的第一行写着「冻结 — agent 只读」,
`CONTRACT.md` 写着「冻结 — agent 只读,变更需双方同意后由人类修改」。
这两句在本节落地之后都是**假的**。落地时一并改掉,写明新的规矩:
两个角色都可以落笔,但要带 `--contract-change`、要留决策。

**边界** 本轮**不**要求对方签字确认。那要等 `discuss` 阶段;在此之前,
防的是"改了没人知道",不是"改了没人同意"。**这是有意的弱版本,代价写在
下面。**

**代价(必须写进取代冻结设计的那条 ADR)** 弱版本对"两个 agent 合谋改契约
去迁就实现"的防护**弱于**双方签字。缓解是 `report` 增加一行契约变更频率,
异常再收紧。**不写下这条代价就落地,等于把冻结文件买来的信任白丢掉。**

## 裁判副本的同步

- 依据: 人类定稿

**背景** 本轮的裁判是 `.pair/enforcer.py`(钉住的副本),理由正当:改
`cmd_status` 时拿正在被编辑的脚本当裁判,改坏一次就再也起不来。但那个理由
覆盖的是**一个回合**,而钉住一旦开始就没有终点。实测的后果:

```
两个文件差 122 行,grep -c orphan → pair.py 8 处、enforcer.py 0 处
```

**W4 上一轮验收通过的孤儿清单,在裁判里根本不存在** —— 整整一轮的每一次
`handoff` 都没有被它保护着,而没人发现,因为少一条警告不会让任何东西变红。
更硬的一档也已经发生:W8/W9 要给 `handoff` 加旗标,实跑

```
$ PAIR_ROLE=tester python3 .pair/enforcer.py handoff "探测" --contract-change "探测"
pair.py: error: unrecognized arguments: --contract-change 探测
```

**注册表比对挡不住这件事。** 实算:`ENFORCEMENTS` 两边都是 30 条、
`HANDOFF_INVARIANTS` 两边都是 16 条,**差集为空**。拿它当护栏会全绿地放过
上面这一整轮 —— 它长得像检测器,实际恒真。

### 不变量

**`.pair/enforcer.py` 存在时,它必须逐字节等于 `pair.py`。**
唯一的例外窗口是**一个工作项进行中**(那时 dev 正在改 `pair.py`)。

**行为** 两条:

- **`claim` 时校验。** 两者不等就拒绝认领,并打印重钉命令。校验放在
  `claim` 而不是 `handoff`,因为工作项进行中本来就该不等 ——
  放在 `handoff` 会让 dev 每一次实现都被自己拦住。
- **`DONE` 时自动重钉。** `handoff` 在 `target == "DONE"` 且全绿时,把
  `pair.py` 复制成 `.pair/enforcer.py`,并把新 sha 写进提交正文。
  **全绿就是证据** —— 那是这个协议唯一信任的东西,不另造一套。

**`.pair/enforcer.py` 不存在时这两条都不触发。** 默认用法里 `pair.py` 自己
当裁判,不存在漂移,也不该凭空多出一份副本。

**不需要改 `frozen_paths`。** 重钉的写入发生在写权限边界校验**之后**,
与 `save_state` 同一手法(实测:边界校验用的是 `handoff` 开头抓的那批改动,
`save_state` 在其后)。靠顺序,不靠豁免 —— 给 `.pair/` 开豁免就是把判官
交出去。

**位置要钉两头:在边界校验之后,而且在 `git add -A` 之前。** 只说"之后"
不够 —— 实测边界校验在 `changed_entries()` 那一行、`git add -A` 在其后
**两百多行**,中间任何位置都满足"之后"。落在 `git add -A` **之后**(比如
顺手写在 `return` 前),重钉过的 `.pair/enforcer.py` 就**留在工作区没进提交**,
于是下一个回合:对方的 `handoff` 被冻结判定拦住,而那个改动不是它做的,
撤销又会把重钉一起撤掉 —— 它没有出路。`save_state` 正好在 `git add -A`
之前,"同一手法"指的就是这个位置,写出来,不靠读者去推。

### 推论:同一个工作项里不能既加旗标又用旗标

重钉发生在 `DONE`,所以**一个工作项里新加的 `handoff` 旗标,要到下一个
工作项才可用**。这不是缺陷,是这条不变量的必然代价,写下来是为了让验收标准
不再写出做不到的事:

- W8 的「这次改写用本条新增的 `--doc-reason` 走一遍」
- W9 的「两份文件的标题一并改掉」(改标题就是改冻结文件,要 `--contract-change`)

**两条都从各自的工作项里摘出去**,挪到裁判重钉之后。

### 自举:第一次重钉要人类动手

W10 把这两条检查写进 `pair.py`,而 W10 自己的 `DONE` 是**旧裁判**执行的
—— 它没有自动重钉那段代码。所以 **W10 完成后人类要再手工重钉一次**,
从 W11 起才自动。这一条必须写在 W10 的验收标准里,否则它会以一个静默的
漂移开场,而那正是它要消灭的东西。

## 开工前校验的产物与退出码

- 依据: 人类定稿

**背景** 两处缺陷,同一条命令。

**报告路径对两个角色是同一个文件名。** 第三轮真的毁过一份结论:dev 的
`verify-setup` 在后台跑的那两分钟里 tester 提交了自己的结论,dev 没看见就
整份覆盖(`2ff494f`),靠 git 逐字节还原。`docs/reviews/` 下所有别的文件都带
`<ID>-<阶段>` 前缀、由评审文件命名检查管着,**唯独这一份是全局固定名**。

**干净工作区必然失败。** `verify-setup` 结尾无条件 `git commit`,而它
`add` 的是状态文件、那份结论、**以及本回合落在 `shared_paths` 下的改动**
(三类,不是两类)。这三类都没变时 git 拒绝空提交,整条命令 `exit 1`,
尽管上面每一项校验都打印了通过。第四轮实测撞到:契约改完想重跑一次确认,
必失败;而 git 把 "nothing to commit" 写在 stdout,所以那次失败连个说得清的
理由都没有。**状态位在 commit 之前就已保存,所以状态是对的、退出码是错的。**

### 报告按角色分

**行为** 契约审查结论的路径按**角色**分开:`docs/reviews/setup-verification-<角色>.md`,
`<角色>` 取 `tester` / `dev`。

**角色从哪来** 用仓库既有的角色解析(`PAIR_ROLE` → `.pair/whoami` → git 分支),
不是 `--drafter`。**`--drafter` 是"审查者有没有参与起草",和"你是哪个 agent"
是两个轴。**

**解析不出角色时回落,不拒绝** `verify-setup` 是新项目接入后的**第一条**命令,
那时 `PAIR_ROLE` 与 `.pair/whoami` 都可以还没配。这种情况下写回旧的单一路径
`docs/reviews/setup-verification.md`,并打印一条警告说明为什么。
**别把接入的第一步卡死。**

**新文件名要进命名豁免** `docs/reviews/` 下的顶层 `.md` 全归评审文件命名检查
管,名字对不上任何工作项 ID 就拒绝交接。所以 `setup-verification-tester.md`
与 `setup-verification-dev.md` 必须进豁免 —— 用前缀规则(`setup-verification-`)
或逐个加进固定名单都行,但**必须做**:不做的话,这一项落地当天,
第一份新报告一出现在工作区就会把下一次交接卡死。

**两份都在时读哪一份** **角色文件优先,缺失才回落到旧的单一路径。**
不读并集 —— 读并集的话,一个角色可以交 120 字废话、靠另一份把小节名点满。

**兼容路径存在时要说出来** 回落到旧单一路径时打印一条警告:它是两个角色
共用的旧位置,建议改名。**判据是"这条警告出现了"**,不是"检测到两个角色都写过"
—— 后者在旧文件里没有任何可读的角色痕迹,任何用例都会恒真。

**不做** 不自动搬迁已有的那一份。搬文件是人类的决定。

### 没有待提交内容时不失败

**行为** `git add` 之后**索引里没有差异**时,`verify-setup` **不提交,也不失败**:
所有校验通过就 `exit 0`。

**判据是索引,不是工作区。** 判据必须是"这次 `add` 的那批路径有没有产生索引差异"
(`git diff --cached --quiet -- <那批路径>` 之类),**与工作区其余部分无关**。
拿"工作区干净"当判据是错的:`changed_entries` 带未跟踪文件,于是
`src/` 下有一份未跟踪的偷跑实现时工作区永远不干净 → 照样提交 → 照样空提交 →
**缺陷原样保留,而用例是绿的**。

**输出** 这种情况下标准输出要含字面子串 **`没有需要提交的改动`**。
这八个字是契约规定的,不得改写成同义词 —— tester 只能断言子串。

**其余输出不变** 跳过提交时,后面那段关于"工作区里有未提交的代码改动、
没有被本次提交带上"的警告**照打**:它的触发条件和提交与否无关。

**边界** 只改"索引里没有差异"这一种情形。有差异时的行为一个字不变。

## 校验与沉淀的有效期

- 依据: 人类定稿

**背景** 两条强制在同一个形状上出错:**一个过期的"做过了"被当成仍然有效**,
或者反过来,**一个仍然有效的"做过了"被当成没做**。

`setup_verified` 一旦为真就永不复位 —— 全仓没有任何一处把它置回 `False`。
于是契约改过之后,`claim` 照样放行,**没有任何机制要求任何一方读过新内容**。
这道门守的是协议自称唯一会致命的失败模式(契约歧义)。

反方向:`contract-change-note` 与笔记晋升闸算的都是
"**这一次交接里新追加的**"决策条目。于是同一个工作项里,在改动那一刻留下的
决策,到完成时不算数。第四轮实测发作三次,**最后一次挡着整轮收尾**。

### 契约变了,之前的校验作废

**行为** `claim` 时,若 `contract_file` 的内容与"这个角色上次通过校验时"不同,
**拒绝认领**,并说明契约变过、要重跑校验。重跑之后恢复。

**是现场算,不是写状态。** `setup_verified` 那个键**不被改写** ——
判据是 `setup_verified` 为真**且** sha 一致,现场比对。
不写状态的理由是硬的:唯一能发现"契约变了"的时机是 `claim` 的拒绝路径,
而那条路径是 `die`;`status` 是只读的;`whose-turn` 承诺退出码始终 0。
硬塞一个写入者会让只读命令产生提交,并撞上"状态文件任何未提交改动一律判篡改"
那条检查。**PLAN 里若写着"置回 `False`",以本节为准。**

**只作用于 `claim`。** `status` 可以加一条**提示**(不阻断),`whose-turn` 不动 ——
它的全部用途是给驱动器一行输出,让它在工作项中途因为契约变更而输出 `stop`,
整轮就在半途停摆。而本轮每一个工作项都要改契约。

**sha 取工作区内容,两端必须同口径。** 记录时和比对时用同一种算法,
都取**工作区那份文件的内容**,不是 `HEAD` 里的 blob。
理由:人类在两个工作项之间改了契约但还没提交,是这个仓库的常态,而 HEAD 口径
完全看不见 —— 那正是这一条要堵的洞。**两端不同口径会把整轮锁死**:
一端记 HEAD、一端比工作区,人类留一个未提交的契约改动就会让 `claim` 永久拒绝,
重跑校验记下的还是 HEAD 的 sha,没有任何操作解得开。

**按角色各存一份。** 每个角色记自己上次通过校验时的 sha,`claim` 只看执行者
自己那一份。**不是单个全局值** —— 单值下"dev 读过新契约、tester 没读过"时门
是开着的,而 tester 正是照契约写断言的那一方,它读的是旧契约就等于
"tester 测 `login()`、dev 写 `authenticate()`",那是这份契约开头点名的
致命失败模式。代价是契约变更后两个 agent 各跑一次校验,这个代价该付。

**键缺失算作废。** 存量项目升级上来时那个键不存在:**要求重跑校验**。
"不知道上次校验的是哪一份"和"上次校验的是另一份"风险等价;放行的话所有存量
项目永远绕过这条新门,而升级代价只是重跑一次。
**`contract_file` 读不到时(被删或改名)同样拒绝**,不照抄既有那条
"取不到就静默放行"的写法。

### 「已沉淀」按工作项算,不按回合算

**行为** **只有两处**改判据:`contract-change-note`(工作项完成时那条)与
**笔记晋升闸**。它们从"这一次交接里新追加的条目"改成
"**决策记录里存在 id 等于本工作项的条目**"。

**判据是纯 id,不看写在哪一回合、也不看是不是 `claim` 之后写的。**
"不限哪一回合追加"这半句就是在放宽时间窗;再引入一个"从 `claim` 起算"的窗口,
等于换一个更隐蔽的偏移量判据。已知代价:上一个工作项里提前写了一条
`## W13 — …`,W13 全程就不再需要留决策。接受它。

**另外两处用同一个函数的检查一个字都不改:**

- **W9 那条「带声明的那次交接必须当场留决策」** —— 它要的**就是**"当场",
  改了就没了;
- **「第二次打回必须留结论」** —— 它要的也是"这一次打回时把分歧写下来"。

**不做** 不放宽"必须有决策"这件事本身。要的仍然是有,只是"有"的判定
从一个回合放宽到一个工作项。

## 声明的生效条件与 report 的净回合

- 依据: 人类定稿

**背景** `report` 的每一行都该被它自己的事实推动。现在有两行不是:

- `--no-decision` 与 `--contract-change` 两行靠提交正文里那句声明计数,
  而正文那一段只看 `if args.<旗标>:` —— **带了不生效的声明照样写、照样计数**。
  实测:空带一次 `--no-decision`,指标从 `0%(0/1)` 跳到 `50%(1/2)`。
- `每工作项回合数` 把"推进交付的回合"与"协议开销的回合"混在同一个分母里。
  第四轮它显示 `7.9 ok`,而 10 个 impl 回合里 **2 个是空转的**
  (按下面那条修正后的判据、在 `385e4cd..HEAD` 上实算;
  口径不写清楚,这个数字本身就是本节要治的那种指标)。
  **一个会给出错误诊断的指标,比没有这个指标更糟。**

### 声明只在生效时留痕

**行为** 声明类旗标(`--allow-deletion` / `--no-decision` /
`--contract-change` / `--doc-reason` / `--basis`)**在它实际生效时**才写进
提交正文;不生效时不写,因此也不进统计。

**"生效"= 这一回合真的有某条检查读到了它**,不是"处在它该出现的阶段"。
两者只在 `--no-decision` 上分叉:在 DONE、但本工作项压根没写笔记时,
笔记晋升闸的条件根本不成立,没有任何检查读到这个旗标 —— **按本节它不生效。**

**这一条会打死一条现在绿着的用例,而那是预期结果。**
`tests/conformance/test_v1_report.py` 的 `ReportBase._cycle` 从不写笔记,
却每个工作项都带 `--no-decision`,而 `test_显式声明没有决策会被统计` 断言
`report` 显示 `100% (2/2)`。落地后它会变成 `0% (0/2)`。
**那条用例要跟着改,由 tester 在 spec 回合改。** 点名写在这里,是因为不点名的话
dev 会以为自己弄坏了别的东西,或者反过来照"处在该阶段就算"实现、
把污染源原样留下。

**`--contract-change` 的"改了承重文件"以写权限边界那一步用的同一批改动为准**
(`handoff` 开头抓的那一批),不是提交内容。按提交内容算的话,
`tick_plan_item` 每次 DONE 都会改 `PLAN.md`,于是每一次完成交接都判成生效,
统计恒偏高 —— 正好是这一节要治的病的镜像。

**不做** **不拒绝**带了不生效的声明。拒绝会把"顺手多带一个参数"变成一次
交接失败,代价大于收益;这一条要治的是**统计被污染**,不是用法不整洁。

### `report` 分开净回合与协议开销

**行为** `report` 用**两个绝对计数**取代现有的「每工作项回合数」那一行:

| 行标签(字面) | 含义 |
|---|---|
| `推进交付的回合` | 交接提交数减去下面那个 |
| `协议开销的回合` | 空转的 impl 回合 |
| `未判定的 impl 回合` | 正文里没有判定行的 impl 交接(W14 之前的提交、旧版本留下的历史)—— 只报告覆盖面,不猜它们空转与否 |

**两个数之和恒等于表头那个「交接提交」数。** 这是一条可断言的不变量 ——
没有它,「至少包含」四个字会让任何数字都合规,tester 除了那一条空转用例之外
写不出任何断言,而本节自己要求"判据要能被变异打死"。

**「空转的 impl 回合」由脚本判定并写进提交正文,不靠散文。**
每一次**从 impl 阶段出发、且不是 `dispute`** 的交接,`handoff` 都往提交正文写
**一行结构化的判定**:这一回合空转与否(是 / 否)。`report` 只认那一行:
判定为"是"的计入「协议开销的回合」;**正文里没有判定行的 impl 交接不猜**,
单独计入「未判定的 impl 回合」。其余阶段(spec、review-impl、review-test)不写判定行、
不参与这项统计。

> 第五轮 W14 的 spec 回合改(原文是"在检出……时,往提交正文写一行")。两处缺陷:
> ① 原句没限定阶段,而评审回合按构造只读,照字面**每一次评审**都会被写上这一行、
> 算成开销,与上表"空转的 impl 回合"自相矛盾;② 只在空转时才写,`report` 就分不出
> "这一回合没空转"与"那时还没有这一行"—— W14 之前的所有提交、任何从旧版本升级
> 上来的项目,空转都会被静默计成 0,**指标在"好看"的方向上少计**,正是本节开头
> 点名要消灭的那种指标。每次都写、值为是/否,覆盖面就自己会说话。

**判据里"角色的路径"要连同承重文件一起算 —— 只按 `roles` 判会把 W9 刚刚
合法化的那类交付判成协议开销。** `plan_file` 与 `contract_file` **按构造
就不在任何角色路径下**(那正是 W9 要为它们开豁免的原因),于是一次"只改了
契约"的交接,按纯角色判据必然是"空转"。实算:第四轮 10 个 impl 回合里,
纯角色判据数出 3 个空转,而其中一个是 **W11 的交付本身**
(`f1508f8`,改的是两份承重文件的标题与导语)。**扣掉它,真正的空转是 2。**

所以判据是:本回合的改动里,既没有落在执行者角色路径下的,
**也没有带 `--contract-change` 生效的承重文件改动**。
"生效"与「声明只在生效时留痕」那一条同口径、用同一批改动判定,
不新增机制。一个会把交付判成开销的指标,正是本节开头点名要消灭的东西。
**不许靠在交接说明里搜关键词** —— 那是把一条统计判据挂在自由中文上,
换个词就漏计,而漏计的方向恰好是"让指标好看",正是本节要治的失效模式。
仓库既有手法一致:`role=… phase=…`、`未留决策(已声明)`、`裁判副本已重钉`
全是脚本写进正文的结构化行。

**`dispute` 回合不算空转。** 异议只能写 `shared_paths`,按定义"没有改动落在
角色路径下" —— 但提异议是协议的正常运转,把它算成开销会让"提异议"看起来
像浪费。判据里要排除它。

**老那一行整个删掉**,连同它在 `HEALTH` 里的健康区间与
`docs/command-reference.md` 那张表里的对应行。背景已经把它判成
"比没有这个指标更糟",留着等于把被判死的诊断继续摆在最显眼的位置。

**不做** 不给这三个新数设健康区间。四轮的样本还不足以说什么算正常,
先让它可观测。

## 三节共同的一条:新代码的字面形状要在 spec 回合定死

- 依据: 人类定稿

`MUTATIONS` 用 `pair.py` 的**整行源码文本**做锚,而一致性检查要求每个锚
恰好匹配一次。本轮至少要动到三个既有锚(`verify-setup` 的提交范围、
完成时的晋升 gate、契约变更当场留决策)。

**`mutation_check.py` 在 tester 的独占路径下,dev 的 impl 回合改不了它,
而 impl 回合结束必须 GREEN。** 所以新代码的字面形状要在 **spec 回合**由 tester
写进锚点 —— 仓库里已有先例:第四轮那条「文档理由不 strip」就是故意锚在尚不
存在的代码上,spec 回合红、impl 回合落地后变绿。

**dev 照锚点写,或者打回并给出自己实际用的片段。** 这把一个时序死结变成了
一次普通的规格协商。前提是那个片段本身有依据(照抄仓库既有写法),
分支形状自由度大时逐字规定实现就是越界,dev 应当打回。

## verify-setup 的提交只带它自己 add 的那批路径

- 依据: 人类定稿

> 第五轮开工后补的一节:W12 的 dev 在 review-test 实测发现,人类授权 dev 代笔立项。
> 不在上面「三节」之内,但「三节共同」那一条同样适用。

**背景** 「提交范围」那条防护把 `verify-setup` 的 `git add` 收窄到三类(状态文件、
那份结论、本回合落在 `shared_paths` 下的改动),为的是**不把工作区里的实现提交进
开工基线** —— 否则 spec 阶段"必须 RED"失效。但紧接着的 `git commit` **不带路径,
提交的是整个索引**。实测:结论改了一句、同时有人事先 `git add src/偷跑的实现`,
那次提交带进去的是结论 + `src/偷跑的实现`,标题仍是「通过开工前校验,含契约审查结论」。
W12 只堵住了"索引无差异"那一半;有差异那条路径原样开着 —— W12 的契约写明
"有差异时的行为一个字不变",所以单开这一节。

**行为** `verify-setup` 的那次提交**只包含它这次 `add` 的那批路径**。
索引里其他已暂存的改动**原样留在索引里**:不提交,也不撤销。

**判据** 预先暂存的那份改动**不在 HEAD 的这次提交里**,且提交之后**仍在索引里**。
**另外,工作区里范围之外、没有暂存的改动,`verify-setup` 之后仍不在索引里。**
这一条让既有变异点「拆掉 verify-setup 的提交范围」(`git add -A`)重新有行为抓手:
`commit` 也只带范围内的路径之后,`add -A` 不再把实现提交进基线、只把它写进索引,
不加这一条它就没有任何行为用例抓得住(实测:全套只红锚点记账那一条)。
`verify-setup` 不该往索引里加它范围之外的东西 —— 和"其他暂存原样留下"是同一个精神。

**判"在不在"要按 `-z` 输出切开、整条路径相等。** 第一版这里写的是"查 HEAD 的树、
不能用 `git ls-files`",只对了一半:`ls-files` 与 `ls-tree` 不带 `-z` 时**都会**按
`core.quotepath` 把中文路径转义成 `"\345\201…"`,`assertNotIn("偷跑的实现", …)`
不管实现怎样都成立。**真正的坑是转义,不是"索引还是 HEAD"。** 仓库里已有三处这样的
死断言:`tests/conformance/test_v1_setup_report.py` 的 `test_工作区不干净…` 与
`test_索引里预先暂存了别的东西时照样不提交`、`tests/conformance/test_v1_setup.py` 的
`test_不把工作区里的代码一并提交进基线`。三条用例各有另一条活断言,W12 的保证没被
掏空;W15 的 spec 回合一并改掉。

**警告不新造** 预先暂存的改动若落在角色路径下,既有的"工作区里有未提交的代码改动,
**没有**被本次提交带上"那段警告会列出它。现状下它被一并提交走了,那段警告反而不出现;
改完之后,那句话才第一次说对。不新增警告出口。

**提交哪些路径** **只提交 `to_add` 里在索引中真有差异的那些**(即
`git diff --cached --name-only -z -- <to_add>` 列出的集合 —— 与 W12 的
`index_has_diff` 判的是同一个集合;为空时正好走 W12 那条"不提交"的路)。
**不能照第一版写成 `git commit -- <to_add 全部>`**:`to_add` 里来自 `shared_paths`
的条目取自 `changed_entries`,可能有**暂存为新增、随后又从工作区删掉**的文件
(porcelain `AD`)。`git add` 把它从索引里拿掉之后,它既不在索引也不在 HEAD,
`git commit -- 它` 直接报 pathspec 不匹配、`exit 1`,而状态位已写进工作区却没提交 ——
正是 W12 刚治好的"状态对、退出码错",这回状态还停在工作区。
**路径在 add 之后已不被 git 认得时,不能让提交失败。**

**字面形状** 列路径的小函数由 dev 定;`index_has_diff` 与它身上的两个既有锚点
**不要动**,新加一个函数即可。tester 可以在 spec 回合把 `git commit` 那一行

## 评审回合可以只追加变异点登记

- 依据: 人类定稿

**背景** 新代码的锚点要到 impl 落地才知道,而 `MUTATIONS` 在 tester 的独占路径下,
tester 在一个工作项里能写 `tests/` 的**只有 spec 回合** —— 那时代码还不存在。第五轮
W12、W13、W14 连续三次:dev 在笔记里点名锚点、tester 在 review-impl 隔离复现、写进
`DECISIONS.md` 欠着、下一项的 spec 回合登记。**欠着的那段时间里,那几个分支没有任何常设
检查。** W14 那一笔提前还清,只因为恰好有一次打回把回合退回了 spec。

**行为** 新配置键 **`review_append_paths`**,形如 `{"tester": ["tests/conformance/mutation_check.py"]}`。
在**评审阶段**,阶段执行者名下的这些路径**额外可写,但只能追加**:

- 文件必须**已在 HEAD 里**;新建文件不算追加 —— 否则评审回合能新写一整个测试文件。
- 相对 HEAD **没有删除行**(与 `--basis` 判改写用的是同一个口径,见 `has_rewrite`)。
  删除整个文件、改名,都有删除行,都拒绝。
- **改名要真的被看成删除。** `changed_entries` 解析的 `git status` 默认把改名合成一条、只给
  **新路径**,旧路径那一侧的删除对本节、写权限边界、删除测试防护、红绿不变量**全部不可见** ——
  把登记表 `git mv` 进 `docs/reviews/` 在评审回合退出码 0;dev 在 impl 回合把红的测试挪进去,
  套件绿了、照样交接。所以 `changed_entries` 的 `git status` 要带 **`--no-renames`**,改名拆成
  删除 + 新增,既有检查自然接住。字面照抄那一行既有写法,只加这一个旗标。

  > W16 的 spec 回合(review-test 打回之后)带声明补的:dev 在 review-test 指出验收标准 ②
  > "改名被拒"没兑现,修法与 tester 在 review-impl 记进决策的那个既有漏洞是同一个旗标;
  > 并进本节是兑现 ②,不是扩范围。dev 在隔离克隆里验过:全套 409 条全绿、0 条红。
- **"追加"指没有删除行,不指"加在文件末尾"。** 在文件中间插入新行同样放行 ——
  `MUTATIONS` 是一个列表,新条目必须插在收尾的 `]` 之前,只认末尾追加会让本节的
  用途本身走不通。**判据不许写成"中间插入被拒"。**
- 不满足时拒绝交接,文案说明"评审回合只能往它追加,不能改或删已有行"。

**不并进 `shared_paths`** —— 与记忆层同一个理由(`writable_paths` 的 docstring):
`shared_paths` 另有语义,异议举证检查认的就是它;`idle` 阶段也不可写这些路径。
`status` 的"可写路径"里把它们标成"只追加"。

**判据** 追加被接受、删改被拒绝、新建被拒绝、没配置的测试文件照旧越界、不配这个键时
行为一个字不变。**追加之后测试必须照旧 GREEN**(评审阶段的既有要求)—— 在本仓库,
一个匹配不到源码的锚点会让 `test_变异点仍能匹配到源码` 变红,这是现成的闸,不另造。

**本仓库配置** 代笔提交里已经写好。键在实现落地前是惰性的(`load_config` 只 `setdefault`,
不认识的键原样留着),隔离克隆里验过全套照旧全绿。

**不做**
- **不让 dev 在 impl 回合登记它自己点名的锚点**(开放条目 18 的方向 ②):锚点字面虽然是
  dev 定的,但变异点守的是"测试抓不抓得住",让被测的一方登记它,等于让它挑自己的考题。
- **不把欠账写成 `DONE` 前的强制检查**(方向 ③):要从笔记里解析"dev 点名了哪些锚点",
  笔记是散文,解析不出来的东西就强制不了。
- **不因为"只追加"就认为无害**:往 `mutation_check.py` 末尾追加一段模块级代码,照样能
  影响导入它的测试。这一处由 review-test 的 dev 在 `inbox` 里看 diff 把关,本节不另设检查。

**边界** 只放开评审阶段;spec / impl 的写权限不变。本节自己(W16)的锚点仍然欠一次:
W16 的 review-impl 由旧裁判判。

**已验证** 验了:配置键惰性(全套 397 条全绿)。**没验**:实现本身 —— 本节没有做原型,
"只追加"的判定直接复用 `has_rewrite`,其"未跟踪的新文件删除行为 0"的既有语义在这里
**恰好是错的方向**(新建文件会被当成纯追加),所以才单独写了"必须已在 HEAD 里"。

## 只涉及测试的打回不再经过 impl

- 依据: 人类定稿

**背景** 第五轮 7 个 impl 回合里 3 个空转,**三个全是同一类**(W13、W14、W15 的第二个 impl
回合):review-test 打回 → tester 在 spec 补测试 → dev 的 impl 回合一行代码不改 →
tester 的 review-impl 只能确认"没有可实现的东西"。**一次只涉及测试的打回实际花三个回合,
其中两个是仪式。** W14 的空转判定行把 impl 那一个计成协议开销,而它对"协议在不在空转"的
含义正相反。

**行为** `feature` / `bug` 流程里:**review-test 打回之后**的那个 spec 回合,若交接时
测试 **GREEN**,且这一回合**实际没有改动规划或契约**,下一阶段是
**review-test**(归属 dev),跳过 impl 与 review-impl。

其余情况照旧进 impl:
- **RED** —— tester 补的测试揭出了实现的真缺陷,需要 dev 改;
- 回弹来自**异议**(impl 的 changes)—— 实现还没被 review-impl 审过;
- 回弹来自 **review-impl 打回** —— 本来就回 impl,不经过 spec;
- 这一回合**改了承重文件** —— 契约变了,已经审过的实现可能不再对得上。**按改动判,
  不按旗标判**(与 W14「声明只在生效时留痕」同口径):带了 `--contract-change` 却没改
  承重文件,照样走捷径;
- **契约内容自 review-impl approve 之后变过** —— 不论是这一回合改的,还是期间被人提交的。
  review-impl approve 时按 W13 的口径(**工作区内容**的 sha)记下契约,捷径还要求现在与那时相同;
  没有这份记录时不走捷径。只看"这一回合的改动"看不见已经提交的变更 —— 第五轮 W15 那一节就是在
  工作项进行中、别人的回合里被直接提交的(`e62bdf5`)。

  > W17 的 spec 回合带声明补的:tester 在第六轮开工前的独立审查(`setup-verification-tester.md`
  > 的 ③)挑出。上一条"按改动判"留着 —— 它还管规划文件,而规划文件的变化不改变契约的 sha。
- 状态里**没有**"回弹来自哪一阶段"的记录(旧状态升级上来)—— 不猜,按不走捷径处理。

**为什么安全** 走捷径时,实现在 review-impl 被 approve 之后**没有任何人能改过**:
review-test 只读,spec 回合只能写测试路径与 `shared_paths`。承重文件是唯一能让"已审过的
实现"失去依据的东西,所以单独排除 —— **两个来源都要排除**:这一回合改的,
与 review-impl approve 之后被提交的。

**判据** 看的是**下一阶段与归属**(`status` / `whose-turn` 可观测),不是提交正文的措辞。
死锁计数不因捷径清零;评审文件名照旧由 `review_file_for` 按打回次数算。

**不做** **不改判定行**(开放条目 19 的另一个方向:让判定行携带"上一次是不是只涉及测试的
打回")。回合不存在,就不需要一行去解释它为什么空。

**边界** 「打回之后的修正回合必须真的动了测试」那条既有检查不变 —— 走捷径的前提仍是
tester 这一回合改了测试。`cover` 本来就是 spec → review-test,`refactor` 没有 spec,都不变。

**已验证** 在隔离克隆里做了原型(新状态键记回弹来源 + 翻转回合前改写 `target`),
**全套 397 条全绿、0 条红** —— 这说明**没有任何既有用例钉着"回弹后 GREEN 进 impl"这条边**,
新用例是它唯一的守护。原型**没有**做"改了承重文件不走捷径"与"旧状态不走捷径"两条,
这两条是写本节时才想到的。

## claim 看两个角色的开工前校验

- 依据: 人类定稿

**背景** W13 起校验按角色记(`setup_verified_contract`),`claim` 只看执行者自己那一份,
而只有 tester 能 `claim` —— **没有任何东西强制 dev 重跑 `verify-setup`**。几乎每个工作项都
改契约,dev 那一份过期之后,`status` 每一次都打"你上次的开工前校验已经不作数了"。
**第五轮 dev 的每一次 `status` 都打了这句。** 一句永远在的提示会教人忽略它,而 W13 自己写的
理由("照契约写断言的是 tester,它读的若是旧契约,两边就会各自对")对 dev 一字不差地成立:
**照契约写实现的是 dev。**

**行为** `claim` 要求**两个角色**记录的契约都等于工作区里这一份。任一角色过期或没有记录
时拒绝,拒绝文案**点名是哪个角色**,并说明**只有那个角色重跑才能解锁**(对方重跑替不了,
W13 的原则不变);两个都过期时两个都点名。

**不变的** `setup_verified` 那道既有门禁;工作项中途契约变了不挡交接;`whose-turn` 不输出
stop;`status` 的提示 —— 它现在有了一个必须处理的时机,不再是常驻的。

**idle 时轮到谁**(W19 的 spec 回合带声明补) —— `claim` 要求 dev 那一份也不过期之后,
**唯一能解锁的是 dev,而 idle 的归属是 tester**:`whose-turn` 照旧输出 `turn tester`、tester 认领被拒、
dev 会话跑 `status` 看到"不是你的回合"就停。交给人类时这只是多一次唤醒,**交给驱动器时是死循环**。
所以 idle 且门禁开着时:

- tester 那一份作数、**dev 那一份过期或没有记录** → 归属是 **dev**:`whose-turn` 输出 `turn dev`,
  `status` 的归属那一行是 dev,dev 的回合说明给出重跑 `verify-setup` 的指引;
- tester 那一份过期(不管 dev 那一份怎样)→ 归属照旧是 tester —— 先让认领的一方读新契约;
- 两份都作数 → tester,照旧。

`whose-turn` 仍然不输出 stop;工作项进行中不受影响(那时契约变了本来就不挡交接)。

> tester 在第六轮开工前的独立审查(`setup-verification-tester.md` 的 ①)挑出。


**被本节取代的用例** 隔离克隆里原型(`claim` 对两个角色逐个判)实测会红 6 条行为用例,
它们都只让 tester 校验就去认领:`tests/conformance/test_v1_validity.py` 的
`test_人类没提交的契约改动也算_且重跑之后不会锁死`、`test_工作项中途契约变了不挡交接`、
`test_提交之后同一份内容不必再校验`、`test_状态里没有这份记录时要求重跑`、`test_重跑校验之后恢复`,
以及 `tests/conformance/test_v1_setup.py` 的 `test_交了结论后通过并允许认领`。
**按新行为改,不删**:它们各自守的性质(工作区内容也算、中途不挡、重跑恢复……)照旧成立,
只是认领前要让 dev 也校验一次。

**代价** 契约每变一次,**两个角色**都要在下一次认领前重跑。本仓库几乎每项都改契约,
等于每项多一次 dev 的 `verify-setup` 提交,dev 的结论按 W18 只能追加。接受这个代价:
另外两条路一条是删掉 dev 的提示(dev 那一半从此没人管),一条是保留常驻提示(教人忽略)。
**接入时的第一次认领也要两个角色都校验过** —— 这是行为变化,`INSTALL.md` 与 `SKILL.md`
里"由还没动手的那一方跑"的说法要跟着改。

**已验证** 原型只做了"逐个角色判、取第一个拒绝理由",**全套红 7 条**(6 条行为 + 锚点记账)。
"两个都过期时两个都点名"与文案点名角色,原型没做。

## report 可以只统计某个起点之后

- 依据: 人类定稿

**背景** W14 落地之后在本仓库跑 `report`,「未判定的 impl 回合」是 25 —— 前五轮的 impl
交接都没有判定行,单独计、不猜,这是对的。但同一批历史提交里,**不生效的 `--no-decision` /
`--contract-change` 声明已经写进了正文,照旧被计数**。第七轮的独立运行若在本仓库里跑,
两条比率与开销那一格都只能靠人手工减。

**行为** `report --since <rev>`:只统计 **`<rev>..HEAD`** 之间的提交(从 HEAD 可达、从 `<rev>`
不可达),表头写明起点。

- `<rev>` 不是合法提交时:非零退出,一句人话,**没有 traceback**。
- `--since HEAD`:交接提交 0;比率行按"样本为 0"的既有处理,不报错。
- 不带 `--since`:输出**一个字不变**。

**不受影响的** 读状态的两行(已完成工作项、进行中)—— 它们不是从提交里数的;
「记忆层空转」那一行也不受影响:它用的是状态里的完成数与决策文件里的条目数。
**这几行与区间内的计数口径不同,表头要说清楚起点只作用于从提交里数的那些。**

**判据** 起点之后的计数正好是起点之后的那几次交接;三行回合计数照旧满足
`推进交付的回合` + `协议开销的回合` = `交接提交`(W14 的不变量在区间内同样成立)。

**两条比率的分母跟着起点走**(W20 的 spec 回合带声明补) —— `--no-decision` 与 `--contract-change`
两行的分子是区间里的声明数,分母原先是状态里的**全部历史**完成数。带 `--since` 之后分子分母不在
一个口径:区间外完成 1 项、区间内完成 1 项且带 1 次生效声明,会显示 `50% (1/2)` 而不是
`100% (1/1)` —— 背景点名要修的正是这两行,这样修完它们仍只能靠人手工算。所以带 `--since` 时,
**这两行的分母(以及它们的偏高判定)用区间内完成的工作项数**:区间里把工作项推进到完成的那几次交接。
区间里没有完成时分母为 0,按"样本为 0"的既有处理。不带 `--since` 时照旧读状态(输出一个字不变)。
「决策/完成项」那一行照旧读状态,不受影响。

`<rev>` 是合法对象但不是提交(比如树)时同样拒绝;拒绝文案点名那个起点。

**起点必须是 HEAD 的祖先**(W20 第二次 spec 回合带声明补) —— 旁支上的提交能解析成提交,
但 `<它>..HEAD` 是两条分支的差集,不是"那个提交之后":dev 在隔离克隆实测退出 0、报交接 3 次。
一张退出 0、看起来合理的表正是本节背景要消灭的静默偏差。不是祖先时拒绝:非零退出、没有 traceback、
文案点名那个起点。

> tester 在第六轮开工前的独立审查(`setup-verification-tester.md` 的 ②)挑出。

**不做** 不做 `--until`、不做按工作项过滤。不改历史提交、不补写判定行。

**已验证** 没做原型。`_handoff_log` 是 `git log --reverse` 读全部历史,改成带区间是局部的。

## report 只认协议写进提交正文的那几行

- 依据: 人类定稿

> 第六轮收尾后补的一节:W20 完成后发现的缺陷,人类裁决"先修复",授权 dev 代笔立项。

**背景** `report` 从提交正文里数五样东西:交接(`item=`)、完成(`-> idle`)、impl 交接(`phase=impl -> `)、

`--checked` / `--uncovered` / `--doc-reason` 这些旗标的值原样进正文,人类手写的提交也有正文。
W14 的 review-impl 里 tester 就警告过"自由文本旗标能伪造 report 要解析的行"。

**本仓库的历史里已经算错了两处**(拿锚定前后两种口径对全部历史逐条比过):

| 提交 | 是什么 | 被算成了 |
|---|---|---|
| `0aea588` | 人类手写的路线图提交,正文散文里提到 `item=` | 一次**交接**(全部历史 149,应为 148) |
| `136cabd` | W20 的 review-impl,`--checked` 里写着 `phase=… -> idle 的交接` | 一次**完成**(第六轮分母 6,应为 5) |

另外三处(两条声明、impl 交接)今天的历史里两种口径恰好一致,但漏洞相同。

**行为** 五样东西**只从协议生成的行里读**:

  impl 交接 = 这一行的来源阶段是 `impl`。
- 两条声明:只认**行首**的 `未留决策(已声明): ` 与 `契约变更(已声明): `。
- **第六处:死锁**(W21 的 spec 回合带声明补) —— 「死锁工作项占比」原先是 `"触发死锁闸" in subject`,
  而交接提交的主题是 `<前缀>: <执行者写的一句话>`,评审写"再打回两次就触发死锁闸"不需要任何恶意。
  只认 `handoff` 生成的那个完整主题 `chore(pair): 工作项 <ID> 打回 <N> 次,触发死锁闸`(整行匹配)。
  tester 在认领前重跑 `verify-setup` 的补记里挑出(⑤)。

**判据** 协议正常生成的提交,每一行计数与今天**一个字不差**;正文散文里出现同样字样(不在行首,或者不是那个完整形状)
时不计。

**不做**
- **不堵"旗标值里带换行、在新的一行行首伪造"**:那要改 `handoff` 对旗标值的处理(拒绝或压平换行),
  是另一处行为变化。W14 review-impl 分析过判定行的同类情形:伪造需要刻意在旗标里写换行,方向也只会让数偏高。
  本节只修"散文里顺带提到就被算进去"这一类 —— 它**不需要任何恶意**,两次都是正常写评审、写路线图时发生的。
- 不改历史提交。

**字面形状** 由 dev 定;W14、W20 在这几行上登记过的锚点(`report 完成数不看 idle`、`没有判定行的 impl 交接不单独计`
等)会跟着改,tester 在 spec 回合按"应该长什么样"重锚(「三节共同」)。

**已验证** 没做实现原型;只做了**口径对比**:用锚定写法与现行写法对全部历史逐条算五样东西,不一致的正是上表两条。
没验的:锚定之后既有用例是否全绿 —— harness 造的提交都走 `handoff`,按道理都有那一行,但没跑。

## 共用目录时角色要来自 PAIR_ROLE

- 依据: 人类定稿

**背景** 两个 agent 共用一个工作目录时(`sync` 为假,协议规格 §配置),角色只能靠 `PAIR_ROLE`:
`.pair/whoami` 是一个文件,只能写一个角色;分支名 `pair/<角色>` 在同一目录里只有一个。第七轮的编排者
在第一条消息里替两个会话说了前缀用法,文档没说 —— 真实用户照 `SKILL.md` 写 `whoami`,后写的那一方
会把先写的那一方的角色改掉,而两边都不会被拒绝(脚本以为自己知道你是谁)。

**行为** `status` 在 `sync` 为假、且角色来自 `.pair/whoami` 或分支名时,打一条**不阻断**的警告:
点名角色来自哪里、说明共用目录时它会被两边读成同一个角色、给出 `PAIR_ROLE=<角色>` 的写法。
角色来自 `PAIR_ROLE`、或 `sync` 为真时不警告。

**判据** 警告有没有出现、`status` 退出码不变。警告的字面不钉,判据只看它点名了来源(`.pair/whoami` 或分支名)
并给出 `PAIR_ROLE`。

**不做** 不拒绝。`sync` 为假也可能是只有一个 agent 在这个目录里、另一个在别处(人类手工同步)——
那时 `whoami` 是对的;脚本判断不了另一个 agent 在哪。

## 验证用的副本放在 .pair/scratch/

- 依据: 人类定稿

**背景** 第七轮两个会话都自发做变异验证(故意改错实现,看测试红不红),为此**四次**在仓库之外建副本或临时脚本。

## status 的可写路径按本角色显示

**判据** 用例断言非归属方跑 `status` 时那一行不含归属方的角色路径、且归属方那一行不变;

`test_非执行者看到的头部那一行也标出只追加`:它以**非执行者**(dev)身份在 review-impl 跑 `status`,断言头部标出

简报那一处怎么传由 dev 定。

**不做** 不动写权限边界本身(`handoff` 的判定)。这是一条显示缺陷,拦截一直是对的;

## verify-setup 的结尾要看另一方

## CLAUDE.md 禁的是转手

- 依据: 人类定稿

**背景** 第十一轮独立运行:dev 的第一个回合只做了只读的事就停下来问人,因为 `init` 写进 `CLAUDE.md`
的那句"不要用 subagent 代跑结对回合……必须由主会话执行 `status` 和 `handoff`",而它自己就是被派出来的
subagent。人类澄清"你本身就是 dev 这个角色唯一的会话,不适用于你"之后才推进。第九轮两个会话都指出过这处冲突。
那条规矩要防的是**某一方把自己的回合转手给别的 agent 或会话** —— 那样回合状态与归属就对不上了;
它不关心跑回合的那个会话是怎么被启动的。

**行为** `CLAUDE_MD` 那一句写成禁止"转手":一个角色的回合由这个角色的会话自己执行 `status` 与 `handoff`,
不交给别的 agent 或会话去跑;并写明"你本身就是这个角色唯一的会话"(不论是不是被派出来的)不在此列。
样板项目与本仓库的 `CLAUDE.md` 跟着改。

**判据** 措辞本身不写成用例(写成子串断言只会是变更探测器)。能写成失败用例的是**一致性**:
样板项目的 `CLAUDE.md` 与 `merge_entry(CLAUDE_MD)` 写出的逐字节一致 —— W26 让它们一致了一次,
但没有任何东西守着,这一次改 `CLAUDE_MD` 就是它漂开的第一个机会。变异点是改了模板而样板没跟上。

**缺陷本身也写成用例**(W28 的 spec 回合带声明补) —— 本项是 `bug`,spec 回合必须红;而一致性那条今天是绿的

## 探测到多个技术栈时 init 拒绝自动配置

- 依据: 人类定稿

契约不好肉眼可见,这一条完全静默。`INSTALL.md` 目前只在「不适用」清单里提醒人类自己核对。

**行为** 没有已有 config 的 `test_cmd` 时,`init` 看仓库根上**全部**命中的探测文件:
- 它们对应**两种及以上不同的测试命令** → 拒绝自动配置,退出码非 0,**不写任何文件**(不建 `.pair/`、不动入口文件、不改 `.gitignore`)。
  输出点名每个命中的探测文件与它对应的命令,并给出出路:手工创建 `.pair/config.json`,写一条覆盖全部的 `test_cmd`

- 只有一个栈 → 行为不变。

③按这个读法,今天豁免之外只剩「定位重框」第 6 条那一处(ADR-020 后面括号里的行号),由 dev 改写或随条目解决。

**判据** 用例今天红(4 处);往一份不在豁免里的规范文档写一个 :123 → 红;写进已标 ✅ 的路线图条目、ADR 或 `dogfood-run-*.md` → 不红;写进围栏 → 不红。

**不做** 不迁移豁免区里的坐标;不改符号引用检查对带文件名引用的规则。

## ADR 字段的偏差登记在案

- 依据: 人类定稿

**背景** `docs/design-decisions.md` 开头写"每条:**背景 / 决策 / 理由 / 代价 / 被否掉的方案**",`docs/README.md` 写"24 条 ADR,每条含背景 / 决策 / 理由 / 代价 / **被否掉的方案**"。
立项时用"段首加粗的字段名"粗扫:13 条 ADR 没有"否掉的方案"这一项(ADR-006、ADR-009 到 ADR-019、ADR-021);ADR-020 写的是"代价与已知边界",理由写成了一句加粗的话;
ADR-022 写的是"理由与取舍";有这一项的条目写的都是"否掉的方案",不是开头说的"被否掉的方案"。人类在第二十九轮立项时裁决(2026-10-13):
不改既有 ADR 的原文(追加式纪律),追加一段说明哪几条用了变体名、缺了哪一项。

**行为**
- `design-decisions.md` 开头那段说明之后,**追加**一段偏差说明:点名每一条缺标准字段或用了变体名的 ADR,写明它缺什么、用的是哪个变体(等同于哪个标准字段)。不改任何一条 ADR。
- `docs/README.md` 那句"每条含……"改成与实际一致(例如"多数条目含……,偏差见 `design-decisions.md` 开头的说明")。
- 用例逐条扫 ADR 的字段,凡是有偏差的 ADR,编号必须出现在那段偏差说明里;以后新增的 ADR 缺字段又没登记 → 红。

**判据** 用例今天红(没有偏差说明)。扫字段的口径由 tester 定(立项时的粗扫口径是"加粗、位于段首的字段名,以标准名开头即算有");粗扫的数字只作参考,以用例的口径为准。
dev 追加说明后绿;再加一条缺字段的假 ADR → 红。

**不做** 不改任何 ADR 的原文;不规定 ADR 必须有哪些字段(那是写新 ADR 时的事)。

## 测试结果按内容记,内容没变就不重跑

- 依据: 人类定稿

**背景** 本仓库全量一次约 1.5 分钟,一个工作项里却要跑 8–10 次:`status` 每次调用都跑(不论轮没轮到调用者)、`verify-setup` 跑一遍门禁还跑一遍全量套件、
每次交接跑一遍,多数时候两次之间内容一字没变。大项目的全量可能是几十分钟到几小时。测试结果是内容的函数:同样的内容、同样的命令,结果就一样。
git 本来就给内容算哈希,拿它做键,结果只算一次。

**行为**
- `run_tests` 对每一条测试命令(`test_cmd` 与 `full_test_cmd` 各自独立)先算指纹:实际要执行的命令字符串(`PAIR_TEST_CMD` 覆盖时就是覆盖后的那一条)
  加上工作区内容的 git 树哈希。树哈希用临时索引算,不碰真实索引(以真实索引为种子 `add -A`,含未跟踪、尊重 `.gitignore`,再去掉排除项,`write-tree`)。
- 排除协议自己写的、测试不该依赖的路径:`.pair/state.json`、协议日志(`PROTOCOL_LOGS`,不论项目的 `.gitignore` 是否忽略它们)、评审目录(`shared_paths`)、
  记忆层(`notes_dir`、`decisions_file`)。`.pair/config.json` 不排除(本仓库的测试会读它)。
- 指纹与退出码记在该命令的日志(`.pair/.last-test.log` / `.pair/.last-full-test.log`)最后一行。下一次调用时指纹相同 → 直接用记下的退出码,不执行命令、不改日志;
  不同、日志不在、或最后一行不是这种记录 → 照常执行,覆盖日志并在末尾写上新记录。
- 环境变量 `PAIR_FRESH_TESTS=1` → 不复用,照常执行。
- `status`、`verify-setup`、`handoff`、`init` 都走这一条,各自不再另判要不要跑;简报里的测试状态仍只有 GREEN/RED。

**前提与边界** 复用的前提是"内容与命令不变,结果就不变"(与第二十九轮 W54 写明的归因前提同一条)。被 `.gitignore` 忽略的东西(依赖目录、虚拟环境、`.env`)
与测试环境本身(装没装 pytest)不在指纹里;变了而文件没变时会复用旧结果 —— 用 `PAIR_FRESH_TESTS=1` 或删掉日志重跑;有改动的交接照常重跑。

**补充**(W57 的 spec 回合带声明补,开工前审查 ⑯)
- 指纹再加一项:**已跟踪路径的集合**(`git ls-files`,去掉同样的排除项)。树哈希里未跟踪与已跟踪不分,提交前后相同;而测试可以依赖"哪些文件被跟踪"——
  本仓库的规范文档检查只扫已跟踪的 `.md`。不加这一项,交接时新写、未跟踪的文档在那一次不被检查,提交之后又一路复用到完成。加了之后,
  只在交接加了新文件时,下一次多跑一次。
- 「前提与边界」再加一条:HEAD 与提交历史不在指纹里,读真实仓库历史的测试会复用旧结果。
- 记忆层只在 `memory` 开着时排除(关着时 `notes_dir`、`decisions_file` 是普通文件)。
- 判据再加一格:一个未跟踪文件,内容不变、只是被提交 → 下一次增加一次。

**判据** 用例用一个往仓库**外**的计数文件追加一行的测试命令数实际执行次数:①内容与命令都不变时,连续的 `status`、`status` 之后的 `verify-setup` 与 `handoff` 不增加次数;
②改测试或实现文件、改测试命令、设 `PAIR_FRESH_TESTS=1`、删日志 → 各增加一次;③只改评审目录、记忆层或 `.pair/state.json` → 不增加;
④复用时 `status` 的 GREEN/RED 与上次运行一致,日志内容仍是那次运行的输出。变异点:不比指纹(恒重跑或恒复用)、排除项多排 `.pair/config.json`、指纹不含命令。

**不做** 不做多条历史结果的缓存(只记每条命令最近一次;回合序列里需要复用的都是"紧挨着的上一次");不选择受影响的测试(开放条目 53);
不改变异检查(`mutation_check` 自己有指纹缓存)。

## 可选的 JUnit XML 报告

- 依据: 人类定稿

**背景** `run_tests` 只看退出码:说不出红的是哪几条,`status` 只能说"现在是红的",dev 每回合要自己再跑一遍才知道修什么;完成时的全量也分不清
"这个工作项弄红的"与"原来就红的"(开放条目 52 要这个区分)。JUnit XML 是各栈通用的结果格式:pytest `--junitxml`、jest-junit、vitest、gotestsum、
PHPUnit、RSpec、Maven Surefire 都能产出。路线图 P0-1 早已提议,本节只做它的地基部分。

**行为**
- 可选配置 `test_report`、`full_test_report`:`test_cmd`、`full_test_cmd` 各自写出的 JUnit XML 的路径(相对仓库根)。不配时一切行为与现在相同。
- 读法:标准库解析;每个 `testcase` 的 ID = `classname` + `.` + `name`(没有 `classname` 就只用 `name`);含 `failure` 或 `error` 子元素算失败,
  含 `skipped` 的不算失败;文件里的多个 `testsuite`(含嵌套)合并。
- 执行测试命令之前删掉旧报告,所以命令没写出报告就是"没有报告"。没有报告或解析失败 → 判定只看退出码(与现在相同),并打一行警告点名报告路径;**绝不因此拒绝或卡住**。
- 与第三十一轮 W57 对齐:报告路径排除出指纹(它是产物,每次运行都变);日志末尾的记录多记一项报告内容的哈希(没有报告时记一个固定占位),
  复用时报告的哈希对不上(被删、被改、被别的运行覆盖)就当没有记录,照常执行。旧格式的记录读不懂,同样照常执行。
- 配置的报告路径与协议日志同样豁免写权限边界;交接把改动暂存之后,把报告退回未暂存(与第十六轮 W35 处理系统文件的做法相同),不进提交,不依赖项目的 `.gitignore`。
- 有报告时 `status` 在测试状态下面列出红着的用例,最多 20 条,其余写"另有 N 条"。
- `protocol-spec.md` 的配置表加这两个键;`INSTALL.md` 写各栈怎么让测试命令写出 JUnit XML。

**补充**(W58 的 spec 回合带声明补,开工前审查 ⑰)报告要与退出码一致才用:退出码非 0 而报告里一条红都没有(套件跑到一半崩了,报告只有崩之前跑完的),
或退出码 0 而报告里有红(测试命令吞掉了退出码)→ 当作"报告读不出",降级回只看退出码,警告点名报告路径并说明对不上。前一种若照样信报告,
W59 会把"半个套件起不来"的回归算成没有新增的红、放行完成。判据再加一格:退出码 1、报告全绿 → 有警告、RED、不列用例;退出码 0、报告有红 → 有警告、GREEN、不列用例。

**判据** 用例用 harness 里的假测试命令按 `tests/`、`src/` 的布局写出 JUnit XML:①列出的红用例名与布局一致;②报告缺失、格式坏 → 有警告、GREEN/RED 照旧由退出码定;
③命令这一次没写报告,而上一次的报告还在 → 不读上一次的(执行前已删);④报告被改过 → 下一次不复用;⑤交接之后报告不在提交里,写权限边界不因它拒绝。

**不做** 不支持 JUnit XML 以外的格式;不做 P0-1 原提议里的"spec 回合的红必须来自本回合改动的测试文件"与"cover 新增用例确实被执行"(见路线图 P0-1 的追加说明)。

## 完成时的全量只拦新增的红

- 依据: 人类定稿

**背景** 工作项完成时跑一次全量套件(`full_test_cmd`),红了只报告不阻断 —— 当初的理由是范围外的红这对结对无权修。但开放条目 53(回合内只跑受影响的测试)
上线后,回合内挑漏的回归要到完成时的全量才现形,而它会被当成"范围外的红"放过,分不清是不是这个工作项弄坏的。有了用例级结果(上一节),
就能只拦"上一次全量是绿、这一次变红"的那些。第二十六轮 W44 起,完成时的全量在提交之前跑,所以能在提交前拦下。

**行为**
- 状态新增 `full_failures`:上一次全量里红着的用例 ID(排序后的列表);不知道时为 `null`(老状态没有这个键同样按 `null`)。
  `verify-setup` 跑全量且有 `full_test_report` 时写入;每次工作项完成时,更新为这一次全量的结果。
- 工作项完成那一次交接,有 `full_test_report` 且基线不是 `null`:**新增的红** = 这一次红着的 − 基线里红着的。
  - 有新增 → **拒绝完成**(在提交之前,什么都不落盘),列出新增的那些用例(最多 20 条),说明它们在上一次全量里是绿的、是这个工作项弄红的;
    这一回合是评审回合、不能改代码,文案写明用 `changes` 打回给对方修(refactor 由 tester 完成时同理打回给 dev)。
  - `--accept-new-failures "<理由>"`:只在真有新增时生效,放行并写进提交正文(与 `--allow-deletion` 的声明同一种写法);没有新增时给了也不写、不拒绝。
  - 没有新增(只有原来就红的)→ 与现在相同:只报告、退出码 2、第二十五轮 W43 与第二十六轮 W44 的提示不变;原来红、这一次绿的用例从基线里去掉。
- 没有 `full_test_report`、报告读不出、或基线为 `null` → 行为与现在完全相同;读得出报告时把这一次的结果记成基线。
- 登记 `ENFORCEMENTS`(`full-new-failures`)与 `architecture.md` 的强制力分布表;`troubleshooting.md` 补一节;`protocol-spec.md` 的状态 schema 加这个键。

**补充**(W59 的 spec 回合带声明补,开工前审查 ⑱)`feature`/`bug`/`cover` 由 dev 在 review-test 完成。被拒后 dev 用 `changes` 打回进 `spec`,
而新增的红多半在实现里;tester 的修正回合只能动测试,门禁多半是绿的,W17 捷径成立就直接回 review-test,dev 再 approve 再被拒,一圈烧一次打回额度。所以:
- review-test 打回之后的 spec 回合,**上一次全量有新增的红**时不走 W17 捷径(那一回合 GREEN 也进 `impl`,由 dev 修)。"上一次全量"按全量日志末尾的记录与
  `full_test_report` 判,不重跑:记录里的报告哈希对得上、报告与退出码一致,新增 = 报告里红着的 − 状态里的 `full_failures`;任何一项读不出就不另拦(照 W17 原样)。
- 拒绝文案按完成者写去向:review-test(dev)—— 用 `changes` 打回,tester 补完用例后会进 `impl`、由 dev 修;refactor 的 review-impl(tester)—— 用 `changes` 打回,直接进 `impl`。
- "什么都不落盘"包括工作区:被拒之后,除协议日志与报告外,工作区与交接之前相同(`PLAN.md` 不能被勾上)。
- 判据再加一格:被拒 → dev `changes` → tester 只改一条测试、GREEN 交接 → 进 `impl` 而不是 `review-test`。

**判据** 用例(假的全量命令按布局写出报告):①基线里 A 红、这一次 A 与 B 红 → 完成被拒、点名 B、不点名 A、什么都没提交;②同样情形带 `--accept-new-failures` → 放行、
提交正文有声明;③只有 A 红 → 放行、退出码 2;④A 修好 → 完成后基线里没有 A;⑤没有报告 → 与今天相同;⑥`verify-setup` 跑全量后基线被写入。变异点:拆掉拒绝、新增按"这一次红着的"而不减基线、声明不生效。

**不做** 不处理 flaky 用例的自动重试(用声明逃生);不在 `report` 里统计基线;不改"原来就红的只报告"这条设计。

## 回合内只跑受影响的测试

- 依据: 人类定稿

**背景** 每次交接都跑 `test_cmd`(门禁);大项目的门禁全量可能要几十分钟到几小时。各栈都有"只跑受影响测试"的工具(jest `--findRelatedTests`、
vitest `related`、pytest-testmon、nx affected),但选择器可能漏选 —— 所以这一层排在第 2 层之后:第三十二轮 W59 起,工作项完成时的全量会把
"上一次绿、这一次红"的用例拦下,挑漏的回归在那里兜住。

**行为**
- 可选配置 `affected_test_cmd`。可以含占位符 `{paths}`:协议把它替换成"本工作项改动的路径",逐个 shell 转义、空格分隔;不含占位符时原样执行
  (例如工具自己判断范围的 `pytest --testmon`)。
- 用它的条件:状态里有当前工作项、这一次跑的是门禁(不是 `full_test_cmd`)、没有 `PAIR_TEST_CMD` 覆盖、配了 `full_test_cmd` 与 `full_test_report`。
  其余情形一律用 `test_cmd`。选择收在 `run_tests` 里一处,`status`、`handoff`、`verify-setup` 共用,同样的内容生成同样的命令,第三十一轮 W57 的复用照常生效。
- 本工作项改动的路径:认领时把当时的 HEAD 记进状态 `item_base`;路径 = `item_base` 到工作区的已跟踪改动(删除的不算,只传存在的文件)加上未跟踪的文件,
  去掉 W57 指纹的排除项(状态文件、协议日志、报告、评审目录、记忆层)。从认领起算:dev 的实现回合里,tester 在 spec 回合写的测试文件也在范围里。
- 退回 `test_cmd`:没有 `item_base`(老状态)、路径集合为空、超过 200 条(避免命令行过长)。
- 配了 `affected_test_cmd` 却没配 `full_test_cmd` 或 `full_test_report` → `verify-setup` 判失败(配置错误),说明第 1 层必须有第 2 层兜底。
- 完成时照旧跑 `full_test_cmd`:选择器漏选的、本工作项新写却没被选中的用例,不在基线里,作为新增的红被拦下。

**判据** 用例里放一个假选择器,把收到的参数写进仓库外的文件:①工作项进行中,门禁执行的是替换后的 `affected_test_cmd`,路径集合含 spec 回合写的测试文件、
不含评审目录/状态/日志、不含已删除的文件;②空闲时、`PAIR_TEST_CMD` 覆盖时、路径为空、路径超过 200 条、状态里没有 `item_base` 时执行 `test_cmd`;
③没配 `full_test_cmd` 或 `full_test_report` 时 `verify-setup` 失败并说明原因;④`status` 与紧跟的 `handoff` 内容不变时只执行一次。
变异点:不退回 `test_cmd`、路径只算本回合、排除项不排、不检查兜底配置。

**不做** 不做依赖分析(交给项目自己的选择器);不支持逗号分隔等其他占位符格式(需要时用脚本包一层);不处理开放条目 54(用例消失)。

## 完成时不再跑的用例也拦下

- 依据: 人类定稿

**背景** 第三十二轮 W59 让工作项完成时的全量只拦"上一次绿、这一次红"的用例,基线(状态里的 `full_failures`)只记红着的。
一次让部分用例不再被收集的回归 —— 改坏了测试发现规则、删了 `__init__.py`、某个测试文件导入就崩而被框架静默跳过 —— 只要退出码与报告一致,
"这一次红 − 基线红"就是空的,照样放行。W59 的 review-impl 里 tester 挑出,登记为开放条目 54。

**行为**
- 跑过的集合:全量报告(`full_test_report`)里所有 `testcase` 的 ID(ID 规则同第三十二轮 W58),**含 `skipped` 子元素的不算跑过** —— 变成跳过也是不再守着。
- 基线写进协议产物 `.pair/full-baseline.json`,内容 `{"executed": [ID, ...]}`(排序)。不进状态文件(大项目几万条用例会让每次提交的状态文件膨胀)。
  它由协议写、随协议的提交落地;在冻结路径 `.pair/` 下,agent 改不了;排除出第三十一轮 W57 的指纹。
  `verify-setup` 跑全量且读得出报告时写入;每次工作项完成时更新为这一次跑过的。文件不在或读不出 → 不知道 → 不拦,下一次读得出时写入。
- 完成那一次交接:**消失的** = 基线里跑过的 − 这一次跑过的。与 W59 的新增的红合在一起判:任一不空就拒绝完成(在提交之前,什么都不落盘),
  分两段列出 —— 新增的红、不再跑的用例,各最多 20 条;去向文案同 W59。
- `--accept-new-failures "<理由>"` 同样覆盖消失的用例(删测试、改名都属于这一类,该显式确认):只在真有新增或消失时生效,两段都写进提交正文。
- 被"消失的用例"拒绝之后打回的 spec 回合不走 W17 捷径(第三十二轮 W59 的 ⑱):判"上一次全量有没有问题"时,一并算消失的。
- `protocol-spec.md` 说明这个协议产物;`command-reference.md` 写明 `--accept-new-failures` 也覆盖不再跑的用例;`troubleshooting.md` 补一节。

**判据** 用例(假的全量命令按布局写报告,可让某个用例不出现或带 `skipped`):①基线跑过 A、B,这一次报告里只有 A → 拒绝、点名 B、什么都没提交;②B 带 `skipped` → 同样拒绝;
③带声明 → 放行、正文有声明、基线更新为这一次跑过的;④基线文件不在 → 照旧放行并写入;⑤`verify-setup` 写入基线文件;⑥被拒 → `changes` → tester 只改测试 GREEN → 进 `impl`;
⑦基线文件不进 W57 指纹(只改它不重跑)。变异点:不比跑过的集合、`skipped` 算跑过、⑱ 不算消失的、完成时不更新基线文件。

**不做** 不把 `full_failures` 从状态文件挪进这个文件(W59 刚落地,迁移另议);不区分"删除"与"改名"(都要声明)。

## run.py 写出 JUnit XML

- 依据: 人类定稿

**背景** 第三十二轮 W58(用例级报告)与 W59(完成时只拦新增的红)只在 harness 的假测试命令上验证过 —— 本仓库的 `tests/conformance/run.py` 只给退出码与文本输出,
写不出 JUnit XML,本仓库自己用不上这两层。`run.py` 把用例分片交给多个 `python3 -m unittest -q` 子进程,知道每个分片跑了哪些用例 ID,
也已经解析各分片输出里的 `FAIL:` / `ERROR:` 行来数失败。

**行为**
- `run.py` 新增参数 `--junit-xml <路径>`:跑完后写出一份 JUnit XML,包含这一次收集到的所有用例。每个用例的 `classname` = unittest ID 去掉最后一段(`模块.类`),
  `name` = 最后一段(方法名);ID 出现在某个分片输出的 `FAIL:` 或 `ERROR:` 行里(`FAIL: <方法> (<模块.类.方法>)` 的括号内),就带一个 `failure` 子元素。
- `-q` 的输出看不到跳过:本仓库里收集到的用例都写成跑过。某个分片整体崩溃(导入失败、没有 `FAIL` 行)时,报告与退出码会对不上,
  第三十二轮 W58 的 ⑰ 会把报告降级 —— 安全方向,不另处理。
- 不给 `--junit-xml` 时输出与行为完全不变(本仓库现有配置、`mutation_check` 的基线运行都不受影响)。

**分工** `run.py` 在 tester 路径:实现与用例由 tester 在 spec 回合写(同第二十三轮 W40),dev 在 review-test 评审。

**补充**(W62 的 spec 回合带声明补,开工前审查 ⑲)`FAIL:` / `ERROR:` 行有两种形态:3.11 起括号里是 `模块.类.方法`,3.10 及以前只有 `模块.类` ——
CI 矩阵有 3.9,只认前一种时那里每个失败都对不上 ID、报告全绿,W58 的 ⑰ 只能把它降级。两种都认:括号内以 `.<方法>` 结尾就是完整 ID,否则拼上方法名
(与 `mutation_check.py` 的 `FAIL_RE` 同一个口径);`subTest` 失败的行在括号之后还有参数,只取第一对括号。判据再加:解析函数直接喂两种形态与带 `subTest` 参数的行。

**判据** 用例:给 `--junit-xml` 跑一个小模块 → 文件存在、能被 `pair.py` 的 `junit_failures` 读出、ID 与 `run.py --list` 列出的一致;
构造一个失败的用例模块 → 它在报告里带 `failure`、退出码非 0;不给参数 → 不写文件。

**不做** 不改分片方式去拿跳过信息;不改默认输出。

## 代办通道

- 依据: 人类定稿

**背景** 两轮真实运行的卡住统计里,有几次卡住的形状是"知道该改成什么,但没权限":用一次完整的异议往返传一个值,还消耗打回额度(路线图 P1-13)。
原设计让 request 不交出回合,可主要场景是 dev 在 impl 被 tester 路径里的东西挡住、测试红着交不了接,那时只能异议、照样计数。人类裁决补上这个缺口。

**行为**
- `request --path <路径> [--path …] "<改什么,含具体值>" --reason "<为什么我改不了>"`:只在自己的回合、spec 或 impl 阶段;评审阶段与 idle 拒绝。
  每个路径必须归对方角色(不在自己的 `roles` 里、在对方的里);冻结路径或孤儿路径拒绝,文案让交给人类并附可直接执行的 diff。内容与理由不得为空。
  记进状态 `requests`(每条含 `id`(R1、R2……本工作项内递增)、`item`、`by`、`to`、`paths`、`what`、`reason`、`base`(当时的 HEAD)、`status`(open)、`carried`(false)),
  只提交状态文件,提交信息 `chore(pair): 代办 R<n> …`,正文含内容、路径与理由;工作区里没提交的改动原样留着。不改阶段、归属与 `changes_count`。
- `fulfill R<n> ["说明"]`:只有被请求方、在自己的回合执行;请求的路径里至少一个自 `base` 起有改动(含工作区),否则拒绝。它是记账,不是执行。
  状态标 fulfilled,只提交状态文件。
- `decline R<n> "<理由>"`:只有被请求方、在自己的回合执行;理由不得为空。状态标 declined,只提交状态文件,提交信息 `chore(pair): 拒绝代办 R<n> …`。
  这条代办被异议带过(`carried`)时,`changes_count` 补加 1;补加后到死锁上限,照死锁闸原样处理。
- dev 在 impl 用 `handoff changes` 异议、而自己发给 tester 的代办还有开着的:这次异议不计入 `changes_count`,那些代办标 `carried`,正文写一行列出它们。异议文件照旧必须写。
- 交接时,发给自己、还开着的代办必须先 fulfill 或 decline,否则拒绝交接;工作项完成时不能有任何开着的代办,否则拒绝完成。`claim` 时清空 `requests`。
- 三条命令开头都做状态篡改检查。`status` 列出发给自己、还开着的代办。`report` 加两行:代办次数、被拒率(按提交信息数)。
- `rules.md` 写明:request 不得用于表达分歧,`--reason` 回答"为什么我改不了"而不是"为什么你错了";被请求方随时可以 decline。
- 登记 `ENFORCEMENTS`(`request-shape`、`fulfill-owner`、`request-closed`);"发给自己的代办还开着"进 `HANDOFF_INVARIANTS` 并同步 `protocol-spec.md` §4;
  §8 状态表加 `requests`;`command-reference.md`、`architecture.md`、`troubleshooting.md`、`SKILL.md` 命令清单跟上;路线图 P1-13、P1-14 标 ✅。

**判据** 用例:request 不改阶段、归属与计数;路径属于自己、孤儿、冻结时拒绝;评审阶段与不是自己的回合拒绝;内容与理由进提交正文;工作区未提交的改动不受影响;
fulfill 由非被请求方执行被拒、路径没改动被拒、成功后为 fulfilled;带开着的代办异议计数不变、代办 carried;tester fulfill 后 GREEN 交接进 impl;
decline 被带过的计数加 1、没被带过的不变、补加到上限触发死锁闸;发给自己的代办开着时交接被拒;有开着的代办时完成被拒;`claim` 清空;`report` 两行数对。
变异点:带代办的异议照样计数、decline 不补计、fulfill 不校验归属、fulfill 不校验改动、交接不查开着的代办。

**不做** 不做 patch 应用器(脚本不代 agent 改文件);代办不跨工作项;异议文件不因带了代办而豁免;不在评审阶段开放;不让 request 交出回合。

## 提案目录

- 依据: 人类定稿

**背景** 方向问题往往是做的过程中才暴露的;真实运行里 tester 多次说"这超出本工作项范围,建议开新工作项",协议却没有地方承载这句话(路线图 P0-5)。
提案目录不能直接并进 `shared_paths`:那个键被异议举证、评审目录命名、打回的位置引用、记忆层自洽检查依赖,并进去"写了一份提案"就会被算成"异议落到纸面"。
所以要一个新的路径类别。这是 P0-5 拆分里的 D1,不碰阶段机。

**行为**
- 新配置键 `proposal_paths`(路径模式列表,同 `shared_paths` 的匹配规则),默认 `[]` = 不启用。`init` 给新项目写 `["docs/proposals"]`。
- 写权限:除 idle 外的四个阶段,两个角色都能写命中 `proposal_paths` 的文件。它不并进 `shared_paths`。
- 已提交的、命中 `proposal_paths` 的顶层 `.md`(直接位于某个提案目录下)只能追加:相对 HEAD 有删除行(含删除、改名)即拒绝,不分阶段、不分角色(与评审目录同一口径)。
- 四处不认它:impl 阶段 `changes` 的异议举证(只写了提案仍算没落到纸面);打回的位置引用(只从评审文件里找);评审目录命名检查;规范性文档(不要求 `--doc-reason`)。
- 与评审目录、记忆层一样:对 `scope` 豁免;排除出第三十一轮 W57 的指纹(也就排除出第三十三轮 W60 的受影响路径);`inbox` 的"对方这一回合写给你的"摆出它的原文。
- 交接正文:本回合新增或追加的提案,写一行 `提案: <路径…>`。
- `verify-setup`:`proposal_paths` 与 `roles`(任一角色)、`shared_paths`、`frozen_paths`、记忆层(memory 开着时的 `notes_dir`、`decisions_file`)、`ignore_paths` 任一重叠即判失败,点名重叠的是哪个键。
- 登记 `ENFORCEMENTS`(`proposal-append-only`);`protocol-spec.md` 配置表、§4 写权限边界与 §4.1;`command-reference.md`;`architecture.md`;`INSTALL.md` 的配置示例;
  `rules.md` 一节"超出本工作项的方向问题写进提案";路线图 P0-5 分轮表 D1 标 ✅,P0-7 的 `artifact_paths` 评估点写结论(不另设)。
- 本仓库 `tests/conformance/test_docs_consistency.py` 里扫"被跟踪的 `.md` 减去记忆层与评审目录"的检查,一并减去 `proposal_paths`(提案和评审一样是历史记录)。

**补充**(W66 的 spec 回合带声明补,开工前审查 ⑳)"重叠"的定义:**有一个文件会同时命中两边**。两边的每个模式各取代表路径 ——
不含通配符的取模式本身与 `<模式>/<某名>.md`(目录前缀语义),含通配符的把每段通配符换成一个具体名字 —— 任一边的代表路径命中另一边的模式就算重叠。
例:`proposal_paths: ["docs/proposals"]` 与 `roles.tester: ["docs"]`(前缀)、与 `ignore_paths: ["docs/proposals/*.md"]`(glob)、与 `frozen_paths: ["docs/proposals/定稿.md"]`(单个文件)都算重叠;
与 `roles.dev: ["docs/*.md"]` 不算(`*` 不跨 `/`)。

**判据** 用例:两个角色在 spec、impl、review-impl、review-test 都能写提案并交接;已提交的提案改一行被拒、删除被拒、追加放行;impl 的 `changes` 只写了提案被异议举证拒;
打回理由没有位置引用、只写了提案被拒;提案名不对应工作项不被命名检查拒;只改提案不要求 `--doc-reason`;配了 `scope` 时提案豁免;只改提案门禁不重跑;
`inbox` 显示提案原文、正文有 `提案:` 一行;`verify-setup` 五种重叠各判失败;默认 `[]` 时那个目录照旧受角色约束;`init` 写出 `docs/proposals`。
变异点:提案算作异议举证、评审阶段不可写、不查只能追加、不查重叠、提案要 `--doc-reason`、提案进指纹。

**不做** 不做 discuss 阶段、挂起与恢复、签字与批准(D2、D3);`report` 不统计提案(D4);提案没有必含小节(形状留给 D3);不另设 `artifact_paths`(副产物仍走 `ignore_paths`);不给老项目默认开启。

## discuss 阶段:挂起与恢复

- 依据: 人类定稿

**背景** 方向问题往往是做的过程中暴露的(路线图 P0-5)。第三十七轮 W66 给了它一个落点 —— 提案目录,但两个 agent 仍没有地方当场把它讨论清楚,
只能写下来等人类排期。这是 P0-5 拆分里的 D2:讨论阶段的进入与退出、工作项挂起与恢复。D3(签字、人类批准、提升为 PLAN/契约改动)与 D4(可配额度、`report` 频次)之前,
D2 要能独立成立。

**行为**
- **进入** `discuss --proposal <路径> "<为什么>"`:只在自己的回合、`phase` 为 spec / impl / review-impl / review-test 时可用;idle 拒绝。
  要配了 `proposal_paths`;`--proposal` 命中 `proposal_paths`,且本回合在它里面新写或追加了内容(相对 HEAD 有新增行或是未跟踪的新文件);"为什么"不得为空。
  工作区里只能有散文改动 —— 命中 `proposal_paths`、`shared_paths`、记忆层(memory 开着时)的路径;其余改动(含未跟踪文件,不含协议日志与 `ignore_paths`)存在时拒绝,点名文件。
  同一工作项已经进过一次 discuss 时拒绝,文案指向"写提案交人类"。
  通过时:`state["discuss"]` 记下 `{proposal, why, opened_by, turn, spoke, suspended}`,其中 `suspended` 是原 `phase`、`last_actor`、`after_rebound`、`rebound_from`;
  `spoke` 起始为 `[发起方]`,`turn` 为对方;`phase` 改为 `discuss`;只提交状态文件与本回合的散文改动,提交主题 `discuss: <为什么>`。`item`、`item_type`、`changes_count`、`requests` 不动。
- **讨论回合** discuss 阶段的 `handoff "<说明>"`:执行者必须是 `discuss.turn`;先查状态篡改;本回合必须在 `discuss.proposal` 里追加了内容;
  改动只能落在散文路径(同上);已提交的提案与评审只能追加(第三十七轮 W66、第十一轮 W18 的口径);不判红绿、不计入 `changes_count`、不改 `after_rebound` 与 `rebound_from`。
  通过时把执行者记进 `spoke`(不重复),`turn` 改为对方,提交主题 `discuss: <说明>`。
- **退出** `resume "<结论>"`:只在 discuss 阶段、执行者是 `discuss.turn` 时可用;结论不得为空。本回合在提案里追加了内容时先把执行者记进 `spoke`;
  `spoke` 不含两个角色时拒绝(单方不能退出)。改动同样只能落在散文路径、已提交的只能追加。通过时把 `suspended` 原样写回 `phase`、`last_actor`、`after_rebound`、`rebound_from`,
  `discuss` 置为 null,当前工作项 ID 记进 `discussed`;提交主题 `discuss(resume): <结论>`。
- **归属** `phase_owner` 在 discuss 阶段返回 `discuss.turn`;`status`、`whose-turn`、`handoff` 都经它判归属。其余直接查 `PHASE_OWNER` 的地方在 discuss 阶段不得抛异常
  (`request` 照旧因阶段不对被拒,`claim` 照旧因有工作项被拒)。`writable_paths` 把 discuss 当只读阶段。`status` 在 discuss 阶段给一段讨论简报:提案路径、理由、谁发过言、怎么交接与恢复。
- **report** 讨论相关的提交正文不含 `role=… phase=… -> …` 那一行,不被算成交接。
- **状态** `DEFAULT_STATE` 加 `discuss`(null)与 `discussed`([],进过 discuss 的工作项 ID;`claim` 不清)。
- 登记 `ENFORCEMENTS`(`discuss-open`、`discuss-prose-only`、`discuss-resume`、`discuss-once`);`protocol-spec.md` 阶段表、§5 新一节、§8 状态表;
  `command-reference.md`、`architecture.md`、`rules.md`(什么时候进 discuss、什么时候写提案交人类)、`SKILL.md` 命令表、`troubleshooting.md` 跟上;路线图 D2 标 ✅。

**补充**(W67 的 spec 回合带声明补,开工前审查 ㉑)`discuss`(进入)与 `resume` 开头同样**先查状态篡改**(还原并拒绝,同 `claim` 与代办命令):
两者都改状态并提交它,不先查的话,agent 手改的那部分(比如把 `changes_count` 改回 0、从 `discussed` 里删掉自己)就随协议自己的提交落地,篡改检测从此看不见。
判据再加:手改状态文件后 `discuss` / `resume` 被拒、状态文件被还原、没有新提交。

**判据** 用例:四个阶段各能进,进入后 `phase` 为 discuss、`whose-turn` 是对方、`item` 与 `changes_count` 不变;没配 `proposal_paths`、提案不在提案目录、本回合没写提案、
"为什么"为空、idle、不是自己回合各被拒;工作区有代码改动被拒且点名;同一工作项第二次进入被拒;讨论回合只写散文且追加提案可交接、回合翻转;没追加提案被拒、写代码被拒、
改写已提交的提案被拒;讨论回合不计数;只有发起方发过言时 resume 被拒,对方发言后任一方可 resume;恢复后 `phase`、归属、`after_rebound`、`rebound_from` 与挂起前一致
(含一条打回之后挂起的场景);恢复后能照常交接并完成工作项;`status` 与 `whose-turn` 在 discuss 阶段给出对的回合;`report` 不把讨论回合算成交接;`request` 在 discuss 阶段被拒。
变异点:进入不查工作区、讨论回合不要求追加提案、讨论回合可写代码、单方可 resume、恢复不还原 `after_rebound`、每项一次不查。

**不做** 签字、人类批准、提升为 PLAN/契约改动(D3);可配额度与 `report` 频次(D4);idle 时进 discuss;讨论中改代码或测试;自动暂存未提交的改动。

## 提案的签字与人类批准

- 依据: 人类定稿

**背景** 第三十八轮 W67 让两个 agent 能当场讨论方向问题,但讨论的结论要改 PLAN 或契约时,仍是人类读提案、手工改冻结文件、手工提交。
这是 P0-5 拆分里的 D3:双方签字 → 人类一条命令批准 → 提升为 PLAN/契约的改动。协议认不出谁是人类(与人类直接提交冻结文件同一个信任级别),
所以批准命令要求显式的 `PAIR_ROLE=human`,脚本把关的是内容:签字齐、签的就是这段 diff、签字由本人的回合提交、diff 只碰 PLAN 与契约、能干净应用。

**行为**
- **提议改动**:提案文件里**最后一个**以一行 ```` ```diff ```` 开头、以一行 ```` ``` ```` 结束的围栏块,是这份提案当前的提议改动;块内是相对仓库根的 unified diff
  (`--- a/<路径>` / `+++ b/<路径>`)。它的哈希 = 块内文本(不含两行围栏)的 sha256 十六进制前 16 位。提案只能追加(第三十七轮 W66),修订就是追加一个新的 diff 块。
- **`sign <提案>`**:只在自己的回合、`phase` 不是 idle 时可用;提案命中 `proposal_paths` 且存在、含 diff 块。在提案末尾追加一行 `签字: <角色> sha256:<哈希>`
  (哈希取当前最后一个 diff 块);提案里已有同一角色对同一哈希的签字行时拒绝。签字行随本回合的交接提交(普通交接或讨论回合的交接)。
- **`ratify <提案>`**:不经角色解析;环境变量 `PAIR_ROLE` 不等于 `human` 时拒绝,文案写明这是人类的批准命令、agent 不得运行。依次校验,任一不过即拒绝,
  PLAN、契约、提案都不改、不产生提交:
  1. 提案命中 `proposal_paths`、在 HEAD 里、工作区里没有改动;
  2. 含 diff 块;
  3. 两个角色对最后一个 diff 块的哈希都有签字行,且这些行在 HEAD 版本的提案里;
  4. 每一行签字由该角色的回合提交:引入这一行的提交(按 `git log -S` 找到的最早那一个)正文里有 `role=<该角色>`(作为独立的一词);
  5. diff 里出现的路径(`---` / `+++` 两行,去掉 `a/`、`b/` 前缀,`/dev/null` 除外)只有 `plan_file` 与 `contract_file`,且这两个文件在工作区里没有未提交的改动;
  6. `git apply --check` 通过(不做模糊匹配)。
  通过时:`git apply` 应用;在提案末尾追加一行 `批准: 人类 sha256:<哈希>`;只提交改到的 PLAN/契约与提案,主题 `chore(pair): 人类批准提案 <提案路径>`,
  正文写签字双方、哈希与改了哪些文件。契约变了之后两个角色的开工前校验按现有机制失效;工作项进行中契约变了,完成时按不变量 ③ 要留决策 —— 不另加规则。
- **`status`**:列出待人类批准的提案 —— 提案目录下的提案,两个角色都签了它最后一个 diff 块的哈希、且没有该哈希的 `批准:` 行;附上人类要跑的命令。
- 登记 `ENFORCEMENTS`(`proposal-sign`、`ratify-signed`);`architecture.md` 加"批准只由人类执行"一行,如实标为只有约定 + `PAIR_ROLE=human` + 提交留痕;
  `protocol-spec.md` §5 新一节;`command-reference.md`;`rules.md`(怎么写提议改动、怎么签字、agent 永远不跑 `ratify`);`SKILL.md` 命令表与和人类的边界;
  `INSTALL.md` 给人类的批准说明;路线图 D3 标 ✅,注明 P1-9 强版本、P0-6、P1-11 可复用这条机制。

**补充**(W68 的 spec 回合带声明补,开工前审查 ㉒)
- 第 4 步的"该角色的回合提交",角色**只从提交正文的第一行取**:普通交接是 `role=<r> phase=…`,讨论回合是 `discuss=<…> role=<r> …`。正文其余位置的 `role=` 一律不认 ——
  `--checked`、`--uncovered`、`--doc-reason` 等理由原样进正文、可以带换行,按"正文里有这个词"判,一方就能在自己的回合替另一方签字。
- 哈希的输入写死:开围栏那一行之后、闭围栏那一行之前的原文字节(每行带它的换行符),不做任何规范化。
- 判据再加一格:tester 的回合里写了 dev 的签字行、`--checked` 里另起一行带 `role=dev` —— `ratify` 照样拒绝。

**判据** 用例:sign 追加的行格式对、哈希等于最后一个 diff 块;没有 diff 块、idle、不是自己回合、提案不在提案目录、重复签各被拒;签字随交接提交。
ratify 被拒(之后 PLAN、契约、提案都不变、没有新提交):`PAIR_ROLE` 是 tester、dev 或未设;缺一方签字;签字之后又追加了新的 diff 块;签字未提交;
tester 的回合里写了 dev 的签字行;diff 碰了别的文件;diff 应用不上;PLAN 有未提交改动。ratify 通过:PLAN 与契约按 diff 改了、提案多一行 `批准:`、主题与正文对、
之后两个角色的开工前校验都不作数;discuss 阶段里批准也行,之后 resume 照常;status 列出待批准的提案,批准之后不再列。
变异点:不查签字哈希、不查签字由本人回合提交、不查 diff 只碰 PLAN 与契约、不查 `PAIR_ROLE=human`、不查签字已提交、应用之前不 `--check`。

**不做** 额度与 `report` 频次(D4);批准范围扩到 PLAN 与契约以外;协议认证人类身份;撤销已批准的改动(P1-11)。

## 讨论额度与频次

- 依据: 人类定稿

**背景** 第三十八轮 W67 为了不让 discuss 成为"遇到困难就逃出去"的出口,把额度写死成每个工作项一次。路线图 P0-5 的 D4 要求额度与死锁闸同构、可配置,
并让 `report` 统计讨论频次 —— 从不进 discuss 说明不敢提方向问题,频繁进 discuss 说明规划太粗,两种相反的病都要看得见。

**行为**
- 新配置键 `discuss_limit`(非负整数),默认 1(与第三十八轮 W67 的行为一致),0 表示不允许 discuss。
- `discussed` 的语义改为可重复:每次 `resume` 往里记一次当前工作项 ID。`discuss` 进入时,本工作项在 `discussed` 里出现的次数 ≥ `discuss_limit` 即拒绝;
  文案说明额度已用完,并指出两条出路:写提案交人类,或由人类调高 `discuss_limit`(文案含"人类"与 `discuss_limit`)。撞上额度只拒绝这一次 `discuss`,不改状态、不停止轮转。
- `verify-setup`:`discuss_limit` 不是非负整数(含布尔值、负数、字符串)时判失败。
- `status`:配了 `proposal_paths` 且当前有工作项时,显示一行"讨论额度:本工作项还剩 n 次"(n = `discuss_limit` − 已记次数,不小于 0)。
- `report` 加三行,都按协议自己写的提交识别:`讨论` = 主题以 `discuss:` 开头、正文第一行以 `discuss=open ` 开头的提交数(讨论回合与恢复不计);
  `讨论 / 认领` = `讨论` 与认领数,认领数 ≥ `MIN_SAMPLE` 时判定 —— `讨论` 为 0 标"从未讨论",`讨论` 超过认领数的一半标"偏高",否则 `—`,样本不足只给数;
  `人类批准的提案` = 主题以 `chore(pair): 人类批准提案 ` 开头的提交数。`--since` 时三行都只数区间里的提交。
- `ENFORCEMENTS` 的 `discuss-once` 改名 `discuss-quota`;`protocol-spec.md` 配置表、§5.6、§8;`command-reference.md` 的 `report` 指标表与 discuss 一节;
  `architecture.md`;`rules.md`;`INSTALL.md` 的配置示例;路线图 D4 标 ✅、P0-5 标已落地。

**判据** 用例:`discuss_limit=2` 时同一工作项能进两次、第三次被拒且文案含"人类"与 `discuss_limit`;默认配置第二次被拒;`discuss_limit=0` 第一次就被拒;
一个工作项的额度不影响下一个;`verify-setup` 遇到负数或非整数判失败;`status` 显示剩余额度、进过一次之后少 1;`report` 在两个工作项各讨论一次时
`讨论` 为 2、`讨论 / 认领` 为 2 / 2;认领满 `MIN_SAMPLE` 且从未讨论时出现"从未讨论";讨论过半时出现"偏高";`人类批准的提案` 计数对;讨论回合与恢复不计入 `讨论`。
变异点:额度写死为 1、额度判定用 > 而不是 ≥、report 把讨论回合也算进讨论次数、"从未讨论"判定不看样本量、"偏高"判定不生效。

**不做** 撞额度停止轮转;按角色分别计额度;跨工作项的总额度。
