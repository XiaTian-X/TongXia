# 决策记录（追加式 — 只能往后加，不能改历史）

> 条目格式(四个字段缺一不可):
>
>     ## <工作项ID> — <一句话结论>
>
>     - 理由: <为什么是这个结论,具体到会导致什么错误行为>
>     - 已否决: <考虑过但放弃的方案和放弃原因 —— 这是本文件最值钱的字段>
>     - 影响路径: `src/foo.py`, `tests/test_foo.py`
>
> `影响路径` 是检索键:今后谁要动这些路径,status 会自动把这条结论摆到他面前。
> 故意没有"分析"字段 —— 只共享事实和裁决,不共享推理过程。
> 单条不超过 1500 字符。

## SETUP — 执行器钉住副本,与工作产物分开

- 理由: 第一个工作项要改 `cmd_status`,而 `status` 是每回合的第一条命令。用正在被编辑的脚本执行判定,改坏一次就再也起不来,而且分不清是协议在拦你还是你把协议拆了。所以两个 agent 只调用 `.pair/enforcer.py`(冻结路径下,谁都改不了),工作产物是 `.agents/skills/pair-protocol/scripts/pair.py`。
- 已否决: 直接用真源当执行器 —— 红绿信号会被自举污染,这一轮的目的恰恰是读那些信号。
- 影响路径: `.pair/enforcer.py`, `.agents/skills/pair-protocol/scripts/pair.py`

## SETUP — 契约在开工前被收紧过一轮,已知歧义清零

- 理由: 起草人自查发现七处问题。其中一条是缺陷不是歧义:契约原本写着"必须进 PROTOCOL_LOGS / GITIGNORE_LINES",那是实现方案,会逼 tester 去断言常量名,直接违反规则 4。已全部改写成可观测行为(文件里有什么、handoff 会不会因它判越界、init 之后 .gitignore 有没有那一行)。其余六条是格式层歧义:简报写成什么形态、四行头部怎么断言、红绿写成什么词、idle 与 PLAN 全完成两个分支算不算自己回合、"五项恒在"与"记忆段落可省"的冲突、以及"写失败"原本无法注入。现在格式定死、两个分支写明、失败可通过把目标路径建成目录来注入。
- 已否决: 只修那条规则 4 缺陷、其余留给结对方去发现 —— 那样能测出"契约歧义审查"这道门的真实漏网面积,但 idle / PLAN 全完成 / 写失败三条很可能让第一个回合就卡死,试验会变成排障。
- 影响路径: `docs/pair-run/CONTRACT.md`, `docs/pair-run/PLAN.md`

## SETUP — 格式类规格用示例锚定,不用散文描述

- 理由: 契约"收紧一轮"之后仍有五处歧义,而且全在同一个位置:用散文去描述一个字节级的东西。标题行算不算规格、冒号半角还是全角、"与终端那段逐字一致"的边界在哪、空行、末尾换行 —— 每一条都能让 tester 的断言和 dev 的实现对不上,而功能本身没错。现在契约里贴了逐字节精确的完整示例 + 逐行规定表 + 无记忆内容时的第二个示例。
- 已否决: 继续用散文逐条描述格式 —— 那正是这五条歧义的共同成因,再写五句只会产生第六条。也否决了"把已知歧义留给结对方去发现":故意留下已知缺陷测不出协议的能力,只测出对方会不会替起草人收拾。
- 影响路径: `docs/pair-run/CONTRACT.md`, `docs/reviews/setup-verification.md`

## SETUP — 契约解析要跳过 markdown 代码块

- 理由: 契约里贴逐字节示例之后,`contract_sections` 把示例里的 `# 回合简报` 当成了小节标题,于是同一份契约被判成"小节重名",`claim` 直接拒绝。而契约里放 markdown 示例是完全正常的事 —— 格式类规格本来就该用示例锚定。围栏内容现在被换成等量空行(不是删除,否则后面的偏移量会错位,`依据` 也会读错)。执行器副本已随之重新钉住。
- 已否决: 改契约绕开(比如把示例里的 `#` 换成别的字符)—— 那是让规格迁就解析器的 bug,而且契约恰恰规定了简报第一行必须是 `# 回合简报`,示例里绕不开。
- 影响路径: `.agents/skills/pair-protocol/scripts/pair.py`, `.pair/enforcer.py`, `tests/conformance/test_v1_brownfield.py`

## W1 — 打回换来的修复必须在同一个工作项里补上测试

- 理由: review-impl 打回修掉了"item_type 为空时写出裸 ID"的契约偏离,但把那行改回去之后 230 个测试仍然全绿 —— 缺陷完全不设防。若 W1 就此完成,历史上会留下"发现→打回→修复→通过"的完整记录,而缺陷此刻谁都能带回来且红绿不响。这个项目自己的信条是"一个恒真的测试集比没有测试更危险",这条对打回换来的修复同样成立。
- 已否决: 按 tester 原计划留到下一个工作项的 spec 回合补 —— "评审回合只读"是对的,但补测试的正确时机不是下一项的 spec,而是把这一项打回到 spec。跨工作项补测试会让 W1 带着一个不设防的修复完成。
- 影响路径: `.agents/skills/pair-protocol/scripts/pair.py`, `tests/conformance/test_v1_brief.py`

## W1 — 打回之后的 spec 回合只豁免 RED,不豁免 GREEN

- 理由: review-test 以"覆盖不足"打回时,tester 要补的回归测试按定义是绿的(修复已落地),而 feature 的 spec 要求 RED —— 正当路径把自己锁死。豁免逻辑本来就存在,注释里那句"异议之后紧接着的 spec 回合"逐字描述了这个处境,缺的只是入口:`after_dispute` 只在 impl 阶段的异议时置位。改成任何打回都置位,并改名 `after_rebound`。但**不能像异议那样整个置空 expect**:cover 的 spec 期望 GREEN,而 cover 同样有 review-test changes → spec 这条边,整个置空会让红着的 cover 过关,而"全程绿"正是 cover 的全部纪律。所以只豁免 RED。
- 已否决: 另开一个 [cover] 工作项去补那条回归测试 —— 零协议改动,但会让 W1 带着不设防的修复完成,而且以后每次"评审要求补测试"都要人类介入。也否决了"不允许 review-test 以覆盖不足打回" —— 那正是 review-test 最有价值的部分。
- 影响路径: `.agents/skills/pair-protocol/scripts/pair.py`, `.pair/enforcer.py`, `tests/conformance/test_v1_disputes.py`, `docs/protocol-spec.md`
