在真实用法下是空的。

## 一处取值我换了写法：`git hash-object`，不是 `blob_sha`

仓库里现成的 `blob_sha(root, path)` 走的是 `git rev-parse HEAD:<path>` ——
**取的是 HEAD 里那一份**。重钉发生在 `git add -A` 之前,那一刻正本的新内容
还没进 HEAD,拿它取出来的是**上一次提交的旧 sha**,写进正文就是错的。

改用 `git hash-object <正本>`,取工作区那一份的 blob sha ——
和你用例里的算法逐字一致。

## 位置钉了两头，并把理由写进了函数 docstring

`repin_judge` 的 docstring 里写明:调用点必须落在写权限边界校验之后
(否则被自己的冻结判定拦住)、且在 `git add -A` 之前(否则副本留在工作区
没进提交,下一个回合对方被拦住且没有出路)。

写在函数里而不是调用点,是因为下一个搬动这个调用的人会先看函数。

# 自举那一步的缺口：手工重钉少了"并提交"，实测把 tester 卡住了

人类按 PLAN 的自举条款做了 `cp`,但**没有提交**。工作区因此留下一个改过的
冻结路径,而下一个回合是 tester 的 review-impl。实测:

```
$ PAIR_ROLE=tester .pair/enforcer.py handoff approve … --checked … --uncovered …
[结对协议] 拒绝交接 —— 以下改动越界:
  .pair/enforcer.py
      冻结路径 .pair 之下,agent 不得修改

请撤销这些改动后重试。
```

**这就是契约「裁判副本的同步」里写下的那个"没有出路"场景,第一次真的发生了**
—— 只是发生在**手工**那一条路上,不是自动那一条:

- 自动重钉的位置要求(边界校验之后、`git add -A` 之前)写进了契约,
  而它的作用**正是保证重钉进同一次提交**
- 手工重钉是同一件事的另一条路径,**同样需要"并提交"这一步**,
  但 PLAN 的自举条款只写了"人类要再手工重钉一次",没写这一句

而且这一次比契约描述的更糟一点:`.pair/enforcer.py` 是**冻结**路径不是孤儿,
所以 W4 那条"多半不是你改的,先找人类划归"的提示**不会触发** ——
agent 拿到的是一句没有任何缓和的"请撤销这些改动后重试"。

**处理:** dev 代为提交那一个文件(不是 `-A`),tester 的回合恢复干净。
**要补的:** PLAN 的自举条款加"并提交"三个字;或者更好 ——
既然重钉这件事已经有代码了,自举那一次也该由人类跑一条命令而不是 `cp`,
那是 W7 之后的账。
