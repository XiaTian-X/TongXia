## 一处取值我换了写法：`git hash-object`，不是 `blob_sha`

仓库里现成的 `blob_sha(root, path)` 走的是 `git rev-parse HEAD:<path>` ——

还没进 HEAD,拿它取出来的是**上一次提交的旧 sha**,写进正文就是错的。

改用 `git hash-object <正本>`,取工作区那一份的 blob sha ——
和你用例里的算法逐字一致。

被挤到下一行的是**右括号**,不是 sha —— 第 4 行里 sha 是**完整**的,
而且那一行同时含 `JUDGE_REL`。所以:

| 判据 | 变异 A 之下 |
|---|---|
| 旧的 `sha[:7] in body` | True(恒真) |
| 你给的"一行同时含路径与完整 sha" | **True(同样恒真)** |
| `sha + "\n" not in body` | False ✓ |
| **正文里没有"只剩标点"的残行** | False ✓ |

这是这个工作项里**第三次**同一个形状:我的原判据、我在 review-impl 里
自己写下的"正确判据"、你在 review-test 里给的改法 —— 三条都指向
"那一行要完整",而三条都用"sha 完整"去代表"行完整",而这两件事在这个
缺陷下正好可以分开。

## 二、最后取的判据，以及为什么它不撞规则 4

拆成两条:

- `test_重钉的_sha_进提交正文` —— 恰好一行同时含副本路径与完整 sha
  (守"记录存在且在一行里",这条你给的判据本身是对的,只是抓不住 A)
- `test_写进正文的值不带换行` —— **正文里不该有"只剩标点"的残行**

第二条才是抓 A 的那条。它为什么是结构判据而不是措辞判据:一个带换行的值
插进模板**中段**,模板剩下的那半必然独占一行、且不含任何字母数字 ——
**不管措辞怎么写都成立**。而值恰好在模板**末尾**时不会留下残行,
那种情况也确实无害(换行和消息本身的换行合并),判据不误伤它。

否掉了 `sha + "\n" not in body`:它等价于假设"sha 后面还有字符",
也就是假设了 `(%s)` 这个措辞。改格式让 sha 收尾就会误红一个正确实现。
