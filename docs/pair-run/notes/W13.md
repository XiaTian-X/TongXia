# W13 — tester 的 spec 回合

契约「校验与沉淀的有效期」是我起草的(第五轮开工前),所以这组用例同样有
"照起草人意图写断言"的风险。补救照旧:**只断言行为,不断言措辞**,每条 docstring
写清判据从契约哪一句来。

## 这一回合交了什么

`tests/conformance/test_v1_validity.py`,四组 18 条:

- **契约变了、校验作废**(10 条,`require_setup_verification` 打开):
  改过之后不能认领(且不写状态、不产生提交)/ 重跑之后恢复 / dev 重跑不替
  tester 解锁 / 只有 dev 校验过时 tester 不能认领 / 人类没提交的改动也算、
  且重跑之后不锁死 / 提交之后同一份内容不必再校验 / 键缺失要求重跑 /
  契约读不到时拒绝 / 工作项中途契约变了不挡交接 / `whose-turn` 与 `status`
  不停也不写
- **门禁没开时不存在**(1 条)
- **已沉淀按工作项算**(5 条):复现第四轮第 1、2 次发作 / 认领之前就有的同 id
  条目也算 / 只有别的工作项的决策时两道闸照样拦
- **另外两处一个字不改**(2 条):第二次打回、带声明改契约,都要求当场

## 判据的取舍(dev 看这里)

**① 拒绝文案只断言 `verify-setup`。** 契约说"说明契约变过、要重跑校验",没给字面。
说"要重跑校验"而不提命令名做不到,所以只钉命令名。"契约变过"怎么措辞你定。

**② 状态里那个新键叫什么、长什么样,我不碰。** "键缺失"用存量升级的真实形状模拟:
一份 `setup_verified` 为真、从没被新代码写过的状态文件,由人类提交。

**③ 契约读不到那条用 `[cover]` 工作项。** 非 cover 的项在契约读不到时**早就**被
既有的「契约小节不存在」拒了,拿它测等于测既有行为、今天就是绿的。cover 跳过
那道检查。这条只断言"拒绝了、阶段还是 idle",理由文案你定。

**④ "两端同口径"那条分两半,各打一种错误实现。** 比对端取 HEAD → 前半截放行;
记录端取 HEAD、比对端取工作区 → 重跑之后永久拒绝(契约说的"锁死")。

## 我对这一节契约的两处读法,请你确认或打回

**(a) 门禁只在 `require_setup_verification` 打开时存在。** 契约没明说,但它写的是
"判据是 `setup_verified` 为真**且** sha 一致"—— 是既有门禁的延伸。关着的时候
还拦,既有几百条用例会一起红。我加了一条用例钉它。

**(b) "按角色各存一份"里 dev 那一份,今天没有任何消费者。** `claim` 只有 tester
能执行,所以"`claim` 只看执行者自己那一份"= 只看 tester 的。契约的理由也只论证了
tester 必须读过新契约。可观测的只剩"dev 重跑不替 tester 解锁",我钉的就是这个;
**不为 dev 发明一道门**。契约允许 `status` 加一条不阻断的提示 —— 如果你愿意,
那条提示对两个角色都说,dev 那一份就有了唯一的读者。这不是分歧、不需要人类裁,
我在这里记一句,免得有人以为 dev 的重新校验是被强制的。

**(c) 顺带一件事,不是 W13 的范围:** 既有的 `contract_sha`(`claim` 时记、`DONE`
时比、给 `contract-change-note` 用)取的是 **HEAD 的 blob**;W13 新记的这一份按契约

两端同口径,没要求改旧的,我也没为它写用例。**命名上请让两者一眼分得开。**

## 怎么实现的

- **沉淀那半边照你定死的字面写**:`settled` 紧接在 `mine` 之后;两道完成时的闸
  `not mine` → `not settled`;第二次打回、当场留决策那两行一个字没动。101 个锚点全部匹配。
- **`worktree_sha`**:`git hash-object -- <path>`,取工作区内容;读不到返回 `None`。
  记录端(`verify-setup`)与比对端(`claim`)**都用它** —— 契约说两端不同口径会锁死。
  先例是 W10 的 `repin_judge` 也用 `hash-object`。
- **新键 `setup_verified_contract`**:`{角色: sha}`。你 (c) 要求和 `contract_sha` 一眼分开 ——
  名字不同,`DEFAULT_STATE` 里两段注释并排写清两者的区别(按工作项 / 按角色,HEAD / 工作区)。
  `protocol-spec` 的状态表也加了一行。
- **`verify-setup` 记录时先复制再写**:`load_state` 是 `dict(DEFAULT_STATE)` 的浅拷贝,
  直接往默认的 `{}` 里写会改到 `DEFAULT_STATE` 本身。解析不出角色(W12 的回落路径)时不记。
- **`claim`**:既有门禁那两行没动(锚点「拆掉 verify-setup 门禁」),新检查另起一段放在后面。
  **门禁没开时这一条不存在** —— 同意你 (a) 的读法。拒绝文案分两种:记录缺失(存量升级)
  与契约变过,都含 `verify-setup` 与"对方重跑不能替你解锁"。
- **`status`**:门禁开着、`setup_verified` 为真、但你那份不作数时,给一句**不阻断**的提示,
  **两个角色都说** —— 你 (b) 提的:dev 那一份记录因此有了唯一的读者。只读,不写状态。
- **`whose-turn`**:没动。
