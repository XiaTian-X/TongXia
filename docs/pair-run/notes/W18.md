# W18 — tester 的 spec 回合

认领前重跑了 `verify-setup`(上次校验之后契约只变了我在 W17 补的那一条,补记在
`setup-verification-tester.md` 末尾)。

## 这一回合带声明改了契约一处(开工前审查的 ④)

契约原文只说 `verify-setup` 那一侧"拒绝,不提交",**没说拒绝在哪一步**。`cmd_verify_setup` 的顺序是
结论检查 → 起草人声明 → 写 `setup_verified` → `save_state` → 提交;新检查插在写状态之后就是 W12、W15
两次治过的"状态对、退出码错",而且这回状态位留在工作区、下一次交接判它篡改。补写明**拒绝发生在写状态之前**,
可断言"拒绝后状态文件不变、HEAD 不变"。PLAN 加 ③′,决策 `## W18 — verify-setup 那一侧的拒绝必须早于写状态`。

## 用例:`tests/conformance/test_v1_review_immutable.py`,10 条

- **拒绝**(4 条):评审回合改写已提交的评审记录(文案要给出本回合该写的文件名)、删掉整份、改名、
  **dev 在 impl 回合改写**(不分角色不分阶段)
- **放行**(4 条):纯追加、新建文件、`ignore_paths` 豁免、子目录与非 `.md` 不管
- **`verify-setup` 一侧**(2 条):改写已提交的结论被拒**且状态文件与 HEAD 都没动**;往结论末尾追加照旧放行

## 判据的取舍

- **拒绝文案只断言三样**:那份文件的路径、本回合该写的文件名、"不要撤销"与"告诉人类"。
  契约写的是"如果这份改动不是你做的",PLAN 写的是"如果不是你改的" —— 两处措辞不同,取都有的部分。
- **`verify-setup` 那条同时断言状态文件逐字不变、HEAD 不变** —— 这是 ④ 那处修改的可观测形式。
- **追加那条用的是"往结论末尾补记"**:W13 起 tester 每次重跑都这么做,这条用例守的是这个既有用法不被打断。

## 两半都在隔离副本里实现过,再说话

参考实现:`review_rewrite_violation`(顶层评审 `.md`、非 ignore/协议日志、已在 HEAD、有删除行)在
`handoff` 的边界判定之后逐条判,`verify-setup` 在 `save_state` **之前**判那份结论。**全套 434 条 OK。**

| 拆掉 | 红 |
|---|---|
| 检查从不触发 | 四条拒绝 + `verify-setup` 那条 |
| `verify-setup` 一侧的检查 | `verify-setup` 那条 |
| 把 `verify-setup` 的拒绝挪到 `save_state` 之后 | `verify-setup` 那条(**改过判据之后**,见下) |
| 「已在 HEAD 里」 | **0 红 —— 等价变异**,PLAN ⑥ 已带声明改成不要求变异点 |

**又抓到自己两条恒绿的判据:**

1. `verify-setup` 那条第一版把结论改写成 `self.REPORT.replace("## 逐节点名", …)` —— 那个小节名根本不存在,
   `replace` 是空操作,**文件压根没变**。改成真的删掉一行,并断言"场景前提成立"。
2. 改对之后仍然恒绿:第一版让 `verify-setup` 先通过一次再改写,那时 `setup_verified` 已是 `true`,
   第二次写状态字节相同 —— **拒绝挪到 `save_state` 之后也测不出来**。改成结论由人类提交、
   `setup_verified` 仍为假时第一次校验,现在挪到 `save_state` 之后就红了。

**一个给你的提醒**:我的参考实现第一版把新函数写成 `if not blob_sha(root, path):`,和 W16 的既有锚点
「只追加路径不在 HEAD 也放行」**字面撞了**,`test_变异点仍能匹配到源码` 当场红(匹配到 2 处)。
换成 `if blob_sha(root, path) is None:` 就好了。你实现时留意这一处。
