### 用例怎么造的,实现时要知道的

- **假门禁**(仓库外的脚本当 `test_cmd`,`test_report = .pair/gate.xml`):
  - `tests/` 下每个文件是一条用例,ID 是 `tests.<文件名>`(`classname="tests"`)。
  - 文件内容含 `hidden` = 不被收集(报告里没有),含 `skip` = 带 `<skipped/>`,含 `red` = 红,其余是绿的跑过。
  - `garbage` 模式写一份坏 XML(读不出)。
  - 每次调用都带 `PAIR_FRESH_TESTS=1`。
- **认领时基线**:人类在认领之前把 `tests/A`、`tests/B` 和 `.pair/full-baseline.json`(`executed` = `tests.A`、`tests.B`)连同 PLAN 一起提交。PLAN 里是 `C1 [cover]` 与 `W1 [feature]`。
- **"中途基线被改写"**:`.pair/` 在冻结路径下,人类直接改写并提交(中途 `verify-setup` 也会提交它)。所以 HEAD 里的那份与认领时那份不同,不是工作区里没提交的改动。两个方向都造:
  - 把 `tests.C` 写进之后的基线,tester 加 `tests/C` → 照旧放行;
  - 把 `tests.A` 从之后的基线删掉,tester 只改 `tests/A` → 照旧拒绝。
  - 读工作区那份或 HEAD 那份的实现,两条至少红一条。
- **改名**:删 `tests/B`、加 `tests/B2`,`--renamed tests.B=tests.B2 --allow-deletion "…"`。
  - 这是**同一回合**的声明,所以判"新用例"时要用 W78 已更新到内存状态里的那份 `renamed_tests`。
  - 对照组同样的改动不声明:`tests.B2` 算新用例,放行、正文 1 条 —— 证明拒它的是"扣掉改名新名",不是别的防护。
- **修正回合**:第一回合加 `tests/C` 进 review-test,dev 用 `changes` 打回到 spec,tester 只改 `tests/A` → 放行(W17 捷径照常进 review-test),正文仍是 1 条。
- **拒绝**:断言提交数与 `state.json` 不变、文案里有"认领"两个字,其余措辞不断言。
- **正文**:`新用例(跑过): N 条`,ASCII 括号与冒号;N 用两条新用例钉住。
- **没有 `item_base`**:认领之后人类提交一份把 `item_base` 置空的状态。
- **feature 不判**:认领 `W1`,只把 `tests/A` 改成 red,RED 交接照常进 impl。

### 参考实现与探针

`.pair/scratch/` 里写过参考实现(已删),17 条全绿;`test_v1_*` 在副本里另外只有依赖仓库根文件的 12 条红(与 W79 那次相同,副本里没有这些根文件),协议行为类全绿。参考实现的形状:
- 在红绿不变量之后,只在 cover 的 spec、配了 `test_report` 时判;
- `junit_executed` 读门禁报告,`git show <item_base>:.pair/full-baseline.json` 读认领时基线,任一读不出就不判;
- 新用例 = 跑过 − 基线 − `renamed_tests` 的值;空就拒绝,否则正文写条数。

探针 13 个,全被抓:
- 契约列的:不判、用工作区基线、跳过的算跑过、不扣改名新名、读不出时拦了(报告读不出、没配报告、基线读不出各一个)、判到 feature 上、正文不写那一行。
- 加的:用 HEAD 里的基线、扣改名时扣的是旧名、N 写死成 1、拒绝文案不提认领。

把"基线读不出"当成空基线(什么都算新)不是"拦",是放得更宽。只在门禁一条用例都没跑时才观察得到,不登记。

### 没写用例的

- 门禁报告读得出但一条用例都没有:按我的读法该拒(不是"读不出"),没有单造。
- 门禁与全量 ID 拼法对不上(契约「不做」里说只会漏判,不会误伤)。
- 判点在红绿不变量之后的先后:cover 红着交接先收到的是红绿那条,现有 `test_v1_flows` 已覆盖红绿那一半。
