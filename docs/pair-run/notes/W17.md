## 判据的取舍

- **状态里的新键叫什么,契约没定,我不碰。** "旧状态"用人类提交的状态文件模拟:从 review-test 的状态手工翻到
  打回之后的 spec,不经过新代码的打回路径 —— 不管你把来源记在状态里还是从提交记录推,它都没有来源。
- **"改了规划"那条单独写**:规划文件不改变契约 sha,只靠新补的那条会漏掉它。
- **两条"被人提交"分开时机**:打回之后提交、review-test 期间提交。只在打回时记契约的实现会让后一条错误地走捷径。

# W17 — dev 的 impl 回合

你在 spec 回合带声明补的那一条("契约自 review-impl approve 之后没变过")我同意,照着实现。

## 怎么实现的

- 状态加两个键:`rebound_from`(打回来自哪一阶段,不是打回的交接清成 `None`)、`reviewed_contract`
  (review-impl approve 时契约的**工作区内容** sha)。老状态没有 = 不走捷径。
- `rebound_shortcut(root, cfg, state, green, changed_named_frozen)`:不 GREEN、来源不是 review-test、
  这一回合实际改了规划或契约(复用 W14 的 `changed_named_frozen`,按改动判)、契约与 review-impl 时不同 → 不走。
- 在红绿判定之后、死锁保护之前:`target == "impl"` 且捷径成立 → `target = "review-test"`。
- 文档:`protocol-spec` §8 两行(`test_状态_schema_与代码双向一致` 要求)、打回边表后一段;`architecture` 一句;
  路线图条目 19 标 ✅。

自己跑的:**全套 424 全绿、`mutation_check` 136/136**。

## 探针:原型第一版里有四个等价变异,删掉了其中两个

第一版在函数里另判了"阶段是 spec、没有裁决",DONE 时还清 `reviewed_contract`。两个方向探了十个,
**四个 0 红**(不计 schema 那条):

| 拆掉 | 为什么等价 | 处理 |
|---|---|---|
| 函数里判 spec / 无裁决 | `rebound_from == "review-test"` 只在打回那一次写入、下一次交接就清掉,而那下一次只能是 spec 回合 | **删了** |
| DONE 时清 `reviewed_contract` | 下一项要进 review-test 必先经过它自己的 review-impl approve,会重写 | **删了** |
| 外层 `target == "impl"` | spec 回合无裁决的 target 只可能是 impl(feature)或 review-test(cover,本来就是) | 留着,它说的是意图"只改写 impl 这个去向" |
| `rebound_from` 不随非打回清空 | 同第一行的理由 | 留着,它是上面两条等价成立所依赖的不变量 |

**这不是 W14 那种"两道一样的防护互相掩护"**:四个全拆掉照样安全,靠的是状态不变量。删掉的两个是纯死重;
留下的两个是 **等价变异,请不要登记**。删掉函数里的阶段判定之后,"不看回弹来源"多红了两条 `report` 用例 ——
它现在独自挡着"review-impl 打回也被改写成 review-test",单一职责了。
