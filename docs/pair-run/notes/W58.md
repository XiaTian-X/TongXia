## 带声明改的契约(开工前审查 ⑰)

报告要与退出码一致才用:退出码非 0 而报告无红、或退出码 0 而报告有红 → 当作读不出,警告点名报告路径。理由见 W58 决策。
(⑱ 是 W59 的,在 W59 的 spec 回合补。)

## 用例 `test_v1_junit_report.py` 15 条,今天红 12 条

假测试命令是仓库外的脚本(见文件头):按布局判红绿,按模式写报告(`normal` / `none` / `garbage` / `lying-green` / `lying-red` / `fixed`),并计数。
报告默认放在 `.pair/junit.xml` —— 故意落在冻结路径下。

- 列用例:红的列、绿的不列;25 条红只列 20 条、写"另有 5 条";全绿不列(绿,守着);不配 `test_report` 时不列(绿,守着)。
- ID 与合并:嵌套 `testsuite` 里的 `failure`、没有 `classname` 的 `error` 都列(`pkg.TestX.t_failed`、`solo_error`),`skipped` 与通过的不列。
- 降级四格(⑰ 占两格):没写报告、坏 XML、退出 1 而报告全绿、退出 0 而报告有红 → GREEN/RED 照退出码、不列用例、
  有一行**正常输出里没有的**、点名报告路径的警告(按"比正常输出多出来的行"判,不被"平时就印报告路径"满足)。
- 旧报告:第一次写了、第二次命令没写 → 不列上一次的、报告文件已不在(执行之前删)。
- 与 W57:报告没动 → 复用、照样列红用例(报告不进指纹);报告被改、被删 → 照常执行(记录里的报告哈希对不上)。
- 交接:报告在 `.pair/` 下,spec 与 impl 两次交接都放行、报告不在提交里、不被跟踪、留在工作区;报告放在两个角色都不拥有的 `reports/` 下同样放行、不提交。
