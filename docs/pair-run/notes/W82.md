### 用例怎么造的,实现时要知道的

- **认领**:人类提交 PLAN 与契约,小节都写 `- 依据: 人类定稿`,所以走得到 `依据` 之后的这道检查。
  - 拒绝时断言退出码非 0,提交数与 `state.json` 原样;放行时断言 `state.json` 的 `item`。
  - harness 的 `require_setup_verification` 为假,认领不需要先跑 `verify-setup`。
- **小节范围**:
  - 子小节是引用小节下面的 `###`。
  - "标题行"是被引用的那个 `##` 自己的标题。PLAN 的 `对应契约` 指向带标记的整串标题,例如 `部件构造 [待澄清: …]`。
  - "未被引用"是紧跟着的另一个 `##`;另一条在它前面先放一个 `###` 子小节,钉住子小节的边界。
- **写法**:契约表里每一种一条。全角冒号与两种全角括号用 `chr(0x...)` 拼。英文换行那条是 `[NEEDS\nCLARIFICATION: …]`。
- **代码豁免**:
  - 双反引号那条照搬契约的例子,即两个反引号、空格、单反引号包住的 `[待澄清]`、空格、两个反引号。
  - "恰好 N 个才关":单反引号 + 标记 + 紧跟一个双反引号串 → 两串都关不上,标记在代码外,拒绝。
  - "没关上":一个落单的单反引号之后是标记,拒绝。
  - 一节之内不留别的反引号,也没有跨段落配对的情形。
  - 围栏两种都有一条:```` ``` ```` 与 `~~~`。另有一条围栏之后的正文里放标记,照样拒绝。
  - `~~~` 那条是探针逼出来的。反引号围栏的开、闭两行本身就是等长的反引号串,行内代码的扫描会把它们配成一对,所以只用反引号围栏的话,"不先抹围栏"的实现照样全绿。
    开工前审查的补记里我写过不对 `~~~` 写断言,这里改了:契约说的是"围栏代码块",CommonMark 的围栏两种都算,W73 也已有"波浪线围栏也算代码块"。
- **文案**:
  - 原样含标记;含"人类";含"开工前校验"或 `verify-setup` 之一。
  - 6 处时恰好 5 处出现,且匹配 `另有\s*1\s*处`;5 处时全列、没有"另有"。
  - 哪 5 处不断言,标记用"第 N 个问题"区分。
- **`verify-setup`**:
  - 小节给齐 W73 的形状(填了数据行的表 + "返回"),用表不用代码块,免得 cover / refactor / bug 引用时冒出漂移警告。
  - 提到小节名的 `[警告]` / `[失败]` 按 W73 的切法数。
  - 3 处标记,断言那条提醒里有数字 `3` 与工作项 ID;单位不断言。
- **简报**:`advance_to("review-impl")` 之后 tester 的 `status` 输出含"契约没要求"。
- **骨架**:`BareRepo` + `init` 生成契约。
  - 断言含 `` `[待澄清 ``(行内代码写的用法)。
  - 把整份骨架当契约、PLAN 里 W1 指向 `<小节名>`,认领应放行。骨架的那段注释在 `<小节名>` 这一节里,HTML 注释照算,所以用法必须写成行内代码。
  - 「不做」:含"tester 不断言""dev 不该实现",没有旧的"dev 也不必实现"。
  - `contract-templates.md` 含同样两段。

### 参考实现与探针

`.pair/scratch/` 里写过参考实现(已删),本文件 40 条全绿。
副本里的 `test_v1_*` 全量是 45 红,都在依赖仓库根文件或 `examples/` 的 9 份文件里(`shipped` 17、`cli` / `make_demo_*` / `remote_push` / `repo_root_files` / `run_env` / `run_junit` / `scratch` 共 28)。
我在没打参考实现的副本里把这 9 份重跑了一遍,红的逐条相同,协议行为类全绿。参考实现的形状:
- **扫描**:
  - 先把围栏换成等长空白,再从左到右扫反引号串;遇到等长的串就把这一对之间抹掉,没关上的跳过。
  - 在"标题 + 换行 + `contract_sections_full` 那一节全文"上找 `[［【] 待澄清|NEEDS\s+CLARIFICATION (冒号 + 不含右括号的文本)? []］】]`,英文不分大小写。
- **认领**:放在 `依据` 那几条之后,只对 feature / bug;列前 5 条,超出写 `另有 N 处`。
- **`verify-setup`**:在未完成项循环里按小节收集 feature / bug 的引用,循环后每节一条 `warn`。

探针 38 个,37 个被抓:
- 契约列的:不查、不含子小节、不看标题行、围栏里的也算、行内代码里的也算、某种写法不认(全角冒号、没有问题文本、英文不认、英文分大小写、两词只认空格、`［］`、`【】`)、
  拦了 refactor、不拦 bug、`verify-setup` 不提醒、每项都报、文案不列标记、简报不写那一条。
- 加的:
  - 任意反引号串都能关、没关上的吞到结尾、HTML 注释先抹掉、没右括号也算、扫整份契约;
  - 全列不截断、截到四条、不写另有、另有条数写错、五条也写另有、文案不提人类与重跑;
  - `verify-setup` 不点名工作项、不写条数、判成失败、提醒 cover;
  - 骨架里的标记不写成行内代码、骨架不写用法、骨架与模板留旧口径。
- **没抓到的一个是"拦了 cover"**:现有的 `check_item_preconditions` 对 cover 整段跳过契约那几条(`if item_type != "cover"`),在里层把 cover 加进判断是死代码,等价变异,不是缺口。
  实现若把这道检查挪到那一段外面,`test_cover_项不拦` 会管住它。
- 第一轮有几个探针我自己的锚点写错(`\u` 拼成了 `\uu`、漏了一个逗号),修正后重跑,结果已并入上面。

### 没写用例的

- 左右括号混用、`待澄清` 与冒号间有空白、`NEEDS` 与 `CLARIFICATION` 间零空白、问题文本里有另一种右括号:契约没写成认或不认。
- 缩进代码块、`~~~` 围栏、没关上的围栏、跨段落的反引号配对。
- 认领时先查 `依据` 再查标记的先后(同时缺依据又有标记的小节)。
- 一个工作项写了多条 `对应契约`:只看第一条,与 `依据` 同一个取法,现有用例已覆盖取法本身。
- 变异点等实现落地后在 review-impl 登记。
