## 结论:三处要在认领前改契约,其余成立

### ① 那一行修法会新造一条 exit 1 —— 实测

`git commit -- <paths>` 走的是 git 的 `--only` 语义:**每个路径都必须是 git 认得的**
(在索引或 HEAD 里)。`to_add` 里来自 `shared_paths` 的条目取自 `changed_entries`,
其中可以有**暂存为新增、随后又从工作区删掉**的文件(porcelain `AD`)。`git add -- x`
把它从索引里拿掉,于是它既不在索引也不在 HEAD,`git commit -- x` 直接报错:

    error: pathspec 'docs/reviews/草稿.md' did not match any file(s) known to git

隔离副本里走完整条 `verify-setup`(`docs/reviews/草稿.md` 先 `git add` 再删掉,结论改一句):

| | 退出码 | `setup_verified` |
|---|---|---|
| 现状(`git commit` 不带路径) | **0** | True,已提交 |
| 打上契约给的那一行 | **1** | **True 已写进状态、但没提交** |

这正是 W12 刚治好的那一类:**状态是对的、退出码是错的**,而且这回状态还停在工作区。
`docs/reviews` 在本仓库就是 `shared_paths`,评审文件写了又删并不罕见。

契约「已验证 · 全套 357 条全绿」是真的 —— 我复现了 —— 但全套里没有 `AD` 这种场景,
所以那句"已验证"只覆盖了快乐路径。**「字面形状」那一段需要改**,例如提交的路径改成
`to_add` 里**在索引里真有差异的那些**(`git diff --cached --name-only -z -- <to_add>`),
它和 W12 的 `index_has_diff` 判的是同一个集合,空集时正好走 W12 那条"不提交"的路。
具体写法由人类或代笔人定;要紧的是契约里得有一句"路径在 add 之后已不被 git 认得时
不能让提交失败",并且 PLAN 验收标准里加这一个场景。

### ② 判据那句"查 HEAD 的树、不能用 `git ls-files`"只对了一半 —— 两者都转义

`git ls-files` 与 `git ls-tree` 不带 `-z` 时,中文路径被 `core.quotepath` 转义:

    ls-files 原样输出: "\345\201\267\350\267\221\347\232\204\345\256\236\347\216\260"

harness 没关掉它。于是 `assertNotIn("偷跑的实现", <输出>)` 不管实现怎样都成立。
**仓库里已经有三处这样的死断言**:`test_v1_setup.py:183`(既有)、
`test_v1_setup_report.py:175` 与 `:205`(我在 W12 写的 —— 后者的 docstring 正是
这一节引用的那句"查 HEAD 的树")。W12 的保证没被它们掏空(见 `W12-review-impl.md`
第二次评审),但照这一节的判据写 W15 的用例,**会写出一条恒绿的用例**,
而这一节恰好就是在教人避坑。

要改成:判"在不在"用 `-z` 输出按 `\0` 切开后**整条路径相等**,或者 harness 统一
`core.quotepath=false`。真正的坑是**转义**,不是"索引还是 HEAD"。

### ③ 修完之后,既有变异点「拆掉 verify-setup 的提交范围」会活下来 —— 实测

那个变异把 `git add -- <to_add>` 换成 `git add -A`。今天它被
`test_不把工作区里的代码一并提交进基线` 抓住,但**抓住它的是"警告列出偷跑的实现"
那一句**(实现被一起提交走了、不再是 stray,警告消失)—— 同一条里的 `ls-files`
断言因为 ② 是死的。

打上 W15 之后,`commit` 自己也只带 `to_add`:`add -A` 把工作区里的实现**暂存**进索引,
但不提交;`changed_entries` 照样看得见它(`A `),警告照打。于是:

- `test_v1_setup` + `test_v1_setup_report`:**35 条全绿**
- 全套 357 条:**只红 1 条,是 `test_变异点仍能匹配到源码`** —— 它红只因为变异把锚点
  那一行从源码里换掉了,是锚点记账,不是行为。**没有一条行为用例红。**

两道防护串联之后,拆掉前一道没有任何用例红。**这不是说 `add` 的收窄变得多余了**:
`add -A` 会把别人工作区里的东西**写进索引**,而这一节自己写的是索引里其他东西
"原样留在索引里:不提交,也不撤销"—— 同一个精神,`verify-setup` 也不该往索引里
加它范围之外的东西。PLAN 的验收标准只列了新变异点 ⑤,**要再加一条**:
工作区里范围之外的改动在 `verify-setup` 之后仍**不在索引里**(用 ② 的正确判法),
让「拆掉 verify-setup 的提交范围」重新有抓手。否则 W15 落地当天 `mutation_check`
就多一个 survived,而 W15 的 DONE 不会被任何东西拦下。

## 核过、成立的

- **"预先暂存的改动若落在角色路径下,既有警告会列出它"**:实测成立。现状下它被一起
  提交走、警告不出现;打上那一行后警告列出它、它不在 HEAD、仍在索引(用 `-z` 判的)。
- **"不拒绝范围之外的暂存"** 的理由(接入的第一条命令不该为无关的事卡住):同意。
- **"索引无差异那条路径一个字不变"**:那一行只动有差异的分支,成立。
- **变异点 ⑤ 的锚点**:`"--", *sorted(set(to_add))` 在 `git add` 那一行里也出现,
  锚点必须带上 commit 那一行的前半截才唯一。我在 spec 回合会用
  `            "-m", drafter_line, "--", *sorted(set(to_add)), cwd=root)` 整行
  —— 前提是 ① 改完之后字面形状还是这样;改了就跟着改。
- **决策用 `SETUP` 做 id 而不用 `W15`**:理由成立(W13 落地后判据是纯 id)。
- **`依据: 人类定稿`**:与第四轮起的惯例一致(`SETUP` 条目早写明它记的是授权定稿)。

## 小的,不要求改

- `shared_paths` 下的**重命名**:`changed_entries` 只取新路径,`git commit -- 新路径`
  提交新文件、旧路径的删除留在索引里。只提交一半的重命名,但不失败,也不进基线。
- 路径是 pathspec,默认按通配符解释。`git add` 那一行本来就是这样,不是本节引入的。

## 谁来改

①②③ 都要改冻结的契约与 PLAN,我改不了。它们不是分歧、是缺陷,修法各有一个显然的
方向,**不需要人类裁决**;按上次的授权由代笔人补上即可。补的时候请让我再读一遍改过的
那几段 —— W13 落地之前,契约变了不会强制任何一方重新校验,正是这一节开头说的那个空档。
