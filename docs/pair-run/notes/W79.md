### 用例怎么造的,实现时要知道的

- **小预算造场景**:`max_item_turns` 配 1~3,`BudgetBase.budget` 为 None 时不配。"不配时是 20"按 `status` 那一行判,不真跑 20 回合。
- **`status` 那一行**用正则 `回合预算[^\n]*?(\d+)\s*次[^\n]*?(\d+)` 取(已换手次数, 上限)。
  - 也就是:同一行里先出现"回合预算",再是"<n> 次",之后第一个数字是上限。
  - 照契约的 `回合预算 : 本工作项已换手 n 次 / 上限` 写就对得上。
  - 上限为 0 时显示什么不断言。
- **撞过的记录**:`status` 输出里要出现 `W1 x3` 这个字面串(怎么排版不管)。
- **第一次撞上**的场景:上限 3,依次做 spec、impl、review-impl `changes` 三次换手,之后 dev 在 impl 的第 4 次被拒。断言:
  - 提交数 +1;HEAD 主题逐字是 `chore(pair): 工作项 W1 交接 3 次,用完回合预算`(ASCII 逗号,与契约一致);
  - HEAD 只改 `.pair/state.json`;
  - `item_turn_budget_hits == ["W1 x3"]`;
  - 阶段仍在 impl、计数仍是 3;
  - `src/W1` 的改动留在工作区、未提交。
  - 用 `review-impl changes` 而不是 review-test `changes` 造第三次,免得碰上死锁闸。
- **讨论的三个入口**都用 `proposal_paths = docs/proposals`,发言 = 往提案末尾追加一段(同 W69)。
  - 开场被拒:上限 2,spec、impl 之后 tester 在 review-impl 开讨论。讨论额度还剩 1,提案写好了。
  - 讨论回合 `handoff` 被拒:上限 1,tester 开讨论(1)之后 dev 回应。
  - `resume` 被拒:同样上限 1,dev 追加后直接 `resume`(W69 的 `round_trip` 证明对方追加后可以直接 resume)。
  - 三条都断言阶段不变、计数不变,`item_turn_budget_hits` 记了一条 —— 第一次撞上发生在这些入口时同样记录。
- **代办**:照 W65 主场景,dev 在 impl `request`,带代办异议 `changes` 打回进 spec(这一次是 handoff,+1),tester `fulfill` / `decline` 前后计数相同。
- **认领清零**:正常完成就清零了,所以由人类在空闲时提交一份 `item_turns = 7` 的状态再认领。
- **老状态**:上限 1。tester 在 spec 时,人类提交一份删掉 `item_turns` 与 `item_turn_budget_hits` 的状态,tester 照常交接,计数变成 1。
  没有键若不当 0,这一次就过不去。
- **完成不拦**:上限 3,spec、impl、review-impl `approve` 用满,dev 的 review-test `approve` 照常进 idle,`item_turns` 清零、没有撞上记录。

### 参考实现与探针

`.pair/scratch/` 里写过参考实现(已删),18 条全绿。`test_v1_*` 在副本里另外只有依赖仓库根文件的 12 条红(remote_push、repo_root_files、run_env、run_junit、scratch,副本里没有这些根文件),协议行为类全绿。参考实现的形状:
- 一个判点函数,在 `handoff` 查完转移表、目标不是 `DONE` 时调,`discuss` 在额度判完之后调,讨论回合 `handoff` 与 `resume` 在回合归属判完之后调;understand 不调。
- 撞上时只记一次:看记录里有没有同一个工作项。
- 计数在各自 `save_state` 之前加 1;完成与认领清零。

探针 24 个,全被抓:
- 契约列的:不计数、完成时不清零、认领时不清零、不拦用满、拦了完成、`0` 不当不限、讨论三个入口各自不计数、各自不拦、撞上时不记录、每次撞都重复提交、`verify-setup` 不查。
- 加的:撞上时不提交、提交时带上工作区、判"用满"差一(放宽、收紧各一个)、默认不是 20、`status` 不显示那一行、不列撞过的记录、老状态缺键当 1、代办提交也计数。

### 没写用例的

- 人类中途调高上限之后同一工作项再撞:契约只说"同一工作项再撞不重复提交",调高之后算不算新的一次没说。
- 同一次交接同时撞死锁闸与回合预算的先后。
- W17 捷径那一次交接也计数(dev 的读法,我同意;它就是一次普通的成功 handoff,不单造)。
- 判点在跑测试之前(只断言被拒与工作区留着)。
- `max_item_turns: true`(按 `discuss_limit` 的口径应拒,契约只点名负数与非整数)。
- 变异点等实现落地后在 review-impl 登记。

## impl(dev)

`pair.py` 里两个小函数,四个入口各调一次:

- **`turn_budget_refusal(root, cfg, state, me)`**:没有工作项、上限 0、没用满 → None。用满时:
  - 同一工作项还没有记录:往**磁盘上的**状态追加 `<ID> x<N>`,用 `_commit_state` 只提交状态文件(和代办那几条窄提交同一个函数),主题照契约逐字写;
  - 返回拒绝文案(含 `max_item_turns`、"不是惩罚"、交给人类的三种处理、完成不拦)。
  - 读磁盘而不是用传进来的 state:调用方在内存里可能已经改了别的东西,不能一起提交。
- **`count_item_turn(state)`**:有工作项才加 1。各入口在 `save_state` 之前调。

判点:
- `handoff`:紧跟 W78 的 `rename_declarations` 之后(转移表查完、跑测试之前),目标是 `DONE` 时不调。
- `discuss`:在额度那一段里面(understand 不进那一段,本来也没有工作项)。
- 讨论回合 `handoff` 与 `resume`:回合归属判完之后。

计数:
- `handoff` 在翻转回合的非 `DONE` 分支里调(W17 捷径改了目标也走这里);`DONE` 分支清零;
- `cmd_claim` 清零;
- 代办三件套、`sign`/`ratify` 不碰它。

其余:
- `status`:有工作项时打印 `回合预算 : 本工作项已换手 n 次 / <上限 或 不限>(max_item_turns)`;有记录时打印"曾用完回合预算: …"。
- `verify-setup`:和 `discuss_limit` 同一种校验,`true` 也拒。你笔记里列的那一条,按 `discuss_limit` 的口径处理了,没有用例。
- `DEFAULT_STATE` 加两个键;`ENFORCEMENTS` 加 `item-turn-budget`(不进交接不变量,README 的 18 不动)。

文档:
- `protocol-spec.md`:§4.4 回合预算、配置表、状态表;
- `command-reference.md`、`architecture.md`(标记与表一行)、`troubleshooting.md`(新节)、`rules.md`(死锁闸那张表下面一段)、`SKILL.md`("协议自己卡住了"的列举);
- 路线图 P1-2 标 ✅,并写明前提核对的结论和为什么默认值不是原提议的 12。

### 给 review-impl 的提示

- 人类调高上限之后同一工作项再撞:按"同一工作项"判,不再记第二条、不再提交;拒绝照常。
- 同一次交接同时撞死锁闸和预算:预算先判(纸面、在跑测试之前),所以先收到预算的拒绝。
- 第一次撞上的那次提交发生在拒绝之前。之后调用方 `die`,工作区原样留着。
