## 和契约的哪一条矛盾

三条的矛盾点不在同一处:①③ 是用例的构造与契约无关的东西耦合了,
② 是断言比契约多要求了一件契约没规定的事。

**① 与契约「文档里的代码引用」的整节矛盾。** 那一节的存在理由就是
"行号是硬编码的坐标,每次插行都漂"。用例用绝对行号当输入,等于在守卫
这条规则的地方自己违反它。契约「旧形式被拒」要求的是**行为**
(区间要按起始行给建议),不是"用 2375-2390 这一对具体数字"。

**② 与契约「`verify-setup` 的孤儿清单」的输出条款不矛盾,但比它多要求了
一件事:清单的顺序。** 契约写的是"超过 10 个时只列前 10 行,再补一行说明
还剩多少个",**没有规定按什么顺序列**。用例的断言只有在"12 个构造出来的
孤儿排在最前面"时才成立,而那是一个契约没有给出的排序承诺。

**③ 与契约无关**,是用例与脚手架 `TEST_CMD` 的耦合。契约「`ignore_paths`
的覆盖清单」只说要列出命中 `ignore_paths` 的已跟踪文件 ——
副产物放在哪个目录不是契约的事。

## 应该改成什么

三条我都实测过改法可行,①②③ 分别是"别写死坐标""别按文件名数行""把副产物
挪出 tests/"。①的改法稍长,因为要在用例里现算坐标。

**① 在用例里现算,不写死。** 用 `ast` 取 `cmd_init` 里嵌套 `put` 的起始行,
和一个落在 `put` 之外、`cmd_init` 之内的结束行 —— 这样 `pair.py` 怎么改都
不会漂,而它守的性质(起止跨符号、必须取起始行)一个字都没弱:

```python
import ast
tree = ast.parse(PY_BY_REL[rel].read_text(encoding="utf-8"))
cmd_init = next(n for n in ast.walk(tree)
                if isinstance(n, ast.FunctionDef) and n.name == "cmd_init")
put = next(n for n in ast.walk(cmd_init)
           if isinstance(n, ast.FunctionDef) and n.name == "put")
bad = self._one("见 `%s:%d-%d`" % (rel, put.lineno, put.end_lineno + 1))
self.assertIn("cmd_init.put", bad[0], "应按起始行的最内层符号,而不是结束行")
```

实测 `put` 现在是 2431-2438,`end_lineno + 1 = 2439` 落在 `cmd_init` 内、
`put` 外 —— 起止跨符号的性质保住了。(我在自己这边跑过这段,拿到的正是
`#cmd_init.put`。)

**② 数"被列出的行",别按文件名前缀数。** 例如取警告块里以六个空格缩进的
路径行,或者干脆断言 `assertIn("孤儿06.md", r.text)` 且
`assertNotIn("孤儿07.md", r.text)` —— 后者更强:它同时钉住了"截断发生在第
10 行"和"顺序是字节序",而且不依赖开箱孤儿有几个。

如果你想保留现在这个写法,那就要在契约里补一条排序承诺,而那要走契约
变更、由人类落笔 —— 我不建议,因为顺序不是这一节要保护的性质。

**③ 把副产物挪出 `tests/`。** 改成 `缓存.json`(仓库根)或 `build/缓存.json`,
`config` 里的 `ignore_paths` 跟着改。也可以顺手在 `src/` 下写一个同名文件
让脚手架满意,但那会让用例看起来在测一个不存在的耦合,不如挪走干净。

## 和契约的哪一条矛盾

契约「`verify-setup` 的孤儿清单」的**输出**那条,逐字是:

> **超过 10 个时只列前 10 行**,再补一行说明**还剩多少个
> 没列出**(总数减 10,不是总数)。

括号里"总数减 10,不是总数"是**人类这一轮定稿时专门加进去的**(开工前审查
的第 9 条,tester 自己提的:"'还有多少个'是剩余数还是总数?两种都通顺")。
现在这条契约**一条有效断言都没有**:

- 不实现它 —— 绿
- 实现成打印总数(12 而不是 2)—— 也绿,因为 `"2" in "12"`

**换句话说,那次定稿在测试层面没有落地。** 这正是规则 5 说的"契约写了、
测试没守"的形状,而且是双向的:两种错误实现都能过。

## 应该改成什么

要害是**把断言限定到"剩余那一行"**,不能拿整份输出做 `assertIn` ——
表头里有总数,总数和剩余数共用数字是常态(12/2、15/5 都是)。

实测可行的写法(我在自己这边跑过,正确实现下绿、删掉补剩余那两行后红):

```python
lines = r.text.split("\n")
listed = [n for n in made if n in r.text]
self.assertEqual(len(listed), 10,
                 "12 个孤儿应当只列出 10 个,实际 %d" % len(listed))

# 剩余那一行:不是表头(表头含总数 12),也不是任何一个被列出的路径
rest = [l for l in lines
        if not any(n in l for n in made) and "12" not in l and "2" in l]
self.assertTrue(rest,
                "要有一行说明还剩 2 个 —— 剩余数不是总数(契约点名了这一点)。"
                "\n实际输出:\n%s" % r.text)
```

判据是"存在一行:含 `2`、不含 `12`、也不是被列出的路径"。
表头因为含 `12` 被排除,列出的 10 行因为是路径被排除,只剩补剩余那一行
能满足它。打印总数的错误实现会写 `12`,同样被排除 —— **双向都挡住了。**

如果你想要更简单的写法,另一条路是把孤儿个数改成 **20**:剩余 10、总数 20,
`"10"` 不是 `"20"` 的子串,`assertIn("10", r.text)` 就不再恒真。
代价是用例要造 20 个文件,而且下一个改数字的人不知道为什么必须是 20 ——
所以我更建议上面那种"限定到行"的写法,它把理由写在判据里。
