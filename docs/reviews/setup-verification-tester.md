## 「声明的生效条件与 report 的净回合」(W14)

### 冷审六条,逐条核过都已吸收

| 冷审 | 契约现在怎么写 |
|---|---|
| C1 "生效"两种读法、会打死一条现有用例 | 定为"真的有检查读到它";点名 `test_显式声明没有决策会被统计` 由 tester 在 spec 改 |
| C2 `--contract-change` 以哪批改动为准 | 以写权限边界那一步的同一批(`entries`)为准,不按提交内容 |
| C3 "声称零改动"不可实现 | 改成 `handoff` 写一行结构化正文,`report` 只认它,不许搜散文 |
| C4 计数还是均值、老行留不留 | 两个绝对计数,行标签字面给定;老行连同 `HEALTH` 与命令参考表一起删 |
| C5 两数之和、`dispute` 归哪 | 和恒等于表头「交接提交」;`dispute` 不算空转 |
| C6 新代码字面要在 spec 定死 | 「三节共同的一条」 |

### "生效"对五个旗标各落在哪一行 —— W13 之后仍然一一对应

对着现在的代码核了:每个旗标**只在一处被检查读到**,正文那五行却都是无条件的
`if args.<旗标>:`,正是背景说的污染源。

- `--no-decision`:只在晋升闸 `len(note) >= MIN_NOTE_PROMOTE_CHARS and not settled and not args.no_decision`。
  **W13 之后判据是 `not settled`**:本工作项已有同 id 决策时闸不成立、旗标不生效。
  这正是 PLAN 里"必须排在 W13 之后"那一段预言的差别,现在它是落地事实。
- `--doc-reason`:`touched_docs` 非空。`--basis`:路线图改写那一支。
  `--allow-deletion`:`deleted` 非空。`--contract-change`:`changed_named_frozen` 非空。
  四者"读到"与"处在该出现的地方"不分叉,契约已说明只有 `--no-decision` 分叉。

### 新发现 ①〔中〕"空转"那一行对**哪些回合**写,契约没限定

「**`handoff` 在检出"本回合没有任何改动落在执行者那个角色的路径下"时,
往提交正文写一行**」—— 这一句没有限定阶段。**评审回合按构造是只读的**,
每一次 review-impl / review-test 都满足"没有改动落在角色路径下";照字面实现,
所有评审回合都会被写上这一行、算进「协议开销的回合」。而同一节的表写的是
`协议开销的回合 | 空转的 impl 回合`。

**我的读法**:只对**从 impl 阶段出发**的交接判定,`dispute` 除外。表格那一行给出了
本意,但判定句本身没写,dev 照判定句实现会得到一个恒偏高的数 —— 又是本节要治的病。
W14 的 spec 回合我会把它钉进用例(评审回合不计入开销)。

### 新发现 ②〔中〕历史提交里没有那一行 —— 新指标会在"好看"的方向上静默少计

`report` 读的是整条 `git log`。W14 之前的提交正文里**不可能有**那行结构化文本,
所以 W14 落地之后在本仓库跑 `report`,前五轮所有的空转 impl 回合都计为 0 ——
`协议开销的回合` 会给出一个接近 0 的数。**这恰恰是背景点名的那种指标**:
"一个会给出错误诊断的指标,比没有这个指标更糟"。任何从旧版本升级上来的项目都一样。

一个直接的修法:**每一次 impl 交接都写一行判定(是/否空转)**,`report` 只统计带判定行的
impl 回合,并说出有多少个 impl 回合没有判定行、未计入。这样覆盖面自己会说话,
不需要写死"从哪个提交起"。代价:本节"在检出……时写一行"要改成"每次都写,值为是/否"。
**这是对契约的一处改动,我会在 W14 的 spec 回合带 `--contract-change` 提出**,
dev 不同意可以打回。

同一个问题在两条比率上也有,但**不在本节范围内修**:W14 之前的提交里,
不生效的 `--no-decision` / `--contract-change` 声明已经写进去了,落地后它们照样被计数。
新数据干净、历史照旧污染。记一句,不要求改。

### 小的:PLAN 里 W14 引的代码已经过期

PLAN 的 W14 条目引用 `pair.py:945` 与 `and not mine and not args.no_decision`。
W13 之后那一行是 `not settled`,行号也变了。它论证的顺序依赖本身仍然成立,
只是引文陈旧。不影响断言。

### 核过、认为无歧义的

- 行标签字面 `推进交付的回合` / `协议开销的回合`、两数之和恒等于表头「交接提交」:可断言。
- 判据里承重文件要一起算、按同一批改动判:与 `changed_named_frozen` 同源,不新增机制。
- 不拒绝不生效的声明:带一个不生效的旗标,交接退出码 0,可断言。
- 不给两个新数设健康区间:那两行判定列为 `—`、`HEALTH` 里没有对应键,可断言。

## 「verify-setup 的提交只带它自己 add 的那批路径」(W15)

我在 W15 追加的当天做过一次独立审查(`docs/pair-run/notes/W15.md`),挑出三处:
一行修法在 `AD` 场景新造 `exit 1`、判据把转义误认成"索引还是 HEAD"、修完之后
「拆掉 verify-setup 的提交范围」失去行为抓手。dev 在 W12 收尾那次交接里带声明改了契约
与 PLAN,**我重读了改过的三段,三处都已对上**:

- **提交哪些路径**:只提交 `to_add` 里在索引中真有差异的那些,与 W12 的 `index_has_diff`
  同一集合;`AD` 的文件在 add 之后不在索引也不在 HEAD,自然不在这个集合里,不会报
  pathspec 不匹配。
- **判"在不在"**:按 `-z` 输出整条路径相等。
- **范围外、没暂存的工作区改动 `verify-setup` 之后仍不在索引里**:给既有变异点重新一个
  行为抓手。

**W13 落地之后与本节的交互,核过无冲突**:`verify-setup` 现在会往状态里写
`setup_verified_contract`,契约变过之后重跑必然有状态差异、走提交那一支;
提交范围仍是 `to_add` 的差异子集,契约文件本身不在 `to_add` 里、不会被这次提交带走。

**一个写给 W15 spec 回合的备忘**(不是歧义):验收标准 ①′ 的 `AD` 场景**在今天的代码上
就是绿的**(今天的 `git commit` 不带路径、不会报 pathspec 错),它守的是"别写成第一版
那一行"。W15 的红要靠 ①。

# 第六轮契约的独立审查(tester,认领 W16 之前)

**起草人声明:`--drafter other`。** 第六轮五节由 dev 代笔(人类授权"开始修复"),本会话没有参与。
**方法**同第五轮:逐句找两种读法、找与既有代码的冲突、核每一处"已验证"验的是什么。
每一条都对照了现在的 `pair.py`。

## 结论:四处缺陷,各在自己那一项的 spec 回合带声明改;其余成立

四处都有一个显然的修法方向,不需要人类裁决。**idle 下 `handoff` 起不来,认领前直提契约等于
绕过声明机制**(dev 在 W12 的决策里否决过这条路),所以照 W14 的先例:我在对应工作项的
spec 回合带 `--contract-change` 改,dev 不同意可以打回。

### ①〔高〕「claim 看两个角色的开工前校验」:idle 时驱动器会死锁

`claim` 要求 dev 那一份也不过期之后,**唯一能解锁的是 dev,而 idle 下没有人会调度 dev**:

- `whose-turn` 在 idle 输出 `turn tester`(idle 的归属是 tester);本节「不变的」写着
  `whose-turn` 不输出 stop;
- tester 认领被拒;dev 会话在 idle 跑 `status`,架构图那一步是"不是你的回合 → 报告在等谁 → 停止"。

交给人类时这只是多一次唤醒;**交给驱动器时是死循环**:它反复调度 tester,tester 反复被拒。
而本节的目的恰恰是给第七轮的独立运行铺路,那一轮很可能就是驱动器在跑。

**修法方向**:idle 时,tester 那一份作数、dev 那一份过期或缺失 → `whose-turn` 输出 `turn dev`,
dev 的 `status` / 简报在这种情况下给出"重跑 `verify-setup`"而不是"不是你的回合"。
两个都过期时先 `turn tester`。可断言:`whose-turn` 的输出与退出码。**在 W19 的 spec 回合改。**

### ②〔高〕「report 可以只统计某个起点之后」:两条比率的分母不跟着起点走

`--no-decision` 与 `--contract-change` 两行是 `_fmt_rate(区间内的声明数, done)`,而
**`done = len(state["completed_items"])` 读的是状态,是全部历史的完成数**。带 `--since` 之后
分子只数区间、分母仍是历史 —— 区间里完成 1 项、带了 1 次生效声明,在本仓库会显示 `8% (1/13)`
而不是 `100% (1/1)`。**本节背景点名要修的正是这两条比率**,这样修完它们仍然只能靠人手工算。

本节把"已完成工作项"归进"读状态、不受影响"是对的 —— 但比率行不是"读状态的行",它的分子已经
在区间里了。**修法方向**:带 `--since` 时,两条比率的分母用**区间内的完成数**(区间里转到
`DONE` 的那几次交接)。可断言:区间外先完成若干项,区间内完成 1 项且带 1 次生效声明 → `100% (1/1)`。
**在 W20 的 spec 回合改。**

### ③〔中〕「只涉及测试的打回不再经过 impl」:"按改动判"看不见已经提交的契约变更

捷径的安全论证是"承重文件是唯一能让已审过的实现失去依据的东西",判据是"**这一回合**实际改动了
规划或契约"。但这一回合的改动是工作区那一批 —— **review-impl approve 之后、spec 回合之前被提交的
契约改动,它看不见**。这不是假设:第五轮 W15 那一节就是在 W12 进行中、tester 的回合里由代笔人
**直接提交**的(`e62bdf5`)。那种情况下捷径会放行一个契约已变、实现没重审的工作项。

**修法方向**:review-impl approve 时按 W13 的口径(工作区内容 sha)记下契约;捷径还要求
**现在的契约与那时相同**。它同时覆盖"本回合改了"与"期间被提交了"两种。可断言:review-test 打回后
人类提交一次契约改动,tester 的 spec 回合 GREEN 结束 → 下一阶段是 impl。**在 W17 的 spec 回合改。**

### ④〔中〕「评审记录只能追加」:`verify-setup` 那一侧的拒绝必须早于写状态

`cmd_verify_setup` 里的顺序是:结论长度与点名检查 → 起草人声明 → `state["setup_verified"] = True`
→ `save_state` → `git add` / 提交。本节说"要提交的那份结论若已在 HEAD 里且有删除行,拒绝,不提交",
**没说拒绝在哪一步**。放在 `save_state` 之后,就是 W12、W15 两次治过的"状态对、退出码错",
这回状态位还留在工作区、下一次交接判篡改。**修法方向**:写明拒绝发生在写状态之前,
可断言"拒绝后状态文件不变、HEAD 不变"。**在 W18 的 spec 回合改。**

## 核过、成立的

- **「评审回合可以只追加变异点登记」**:"追加之后测试必须照旧 GREEN(评审阶段的既有要求)"
  核过是真的 —— `feature` 流程的 `expect` 里 review-impl 与 review-test 都是 `GREEN`,匹配不到源码的
  锚点会让交接被拒。`has_rewrite` 比的是 `HEAD`、未跟踪文件删除行为 0,所以"必须已在 HEAD 里"
  单写一条是必要的,本节的判断对。**提醒 spec 回合**:既有锚点「拆掉评审只读」锚的是
  `writable_paths` 里 review / idle 返回 `shared` 那两行,最顺手的实现正好改那里 ——
  我会在 W16 的 spec 回合说清楚"追加路径另行判定,不改那两行",或者照「三节共同」重锚。
- **「只涉及测试的打回不再经过 impl」**:after-rebound 的 spec 豁免的只是 RED、不豁免 GREEN,
  GREEN 结束走捷径与既有红绿不变量不冲突;`review_file_for` 按打回次数算名字,捷径不影响。
  "原型全套 0 红 = 没有既有用例钉着那条边"的推论成立。
- **「评审记录只能追加」**:范围复用 `_review_top_level`、豁免协议日志与 `ignore_paths`、
  文案写死"不是你改的不要撤销" —— 与孤儿路径同一个理由,成立。
- **「claim 看两个角色的开工前校验」**:被取代的 6 条用例名单我核过,都是只让 tester 校验就去认领的
  (其中 5 条是我在 W13 写的);"按新行为改、不删"成立。
- **「report 可以只统计某个起点之后」**:`<rev>..HEAD` 的语义、非法 `<rev>` 非零退出无 traceback、
  区间内两数之和的不变量,都可断言。

## 小的,不要求改

- `review_append_paths` 的路径按 `matches_any` 的通配语义还是精确路径,本节没说。本仓库配的是
  单个文件,两种实现都过;若配成目录,评审回合就能往任何已提交的测试文件里追加新测试。
  我在 W16 用精确文件测,不钉通配。
