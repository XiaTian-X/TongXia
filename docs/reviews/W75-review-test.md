## 查过的地方

- **拒绝类用例拒得是不是本节**:17 条里拒绝类大多不断言文案,只断言"被拒 + 提交数与 `state.json` 逐字节不变",所以关键是有没有别的防护替本节挡掉。逐条推了一遍:
  - 空说明那条改的是 `tests/W1` 的内容(绿),去掉空说明那道之后它会被当成正常的 `approve --test-gap` 放行 —— 能区分;
  - spec 阶段那条写的 `tests/W1` 没有 `src/` 对应、是红的,spec 期望 RED,去掉阶段那道就放行;impl 那条 dev 写了 `src/W1`、是绿的,同理;
  - dev 在 review-test 那条同时改了 tester 名下的 `tests/W1`,去掉阶段那道之后"可写"会被旗标放开 —— 变异 `缺口_评审阶段都放行` 就是它抓的;
  - 只删测试那条带了 `--allow-deletion`,改写登记表那条同时补了真用例,都把前面的防护让开了。
- **断言了文案的三条**:`approve --test-gap`(绿着打回)、`[cover]`(refactor)、`追加`(既有只追加文案)。这三处正是区分"哪一道拒的"需要文案的地方,别的拒绝不断言措辞,不会变成变更探测器。
- **全流程那条**在 review-test 那一刻读 `changes_count == 1`,DONE 之后清零不依赖它;完成以 PLAN 打勾判,不读内部字段。
- **简报**只断言 review-impl 的 `status` 里出现 `--test-gap`,不断言措辞。
- **变异点**:`--only 缺口_` 10 个全被抓(缓存命中,各自的抓手不同:阶段两个、流程、RED、动测试、只追加、删除、放开路径、空说明、正文)。
