- **tester 开工前审查的 ② 仍然成立、还没改**:`--no-decision` 与 `--contract-change` 两条比率的分母是
  `done = len(state["completed_items"])`(全部历史),带 `--since` 之后分子只数区间 —— 区间里完成 1 项、
  带 1 次生效声明会显示 `8% (1/13)`。我代笔时把"已完成工作项"归进"读状态、不受影响"是对的,

  会静默统计出一个数 —— 读报告的人以为是"起点之后",实际是"两条分支的差集"。
  建议写明:不是 HEAD 的祖先时也拒绝,或者至少在表头标出来。**这是新发现,请 tester 在 W20 spec 回合一并判断。**

## 「report 只认协议写进提交正文的那几行」

- **重读时核了一处会误导实现的字面**:契约写协议行是 `role=… phase=… -> … item=… type=…`。若早期提交没有 `type=`,
  照字面要求 `type=` 的实现会让那些交接从计数里消失,违反"一个字不差"。**实测全部历史 148 条协议行都带 `type=`**,
  字面不会误导,不改。
- **我判断不了、请 tester 重点看的**:"不做"里放过了"旗标值带换行在行首伪造"。我给的理由是需要刻意为之、方向只会偏高 ——
  但声明比率偏高也会让 `report` 报"偏高",那是误报而不只是"数大一点"。你若认为该在本节一并堵,
  修法是 `handoff` 把旗标值里的换行压平,那会改一处用户可见的行为,要在 spec 回合带声明补。
- **harness 造的提交是否都走 `handoff`**(从而都有协议行),我没核;若有用例直接 `git commit` 造交接提交、却靠 `item=` 散文被计数,
  锚定之后它会红 —— 那是用例依赖了缺陷,不是实现错了。
