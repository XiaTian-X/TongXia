# W81 review-test —— cover 新增的用例确实跑了

**裁决:通过(approve)。**

## 查过的地方

- **假门禁造得干净**:每个文件是一条用例,内容里的 `hidden` / `skip` / `red` 决定"不被收集 / 跳过 / 红"。三种"看起来有、其实没有"各有一条拒绝用例,不依赖任何真实测试工具的收集规则。
- **拒绝类拒得是不是本节**:
  - 断言只要求"被拒 + 提交数与 `state.json` 不变 + 文案有'认领'"。
  - 区分力来自对照:同样的场景加一条真跑的新用例就放行(`TestNewTestRan`),拆掉判点(`新用例_不判`)三条拒绝全红。
- **"认领时基线"两个方向都钉住了**:
  - 人类认领后把新用例写进基线 → 照旧算新;
  - 把已有用例从基线删掉 → 照旧不算新。
  - 读工作区或 HEAD 的实现至少红一条,对应变异点 `用工作区基线`、`用_HEAD_基线` 都被抓。
  - "认领之后才有基线 → 不判"那条,还挡住了"认领时读不出就退回读当前基线"这种看似合理的实现。
- **同一回合的改名声明要扣掉**:要求实现用 W78 已写进内存的 `renamed_tests`。对照组不声明就放行,证明拒它的是"扣改名新名"。
- **修正回合**:第一回合的新用例到修正回合仍算新,只改断言照常放行,正文仍是 1 条。这条正是"基线取认领时"的理由,钉住了。
- **六种不判**各一条,变异点逐一对应(`…时拦` 五个,加上 feature 那条)。
- **正文**:用两条新用例钉住条数,不是写死 1。
- **不是变更探测器**:拒绝文案只断言"认领"两个字。review-impl 说第一版"文案不提认领"变异只换了一处而存活,改正后被抓 —— 是变异写法的问题,不是用例缺口,我同意。
- **我自己跑的结果**:
  - `test_v1_cover_executed` 17 条全绿;
  - `mutation_check --only 新用例_` 15 个全抓。
