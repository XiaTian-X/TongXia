# W79 review-test —— 工作项的回合预算

**裁决:通过(approve)。**

## 查过的地方

- **不是变更探测器**:
  - 计数读 `state.json` 的 `item_turns`,缺键当 0;
  - `status` 那一行用宽松的正则取"<n> 次"和其后第一个数字,排版不钉;
  - 撞上记录只要求字面 `W1 x3` 出现;
  - 撞上那次提交的主题逐字比对,这是契约原文。
- **拒绝类拒得是不是本节**:
  - 交接用满:上限 3,第 4 次是 dev 在 impl 写了实现的正常交接,去掉预算就放行(`预算_交接不拦用满` 抓到)。
  - 讨论三个入口:额度有剩、提案写好,能拒它们的只剩预算,每个入口各有一个"不拦"变异点。
  - 断言都带 `max_item_turns` 字样,区分得开别的拒绝。
- **第一次撞上**:
  - 提交数 +1;
  - HEAD 只改状态文件;
  - 工作区改动留着、未提交;
  - 阶段与计数不变。
  四件事都断言了,"撞上时不提交 / 不记录 / 每次都提交"三个变异点各被抓。
- **完成不拦**:用满时 review-test approve 进 idle、清零、没有记录。`预算_拦了完成` 抓到。
- **篡改**:`TestTamperedStateNotCommitted` 四个入口各一条。只断言"被拒 + 提交数与状态文件逐字节不变",这正是那个缺陷的可观测后果。`预算_讨论回合判在篡改检查之前` 把上一轮的缺陷原样钉住。
- **计数口径**:
  - handoff、讨论三个入口各加 1;
  - 代办三件套前后相同,带代办异议的打回照常算 handoff;
  - 认领清零用人类提交的状态造,老状态缺键用删键的状态造。
  两条都选了"不这样造就观察不到"的场景。
- **配置**:`verify-setup` 拒 `-1`、`1.5`、`"20"`,对照组 0 与 5 通过;默认 20 按 `status` 判。
- **我自己跑的结果**:
  - `test_v1_item_turns` 22 条全绿;
  - `mutation_check --only 预算_` 22 个全抓。

## 探针

- 让 `count_item_turn` 在没有工作项时也计数(空闲时的 understand 也加 1):`test_v1_item_turns` 与 `test_v1_understand` 47 条全绿,**存活**。
- 不为它打回:空闲时多出来的计数在下一次认领时被清零,`status` 只在有工作项时显示预算,行为上观察不到差别。
- 契约"空闲时的 understand 不加"这一句因此只钉在实现上,列进下面。
