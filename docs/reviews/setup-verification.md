# 契约歧义审查结论

**审查者:起草人本人。** 这份结论的证明力因此是打折的——契约是我写的,
我看不见自己的盲区。记在这里,是为了让后面读它的人知道成色。
理想流程是由没参与起草的一方来做这一步。

审查对象:`docs/pair-run/CONTRACT.md` 的「status 简报落盘」一节。
此前已按自查结果收紧过一轮(见 `docs/pair-run/DECISIONS.md` 第二条),
以下是**收紧之后仍然存在**的问题。

## 结论:五处格式层歧义,都在同一个位置——"逐字"到底逐到哪

契约把简报定成了"字段化产物",格式写死了,但**写死的粒度不够**。
下面五条,tester 和 dev 各自都能读出一种合理解释,而且两种解释都能自洽:

### 1. `# 回合简报` 这一行算不算规格(严重)

契约正文说"**头部四行恒在**",逐项给了四个字段的取值。但示例里第一行是
`# 回合简报`,正文从没提过它。

- tester 读法:正文说四行,那就断言四行,标题可有可无
- dev 读法:示例长什么样就写什么样,标题当然要有

两边都对。**如果 tester 断言"文件第一行是 `- 角色:`",而 dev 写了标题行,
这条测试会红,而实现并没有错。** 这是最可能在第一个回合就炸的一条。

### 2. 冒号是半角还是全角

示例里四行用的是半角 `: `(冒号 + 空格),而契约正文其余部分统一用全角 `:`。
中文文档里这两种混用极常见,dev 很可能顺手写成全角。
tester 若按示例断言 `"- 角色: "`,就会因为一个标点红掉。

### 3. "与终端那段逐字一致"——那段的边界在哪

契约说记忆段落"与 `status` 打印到终端的那段记忆内容逐字一致"。
但终端上那一段实际是**五个部分**:

```
====================================================
 你不在场时留下的东西
====================================================
<记忆内容>
<空行>
```

"那段"是指整块(含两条 `=` 分隔线和标题),还是只指 `<记忆内容>`?
契约的示例里写的是 `--- 本工作项笔记 (…) ---` 开头的内容,
看起来只要内容不要边框——**但正文没说**,而示例和正文冲突时该信哪个,
契约也没规定。

### 4. 头部与记忆段落之间的空行

示例里有一个空行。正文没提。dev 写不写、tester 断不断言,各凭猜测。

### 5. 文件末尾有没有换行

同上。`assertEqual` 全文比对时这一个字节就能让测试红。

## 这五条的共同点

它们全都不影响"这个功能对不对",只影响"tester 写的断言和 dev 写的实现
能不能对上"。**换句话说,它们全都是契约漂移的种子**,而且是最难通过评审
发现的那种——双方各自看自己那半边,都挑不出毛病。

## 建议

第 1 条必须在开工前定掉,它最可能让第一个回合直接卡住。
第 2、3 条紧随其后。第 4、5 条可以由 tester 在写第一条断言时提出来,
走契约变更流程。

**更根本的建议:** 与其继续用散文描述格式,不如在契约里直接贴一份
**完整的、逐字节精确的示例文件**,并写明"简报必须与此示例结构完全一致,
只有字段值随状态变化"。格式类的规格用示例锚定,比用散文描述可靠得多——
这也正是这五条歧义的共同成因。
