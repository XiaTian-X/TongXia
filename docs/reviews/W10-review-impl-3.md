**副本停在 `899b0fa` 之前,也就是我打回的那个版本。** 手工重钉发生在
`35136c4`,而 dev 在那之后又改了 `pair.py`(修 `.strip()`)。

后果是确定的、可预测的:**W10 的 `DONE` 由这个旧副本执行,它会重钉,
但会把那条记录写成断成两行的样子** —— 也就是说,修掉这个缺陷的那个工作项,
它自己的完成提交里会带着这个缺陷,而且那是重钉唯一的纸面记录。

**要做的:在 `DONE` 那次 `handoff` 之前,人类再手工重钉一次并提交**
(`cp` 之后 `git add` 那两个文件再 commit —— `-A` 会把别的东西一起带上)。
重钉之后 `DONE` 就由修好的那份执行。

**为什么不拿这个打回:** `changes_count` 已经是 2,`DEADLOCK_LIMIT` 是 3 ——
第三次打回会停转并要求人类裁决。而这里根本没有分歧,这也不是代码缺陷,
是一次操作时序。死锁闸守的是"两个 agent 谈不拢",拿它推一件双方都会立刻
同意的事,是把闸用歪。

## 顺带更正契约里一句写错的理由（是我写的，不是你）

契约「裁判副本的同步 → 自举」写着:

> W10 自己的 `DONE` 是**旧裁判**执行的 —— **它没有自动重钉那段代码**。
> 所以 W10 完成后人类要再手工重钉一次。

**"它没有自动重钉那段代码"现在是假的**:`35136c4` 那次手工重钉已经把
第一版实现搬进了副本,`judge_in_sync` / `repin_judge` 在副本里都有。
副本缺的不是重钉能力,是 `.strip()` 那一个修复。

所以结论(要手工重钉一次)仍然成立,理由变了,而且时机也变了 ——
**从"DONE 之后"变成"DONE 之前"**。这一句是我起草契约时写的,记在这里,
等哪一轮解冻契约时一并改;本轮不动它。
