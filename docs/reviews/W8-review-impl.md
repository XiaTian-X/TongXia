## 我检查了什么

**没有拿 spec 回合那批变异脚本交差。** 你在 W10 记过那条决策:临时变异脚本
在实现落地后会变成死代码而安静全绿。我 spec 回合那十个是打在**参考实现**上的,
实现换成你的之后它们不一定还打得中,所以重写成直接改你的代码:

| 改你的实现 | 红的用例 |
|---|---|
| `has_rewrite` 的 `git diff` 去掉 `HEAD` | 先 git add 不能绕过依据 |
| `basis` 不按空白切(整串匹配) | 一句话里含一个真实路径 |
| `basis` 不剥 `:行号` | 允许带行号后缀 |
| `known` 不含本回合改动 | 可以指向本回合刚写的文件 |
| `normative_docs` 不排除评审目录 | 只改笔记与评审记录不要求理由 |
| 范围改回 `tracked_files` | 新建的规范性文档同样要理由 |
| 去掉 `has_rewrite` 条件(追加也要 basis) | 纯追加只要理由 |
| 理由不写进正文 | 理由进提交正文 |
| 整段检查挪到 `git add -A` 之前 | 勾选 PLAN 不触发 |

**九对九,没有一条误伤。** 用例经受住了"参考实现 → 真实实现"的迁移。

**你说的锚点冲突,我核实了,成立。** `MUTATIONS` 里
`拆掉 ignore_paths` 与 `拆掉协议日志的边界豁免` 两个锚点都锚在
`        if path in PROTOCOL_LOGS or matches_any(...)` 上;照抄那个操作数顺序,
两个锚点各命中两处,`test_变异点仍能匹配到源码` 立刻红,而你改不了
`mutation_check.py`。反过来写是对的,注释也写清楚了。

**`PROTOCOL_LOGS` 那条排除是防御性的,不是必需的** —— 我查过:
`BRIEF_REL` 是 `.pair/.last-brief.md`,既在 `GITIGNORE_LINES` 里
(不进 `git status`),`.pair` 又在默认 `frozen_paths` 里(冻结分支先拦)。
两道都失效的项目才走得到那一句。留着没坏处,记一句免得以后有人当死代码删掉
——它挡的是"老项目 .gitignore 还没更新"那种情况。

## 未覆盖

### ① 两条新强制,零个变异点,而且没有任何东西会红

`ENFORCEMENTS` 现在 32 条,新增的 `doc-reason` 与 `roadmap-basis` 在里面;
`architecture.md` 那行也同步了 —— **那一侧有检查守着**
(`test_docs_consistency` 拿 `ENFORCEMENTS` 和 `architecture.md` 对表)。
**`MUTATIONS` 那一侧没有对应的检查。** 所以:强制加了、文档同步了、
全绿,而"这条防护有没有人拆得动"没有任何一处在问。

`docs/contributing.md` 自己写着"没补变异点的防护等于没有保障"。

**这是同一个结构问题的第三次**:W3/W4 五条(拖到 W7 才补)、W10 四条
(我在 W7 顺手补的)、现在 W8 两条。每一次都是"dev 加了防护、tester 才能补
变异点、而 tester 在这个工作项里已经没有能写 `tests/` 的回合了"。

**我核实过一条看起来最省事的解法,它是死的**:让
`tests/conformance/mutation_check.py` 同时进两个角色的路径 ——
`verify-setup` 有一条硬检查会直接 `bad`(「以下文件同时属于两个角色
(边界重叠,零冲突保证失效)」)。**别再往这个方向想了,我替下一个人试过了。**

剩下的方向我只列不选,这是人类的决定:
- 每个 feature 后面挂一个 `cover` 尾巴(W7 就是这么当的,但那是临时安排)
- 变异点的登记方式换成**不依赖字面源码**(比如 dev 在自己文件里用注释标记,
  tester 的检查器去读)—— 那顺带也解掉上面那个"操作数顺序被锚点绑架"的问题
- 承认它,把"新强制暂无变异点"做成一条显式的、可见的欠账清单
