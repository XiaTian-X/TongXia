下面是我认为它正确的依据,不是我懒得挑。

## 空转是对的,不是漏做

打回理由是"那处修复没有回归测试守着"。测试是 tester 的可写路径,
dev 做不了;而 W1 的契约行为(头部四行、边界豁免、`item_type` 为空按
feature)在 `4b34124` 和 `1f18602` 里早已全部落地。

**这一回合 dev 能做的正确的事就是什么都不做。** 它没有为了让回合"看起来
有产出"去动 `render_brief` 或补一段没人要的实现 —— 那才是我该打回的。

阶段序列 `review-test changes → spec → impl → review-impl` 在打回理由纯粹
是覆盖不足时会强制绕经 dev 一趟。dev 把这一点记下来交给人类,没有自作主张
去改阶段序列。这个边界守得对。

  临时副本里把 `pair.py:947` 的 ` or "feature"` 改回打回前的写法,
  `test_旧状态没有类型时按_feature_写` 变红,**且只有它变红**。

  和 `docs/pair-run/notes/W1.md`(它的可写路径)。零代码改动,符合空转的自述。
- **全量套件**:234 个用例全绿,`test_v1_brief.py` 七条全过。人类在
  `989672c` 改过 `pair.py` 的红绿豁免逻辑,我确认那次改动没有波及简报。

## 为什么这不是"打回两次之后的妥协"

W1 已经被打回两次,再打一次就撞死锁闸 —— 我知道这个背景,所以说清楚:
**我找不到可打回的东西,不是不敢打。**

我按顺序找过这些,都没有命中:契约里还有没有没落地的行为(没有,
三条验收标准全部有用例)、dev 有没有借空转夹带改动(没有)、
它的自述和实际改动对不对得上(对得上)、有没有该实现却推给 tester 的
东西(没有,打回要的就是测试)。

为了不显得"互相点头"而制造一次打回,比点头更糟 —— 那会把死锁闸烧掉,
而真正需要它的时候就没有了。

## 我同意 dev 提出的两条,并且认为它们该出这个目录

1. **人类介入需要和 `verify-setup` 一样的纪律:只提交自己产生的东西。**
   `git add -A` 会把结对方停在工作区里的产出一并提交,而"打回之后必须真的
   动了测试"这条检查按工作区判断,会把它读成"你什么都没干"。
   dev 说得比我准:这条检查的**前提**是"这一回合的产出还在工作区里",
   人类在结对期间提交任何东西都可能悄悄破坏这个前提。
2. **空转的 impl 回合**是阶段序列的一个特性,值得记成待定问题。
   dev 提的"自打回以来 dev 路径无改动就从 spec 直接回 review-test"是个
   可行方向,但它需要新判定,而这条路径有多常见还不知道。**同意先记着不动。**

这两条现在只在 `docs/pair-run/notes/W1.md` 里,而笔记是工作项级的 ——
按记忆层自己的设计,W1 一关就没人再读它。晋升到 `rules.md` /
`troubleshooting.md` / `improvements.md` 是 dev 的可写路径,我做不了,
在这里记一笔。
