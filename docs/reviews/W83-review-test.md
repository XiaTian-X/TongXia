# W83 review-test —— 每个待办项都认领不了时,`whose-turn` 停下交给人类

**裁决:通过(approve)。** 24 条用例都断言在接口上(`whose-turn` 那一行的前缀、ID、理由关键词,以及只读、退出码),没有钉住私有实现。14 个变异点全被抓到。

## 查过的地方

- **断言粒度**:`assertStop` 只看四样:`stop ` 前缀、点名的 ID 与理由关键词、不含"拒绝认领"、一行。
  - 不断言项的顺序与整句措辞。实现里我把类型检查并进了 `check_item_preconditions`,这些用例一条没动就全绿,说明它们不是变更探测器。
  - 理由关键词取的是 `claim` 拒绝文案的头一行("依据""保护""待澄清""非法"),那是已有的接口文案,不是新函数的内部细节。
- **对照组**:每种"停下"都配了反方向的用例:
  - 唯一项能认领、一项被拦一项能认领(两种排列)、已完成项被拦 → `turn tester`;
  - 副本一致 → `turn`;能认领时归属 dev → `turn dev`。
  - 另有两条确认"被判成认领不了的项,`claim` 真的被拒"。这两条把 `whose-turn` 的判定和 `claim` 钉在一起,复用这条契约要求有了实证。
- **边界**:
  - 进行中有三条:副本不一致、当前项与其余项都被拦、到了 impl,都照旧 `turn`。
  - 已完成项双向各一条。
  - cover 项指向不存在的小节,照旧 `turn`(cover 不查契约)。
  - 现有校验那条 `stop` 排在前面。
- **只读**:提交数、`state.json`、`git status --porcelain` 前后比对。`check_item_preconditions` 以后若加了提交副作用(像 W79 的回合预算那样),会直接红。
- **与 PLAN 对得上**:验收标准 ①–⑤ 都有对应用例。
- **变异点**:`--only 认领不了_` 共 14 个,全抓;`mutation-cache.json` 的改动已还原。
  - `认领不了_类型非法不拦` 改的是 `check_item_preconditions` 本身,报告里记下的是 `claim` 侧的 `test_非法类型被拒绝`;`whose-turn` 侧的 `test_类型非法` 按推理也会红,没有单独跑。

- **PLAN 里同一 ID 出现两次**:取第一个块,与 `claim` 一致,未造用例。
