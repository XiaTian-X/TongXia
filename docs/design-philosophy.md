# 设计理念

> 这份文档解释**为什么**。规范性的"是什么"在 [protocol-spec.md](protocol-spec.md),
> 别处的做法和依据在 [prior-art.md](prior-art.md)。

两个 agent 结对,是为了**把 `docs/PLAN.md` 里规划的工作项一起做出来**:
一个只写测试、一个只写实现,轮流推进,直到 PLAN 全部勾选、门禁套件全绿。
协议存在的意义是让两份努力**可以合并、不互相抵消**,收敛到同一个交付,
而不是把它们摆成对立面。

每个 agent 的职责,是**尽自己最大努力做好本角色的活,按回合如实交付**。
协议不要求两个 agent 互相敌对;它要求各自把本职做到最好,并留下对方和
人类都能核对的痕迹。

**"完成"有明确定义:** PLAN 里的工作项全部勾选、门禁套件绿、
全量状态如实上报。配了 `full_test_cmd` 时,工作项完成那一回合还会跑一次
全量套件。它红了,工作项本身仍算按纪律走完了(PLAN 照常勾选,`claim` 也
会拒绝重认领),但**不能向人类宣布"完成"** —— `handoff` 返回退出码 2,
要求把这件事告知人类,由人类决定扩大范围、开新工作项,还是接受它。

那次 `handoff` 的同屏还会打印一句"PLAN 里的工作项已全部完成、请向人类
报告完成"。**那句是 PLAN 维度的结论** —— 工作项确实都勾选了;全量红时
以退出码 2 与上面那句"不能宣布完成"为准,两者不冲突。

真正的难点不在"让它们合作",而在**合作会悄悄退化**:一方产出、另一方说
"看起来不错",两轮之后没有任何真实缺陷被发现,双方都留下了工作痕迹,
人类以为交付是好的 —— 而它其实是废的。一个"看起来完成了、其实是废的"
交付比没交付更糟,它会污染最终目标。防互相点头、防硬编码蒙混、防测试
过拟合、防契约漂移,这些机制之所以存在,正是为了拦住这种退化 ——
它们是**保障交付质量的手段,不是目的本身**。

下面九条,是为了让"共同交付"成立而做的**九个取舍**:每一条都要在"把 PLAN
做出来"与"别让交付悄悄变废"之间付出代价,只是各条付的地方不同。

## 一、回合信号取自程序,不取自模型判断

"这一回合做完了没"是一个必须有答案的问题。可选的答案来源只有两个:
让模型自己说,或者让程序判定。

本协议选后者:**spec 回合结束时测试必须是红的,impl 回合结束时必须是绿的。**
`handoff` 跑一遍测试,拿退出码判定,不合规直接拒绝提交。

- 模型说"我做完了"是不可证伪的,而且模型有很强的动机说这句话。
- 测试的红绿是二值的、可复现的、跨模型一致的。
- 更关键:它**同时**判定了另一件事 —— tester 交出来的必须是一条**会失败**的
  测试。一条恒过的断言在 spec 回合会被直接拒绝,而这正是"看起来干了活、
  实际什么都没验收"最常见的形态。

这条与 MetaGPT 的 executable feedback、AgentCoder 的 test executor 是同一个
原理:**让运行结果驱动迭代,不让 LLM 评审驱动迭代。**

**代价:** 依赖基线全绿(否则 GREEN 不变量形同虚设),依赖测试跑得完,
依赖 harness 能执行 shell。这三条都写进了 [已知边界](#已知边界)。

**当前的弱点:** 判定粒度只有整体 0/非 0,不知道"哪一条红了"。
参见 [improvements.md](improvements.md) 的 P0-1。

## 二、写权限按路径切分,冲突在物理层消失

tester 只能写 `tests/`,dev 只能写 `src/`。越界的文件在 `handoff` 时被逐条列出、
拒绝提交。

因此:

- 不需要锁。
- 不需要 merge 策略。
- 不需要 worktree,两个 agent 可以共用一个工作目录。
- 不需要"谁先提交谁赢"这类约定。

2025—2026 年成熟起来的一整类工具(container-use、Conductor、Crystal、Emdash……)
解决的是同一个问题的另一个版本:**N 个 agent 做 N 件不相干的事**,
隔离靠给每人复制一份工作区。本协议解决的是 **2 个 agent 做同一件事**,
隔离靠切分命名空间 —— 更便宜,而且天然保证两人看的是同一份代码。

**代价:** 布局必须能切分。Rust 的 `#[cfg(test)] mod tests` 与实现同文件,
目录切分物理上不成立,所以明确不支持 —— 这不是懒,是这条设计的必然推论。

**推论:** 两个角色的路径**绝对不能重叠**,这是零冲突保证的全部来源。
`verify-setup` 会拿真实文件树逐个试匹配,报出任何同属两个角色的文件。

## 三、对抗性写进角色定义,不写进 prompt

"请认真评审"是一句没有强制力的话。模型会认真,也会敷衍,取决于当天的温度。

本协议不请求对抗,而是**让对抗成为角色的工作定义**:
tester 的任务就是写出 dev 过不了的用例。它不需要被鼓励挑刺,挑刺就是它的产出。

这条与 AgentCoder 的论证同源:同一个 agent 既写代码又写测试,
那些测试验证的是**有缺陷的逻辑本身**,而不是真实需求。切开之后,
测试才第一次成为独立的验收标准。

Adversarial Review 给这件事起了名字 —— **false-consensus failure mode**:
双方在没有充分证据的情况下收敛到一致。它的处方是让异议
"minimal, structured, and evidence-grounded"。

本协议目前做到了 minimal 和 structured(异议必须写进 `docs/reviews/`,
`handoff changes` 必须附理由,空字符串被拒),**没做到 evidence-grounded** ——
脚本拦不住"看起来不错"。这是已知的最大缺口,见 improvements.md 的 P0-2。

### 对抗是为了交付,不是为了显得没在点头

评审的价值在于**真的挑出问题**。但为了显得"没有互相点头"而制造一次打回,
比点头更糟**在明处**:点头至少不额外烧额度,而它会消耗掉该工作项三次打回
额度里的一次(额度用尽即撞死锁闸、停轮转交人类)、浪费至少两个回合
(在 review-test 上打回要绕经 spec、impl、review-impl,是四个回合)、
把交付往后拖。
dogfood 的真实评审里,tester 写下过这么一句 ——
**"我找不到可打回的东西,不是不敢打"**
([reviews/W1-review-impl-2.md](reviews/W1-review-impl-2.md))。那一回合它选择了
通过,并把独立验证过的依据逐条摆出来。这才是对抗性该有的样子:
该打回时打回得动,该通过时敢通过、并且说得清依据,两个方向都不失真。

### 为什么是两个,不是三个五个

多 agent 辩论的实证结果不支持"人多力量大":

- Adversarial Review 用 3 个 agent 打赢了 5 个 agent 的基线 —— **结构比数量重要**。
- 《Talk Isn't Always Cheap》发现辩论里**正确→错误的翻转多于错误→正确**;
  一个 agent 被其他人反对时最容易翻供,与对错无关;弱 agent 会拖垮强 agent。

两方结构没有"多数压少数"的孤立压力,这是特性不是妥协。
**不要加第三个评审角色**,这是一条明确的反向设计约束。

## 四、协议是可执行的,不是散文

同一段 prose rules,不同模型的遵守程度差别巨大 —— 甚至同一个模型在上下文
长了以后也会漂。凡是"靠模型自觉"的规则,在跨 harness 场景下强制力都趋近于零。

所以规则分两类,分得很清楚:

| | 能编码的 | 不能编码的 |
|---|---|---|
| 例子 | 越界写、红绿、回合归属、删测试、状态篡改、决策格式 | "评审要有实质"、"不许过拟合"、"契约不许含糊" |
| 落在哪 | `pair.py` 的拒绝分支 | `SKILL.md` / `references/rules.md` |
| 失效方式 | 只有改代码才能失效 | 换个模型就可能失效 |

**能编码的一律编码。** 剩下那些,协议至少做到一件事:**强制留痕**。
删测试要 `--allow-deletion "理由"`,笔记不沉淀要 `--no-decision "为什么没有"`,
契约歧义审查必须交出一份不短于 120 字的结论 —— 脚本查不了内容质量,
但它能保证有一份东西摆在人类面前。

这也是**变异检查**存在的理由:一个恒真的测试集比没有测试更危险,
它会让人以为强制力还在,而执行层可能已经什么都不拦了。
`mutation_check.py` 逐个拆掉 `pair.py` 里的防护,确认每一条都有测试能发现它消失。

## 五、通信只走 git,上下文靠重新推导

两个 agent 看不到对方的对话,也不共享各自工具的记忆。唯一的信道是 git 提交,
和仓库里三个位置:`docs/reviews/`(评审与异议)、`docs/notes/`(工作项笔记)、
`docs/DECISIONS.md`(长期结论)。`pair.py inbox` 就是收件箱。

这不是将就,是选择:

- **传对话记录会衰减。** MetaGPT 把这叫"传话游戏"—— 纯自然语言在多轮转述中
  失真,所以它让 agent 交换文档而不是对话。
- **重新推导恰好是 agent 擅长的事。** 从仓库现状重建理解,是它们每天都在做的;
  而且比携带一份越来越长的对话历史便宜。
- **git 已经是每个 harness 都会用的东西。** 不引入新的运行时、新的服务、
  新的协议端口。
- **它顺带解决了持久化。** 崩溃、换机器、隔一周继续,状态都在 `.pair/state.json`
  和提交历史里,没有需要恢复的会话。

**推论:** 提交推送失败等于没交接。`sync` 模式下 `handoff` 会显式检查 push
结果,失败时打断并要求 agent 报告"推送失败"而不是"已交接" —— 因为提交只在
本地时,对方在信道上什么都收不到。

## 六、记忆沉在仓库里,召回挂在强制时刻

各家 agent 的私有记忆格式、召回机制都不一样。统一不了,也不该去统一 ——
**你能统一"写什么",统一不了"什么时候被读出来"。**

所以记忆分两层,寿命不同:

| | `docs/notes/<ID>.md` | `docs/DECISIONS.md` |
|---|---|---|
| 寿命 | 工作项级 | 项目级 |
| 内容 | **负空间**:试过什么没成、否掉了什么、哪里拿不准 | 结论与裁决 |
| 格式 | 无 | 四个必填字段,受校验 |
| 写法 | 随手写 | 追加式,不能改历史 |

文档天然记录**正空间**(现在是什么样),而重构和排查里值钱的知识几乎全在
**负空间**(为什么不是别的样)。负空间没有任何常规文档形态会去承载它,
所以协议专门给它开了一个位置,并且把成本压到最低 —— 笔记没有格式要求。

**关键一步是召回,不是存储。** 存了没人读等于没存。所以召回点挂在 `status`
上 —— 它是协议强制的第一条命令,也是唯一能跨 harness 保证会被执行的时刻。
`status` 在轮到你时自动注入:本工作项笔记全文 + 影响路径与本回合相干的决策条目。

这与 Anthropic 关于上下文工程的结论一致:上下文是有限资源,
要找"最小的高信号 token 集合";结构化笔记是把记忆放到上下文窗口之外的手段。
本协议的注入有硬上限(笔记 3000 字符、决策 2000 字符 / 最多 5 条),
就是防止记忆层反过来吃掉上下文。

### 两条刻意的克制

**单条决策不得超过 1500 字符。** 它此后每一次 `status` 都会被读一遍,
长了就没人读,然后整套机制退化成又一份没人看的文档。

**决策条目里故意没有"分析"字段。** 只共享事实和裁决,不共享推理过程。
记忆层的目的是让下一回合的努力不必从零重新推导,不是让两边想到一块去 ——
共享同一条推理路径会让两份产出趋同,合起来就少了一道验收。
**记忆不同不是缺陷,是两份努力能互相验收的前提。**

---

## 七、范围收窄是前提,不是遗憾

记忆层只解决"这一个工作项 + 约束它的前提",不解决"完全理解整个项目"。
没有方案能做到后者。

协议本来就把范围收到**一回合一个工作项** —— 正是这个收窄让"仓库即记忆"成立。
如果某个工作项大到 agent 必须先理解全局意图才能动手,那是工作项切得太大了。

同理:
- tester 一回合只提一个(或一组紧密相关的)失败用例。一次砸 20 条会让 dev
  无法定位、无法最小实现、无法有效评审,直接退化成"批量生成代码"。
- 工作项粒度的判断标准:"实现用户系统"太大;
  "密码哈希用 bcrypt,cost=12"才是一个工作项。

---

## 八、人类是时钟,也是唯一的裁决者

agent 之间不会自动唤醒对方。每次交接后需要人到另一个终端敲一句。

这条现在是**限制**,但它顺带保证了三件事:

1. 有一个天然的观察窗口,人类每一回合都会看到状态。
2. 跑飞的成本有上界。
3. 契约由人类维护 —— agent 一律只读。契约漂移(tester 测 `login() -> token`、
   dev 写 `authenticate() -> Session`,两边各自都"对"、合起来是废的)是这套
   机制唯一会致命的失败模式,所以变更契约必须双方书面同意后由人类落笔。

死锁闸同理:同一工作项被打回 3 次,协议强制停止轮转并交给人类。
这与 the-pair 的"20 轮预算 + 人类闸门"、以及辩论研究里"轮次越多准确率越低"
的结论方向一致。

**要做全自动是可以的**(handoff 后用 headless 拉起对方),但先把手动流程跑顺 ——
自动化会把每一个还没暴露的设计缺陷放大成事故。

## 九、单一真源,防漂移

协议目录 `.agents/skills/pair-protocol/` 是唯一真源:

- CLI(`cli/pair_bootstrap/`)**不含任何协议逻辑**,只负责把 skill 搬进目标项目、
  建软链接,然后调用刚复制过去的 `pair.py init`,把后续全部交出去。
- 构建时协议目录被原样打进 wheel,CLI 不复制、不改写内容。
- 判定、边界、红绿、回合,全部只有一处实现。

一旦 CLI 里出现协议逻辑,它就会和 skill 漂移 —— **而漂移会让 agent 读到的规则
不再是被强制的规则,交付质量因此失去保障**。文档也适用同一条:本目录下的文档
描述行为,`pair.py` 定义行为;两者不一致时以 `pair.py` 为准,并且这是一个 bug。

## 已知边界

脚本能保证的是**努力可以合并、痕迹可以审计**;努力本身的质量,仍然依赖
每个 agent 尽到本职、依赖人类在死锁和契约这些关口上裁决。下面这些不是
待办,是设计的必然推论。想清楚了再动。

| 边界 | 为什么 |
|---|---|
| 不能跑 shell 的 harness 不支持 | 执行层跑不起来,协议退化成纯 prose,强制力归零 |
| Rust 文件内单测不支持 | `#[cfg(test)] mod tests` 与实现同文件,路径切分物理上不成立 |
| 基线必须全绿才能接入 | `impl` 的 GREEN 不变量依赖它,否则协议要么卡死、要么不变量形同虚设 |
| 技能激活不是 100% 可靠 | 渐进式披露意味着 agent 自己判断要不要加载。入口文件里的激活器是硬命令,但没有硬保证 |
| 人类是时钟 | 见第八节 |
| 记忆层不解决"理解整个项目" | 见第七节。没有方案能做到 |
| 契约质量决定成败 | 唯一会致命的失败模式。脚本查得了引用完整性,查不了语义清晰度 |
