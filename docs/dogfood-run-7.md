# 第七轮真实运行报告:独立运行

**主题:两个没参与协议设计的会话,只靠仓库里的文档,把一个项目从开工跑到完成。**
六轮下来欠着的那件事。样板项目(`examples/make-demo.py` 生成)的 W1–W4,加上运行中
人类追加的 W5、W6,**6 个工作项全部双向通过**:24 次交接、6 次认领、2 次打回、0 次死锁、
0 次测试异议、53 条测试全绿。

编排日志原文附在 [dogfood-run-7-log.md](dogfood-run-7-log.md),编排者发出的每一条消息都在里面。

---

## 一句话:协议机制没有一次需要人来救,需要人的三次全是契约本身的缺陷

| 人类介入 | 起因 | 谁先发现 |
|---|---|---|
| 1(W3 之前) | 样板契约自相矛盾:「返回只含 `a-z0-9-`」与「非 ASCII 原样保留」;另有模块路径没写、`-`/`_` 去留、`"!!!"`、truncate 的"最多 n-1"等 | 两个会话在开工前审查里**各自独立**挑出同样三处 |
| 2(W4 之前) | W4 标题"把正则提成常量",而实现里从来没有正则 | 两个会话都在认领前指出 |
| 3(W4 之前) | 重音分开写(NFD)被吃掉,同一个词两种 slug | tester 在 W3 发现、**刻意不写测试定死**;dev 把它写进决策记录免得随笔记作废 |

三次都是"契约或计划写错了",没有一次是"协议卡住了、agent 不知道下一步做什么"。
另有一次基础设施中断(用量上限,HTTP 429),tester 回合中途被终止,没有留下半截产出,原样重发即可。

---

## 实验怎么做的

- **参与者**:两个 `general-purpose` subagent,各自一个持续会话(tester / dev),用消息续接,记得前面的回合。
- **编排者**(写本文的会话)只发两种消息:
  - 第一条:角色、工作目录、共用目录要带 `PAIR_ROLE=` 前缀、先跑 `status`;
  - 之后每回合:`drive.py` 里 `DEFAULT_PROMPT` 的原文。
- **轮到谁,只问 `whose-turn`**。编排者不回答任何需要判断的问题,原样交给人类。
- 为什么不用 `drive.py`:本机没有 `claude` 命令行。

## 这一轮要打的折扣

- **上下文污染,证实存在**:subagent 从带着 TongXia 上下文的会话派生,tester 第一回合就提到
  "TongXia 主仓库里的 `.pair/enforcer.py`"。它自己判断出样板项目该用 `pair.py`,判断正确,
  但"只读样板文档"这个前提是打了折的。
- **编排者本身是污染的**:人类介入的三次定稿由编排者代笔("按最优方案继续"),写法带着六轮的经验。
- **参与者与设计者是同一个模型家族**。
- **项目很小**:两个字符串函数。协议在大项目上的摩擦,这一轮测不出来。

## 第六轮修的东西,在独立运行里都真的发生了

| 机制 | 独立运行里的样本 |
|---|---|
| W19 claim 看两个角色 | 契约两次被改(`621cbd5`、`decf752`),两次都是:tester 从 `status` 发现校验作废 → 结论**末尾追加**补记 → 重跑 → 试认领被拒 → idle 自动归 dev → dev 重跑 → 回到 tester。**编排者一句都没提契约改过** |
| W17 只涉及测试的打回走捷径 | W2 的打回:`phase=spec -> review-test`,跳过 impl 与 review-impl |
| W18 评审记录只能追加 | 两份开工前结论各追加了两段补记,没有一次改写;第二次评审都新建了 `-2` 文件 |
| 记忆层晋升闸 | W4 完成时 tester 的交接被拒:笔记还有内容。补了一条决策才过 |
| 决策记录跨工作项被用上 | W1 定下"从 `src` 顶层导入、文件不与函数同名",W2 的 tester 与 dev 各自照做,两个会话之间没有任何直接沟通 |

**两次打回都是同一个形状 —— 判据看起来在守、其实守不住**,和本仓库前六轮反复出现的一样,这次由两个全新会话自己挖出来:

- **W2**:截断用例保留的那部分里一个空格都没有,"截到最后一个空格""去掉末尾空白"两种错误实现全套照绿。
- **W3**:`isalnum()` 里只算"数值"的 1023 个字符(`½`、`Ⅻ`)一个没测,改成 `isalpha() or isdigit()` 全套照绿 ——
  而 W4 要重写的正好是这段判定,那正是最顺手的写法。

挖出它们的手段都是**自发的变异测试**:故意改错实现,看测试红不红。协议文档没有要求这样做,两个会话都这样做了。

## 运行中暴露的协议问题

### ① 文档没说"共用一个目录时必须用 `PAIR_ROLE`"

`SKILL.md` 列了角色解析的优先级(`PAIR_ROLE` → `.pair/whoami` → 分支名),没说两个 agent 共用目录时
`.pair/whoami` 会互相覆盖。编排者在第一条消息里告诉了它们;没告诉的话,第一个写 `whoami` 的会把对方的角色改掉。

### ② 做变异验证没有合法的地方可去,四次越界

两个会话**都**反复在样板目录之外(scratchpad 里)建副本或临时脚本来换入错误实现:dev 三次、tester 至少一次,
都违反了编排者"只在这个目录里工作"的要求,用完都删了。tester 事后主动承认。
**这不是某个 agent 的疏忽,是需求真实存在、协议没给出口**:写权限边界只管仓库里的路径,仓库外面它管不到;
而在仓库里换入错误实现,又会在工作区留下被判越界的改动。

### ③ 样板项目自己的契约与计划有缺陷

`examples/demo-project` 的 CONTRACT.md 自相矛盾、缺模块路径;PLAN.md 的 W4 前提不成立、缺"保护测试"。
一个新用户照 INSTALL 接入,第一次开工就会撞上这些 —— 而它是协议的出厂样例。

### ④ 两个会让测试"看起来有、其实没有"的新来源

- **工具悄悄改写字符**:tester 手敲的全角逗号存进文件后变成了 ASCII 逗号,测试照绿、什么都没测到。
  它改用 `\uXXXX` 转义并逐码点核对;dev 后来给候选用例时也主动要求用转义写。
- **Python 编译缓存**:原地改写实现做变异时,两次改写的那一行长度相同、又在同一秒写入,Python 复用了旧的 `.pyc`,
  跑的其实是上一个版本。dev 关掉编译缓存重跑才得到可信结果。
