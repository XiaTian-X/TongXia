# 改进提案与路线图

> 每一条都来自 [prior-art.md](prior-art.md) 里某个项目已经验证过的做法。
> 格式统一:**来源 / 问题 / 提议 / 与现有设计的冲突 / 验收方式**。
>
> 优先级不是按工作量排的,是按"不做会让协议的核心主张站不住"排的。

## 排序理由

协议的三条核心主张里,有两条目前是**部分兑现**的:

> **2026-09 更新:第一次真实运行之后,P0-1 与 P0-2 的相对次序换了。**
> 见 [dogfood-run-1.md](dogfood-run-1.md):那一轮的两次打回**都不是红绿发现的** ——
> 一次是评审读代码读出的契约偏离,一次是把修复改回去跑出来的(手动变异检查)。
> 用例级红绿对"契约偏离"和"修复没有测试守着"这两类**天然失明**,
> 而这两类是那一轮全部的真实产出。P0-2(评审带证据)因此先做,而且已落地。

| 主张 | 兑现程度 | 缺口 |
|---|---|---|
| 回合信号取自程序 | 🟡 部分 | 只有整体红绿,不知道哪条红了 → P0-1。**实测优先级低于原估**:它抓不到契约偏离,也抓不到"修复没测试" |
| 对抗性是结构性的 | 🟡 部分 | ~~评审质量无机器约束~~ 已加结构门禁(ADR-014),但脚本只查得了结构、查不了内容 |
| 通信只走 git | 🟢 已兑现 | — |

P0 就是这两个缺口。其余是扩面和体验。

# P0 — 补上核心主张的缺口

## P0-1 测试结果从布尔值升级到用例级

**来源:** [TDD Guard](https://github.com/nizos/tdd-guard) 的 reporter 架构
(Vitest / Jest / pytest / PHPUnit / Go / Rust / RSpec / Minitest 各有适配)。

**问题:** `run_tests()` 只看 `subprocess.call()` 的退出码。于是:

- spec 回合只要**整体** RED 就放行。协议无法验证"红的那条正是你这回合新写的"。
- `status` 只能说"现在是红的",说不出红在哪 —— dev 每回合都要自己再跑一遍
  才知道要修什么。
- 无法做 over-implementation 检测(TDD Guard 的第二条强制)。
- `cover` 类型的"必须真的新增了测试"只能靠 git diff 判断文件被碰过,
  判断不了新增的用例有没有被执行到。

**提议:** 在 config 里加可选的 `test_report`:

```json
"test_report": {
  "kind": "junit-xml",
  "path": ".pair/report.xml",
  "cmd": "python3 -m pytest --junitxml=.pair/report.xml"
}
```

`run_tests()` 在有 `test_report` 时改为返回结构化结果
`{green: bool, failed: [用例ID], total: int}`,并据此:

1. spec 阶段增加检查:**失败用例中至少有一条属于本回合改动的测试文件**。
2. `status` 直接列出红着的用例名,dev 不必重跑。
3. `cover` 阶段增加检查:本回合新增的用例确实出现在报告的已执行列表里。

优先支持 JUnit XML(pytest / Go 的 gotestsum / vitest / jest / PHPUnit / RSpec
全都能产出),一种格式覆盖绝大多数栈。**保持可选** —— 没配 `test_report` 时
一切行为与现在完全一致,存量仓库零成本。

**与现有设计的冲突:** 没有。这是"回合信号取自程序"的**增强**,不是转向。
唯一要守住的是:解析失败必须**降级**回布尔判定并给出警告,绝不能让协议
因为解析问题卡死。

**验收:** 一致性测试新增"tester 写了一条恒过的测试、同时靠别的手段让套件变红"
的作弊场景,断言 spec 阶段拒绝;`mutation_check.py` 补上对应变异点。

## P0-2 评审必须带证据,由脚本校验  ✅ 已落地

**来源:** [Adversarial Review](https://arxiv.org/abs/2608.18167) —— 它给本项目
最怕的东西起了名字:**false-consensus failure mode**,处方是
"disagreement must be minimal, structured, and **evidence-grounded**"。

**问题:** `rules.md` 规则 6 写着"禁止 LGTM 这类空话",`handoff` 也强制裁决
必须附非空理由。但**非空 ≠ 有实质**:`handoff approve "看起来不错"` 现在能过。

这是协议里"靠职业操守"占比最高的一处,而它恰好守着最重要的那道门。

**提议:** 分两级,都很便宜:

**① `changes` 必须具体到位置。** 裁决理由或本回合写入 `shared_paths` 的文件里,
至少出现一处 `路径:行号` 形态的引用(正则 `[\w./\-]+\.\w+:\d+`)。
`rules.md` 已经把这条写成了判例:

> "实现有问题"不是评审意见,"`src/auth.py:42` 对 `test@example.com` 特判,
> 换任意其他邮箱就会失败"才是。

**把已经写在规则里的判例变成检查,零新增概念。**

**② `approve` 必须交出检查清单。** 要求理由中包含"检查了 …"与"未覆盖 …"
两个部分(或落到 `docs/reviews/` 的对应文件里,由脚本检查小节标题)。
`rules.md` 的示例已经是这个形状:

> 检查了 hash 函数无特判、cost 参数取自配置而非常量、空密码路径抛的是契约里写的
> ValueError。未覆盖:超长密码,下轮补测试。

脚本能查结构,查不了内容 —— **但结构本身就把"看起来不错"挡在门外了**,
因为它逼你写出具体检查了什么。这与协议里 `--allow-deletion`、`--no-decision`
的"强制留痕"是同一个手法。

**与现有设计的冲突:** 有一处要小心。加检查会诱发"为了过检查而编造引用"。
缓解:引用的文件路径必须**真的在本工作项的 diff 里出现过**,脚本可以查;
行号查不了,但编一个存在的文件 + 假行号的成本已经高于认真看一眼。

**验收:** 一致性测试扮演"敷衍评审的 agent",断言 `approve "LGTM"` 与
`changes "有问题"` 都被拒;`mutation_check.py` 补两个变异点。

**实际落地(与上面的提议有出入,以此为准):**

- **`approve` 用两个必填参数,不解析散文。** `--checked` / `--uncovered`。
  上面提议的"检查理由里有没有'检查了…''未覆盖…'两部分"被否掉了 ——
  脚本一旦开始猜中文措辞,换个说法就绕过,而且会把协议绑死在一种语言上。
- **`changes` 的位置引用不要求文件后缀**(Makefile、Dockerfile 都没有),
  真正的把关是"路径必须对得上一个真实文件"。
- **多做了一条上面没提的:** 评审简报从负向禁止改成正向要求。
  Adversarial Review 里真正扭转 false-consensus 的就是这个,不是更多禁令。

见 [ADR-014](design-decisions.md#adr-014-评审证据用参数强制不解析散文)。

## P0-3 契约的机器可校验性

**来源:** [GitHub Spec Kit](https://github.com/github/spec-kit) 的
`/clarify`(消歧)和 `/analyze`(跨产物一致性校验)。

**问题:** README 自己承认 **"契约质量决定成败,这是唯一会致命的失败模式"**,
但 `verify-setup` 对契约只做两件事:

- 每个工作项必须有 `对应契约:` 一行,且指向的小节标题真实存在;
- 强制交出一份不短于 120 字的歧义结论。

它查不了**契约小节里到底有没有可断言的东西**。一个只写了
"### 登录 \n 用户可以登录" 的小节能顺利通过全部检查,而这正是致命失败的入口。

**提议:** `verify-setup` 增加契约小节的**结构性**检查(全部是 warn,不是 bad,
除非配置里显式开严):

1. 被工作项引用的小节必须包含至少一个代码块或表格 —— 接口签名、错误类型、
   状态转换,总得有一个能被断言的形状。
2. 小节里应出现返回值/错误两类描述之一(关键词或代码块内容匹配)。
3. **新增 `analyze` 式的交叉检查**:契约小节里出现的标识符
   (代码块里的函数/类名),在已有测试或实现中是否出现过 —— 出现率为 0 且
   工作项不是新建的,提示可能的契约漂移。

再加一条便宜的:`CONTRACT_SKELETON` 里补一个**填空模板**
(签名 / 输入约束 / 返回 / 错误 / 不做什么),让人类第一次写契约时就落在
可校验的形状上。**模板比校验更有效** —— 这是 Spec Kit 和 BMAD 共同的经验。

**与现有设计的冲突:** 契约是人类的产物,不能让脚本把人烦到关掉检查。
所以默认全部 warn,`"strict_contract": true` 时才升级为 bad。

**验收:** `test_v1_setup.py` 增加"空洞契约"用例,断言 verify-setup 给出警告
且警告文案指名道姓。

# P1 — 明显该有,但不动摇核心

## P1-1 协议健康度报告:把"互相点头"变成可观测指标  ✅ 已落地

**来源:** the-pair 的 per-turn 观测(token / 事件 / 工具调用),
以及辩论研究里"轮次—准确率"的关系。

**问题:** 人类现在无法回答"这两份努力有没有在互相验收,还是在合规地走过场"。
唯一的信号是逐条读 commit。

**提议:** 新增只读命令 `pair.py report`,从 git 历史里统计:

| 指标 | 健康区间 | 异常信号 |
|---|---|---|
| 打回率(changes / 评审总数) | 15%–50% | **接近 0 = 互相点头**;接近 100% = 契约有问题 |
| 每工作项平均回合数 | 4–8 | 过高 = 工作项切太大 |
| 撞死锁闸的工作项占比 | <10% | 过高 = 契约含糊 |
| spec 回合平均新增用例数 | 1–5 | 过高 = 违反"一回合一个用例" |
| 决策条目 / 完成工作项 | — | 长期为 0 = 记忆层空转 |
| `--no-decision` 使用率 | <50% | 过高 = 晋升 gate 被当成噪音绕过 |

**打回率接近 0 是最值钱的那个数字** —— 它是"互相点头"唯一的量化证据。
防点头不是这套协议的目的;但打回率是最能暴露"交付悄悄变废"的信号 ——
它长期接近 0,说明两份努力可能根本没在互相验收。

纯读 git log 即可实现,不需要新增任何状态。

**验收:** `report` 在 demo 项目上跑出非空结果;一致性测试断言全 approve 的
历史会被标红。

**实际落地:** 去掉了「spec 回合平均新增用例数」—— 数用例要按语言解析测试文件,
和"不解析测试框架输出"是同一类坑。新增了一条上面没写的**样本门槛**:
少于 5 次评审时不下任何结论,报一个假精确的数字比不报更糟。
退出码始终 0,它是仪表盘不是门禁 —— 见
[ADR-015](design-decisions.md#adr-015-健康度报告只观测不设门禁)。

## P1-7 多语言仓库只有一半有门禁(静默)

**来源:** 文档规范那一轮的评审。

**问题:** `_detect_stack` 第一个探测文件命中就返回。一个同时有 `pom.xml` 和
`package.json` 的仓库,`init` 会配一条**只跑 Java** 的 `test_cmd`,
然后基线绿、每回合绿、红绿不变量全程"有效" —— 而 JS 那半从头到尾没有任何门禁。

**这比契约形状不对危险得多,因为它是静默的。** 契约形状不对肉眼可见。

**可能的提议:** `init` 探测到多个栈时**拒绝自动配置**,列出全部命中的栈,
要求人类手工写一条覆盖全部的 `test_cmd`(或显式确认只测其中一部分,
并写进 `docs/reviews/baseline.md`)。

**先记着的理由:** 没有样本 —— 还没有人拿多语言仓库跑过。
但这一条已经写进 INSTALL.md 的「不适用」清单,不会静默伤人。

## P1-6 空转的 impl 回合(待定,先记着)

**来源:** 第一次真实运行,见 [dogfood-run-1.md](dogfood-run-1.md)。

**问题:** `review-test changes → spec → impl → review-impl` 这条序列,
在打回理由**纯粹是覆盖不足**时会强制绕经 dev 一趟,而 dev 无事可做 ——
实现早就落地了,要补的是测试,而测试是 tester 的路径。

**可能的提议:** 当"自打回以来 dev 的可写路径没有任何改动"时,
允许从 `spec` 直接回到 `review-test`,跳过空转的 `impl`。

**为什么先不做:** 需要新增一条判定(比对自打回以来 dev 路径的 diff),
而这条路径有多常见还不知道 —— 一个样本。**加判定的代价是确定的,
收益是猜的。** 等它再出现两次再说。

**代价(不做的话):** 每次"评审以覆盖不足打回"都多烧一个回合。
在"人类是时钟"的前提下,那是一次真实的人类上下文切换。

## P1-2 活性保护:全局回合预算与停滞检测

**来源:** the-pair 的 20 轮默认预算 + 60 秒停滞检测;
《Talk Isn't Always Cheap》的"轮次越多越差"。

**问题:** 死锁闸只管**同一工作项被打回 3 次**。一个工作项可以在
spec→impl→review→changes→spec 的循环里,通过每次都换个理由打回,
或者在 approve 路径上反复重开,消耗掉任意多轮而不触发任何闸。

**提议:** 在 `state.json` 里加 `item_rounds`(本工作项累计交接次数),
超过 `max_item_rounds`(默认 12)时 `handoff` 拒绝并要求交给人类。
文案沿用死锁闸的口径:不是惩罚,是提示工作项切得太大。

停滞检测不做 —— 本协议里"人类是时钟",没有后台进程,没有可以计时的主体。

**与现有设计的冲突:** 无。这是死锁闸的同类扩展,共用一套话术。

## P1-3 契约变更走成一条命令

**来源:** Spec Kit 把每个阶段做成显式命令;
本项目 `rules.md` 里的"契约变更流程"目前是四步 prose。

**问题:** 契约变更是**重新推导代价最高**的事(协议自己这么说,
所以给它设了强制记录的时刻 ③)。但发起变更的流程完全靠 agent 自己照着散文走:
写一份包含四个要素的文档、`handoff changes`、对方评估、人类落笔。
四步里任何一步的格式走样,后面的强制检查就抓不到。

**提议:** `pair.py propose-contract <小节名>` 生成骨架到
`docs/reviews/contract-change-<ID>.md`(**这个名字已落地,四个小节由 handoff 强制**)
(现在是什么 / 为什么不行 / 提议改成什么 / 影响哪些测试和实现),
并把这份文件登记进 state。对方在自己的回合里必须在同一份文件追加
"同意 / 反驳"小节,`handoff` 校验小节存在。人类落笔后 `claim` 时记录的
`contract_sha` 自然变化,触发已有的强制记录 ③,闭环。

**与现有设计的冲突:** 增加了一个命令,与 SKILL.md 的"五条命令"表述冲突 ——
可以放在 references 里作为进阶命令,不进主表。

## P1-4 status 注入的可审阅化

**来源:** BMAD 的 **story 文件自包含**设计 —— Dev agent 只读 story 就能干活,
不需要回溯上游文档。

**问题:** 本项目的 `status` 注入(笔记全文 + 相干决策)是**运行时拼出来的**,
只存在于那一次终端输出里。人类想知道"这一回合 agent 到底看到了什么"
只能自己再跑一遍 `status`,而那时状态可能已经变了。

**提议:** `status` 把注入内容同时落盘到 `.pair/.last-brief.md`(gitignore),
出问题时人类可以直接看到当时的输入。零协议语义变更,纯可观测性。

顺带解决一个真实痛点:agent 说"我没看到那条决策"时,现在无从对质。

## P1-5 同一模型分饰两角要写进文档  ✅ 已落地

**来源:** [aider architect/editor](https://aider.chat/2024/09/26/architect.html) ——
Claude 3.5 Sonnet **自己配自己**也从 77.4% 提升到 80.5%。收益部分来自
"一次只干一件事",而不只是来自"两个不同厂商"。

**问题:** README 的开头"让**任意两个** AI coding agent…… 结对开发"容易被读成
"必须是两个不同的 agent"。实际上两个终端跑同一个工具、同一个模型完全成立 ——
而且这是**上手成本最低的入门配置**,应该被明确推荐。

**提议:** README 的"启动两个 agent"一节加一句显式说明,并把
"同工具同模型、两个终端、靠 `PAIR_ROLE` 区分"列为**推荐的起步配置**。
这是纯文档改动,零成本,直接降低上手门槛。

**实际落地时收窄了措辞:** aider 的 architect/editor 是**同一回合内的流水线**,
两个角色不互相评审、没有独立的产物所有权。所以那条实证支持得起"分工的收益
同模型也成立",支持不起"对抗性评审的收益同模型也拿得到"。后者没有证据,
它正是 P1-1 的打回率要测的东西 —— 写成结论就等于把待测假设当成了已知。

# P2 — 扩面,做之前先确认真的有人要

## P2-1 worktree 拓扑升为一等公民

**来源:** container-use / Conductor / Crystal / Emdash / Mux 这一整类工具。

**现状:** 拓扑 B(分离工作副本)只有 `"sync": true` 加 pull/push,
建 worktree、建分支、分配角色全靠人手动。

**提议:** `pair.py init --topology worktree` 自动:建 `pair/tester`、`pair/dev`
两个分支与对应 worktree,各写好 `.pair/whoami`,`sync` 置 true,
并打印两条可直接粘贴的启动命令。

**为什么是 P2:** 拓扑 A(同目录)是本协议的**优势场景** —— 路径切分让它成立,
而这正是本项目相对 worktree 系工具的差异点。把 B 做漂亮属于补齐,不属于强化。

## P2-2 通过 MCP 打开"不能跑 shell"的边界

**现状:** 明确不支持不能执行 shell 的 harness —— 执行层跑不起来,强制力归零。

**提议:** 把 `status` / `claim` / `handoff` / `inbox` 暴露成一个 MCP server
(仍然只是 `pair.py` 的薄封装,协议逻辑不复制)。GUI 与云端 harness
只要支持 MCP 就能接入。

**风险:** 违反"CLI 不含协议逻辑"的同类约束 —— MCP 层必须同样是纯转发,
一旦它开始自己判定就会漂移。**先写清楚这条约束,再动手。**

## P2-3 与 TDD Guard 叠加使用的说明

TDD Guard 保证"一个 agent 按 TDD 的顺序写代码",本协议保证"两个 agent
各写各的、互相验收"。两者不冲突,理论上可叠加:dev 侧挂 TDD Guard,
能在**回合内**就拦住硬编码和 over-implementation,而不必等到 tester 评审。

值得写一份 `docs/interop-tdd-guard.md`,但要先实测冲突面
(TDD Guard 会不会拦住 tester 写测试的动作)。

## P2-4 Rust:明确不做,或换机制

目录切分对 `#[cfg(test)] mod tests` 物理上不成立。唯一可能的路是
**块级 diff 检查**:允许双方写同一文件,但 tester 只能改 `#[cfg(test)]` 块内、
dev 只能改块外。这需要一个 Rust 感知的 diff 分析器 —— 成本远高于收益,
而且会在协议里引入第一个语言特化的组件。

**建议保持"不支持",并在文档里给出迁移路径**(把测试移到 `tests/` 集成测试目录)。

### 1. `2a32b5f` 新增的基线预检闸零测试覆盖

`mutation_check.py:596` 的 `precheck_no_baseline` 与 `:466` 的
`isolated_copy`,在 `tests/conformance/test_mutation_tooling.py` 里
**0 命中**;作为对照,同一次提交要守的另一道闸 `baseline_verified` 有
**5 处**(`:90`、`:91`、`:94`、`:96`、`:99`)。14 条全绿**不等于**新闸被测住:
下一次重构可以把它整个删掉,套件照样 14/14。

它守的正是本项目最怕的失败模式:基线本来就红的环境里,回退路径的判据只有
rc≠0,分不清失败来自变异还是来自环境,于是每条变异都被判成"抓到",报出一个
恒真的 70/70 与退出码 0。而它自己没有测试。

**为什么至今没被测住 —— 成本。** `precheck_no_baseline` 内部硬编码两件事:
`isolated_copy(tmp)`(从 `REPO` 整仓 copytree)与跑
`dst / "tests/conformance/run.py" -j jobs`(全量套件)。端到端调它一次等于
跑一次全量。实测(本机 8 进程):

| 动作 | 实测 |
|---|---|
| `isolated_copy` 等价的 copytree(排除 `.git`/`__pycache__`) | 0.02~0.03s |
| 整仓副本跑一次全量(`run_baseline` 自己打印的值) | 44.3s |
| 极小假仓库(1~2 个用例)跑 `run.py -j 8` | 0.10s |
| 当前 `test_mutation_tooling.py` 全 14 条 | 0.17s |

**copytree 不是瓶颈,跑全量才是。** 直接把端到端预检加进 conformance 套件,
套件会从约 47s 涨到约 91s(接近翻倍),而变异检查的默认路径本来就要付这
44s 一次 —— 同一份成本付两遍,换来的额外覆盖只有"子进程真的起起来了"
这一层,不值。

**候选 A:参数化 `precheck_no_baseline(jobs, root=None)`,`root` 非空时跳过
copytree、直接用给定目录。** 测试侧造一个极小假仓库(`tests/conformance/`
下放一份从真仓 copy 来的 `run.py` 加一个必败用例),喂绿/红两种,断言返回
契约。成本 0.10s × 2 = **0.2s**。
守住:`precheck_no_baseline` 的全部内部逻辑 —— 设 `PAIR_MUTATION_RUN=1`、
起 `run.py` 子进程、`_ids` 解析输出、`(rc, fails, text)` 三元组契约。
守不住:真实的 `isolated_copy` 被 `root` 绕过了,所以"副本与判定环境同构"
这一层测不到 —— 而那正是这道闸的关键前提(`:599-602` 用了四行 docstring
解释它)。另需一条测试单独钉 `isolated_copy`。
代价:改签名(禁改区),并同步 `:544` 的调用点。

**候选 B:测试侧 monkeypatch `MUT.isolated_copy` 让它返回极小假仓库。**
不动产品代码,成本同样 **0.2s**。守住的范围与候选 A 相同,守不住的也相同,
但多一层脆弱:桩打在模块属性上,若实现改成内联 `shutil.copytree`(不再调
`isolated_copy`),桩会**静默失效**,那条测试就变成在真仓上跑全量(44s)
或直接失败。用一个会静默失效的桩去守一道"防止静默假绿"的闸,方向不对。

**候选 C:把判定抽成纯函数,照 `baseline_verified` 的既有先例。**
判定现在嵌在 `main:545` 的 `if rc != 0 or fails:` 里,无法单独调用。而
`baseline_verified`(`:427-436`)的 docstring 已经写下本仓的处理惯例:
"抽成纯函数是为了能被测住:它是这套缓存机制里唯一一处判断错了就会让
整个检查变成恒真的地方"。预检的判据是同一类东西,应当同办。成本**微秒级**。

**推荐:候选 C,再加两条不需要改签名的补充,共三层。** 不选 A/B 的理由是
它们都为了覆盖"子进程起起来了"而付 0.2s,却**恰好绕开了最该守的那层**
(同构性);而 `_ids` 解析已被 `TestCacheStalenessIsDetected`(`:39-55`,
走 `run_suite`,`:415` 同样是 `fails = _ids(text)`)间接覆盖。

**层 A —— 判定真值表(纯函数)。** 在 `mutation_check.py` 加

```python
def precheck_verdict(rc, fails):
    """预检放行吗 —— rc=0 且失败集为空,两个条件缺一不可。"""
    return rc == 0 and not fails
```

`main:545` 改成 `if not precheck_verdict(rc, fails):`。测试断言真值表,
其中最关键的一条是 **`precheck_verdict(0, ["x.Y.z"])` 必须为 False**:
rc=0 但 `_ids` 抓到了 FAIL 行也要拒。这条最容易被写漏,因为直觉上
"rc=0 就是绿";而它恰好是并行运行器最可能出现的形态(某一片失败,
汇总行却仍然打印)。

**层 B —— 同构条件的源码断言。** 照 `test_v1_shipped.py:136-145` 的

### 2. `MAX_CACHED = 1` 与缓存里实际抓手数漂移

三方口径一致:`mutation_check.py:360` 的 `MAX_CACHED = 1`、`:354-359` 的

**成因:** `MAX_CACHED > 1` 的时代留下的历史数据。

**不会自愈:** `:661` 的写回条件是

### 6. `pair.py:1814` 与 `:1787-1797` 两个 `if` 无互斥,同屏打印相反指令

那个:向人类宣布"完成"。

**修法:** `:1799` 改成 `if plan_all_done(root, cfg) and not full_failed:`,

### 8. `mutation_check.py:372-375` 的注释把归因前提说得过强

那段注释写的是:预检的失败集"为空则两条路径的 rc≠0 都**必然**由变异
引起"。成立需要的条件比"必然"多:

- 预检是**一次**采样 —— 一个副本、一个时刻;
- 而 `check_one` 之后要在 70 个**另建的**副本里各跑一次;
- 运行器还不同:预检用并行 `run.py -j <jobs>`(`:614-617`),而
  `check_one` 的判定用串行 `unittest`(快路径 `unittest -q <ids>`,回退
  路径 `unittest discover -f`);
- `loaded`(`:422-423`)校验的是"请求了几个就跑了几个",挡不住"同一个
  测试在预检副本里绿、在某个 `check_one` 副本里红"。

所以一个负载敏感或时序敏感的测试完全可以预检绿、某个副本红。此时
rc≠0 **不是**变异引起的,却会被记成 `caught` —— 高估了测试集的拦截力,
而且这条结论还会被写进缓存、当以后的快路径依据(`:661-664`)。

**成立的是:**"在测试确定、环境不变的前提下可归因",不是"必然"。

**修法:** 降级注释措辞并把前提写出来。它不改行为,但一句过强的注释会
让后来者以为这里不需要再复核 —— 而第二道闸的全部合法性正挂在归因
可靠这件事上。

### `test_v1_shipped` 的环境依赖  ✅ 已解决(原第 10 条,`6f7afe0`)

`test_开工前校验只卡在契约审查结论那一步`(`:64`)在没有 git 身份的机器上
必红,把基线钉在 265/266,并因此锁死上面那条的刷新入口。

**病灶不是"env 被剥离"。** 6 组受控实验:在
`{"PAIR_ROLE": "dev", "PATH": "/usr/bin:/bin"}` 这个剥离 env 下,四条注入
身份的路径**全部 rc=0** —— `git -c user.name=… -c user.email=…`、
`GIT_CONFIG_GLOBAL` 指向含身份的临时文件、样板仓库的 `.git/config` 里写
仓库级身份、`HOME` 指向含 `.gitconfig` 的目录。

**病灶也不是沙箱。** 升级权限后的只读探测,沙箱内外逐项一致:`hostname` 与
`hostname -f` 都返回 `Mac`;`scutil --get HostName` = `not set`;
`socket.getfqdn()` = `Mac`(不含点);`getaddrinfo` 的 `AI_CANONNAME` =
`mac`;`/tmp` 里新建的临时仓库跑 `git commit`,沙箱外同样 rc=128。

**真正的根因是一条链:** hostname 不是 FQDN → git **主动拒绝**从
`username@hostname` 自动推导 email(它拼出 `xbase@Mac.(none)` 然后拒绝用)
→ 各级配置又没有任何 `user.*` 兜底(`git config --list --show-origin` 里
零条 `user.*`;`/etc/gitconfig`、`/opt/homebrew/etc/gitconfig`、
`/usr/local/git/etc/gitconfig` 三个系统级文件均不存在;`~/.gitconfig` 存在
但只有两个 credential 段)→ 任何 commit 永久 rc=128。这是这台机器的持久
状态,不是环境波动。

**一并订正两处旧结论:**

1. "在真实终端里应当通过"—— **错**。本机真实终端同样红,因为
   `scutil --get HostName` 就没设置过。
2. 第五轮交接时给的"选项 b:`GIT_AUTHOR_*`/`GIT_COMMITTER_*` 环境变量
   前缀"作为让基线变绿的手段 —— **不成立**。实测它对**直接调用**
   `make-demo.py` 有效,但 `test_v1_shipped.py:73` 传的是整个 `env=` 字典
   (**整体替换**,不是合并),环境变量到不了 `pair.py`。只有仓库级配置
   (已采纳)或全局配置才行。

**同源铁证(照抄既有约定的依据):** `harness.py:204` 与 `make-demo.py:83` 的
commit message `"chore: 装上结对协议"` **逐字相同**,git 命令序列同为
`init → (config) → add -A → commit`。harness 就是 make-demo 的测试镜像,
只是它多写了身份(`:200-201`)—— **这正是缺陷本身**:镜像的一半有身份,
另一半没有。

**最终采纳的方案:** 在 `make-demo.py` 里加 `ensure_identity(target)`
(`:22-60`),`git init` 之后、`add`/`commit` 之前调用(`:80-84`),写仓库级
`user.name=conformance` / `user.email=conformance@test`,取值照抄
`harness.py:204-205` 与 `:376-377`。一处改动解决两级失败,因为
`pair.py:2847` 的 `cwd=root` 来自 `repo_root()`(`:259-265`,
`git rev-parse --show-toplevel` 从进程 cwd 求得),而 `test_v1_shipped.py:73`
的 `cwd=str(proj)` 就是 make-demo 的输出目录;仓库级身份既不依赖 `HOME`
也不依赖环境变量,所以能穿过那处 env 剥离。

**两处有意偏离既有约定:**

- **条件式,不是无条件。** 探测用 `git var` 的退出码,只在探测失败时才写
  (`6f7afe0` 当时只探 `GIT_AUTHOR_IDENT` 一条;`72ab252` 把它扩成
  `GIT_AUTHOR_IDENT` 与 `GIT_COMMITTER_IDENT` 两条,任一失败就写 ——
  理由见 `docs/contributing.md` 的身份兜底那段)。harness 无条件是
  可接受的 —— 它的目录来自 `mkdtemp`
  (`:198`)、由 `addCleanup` 注册 `shutil.rmtree`(`:206-207`、`:323-325`),
  生命周期完全在测试进程内;而且测试要的就是不受宿主机影响的确定身份。
  `make-demo.py` 不同:它面向用户,产出目录可能被长期留存,无条件写假身份
  会**静默把用户后续所有提交错误归属**,比响亮地 rc=128 更坏。
- **没有照抄 `commit.gpgsign false`**(`harness.py:206` 有、`:377` 没有)。
  理由与代价见开放条目第 3 条。

**验证:** 266/266 全绿(此前 265/266)。三组反向验证确认条件式真的是
条件式:用 `GIT_CONFIG_GLOBAL` 造出身份时兜底一字不写、author 保持
`Real Human <real@example.com>`;用 `GIT_AUTHOR_*` 造出身份时同样零写入、
author 保持 `Env Person <env@example.com>`;无身份时 rc 从 128 变 0、写入
两条、author 是 `conformance <conformance@test>`。

`72ab252` 之后又补了四组受控实验,专门盖 author/committer 不对称的缝隙:
只注入 `GIT_AUTHOR_*` 时(author 探测 rc=0、committer 探测 rc=128),修复前
`make-demo.py` rc=1、修复后 rc=0 且 `.git/config` 里出现兜底身份 2 条,而
author 仍是人类注入的那一个;两个 ident 都注入时兜底身份 0 条、人类身份
完整保留。
