# 改进提案与路线图

> 每一条都来自 [prior-art.md](prior-art.md) 里某个项目已经验证过的做法。
> 格式统一:**来源 / 问题 / 提议 / 与现有设计的冲突 / 验收方式**。
>
> 优先级不是按工作量排的,是按"不做会让协议的核心主张站不住"排的。

## 排序理由

协议的三条核心主张里,有两条目前是**部分兑现**的:

> **2026-09 更新(两轮真实运行后):P0-1 与 P0-2 的相对次序换了。**
> 见 [dogfood-run-1.md](dogfood-run-1.md):那一轮的两次打回**都不是红绿发现的** ——
> 一次是评审读代码读出的契约偏离,一次是把修复改回去跑出来的(手动变异检查)。
> 用例级红绿对"契约偏离"和"修复没有测试守着"这两类**天然失明**,
> 而这两类是那一轮全部的真实产出。P0-2(评审带证据)因此先做,而且已落地。

| 主张 | 兑现程度 | 缺口 |
|---|---|---|
| 回合信号取自程序 | 🟡 部分 | 只有整体红绿,不知道哪条红了 → P0-1。**实测优先级低于原估**:它抓不到契约偏离,也抓不到"修复没测试" |
| 对抗性是结构性的 | 🟡 部分 | ~~评审质量无机器约束~~ 已加结构门禁(ADR-014),但脚本只查得了结构、查不了内容 |
| 通信只走 git | 🟢 已兑现 | — |

P0 就是这两个缺口。其余是扩面和体验。

# P0 — 补上核心主张的缺口

## P0-1 测试结果从布尔值升级到用例级

**来源:** [TDD Guard](https://github.com/nizos/tdd-guard) 的 reporter 架构
(Vitest / Jest / pytest / PHPUnit / Go / Rust / RSpec / Minitest 各有适配)。

**问题:** `run_tests()` 只看 `subprocess.call()` 的退出码。于是:

- spec 回合只要**整体** RED 就放行。协议无法验证"红的那条正是你这回合新写的"。
- `status` 只能说"现在是红的",说不出红在哪 —— dev 每回合都要自己再跑一遍
  才知道要修什么。
- 无法做 over-implementation 检测(TDD Guard 的第二条强制)。
- `cover` 类型的"必须真的新增了测试"只能靠 git diff 判断文件被碰过,
  判断不了新增的用例有没有被执行到。

**提议:** 在 config 里加可选的 `test_report`:

```json
"test_report": {
  "kind": "junit-xml",
  "path": ".pair/report.xml",
  "cmd": "python3 -m pytest --junitxml=.pair/report.xml"
}
```

`run_tests()` 在有 `test_report` 时改为返回结构化结果
`{green: bool, failed: [用例ID], total: int}`,并据此:

1. spec 阶段增加检查:**失败用例中至少有一条属于本回合改动的测试文件**。
2. `status` 直接列出红着的用例名,dev 不必重跑。
3. `cover` 阶段增加检查:本回合新增的用例确实出现在报告的已执行列表里。

优先支持 JUnit XML(pytest / Go 的 gotestsum / vitest / jest / PHPUnit / RSpec
全都能产出),一种格式覆盖绝大多数栈。**保持可选** —— 没配 `test_report` 时
一切行为与现在完全一致,存量仓库零成本。

**与现有设计的冲突:** 没有。这是"回合信号取自程序"的**增强**,不是转向。
唯一要守住的是:解析失败必须**降级**回布尔判定并给出警告,绝不能让协议
因为解析问题卡死。

**验收:** 一致性测试新增"tester 写了一条恒过的测试、同时靠别的手段让套件变红"
的作弊场景,断言 spec 阶段拒绝;`mutation_check.py` 补上对应变异点。

## P0-2 评审必须带证据,由脚本校验  ✅ 已落地

**来源:** [Adversarial Review](https://arxiv.org/abs/2608.18167) —— 它给本项目
最怕的东西起了名字:**false-consensus failure mode**,处方是
"disagreement must be minimal, structured, and **evidence-grounded**"。

**问题:** `rules.md` 规则 6 写着"禁止 LGTM 这类空话",`handoff` 也强制裁决
必须附非空理由。但**非空 ≠ 有实质**:`handoff approve "看起来不错"` 现在能过。

这是协议里"靠职业操守"占比最高的一处,而它恰好守着最重要的那道门。

**提议:** 分两级,都很便宜:

**① `changes` 必须具体到位置。** 裁决理由或本回合写入 `shared_paths` 的文件里,
至少出现一处 `路径:行号` 形态的引用(正则 `[\w./\-]+\.\w+:\d+`)。
`rules.md` 已经把这条写成了判例:

> "实现有问题"不是评审意见,"`src/auth.py:42` 对 `test@example.com` 特判,
> 换任意其他邮箱就会失败"才是。

**把已经写在规则里的判例变成检查,零新增概念。**

**② `approve` 必须交出检查清单。** 要求理由中包含"检查了 …"与"未覆盖 …"
两个部分(或落到 `docs/reviews/` 的对应文件里,由脚本检查小节标题)。
`rules.md` 的示例已经是这个形状:

> 检查了 hash 函数无特判、cost 参数取自配置而非常量、空密码路径抛的是契约里写的
> ValueError。未覆盖:超长密码,下轮补测试。

脚本能查结构,查不了内容 —— **但结构本身就把"看起来不错"挡在门外了**,
因为它逼你写出具体检查了什么。这与协议里 `--allow-deletion`、`--no-decision`
的"强制留痕"是同一个手法。

**与现有设计的冲突:** 有一处要小心。加检查会诱发"为了过检查而编造引用"。
缓解:引用的文件路径必须**真的在本工作项的 diff 里出现过**,脚本可以查;
行号查不了,但编一个存在的文件 + 假行号的成本已经高于认真看一眼。

**验收:** 一致性测试扮演"敷衍评审的 agent",断言 `approve "LGTM"` 与
`changes "有问题"` 都被拒;`mutation_check.py` 补两个变异点。

**实际落地(与上面的提议有出入,以此为准):**

- **`approve` 用两个必填参数,不解析散文。** `--checked` / `--uncovered`。
  上面提议的"检查理由里有没有'检查了…''未覆盖…'两部分"被否掉了 ——
  脚本一旦开始猜中文措辞,换个说法就绕过,而且会把协议绑死在一种语言上。
- **`changes` 的位置引用不要求文件后缀**(Makefile、Dockerfile 都没有),
  真正的把关是"路径必须对得上一个真实文件"。
- **多做了一条上面没提的:** 评审简报从负向禁止改成正向要求。
  Adversarial Review 里真正扭转 false-consensus 的就是这个,不是更多禁令。

见 [ADR-014](design-decisions.md#adr-014-评审证据用参数强制不解析散文)。

## P0-3 契约的机器可校验性

**来源:** [GitHub Spec Kit](https://github.com/github/spec-kit) 的
`/clarify`(消歧)和 `/analyze`(跨产物一致性校验)。

**问题:** README 自己承认 **"契约质量决定成败,这是唯一会致命的失败模式"**,
但 `verify-setup` 对契约只做两件事:

- 每个工作项必须有 `对应契约:` 一行,且指向的小节标题真实存在;
- 强制交出一份不短于 120 字的歧义结论。

它查不了**契约小节里到底有没有可断言的东西**。一个只写了
"### 登录 \n 用户可以登录" 的小节能顺利通过全部检查,而这正是致命失败的入口。

**提议:** `verify-setup` 增加契约小节的**结构性**检查(全部是 warn,不是 bad,
除非配置里显式开严):

1. 被工作项引用的小节必须包含至少一个代码块或表格 —— 接口签名、错误类型、
   状态转换,总得有一个能被断言的形状。
2. 小节里应出现返回值/错误两类描述之一(关键词或代码块内容匹配)。
3. **新增 `analyze` 式的交叉检查**:契约小节里出现的标识符
   (代码块里的函数/类名),在已有测试或实现中是否出现过 —— 出现率为 0 且
   工作项不是新建的,提示可能的契约漂移。

再加一条便宜的:`CONTRACT_SKELETON` 里补一个**填空模板**
(签名 / 输入约束 / 返回 / 错误 / 不做什么),让人类第一次写契约时就落在
可校验的形状上。**模板比校验更有效** —— 这是 Spec Kit 和 BMAD 共同的经验。

**与现有设计的冲突:** 契约是人类的产物,不能让脚本把人烦到关掉检查。
所以默认全部 warn,`"strict_contract": true` 时才升级为 bad。

**验收:** `test_v1_setup.py` 增加"空洞契约"用例,断言 verify-setup 给出警告
且警告文案指名道姓。

# P1 — 明显该有,但不动摇核心

## P1-1 协议健康度报告:把"互相点头"变成可观测指标  ✅ 已落地

**来源:** the-pair 的 per-turn 观测(token / 事件 / 工具调用),
以及辩论研究里"轮次—准确率"的关系。

**问题:** 人类现在无法回答"这两份努力有没有在互相验收,还是在合规地走过场"。
唯一的信号是逐条读 commit。

**提议:** 新增只读命令 `pair.py report`,从 git 历史里统计:

| 指标 | 健康区间 | 异常信号 |
|---|---|---|
| 打回率(changes / 评审总数) | 15%–50% | **接近 0 = 互相点头**;接近 100% = 契约有问题 |
| 每工作项平均回合数 | 4–8 | 过高 = 工作项切太大 |
| 撞死锁闸的工作项占比 | <10% | 过高 = 契约含糊 |
| spec 回合平均新增用例数 | 1–5 | 过高 = 违反"一回合一个用例" |
| 决策条目 / 完成工作项 | — | 长期为 0 = 记忆层空转 |
| `--no-decision` 使用率 | <50% | 过高 = 晋升 gate 被当成噪音绕过 |

**打回率接近 0 是最值钱的那个数字** —— 它是"互相点头"唯一的量化证据。
防点头不是这套协议的目的;但打回率是最能暴露"交付悄悄变废"的信号 ——
它长期接近 0,说明两份努力可能根本没在互相验收。

纯读 git log 即可实现,不需要新增任何状态。

**验收:** `report` 在 demo 项目上跑出非空结果;一致性测试断言全 approve 的
历史会被标红。

**实际落地:** 去掉了「spec 回合平均新增用例数」—— 数用例要按语言解析测试文件,
和"不解析测试框架输出"是同一类坑。新增了一条上面没写的**样本门槛**:
少于 5 次评审时不下任何结论,报一个假精确的数字比不报更糟。
退出码始终 0,它是仪表盘不是门禁 —— 见
[ADR-015](design-decisions.md#adr-015-健康度报告只观测不设门禁)。

## P0-4 roles 配置没覆盖全仓:33 个"孤儿路径"

**来源:** [dogfood-run-2.md](dogfood-run-2.md)。四条决策记录都指向它。

**问题:** 按 `.pair/config.json` 的 `roles` 对 `git ls-files` 实算:
刻意冻结的只有 **6 个**(PLAN、CONTRACT、`.pair/*`、`.claude`),
而**不属于任何角色、也没被冻结的"孤儿"有 33 个** —— `README.md`、
`INSTALL.md`、`pyproject.toml`、`cli/pair_bootstrap/`、整个 `examples/`。

孤儿路径上的改动**两个 agent 都写不了**,只有人类能改。而它不会在开工前
暴露:`verify-setup` 查的是角色路径有没有重叠、有没有撞冻结,**不查覆盖面**。
缺口在第 N 个回合突然发作 —— run-2 的三次卡顿(`INSTALL.md` 行号、
`examples/.gitignore`、`improvements.md` 行号)全部出自孤儿,一次都不出自冻结。

**这不是"文档只许人类改"太严。** 那是刻意设计,只有 6 个。症结是配置压根
没覆盖全仓,而这一点此前没有任何东西会提醒你。

**提议:** `verify-setup` 增加一条**覆盖面**检查(warn,不是 bad):
把 `git ls-files` 的结果按 `roles` + `frozen_paths` + `ignore_paths` 分类,
列出落在三者之外的路径数与前若干条,并说明"这些路径结对期间只有人类能改"。

它不该是 bad —— 有意留给人类的路径是正当配置(`examples/` 可能就该如此)。
它要做的只是**把"第 N 个回合才发作"提前到开工前**。

**与现有设计的冲突:** 没有。这是 `verify-setup` 已有的那批配置自洽检查的
同类扩展,共用一套话术。

**验收:** `test_v1_setup.py` 增加一个"仓库里有文件不属于任何角色"的用例,
断言 `verify-setup` 给出警告且警告里含那些路径;`mutation_check.py` 补变异点。

# 阶段模型 — 协议只覆盖了三分之一

**来源:** 两轮真实运行 + 2026-09 的设计讨论。

协议现在只承载一种不确定性,所以只有一个时钟。但一次结对实际要消除三种:

| 阶段 | 消除什么不确定性 | 时钟(怎么知道做完了) | 现状 |
|---|---|---|---|
| **understand** | 对**现状**的(存量项目) | 特征测试变绿 —— **客观** | ❌ 只有 `brownfield.md` 一份散文指引 |
| **discuss** | 对**方向**的 | 双方签字 + 人类批准 —— **必须靠人** | ❌ 没有;只能塞进笔记等人类排期 |
| **pair** | 对**实现**的 | 红绿 —— **客观** | ✅ 已兑现 |

两个推论,它们决定了下面几条的形状:

**① 三个阶段里只有 discuss 必须靠人。** "该做什么"是价值判断,不是事实判断。
另外两个阶段都能有客观时钟 —— 这也意味着**人类的介入面应该收缩到这一格**,
而不是像现在这样被迫去当打字员(见 P1-9)。

**② understand 的时钟已经存在,只是没接上。** 存量项目的理解产出不该是散文,
该是一批绿着的特征测试 —— 而 `cover` 类型正是为此设计的(全程 GREEN、必须
新增测试、必须交出「行为来源」与「我冻结了哪些可疑行为」)。协议已有的
`考古观察@<sha>` 依据等级只校验 sha 存在、不校验结论对不对,特征测试补的
正是那一半。

## P0-5 discuss 阶段,而且必须可重入

**来源:** 两轮真实运行。

**问题:** 方向问题**恰恰是实现过程才暴露的**。这两轮发现的四个结构性问题
——孤儿路径、行号绊线跨边界、验证命令副作用、阶段限制——**没有一个是开工前
发现的**,全是做的过程中撞出来的。而协议没有地方承载它们,只能写进
`DECISIONS.md` 与本文件,然后停下来等人类排期。
`docs/dogfood-run-2.md` 里 tester 至少三次说过"这超出本工作项范围,建议你开
新工作项"——**那句话本身就是这个缺口的症状**。

把 discuss 只放在项目开头,等于把它做成 `verify-setup` 的升级版,仍然是
一次性的,解决不了上面这件事。

**提议:** 形状是**契约变更流程的泛化** —— 现有流程只能改契约(接口),
改不了 PLAN(方向),而方向恰恰更该讨论。

- 触发:`pair.py discuss "为什么"`,**任一方、任何阶段**
- 效果:当前工作项**挂起**(不是作废),进入 discuss 阶段,双方交替提案
- 产物:`docs/proposals/<主题>.md`,双方在同一份文件里签字
- 退出:双方签字 → 人类一条命令批准 → 提升为 PLAN/CONTRACT 的改动 → 恢复轮转

**实现时最容易踩的坑(开工前复查发现):** 提案目录**不能直接加进
`shared_paths`**。那个键不是"双方都能写的地方"的泛称 —— 它被五处逻辑依赖:
`dispute-evidence` 强制点、评审文件命名检查、打回时的位置引用检查、
异议举证、以及 `verify-setup` 里"记忆层不得落在 shared_paths 之下"那条。
把 `docs/proposals/` 并进去,**"写了一份提案"就会被算成"异议落到纸面"**,
`dispute-evidence` 那条防护被静默削掉。`writable_paths` 的 docstring 里
已经为记忆层留过同样的警告,这是第二次。**提案目录需要一个新的路径类别**,
而这也正是 P0-7 里 `artifact_paths` 被推迟到本条落地时再评估的原因。

**与现有设计的冲突:** 这是全协议**唯一一个"遇到困难就能逃出去"的出口**。
两个 agent 卡在实现上时,开个讨论比写代码轻松。缓解与死锁闸同构:给 discuss
一个额度,并让 `report` 统计频率 —— **从不进 discuss 和频繁进 discuss 是两种
相反的病**,前者说明不敢提方向问题,后者说明规划太粗。

**验收:** 用例覆盖"挂起后能恢复到原阶段原工作项"、"单方签字不能退出"、
"额度耗尽撞闸交人类";`report` 增加 discuss 频次一行。

## P0-6 understand 作为 discuss 的一种模式,不是第四个阶段

**来源:** 2026-09 设计讨论;`brownfield.md` 现状。

**问题:** 存量项目接入时,两个 agent 对代码库一无所知,而现在的流程是
`init` → 人类写 PLAN/CONTRACT → `verify-setup` → 直接开工,**没有任何一步是
"读懂这个项目"**。更要命的是时序:brownfield 的契约本该从代码考古中来
(ADR-016 的 `考古观察@<sha>` 就是为此),而考古现在发生在 `cover` 工作项的
spec 回合 —— **那已经太晚了,契约必须在 `claim` 之前就存在**。

**提议:** 不新增阶段机,让 understand 复用 discuss 的全部机制,只换产物与
时钟:双方**各自独立**读代码、写下理解,再交叉检查对方漏了什么、说错了什么
(这是对抗性的正确用法),收敛后提升成契约草案 + 一批 `cover` 工作项。

**与现有设计的冲突:** 无新增状态。**这是刻意的** —— `pair.py` 已经逼近三千行,
再加两套阶段机会让协议垮在复杂度上,而这个项目的论点恰恰是"规则要可执行、
可测"。判据:**三个阶段只在时钟上不同**,回合交替、写权限边界、留痕、
评审证据全部复用;如果实现时发现某个阶段需要一套自己的规则,那多半是
阶段划错了。

**验收:** 一个存量项目样板(可用 `examples/` 扩),跑完 understand 之后
契约每个小节都带 `考古观察@<sha>`,且每条都有对应的绿着的特征测试。

## P0-7 写权限边界按"谁"和"何时"切,但有第三类文件两者都不该管

**来源:** 第二轮真实运行,`DECISIONS.md` 里两条同源条目。

**问题:** P0-4 只解决了**覆盖面**(33 个孤儿),解决不了**阶段限制**。
实证:tester 在 `review-impl` 回合为复验跑 `mutation_check.py`,它刷新
`tests/conformance/mutation-cache.json` 的指纹 —— 那**在 tester 路径里**,
不是孤儿,P0-4 覆盖不到;但只读评审回合的可写路径没有 `tests/`,提交不了,
留在工作区又会让下一个回合 dev 的 `git add -A` 把它算到 dev 头上判越界。
**规则和它自己的要求冲突了:评审要求"证据是跑出来的",而跑证据必然产生
副产物,同一条规则又禁止写下副产物。**

协议只有"写"一个概念,但实际有三种:

| 类型 | 例子 | 该受什么约束 |
|---|---|---|
| **主张** | 测试、实现 | 角色 + 阶段(零冲突保证的全部来源) |
| **陈述** | 评审、笔记、决策 | 只受阶段约束(已是共享路径) |
| **副产物** | 缓存指纹、日志、行号引用、样板同步 | **两者都不该受** —— 它不是谁的主张,是命令跑出来的 |

**提议(2026-09 开工前复查后**已重写**):原提议是新增 `artifact_paths`
配置键。**那是过度设计** —— 复查 `pair.py` 写权限边界那个循环发现,
`ignore_paths` 的 `continue` 落在角色与阶段判断**之前**,所以它
**已经同时豁免了角色与阶段**,正是新键要的核心功能。新键相对它的安全增量
约等于零:那条"随附命令名"的留痕防不住任何东西(副产物的改动本来就在
`git diff` 里可见),而两者同样都是"不受边界保护"。

**真缺口只有一个:可见性。** `ignore_paths` 里有哪些文件已经不受保护,
没有任何地方摆给人看。所以改成两条,都并进 P0-4 的那次 `verify-setup` 改动:

1. `verify-setup` 另打印一段 `ignore_paths` 覆盖的被跟踪文件清单
2. **`handoff` 因越界拒绝时,若越界文件是孤儿,文案要指出"它不属于任何角色,
   需要人类划归"** —— 开工前的警告与真正撞上的时刻相隔几十个回合,
   而前两轮实测,拒绝文案说的是"请撤销这些改动后重试",那个文件却是人类刚
   改的,agent 照做就会撤销掉不是它写的东西。**这一刻才是信息有用的时候。**

把副产物划进 `ignore_paths` 是一次 config 改动,人类做,不是工作项。

另附一处时序事实(不改代码,只登记):`full_test_cmd` 在 `cmd_handoff` 里
跑在 `git commit` **之后**,所以工作项完成那次的缓存改动必然以脏工作区形态
留给下一个人。

**与现有设计的冲突:** 没有了 —— 它现在只是 P0-4 那次改动的两条附加输出。
**保留的风险是命名语义**:`ignore_paths` 字面意思是"忽略",拿它承载"副产物"
会让后来的人困惑。**重新评估点定在 P0-5 落地时**:`discuss` 阶段会引入提案
目录,那时若确实需要新的路径类别,连同语义一起设计;现在加等于为不存在的
问题建基础设施。

**验收:** 用例覆盖"只读评审回合跑验证命令后仍能交接"(现有 `ignore_paths`
就该做到,补一条把它钉住)、"`verify-setup` 打印 `ignore_paths` 覆盖清单"、
"越界拒绝时孤儿文件的文案含划归提示"。

## P1-8 `report` 要分开"推进交付的回合"与"协议开销的回合"  ✅ 已落地(第五轮 W14)

**来源:** 两次真实运行都记过,一次都没落地。
`dogfood-run-1.md` 的三条观察之一,以及 [dogfood-run-2.md](dogfood-run-2.md)。

**问题:** `每工作项回合数` 把两类回合混在同一个分母里:

- 真正推进交付的
- 协议自身造成的(撞死锁、跨边界常量挡住 impl、空转的 impl 回合)

run-2 里 20 次交接有 **8 次**属于后者,而 `report` 把「10.0」判成"偏高"
并提示"工作项切太大" —— **判错了**,工作项切得没问题。
run-1 里 W1 走了 10 个交接,主因是撞了协议死锁,同样被读成"切太大"。

**一个会给出错误诊断的指标,比没有这个指标更糟。**

**提议:** 纯读 git log 就能分:`dispute:` 前缀的交接、以及紧随其后的那次
`spec` 受理,是协议开销;`deadlock_hits` 非空的工作项同理。
把「每工作项回合数」拆成 `净回合数` 与 `协议开销`,健康区间只挂在前者上。

**做不到的部分要说清楚:** "空转的 impl 回合"(dev 路径空 diff)读 git 能判,
但它同时也是 P1-6 要消掉的东西 —— 两条一起做更省。

**验收:** `test_v1_report.py` 增加"历史里有 dispute 交接"的用例,
断言两个数字分开出现且净回合数不含那些。

## P1-7 多语言仓库只有一半有门禁(静默)

## P1-6 空转的 impl 回合(待定,先记着)

**可能的提议:** 当"自打回以来 dev 的可写路径没有任何改动"时,

**为什么先不做:** 需要新增一条判定(比对自打回以来 dev 路径的 diff),

## P1-2 活性保护:全局回合预算与停滞检测

**来源:** the-pair 的 20 轮默认预算 + 60 秒停滞检测;
《Talk Isn't Always Cheap》的"轮次越多越差"。

**问题:** 死锁闸只管**同一工作项被打回 3 次**。一个工作项可以在
spec→impl→review→changes→spec 的循环里,通过每次都换个理由打回,
或者在 approve 路径上反复重开,消耗掉任意多轮而不触发任何闸。

**提议:** 在 `state.json` 里加 `item_rounds`(本工作项累计交接次数),
超过 `max_item_rounds`(默认 12)时 `handoff` 拒绝并要求交给人类。
文案沿用死锁闸的口径:不是惩罚,是提示工作项切得太大。

停滞检测不做 —— 本协议里"人类是时钟",没有后台进程,没有可以计时的主体。

**与现有设计的冲突:** 无。这是死锁闸的同类扩展,共用一套话术。

## P1-3 契约变更走成一条命令

**来源:** Spec Kit 把每个阶段做成显式命令;
本项目 `rules.md` 里的"契约变更流程"目前是四步 prose。

**问题:** 契约变更是**重新推导代价最高**的事(协议自己这么说,
所以给它设了强制记录的时刻 ③)。但发起变更的流程完全靠 agent 自己照着散文走:
写一份包含四个要素的文档、`handoff changes`、对方评估、人类落笔。
四步里任何一步的格式走样,后面的强制检查就抓不到。

**提议:** `pair.py propose-contract <小节名>` 生成骨架到
`docs/reviews/contract-change-<ID>.md`(**这个名字已落地,四个小节由 handoff 强制**)
(现在是什么 / 为什么不行 / 提议改成什么 / 影响哪些测试和实现),
并把这份文件登记进 state。对方在自己的回合里必须在同一份文件追加
"同意 / 反驳"小节,`handoff` 校验小节存在。人类落笔后 `claim` 时记录的
`contract_sha` 自然变化,触发已有的强制记录 ③,闭环。

**与现有设计的冲突:** 增加了一个命令,与 SKILL.md 的"五条命令"表述冲突 ——
可以放在 references 里作为进阶命令,不进主表。

## P1-9 PLAN / CONTRACT / 路线图的修改:从"只有人类"改成"强制留痕"

**来源:** 第二轮真实运行;是 P1-3 的实质升级(P1-3 的终点仍然是"人类落笔")。

**问题:** 冻结文件只有 6 个,数量不是问题,**它产生的结果才是**。这一轮
契约定稿是 dev 代人类执行的,它自己在 `DECISIONS.md` 里写下:

> tester 无法从仓库里分辨这次改动是人类定稿还是 dev 迁就自己的实现 ——
> 那正是冻结文件买来的信任,这一次它没有了。

**限制没有产生安全,只产生了一次无法核对的代笔。** 而人类那一侧同样别扭:
它被迫从"裁决者"变成"打字员",`SETUP` 决策条目里那句"`依据: 人类定稿` 记的
是**授权定稿**,不是**逐条通读**"就是这个矛盾的自述。

**提议:** 换一个轴 —— 不是限制**谁能改 / 何时能改**,而是限制**改动必须
留下什么凭据**。契约的安全性从来不来自"改不了",来自"改了必然被对方看见、
且必须说明依据"。协议已经有三个这形态的先例:`--allow-deletion`、
`--no-decision`、`--drafter`,全都是"允许做,但强制留痕"。

让契约/PLAN 变更成为第四个:任一方可改,但必须
`handoff --contract-change "依据"` —— 声明进提交正文、强制写决策记录、
对方在 `inbox` 里必然看到,`claim` 时 `contract_sha` 变化触发已有的强制记录 ③。

**分两步,弱版本不依赖 P0-5(2026-09 复查后拆开):**

原条目写着"P0-5 落地之前不要单独做",理由是要靠 discuss 的双方签字防合谋。
复查发现**P1-3 里已经有一套等价的轻量流程**:`contract-change-<ID>.md`
的四小节**已经由 `handoff` 强制**,而"契约在工作项期间变过就必须留决策"
**也已经是强制写入的三个时刻之一**。缺的只有两样:

- **弱版本(不依赖 P0-5,可在第四轮做):** 对方必须在同一份变更请求文件里
  追加「同意 / 反驳」小节(P1-3 的后半,尚未实现);发起方
  `handoff --contract-change "依据"`,声明进提交正文。两样齐了,agent 就可以
  落笔改 `PLAN`/`CONTRACT`/路线图,人类退回裁决者。
- **强版本(P0-5 之后):** 变更改走 discuss 的正式签字与批准,
  `report` 增加契约变更频率。

**为什么值得提前:** 人类当打字员的成本**每一轮都要付**,而合谋的风险可以
先靠 `report` 观测(频率异常再收紧)。把它压到第七轮,等于让最早提出的那条
诉求最后才兑现,中间四轮每轮都要人类落一次笔。

**与现有设计的冲突:** 与"冻结文件"这条设计直接冲突,需要一条 ADR 明确
取代它。风险仍是两个 agent 合谋改契约去迁就实现 —— false-consensus 最危险的
形态;弱版本对它的防护弱于强版本,这是提前的代价,要写进那条 ADR。

**验收:** 用例覆盖"不带 `--contract-change` 改契约会被拒"、"带了则声明进
提交正文"、"变更后未写决策记录会被拒"。

## P1-15 文档改动要留下"谁改的、为什么改";路线图与计划的**改写**要有讨论依据

**来源:** 2026-09 设计要求。

**问题:** 分两半,现状不同。

**归属这一半其实已经有了**,但依赖一处容易被忽略的事实:两个 agent
**共用同一个 git 身份**(`git log --author` 全是同一个人),所以
`git blame` 分不出是谁改的 —— **唯一的归属证据是 `handoff` 写进提交正文的
`role=<角色> phase=… item=…` 那一行**,而它是脚本写的,不是 agent 自述,
可靠。这一点没写进任何文档,读 `git log` 的人会误以为归属来自 author。

**理由这一半是真缺口。** 一次交接可能改了实现加三份文档,而说明只有提交
标题那一句;读文档本身完全看不出某一节为什么被改成现在这样。本轮
`improvements.md` 的 P0-7 被整条重写,理由只存在于提交信息里 ——
靠的是自觉在正文里补了一句"(开工前复查后已重写)",不是强制。

**路线图与计划则完全没有约束:** `PLAN`/`CONTRACT` 是冻结的(只有人类),
而 `improvements.md` 归 dev,它可以随手改优先级、删条目、改方向,
没有任何东西要求它说明依据。

**提议:** 两条,分别对应两半。

**① 规范文档的改动要带理由。** 本回合若动了规范性文档
(`protocol-spec` / `architecture` / `rules` / `README` / `INSTALL` /
`contributing` 等),`handoff` 要求 `--doc-reason "…"`,声明进提交正文 ——
和 `--allow-deletion` / `--no-decision` / `--drafter` 同一手法:
**不是放行,是强制留痕**。过程文档(笔记、评审记录)**豁免** ——
它们本身就是理由,再要一句说明是纯噪音。

**② 路线图与计划的改写要有讨论依据,追加不用。** 这个区分是必须的:
路线图的新条目往往是审查中发现的待办(本轮的 P1-14 就是),
**一刀切会让路线图变成不能记录发现的死文档**。

| 动作 | 要求 |
|---|---|
| 新增一条待办 / 追加一段说明 | 只要 `--doc-reason` |
| 改优先级、删条目、改验收标准、新增工作项 | 要讨论依据 |
| 工作项完成时脚本勾选 PLAN | 不管(那是脚本的权限) |

**判据是机器可判的:** `git diff --numstat` 对这些文件的**删除行数为 0**
即纯追加。这有先例 —— `DECISIONS.md` 的追加式检查判的是同一件事,
只是那里能靠 `startswith`(只在末尾追加),而路线图的新条目会插在中间,
所以改用删除行数。

**与现有设计的冲突:** ② **依赖 P0-5**(discuss 阶段),因为"讨论依据"要指向
一个提案产物,而那个产物现在不存在。**P0-5 之前只能做 ①**,以及把 ② 的判据
先实现成**警告**(改写了但没有依据 → 提示,不阻断),等 discuss 落地再收紧。

这条同时**扩大了 P1-9 的范围**:那一条原本只覆盖 `PLAN`/`CONTRACT`,
按本条应当把 `improvements.md` 一并纳入 —— 路线图和计划在"改它要有依据"
这件事上没有区别。

**验收:** 按五步纪律。用例覆盖:改了规范文档但没给 `--doc-reason` 被拒;
只改笔记/评审不要求 `--doc-reason`;`--doc-reason` 的内容进提交正文;
路线图纯追加放行、有删除行时给出警告(P0-5 之后改为拒绝)。
变异点至少两个:拆掉 `--doc-reason` 强制、拆掉追加/改写的判据。

## P1-10 `chore` 回合:维护性改动不该占用一个完整回合

**来源:** 第二轮真实运行的回合账。

**问题:** `report` 判"每工作项回合数 10.0 偏高"并提示"工作项切太大",
**但真相不是切太大**:回合大多烧在维护性改动上 —— 改三个行号、同步一行
`.gitignore`、更新一个常量。这些各自要走 spec → impl → review-impl →
review-test 的完整轮转,而它们既没有红绿可验,也没有值得评审的内容。

P1-8 是在**统计**上把两类回合分开,这一条是在**机制**上让后一类不占回合。

**提议:** 增加 `chore` 工作项类型或一个不推进状态机的旁路通道:双方都能做、
不改变当前阶段与归属、仍受写权限边界约束、仍要留提交记录。

**与现有设计的冲突:** 与"严格轮流"有张力 —— 需要明确 `chore` 不能夹带
`src/` 或 `tests/` 的行为改动,否则它会变成绕过评审的后门。判据可以复用
现有的 `scope` 检查。

**验收:** 用例覆盖"chore 不改变 phase 与 owner"、"chore 夹带行为改动被拒"。

## P1-11 决策记录需要"撤销",而它属于 discuss

**来源:** 2026-09 设计讨论。

**问题:** `DECISIONS.md` 是**追加式不可改**的(`handoff` 强制)。这在一轮之内
是对的 —— 它防的是伪造共识。但跨轮之后:一条后来被证明是错的决策会**永远**
留在记忆层里,每回合被 `status` 读给双方听,而"它已经被推翻了"只能靠再追加
一条来表达。两三轮之后,记忆层里正确的和已废止的混在一起,而 `status` 一视
同仁地全读出来 —— 注入预算被废止的结论占着。

**提议:** 不放宽追加式纪律。**推翻一条旧决策是一次讨论的产出,不是随手追加**
—— 走 P0-5 的 discuss,产出一条带 `推翻: <旧条目 ID>` 字段的新条目,
`status` 注入时把被推翻的条目降级(不删除,标记为已废止且不再计入注入预算)。

**与现有设计的冲突:** 与 ADR 的追加式纪律同源,不冲突 —— 这里加的是
**标记**,不是**改写**。

**验收:** 用例覆盖"带 `推翻:` 字段的条目会让旧条目退出 status 注入"、
"旧条目仍然留在文件里"、"不经 discuss 直接写 `推翻:` 会被拒"。

## P1-12 取消坐标:文档引用代码不该用行号  ⚠ 第三轮 W6 部分落地

**来源:** 第二轮真实运行(两次异议都把行号失配列为阻塞项之一,人类为它
落笔两次);兑现「后续几轮登记的开放条目」第 11 条里那句"真正的解法是取消
坐标"。

**问题:** 现在的防线是 `test_docs_consistency` 的 `CITED_LINE_COUNTS` 绊线 ——
被引文件行数一变就红,人工逐条核对。它**只是绊线,不是校验器**:
行数不变的内容改写抓不到,省掉文件名的续引(`` `:466` ``)对它的正则隐形,
而且每次 `pair.py` 增删几行都要付一次人工核对。

**实测过全部 27 处引用,结论比预期强:**

| | 处数 |
|---|---|
| 能定位到封闭 `def`/`class` | 22 |
| 落在模块级(docstring / 常量区注释) | 5 |
| **真正需要行号的** | **0** |

那 5 处模块级的也不需要坐标 —— 它们指的是"`drive.py` 的模块 docstring"、
"`mutation_check.py` 里 `MAX_CACHED` 那段设计注释"。**这个仓库里没有一处
引用真的需要行号**;行号是写作时手边有,不是内容需要。

**提议:** 三层,各管各的。

**① 防止(主力)** —— 引用改成符号形式,用 `ast` 验证符号存在:

```
pair.py:NNN             →  pair.py#cmd_handoff
mutation_check.py:NNN   →  mutation_check.py#precheck_no_baseline
mutation_check.py:NNN   →  mutation_check.py#MAX_CACHED
drive.py:NNN            →  drive.py(模块 docstring)
```

(左列刻意写成 `NNN` 而不是真实行号 —— 否则这份提案里的**示例**会被引用
扫描器当成真实引用,`pair.py` 一变就把它们列进"受影响的引用"当噪音。
这个坑本身就是本条要消灭的那类。)

插入行、移动函数、重排文件顺序**全部免疫** —— 漂移在源头就不发生,
不需要检测也不需要修复。符号不够精确时用内容片段作**人读的**补充,
**不拿它做机器判定**(那正是第 11 条里否掉内容比对的原因:人写的描述
与源码原文必然错配)。

**② 兜底** —— 真出现"必须指到某一行"的场景时(目前一处都没有),
用**上下文窗口锚**:机器首次记下该行前后各 2 行的实际内容,漂了就按锚
搜索并自动重定位。原型实测:让 `pair.py` 与 `mutation_check.py` 整体下移后,
**11/11 全自动修正,零人工**(单行内容做锚时 `return 1` 一类会多命中,
加窗口即唯一)。

**④ 历史快照豁免** —— 形如 `` `<文件>:<行号>@<sha>` `` 的引用不参与检查。
运行报告(`dogfood-run-*.md`)与"已解决"留档记的是**当时**的状态,把它们
改写成指向当前代码的符号等于篡改历史;而若那个符号后来被删,报告还会无端
变红。形式与契约既有的 `考古观察@<sha>` 一致,不新造概念。

**③ 可导航** —— 用 markdown 链接语法承载,路径由现有的
`test_相对链接与锚点都能解析` 守着。实测那条测试**已经**能抓到路径不存在
与 `.md` 假锚点,但对指向 `.py` 的 `#L123` 行号锚完全不查 ——
顺带补上"行号落在文件范围内"是零成本增量。

**与现有设计的冲突:** 取代 `CITED_LINE_COUNTS` 绊线(连同它在
`docs/contributing.md` 里那节说明)。失败模式要对比清楚,因为它变了:

| 变化 | 行号引用 | 符号引用 |
|---|---|---|
| 插入无关行 | **漂**(这两轮的全部痛点) | 免疫 |
| 函数改名 | 不受影响,但可能指向已变的代码 | **断,`ast` 报错** ← 正确的失败 |
| 函数内容改写 | 静默指错 | 仍指对函数,语义可能已变(残留风险) |

第二行是关键:改名会红,而**改名了本来就该看一眼引用它的文档**。
第三行是残留风险,但比行号漂移轻一个量级。

**迁移成本接近零:** 原型已证明工具能从行号反推封闭符号,27 处改写由机器
生成 diff、人过目,不是人工逐条改 —— 也就不会在改的过程中又引入新的错。

**验收:** `test_docs_consistency` 用符号存在性检查取代行数绊线;
用例覆盖"引用了不存在的符号会红"、"插入无关行不会红"、"函数改名会红";
`CITED_LINE_COUNTS` 及其在 contributing 的说明一并移除。

### ⚠ 第三轮 W6 落地了多少 —— 三项没做,别把它当已完成划掉

**做了的:** 引用形式改成 `` `<路径>#<符号>` ``(含类内方法与嵌套函数、
重名要写限定名);行号形式与区间形式都被拒并给出应改成的符号;两类豁免
(围栏、目标文件不存在)与 `@<sha>` 历史快照;全仓引用迁移完毕;
`CITED_LINE_COUNTS` 连同它在 `docs/contributing.md` 的说明一并移除。
检查在 `tests/conformance/test_docs_consistency.py` 的 `TestSymbolReferences`,
10 条。

**没做的三项,都不在 W6 的验收标准里:**

1. **「③ 可导航」没做。** 上面写的是"用 markdown 链接语法承载",实际形式
   是纯文本 `` `<路径>#<符号>` ``,点不开。要做成链接得再定一次锚点语法
   (`.py` 文件在 GitHub 上没有符号锚,只有 `#L<行号>` —— 而那正是这一条
   要消灭的东西)。
2. **「插入无关行不会红」没有用例。** 10 条里没有这一条。它现在是
   **结构性成立**的(检查根本不看行号),但"结构性成立"在这个仓库里不算
   防护 —— 见 W2 那条决策记录。
3. **省掉文件名的裸 `:行号` 续引仍然不在扫描范围内**,而且防护是**净减少**的
   (旧绊线按被引文件行数触发,对它们还有间接覆盖)。实测 66 处,
   见开放条目第 14 条。

## P1-13 `request` 代办通道:跨边界的机械改动不该走一次打回

**来源:** 两轮真实运行的卡住统计。6 次打回里 **4 次是协议在正确工作**
(发现了真缺陷:契约没写的第三种形态、修复没有测试守着、契约条款零测试
守着、用例分不出 stdout/stderr),**2 次是机械性的**(跨边界常量挡住交接)。
人类为卡住手工介入 3 次,其中 **2 次是机械性的**(`INSTALL.md` 行号、
样板 `.gitignore`)。

**问题:** 那 4 次机械性卡住的共同形状是 **"知道该改成什么,但没权限"** ——
dev 甚至已经把正确值算好写进异议里了。用一次完整的异议往返(两个回合)
去传递一个数字,而且**要消耗打回额度**(第二次强制写决策、第三次撞死锁闸),
成本与内容完全不匹配。

**这不能靠"消除卡住"解决,也不该靠第三个 agent 解决。** 决定性的卡住
(契约含糊、真实分歧)必须保留 —— 目标若是"永不卡住",它会先卡不住那
4 次真缺陷。而第三个 agent 读的是同一份含糊的契约,不会比前两个更清楚,
只会多一个意见、多一个推卸责任的去处;要它能解决 `INSTALL.md` 那类,
还得给全路径写权限,那等于在写权限边界上开后门。

**提议:**

```
pair.py request "<改什么,含具体的值>" --reason "<为什么我改不了>"
pair.py fulfill <id>
```

- `request` 记进 state,并进提交正文 —— 对方在 `inbox` 里必然看到
- 另一方在**自己的回合**里自己动手改,然后 `fulfill` 标记闭环。
  **`fulfill` 是记账,不是执行** —— `request` 的内容是自然语言,脚本没法
  执行它;更重要的是,让脚本代 agent 改它自己路径下的文件会绕过
  "自己写自己的路径"这条原则。**不要实现成 patch 应用器。**
- **不改变 phase,不计入 `changes_count`** —— 它不是打回,不消耗额度
- 双方都无权限(孤儿路径)时升给人类,附**可直接执行的 diff**

**与现有设计的冲突:** 两处,都必须写死,否则它会变成绕过评审的后门。

**① 与规则 1 的边界。** 规则 1 是"认为对方写错了 → 写进 `docs/reviews/`,
用 `handoff changes` 打回,由对方自己改"。`request` **不得用于表达分歧** ——
它只适用于"我算出了一处改动,它落在你的路径,但这不是你写错了"。
判据落在 `--reason` 上:它要回答**"为什么我改不了"**(路径归属),
不是**"为什么你错了"**。`fulfill` 的一方随时可以拒绝,拒绝就退回正常的
打回流程 —— 这条出路必须留着,否则 `request` 就成了单方面指派。

**② 不得用来规避死锁闸。** 因为它不计入 `changes_count`,一方可能用
连续 `request` 表达本该是打回的分歧。缓解:`report` 统计 request 频次与
被拒率 —— **被拒率高说明它正在被当成打回用**,那是误用的信号。

**验收方式:** 按 `contributing.md` 的五步走。用例覆盖:`request` 不改变
phase 与 owner、不计入 `changes_count`;`fulfill` 只能由路径归属方执行;
非归属方 `fulfill` 被拒;request 内容进提交正文;`report` 出现 request
频次与被拒率两行。变异点至少两个:拆掉"不计入 changes_count"、
拆掉 `fulfill` 的归属校验。

## P1-14 两个高影响文件零测试覆盖,划归 dev 之后风险上升

**来源:** 第三轮开工前的孤儿划归审查。

**问题:** 划归把 33 个孤儿分给了角色,其中两个文件**内容零测试覆盖**,
而它们此前正是靠"谁都改不了"才没坏:

- **`pyproject.toml`** —— `tests/conformance/` 里确实引用它,但那是把它当
  **栈探测的标志文件**用的假 fixture(`"[project]\nname = \"demo\""`),
  **不校验真实文件的内容**。`force-include` 那行决定 skill 目录进不进 wheel,
  改坏了没有任何东西会红,而 `pair init` 分发的就是它。
- **仓库根的 `.gitignore`** —— `test_v1_shipped.py` 查的是
  `examples/demo-project/.gitignore`,不是根目录这份。删掉 `__pycache__/`
  那行,`.pyc` 会进 git 并落到对方路径下 —— **那正是前两轮撞过的跨角色污染**。

**提议:** 补两条内容校验,都很便宜:

1. `pyproject.toml` 的 `force-include` 指向 `.agents/skills/pair-protocol`
2. `GITIGNORE_LINES` 的每一行都在仓库根的 `.gitignore` 里
   (照抄 `test_v1_shipped.py` 已有的那条,只换目标文件)

**与现有设计的冲突:** 无。两条都落在 tester 路径,是既有检查的同类扩展。

**验收:** 各一条用例;变异点各一个(拆掉 `force-include` 校验、
拆掉根 `.gitignore` 校验)。

## P2-5 死锁时的第三个会话:只读的材料整理

**来源:** 2026-09 设计讨论;`prior-art.md` 的 Adversarial Review
(三 agent 里第三个角色是 **critic,审计评审本身**,不是 fixer)。

**问题:** 死锁闸触发后(同一工作项三次打回),协议停止轮转交给人类,
而人类要读完两个 agent 的全部评审、异议、笔记与决策才能裁决。两轮实测下来
这些材料确实完整,**成本不在信息不足,在阅读量**。

**提议:** 一个**只读**的第三会话,仅在死锁闸触发后启动:读全部材料,
产出一份带建议的决策包给人类。**不给写权限、不做决定、不进轮转。**

**与现有设计的冲突:** 引入第三个模型的直接风险是稀释责任 —— 前两个 agent
会把"谈不拢"当成可以外包的事。所以它的启动条件必须**严格绑定死锁闸**,
不能由 agent 自行召唤。另外它的建议**不具备裁决效力**,人类可以完全不采纳;
一旦它的建议被当成裁决,协议就从"人类是时钟"退化成"第三个模型是时钟"。

**排期:** **排在第一组(P0-4/P0-7/P1-12)与 P1-13 之后。** 那几条落地后,
机械性卡住基本消失,死锁闸触发的绝对次数会降一个量级 —— 到那时再判断
这个会话值不值得引入。**现在做等于为一个正在缩小的问题建基础设施。**

**验收方式:** 无脚本改动(它在协议之外),所以不走五步纪律;
验收标准是一次真实的死锁演练:人类拿到决策包后的裁决时间,
与两轮实测里直接读原始材料的时间对比。

## P1-4 status 注入的可审阅化

**来源:** BMAD 的 **story 文件自包含**设计 —— Dev agent 只读 story 就能干活,
不需要回溯上游文档。

**问题:** 本项目的 `status` 注入(笔记全文 + 相干决策)是**运行时拼出来的**,
只存在于那一次终端输出里。人类想知道"这一回合 agent 到底看到了什么"
只能自己再跑一遍 `status`,而那时状态可能已经变了。

**提议:** `status` 把注入内容同时落盘到 `.pair/.last-brief.md`(gitignore),
出问题时人类可以直接看到当时的输入。零协议语义变更,纯可观测性。

顺带解决一个真实痛点:agent 说"我没看到那条决策"时,现在无从对质。

## P1-5 同一模型分饰两角要写进文档  ✅ 已落地

**来源:** [aider architect/editor](https://aider.chat/2024/09/26/architect.html) ——
Claude 3.5 Sonnet **自己配自己**也从 77.4% 提升到 80.5%。收益部分来自
"一次只干一件事",而不只是来自"两个不同厂商"。

**问题:** README 的开头"让**任意两个** AI coding agent…… 结对开发"容易被读成
"必须是两个不同的 agent"。实际上两个终端跑同一个工具、同一个模型完全成立 ——
而且这是**上手成本最低的入门配置**,应该被明确推荐。

**提议:** README 的"启动两个 agent"一节加一句显式说明,并把
"同工具同模型、两个终端、靠 `PAIR_ROLE` 区分"列为**推荐的起步配置**。
这是纯文档改动,零成本,直接降低上手门槛。

**实际落地时收窄了措辞:** aider 的 architect/editor 是**同一回合内的流水线**,
两个角色不互相评审、没有独立的产物所有权。所以那条实证支持得起"分工的收益
同模型也成立",支持不起"对抗性评审的收益同模型也拿得到"。后者没有证据,
它正是 P1-1 的打回率要测的东西 —— 写成结论就等于把待测假设当成了已知。

# P2 — 扩面,做之前先确认真的有人要

## P2-1 worktree 拓扑升为一等公民

**来源:** container-use / Conductor / Crystal / Emdash / Mux 这一整类工具。

**现状:** 拓扑 B(分离工作副本)只有 `"sync": true` 加 pull/push,
建 worktree、建分支、分配角色全靠人手动。

**提议:** `pair.py init --topology worktree` 自动:建 `pair/tester`、`pair/dev`
两个分支与对应 worktree,各写好 `.pair/whoami`,`sync` 置 true,
并打印两条可直接粘贴的启动命令。

**为什么是 P2:** 拓扑 A(同目录)是本协议的**优势场景** —— 路径切分让它成立,
而这正是本项目相对 worktree 系工具的差异点。把 B 做漂亮属于补齐,不属于强化。

## P2-2 通过 MCP 打开"不能跑 shell"的边界

**现状:** 明确不支持不能执行 shell 的 harness —— 执行层跑不起来,强制力归零。

**提议:** 把 `status` / `claim` / `handoff` / `inbox` 暴露成一个 MCP server
(仍然只是 `pair.py` 的薄封装,协议逻辑不复制)。GUI 与云端 harness
只要支持 MCP 就能接入。

**风险:** 违反"CLI 不含协议逻辑"的同类约束 —— MCP 层必须同样是纯转发,
一旦它开始自己判定就会漂移。**先写清楚这条约束,再动手。**

## P2-3 与 TDD Guard 叠加使用的说明

TDD Guard 保证"一个 agent 按 TDD 的顺序写代码",本协议保证"两个 agent
各写各的、互相验收"。两者不冲突,理论上可叠加:dev 侧挂 TDD Guard,
能在**回合内**就拦住硬编码和 over-implementation,而不必等到 tester 评审。

值得写一份 `docs/interop-tdd-guard.md`,但要先实测冲突面
(TDD Guard 会不会拦住 tester 写测试的动作)。

## P2-4 Rust:明确不做,或换机制

目录切分对 `#[cfg(test)] mod tests` 物理上不成立。唯一可能的路是
**块级 diff 检查**:允许双方写同一文件,但 tester 只能改 `#[cfg(test)]` 块内、
dev 只能改块外。这需要一个 Rust 感知的 diff 分析器 —— 成本远高于收益,
而且会在协议里引入第一个语言特化的组件。

**建议保持"不支持",并在文档里给出迁移路径**(把测试移到 `tests/` 集成测试目录)。

### 1. `2a32b5f` 新增的基线预检闸零测试覆盖

`tests/conformance/mutation_check.py#precheck_no_baseline` 与
`tests/conformance/mutation_check.py#isolated_copy`,在
`tests/conformance/test_mutation_tooling.py` 里**0 命中**;作为对照,
同一次提交要守的另一道闸 `baseline_verified` 有 **5 处**命中。14 条全绿**不等于**新闸被测住:
下一次重构可以把它整个删掉,套件照样 14/14。

它守的正是本项目最怕的失败模式:基线本来就红的环境里,回退路径的判据只有
rc≠0,分不清失败来自变异还是来自环境,于是每条变异都被判成"抓到",报出一个
恒真的 70/70 与退出码 0。而它自己没有测试。

**为什么至今没被测住 —— 成本。** `precheck_no_baseline` 内部硬编码两件事:
`isolated_copy(tmp)`(从 `REPO` 整仓 copytree)与跑
`dst / "tests/conformance/run.py" -j jobs`(全量套件)。端到端调它一次等于
跑一次全量。实测(本机 8 进程):

| 动作 | 实测 |
|---|---|
| `isolated_copy` 等价的 copytree(排除 `.git`/`__pycache__`) | 0.02~0.03s |
| 整仓副本跑一次全量(`run_baseline` 自己打印的值) | 44.3s |
| 极小假仓库(1~2 个用例)跑 `run.py -j 8` | 0.10s |
| 当前 `test_mutation_tooling.py` 全 14 条 | 0.17s |

**copytree 不是瓶颈,跑全量才是。** 直接把端到端预检加进 conformance 套件,
套件会从约 47s 涨到约 91s(接近翻倍),而变异检查的默认路径本来就要付这
44s 一次 —— 同一份成本付两遍,换来的额外覆盖只有"子进程真的起起来了"
这一层,不值。

**候选 A:参数化 `precheck_no_baseline(jobs, root=None)`,`root` 非空时跳过
copytree、直接用给定目录。** 测试侧造一个极小假仓库(`tests/conformance/`
下放一份从真仓 copy 来的 `run.py` 加一个必败用例),喂绿/红两种,断言返回
契约。成本 0.10s × 2 = **0.2s**。
守住:`precheck_no_baseline` 的全部内部逻辑 —— 设 `PAIR_MUTATION_RUN=1`、
起 `run.py` 子进程、`_ids` 解析输出、`(rc, fails, text)` 三元组契约。
守不住:真实的 `isolated_copy` 被 `root` 绕过了,所以"副本与判定环境同构"
这一层测不到 —— 而那正是这道闸的关键前提(`:599-602` 用了四行 docstring
解释它)。另需一条测试单独钉 `isolated_copy`。
代价:改签名(禁改区),并同步 `:544` 的调用点。

**候选 B:测试侧 monkeypatch `MUT.isolated_copy` 让它返回极小假仓库。**
不动产品代码,成本同样 **0.2s**。守住的范围与候选 A 相同,守不住的也相同,
但多一层脆弱:桩打在模块属性上,若实现改成内联 `shutil.copytree`(不再调
`isolated_copy`),桩会**静默失效**,那条测试就变成在真仓上跑全量(44s)
或直接失败。用一个会静默失效的桩去守一道"防止静默假绿"的闸,方向不对。

**候选 C:把判定抽成纯函数,照 `baseline_verified` 的既有先例。**
判定现在嵌在 `main:545` 的 `if rc != 0 or fails:` 里,无法单独调用。而
`baseline_verified`(`:427-436`)的 docstring 已经写下本仓的处理惯例:
"抽成纯函数是为了能被测住:它是这套缓存机制里唯一一处判断错了就会让
整个检查变成恒真的地方"。预检的判据是同一类东西,应当同办。成本**微秒级**。

**推荐:候选 C,再加两条不需要改签名的补充,共三层。** 不选 A/B 的理由是
它们都为了覆盖"子进程起起来了"而付 0.2s,却**恰好绕开了最该守的那层**
(同构性);而 `_ids` 解析已被 `TestCacheStalenessIsDetected`(`:39-55`,
走 `run_suite`,`:415` 同样是 `fails = _ids(text)`)间接覆盖。

**层 A —— 判定真值表(纯函数)。** 在 `mutation_check.py` 加

```python
def precheck_verdict(rc, fails):
    """预检放行吗 —— rc=0 且失败集为空,两个条件缺一不可。"""
    return rc == 0 and not fails
```

`main:545` 改成 `if not precheck_verdict(rc, fails):`。测试断言真值表,
其中最关键的一条是 **`precheck_verdict(0, ["x.Y.z"])` 必须为 False**:
rc=0 但 `_ids` 抓到了 FAIL 行也要拒。这条最容易被写漏,因为直觉上
"rc=0 就是绿";而它恰好是并行运行器最可能出现的形态(某一片失败,
汇总行却仍然打印)。

**层 B —— 同构条件的源码断言。** 照 `tests/conformance/test_v1_shipped.py#TestDriverHasNoProtocolLogic.test_不碰_git`
的
`test_不碰_git` 先例(读源码 `re.findall` 断言意图),钉三条:
`precheck_no_baseline` 的函数体里出现 `isolated_copy(`;出现
`PAIR_MUTATION_RUN`;`isolated_copy` 的 ignore 模式里有 `".git"`。
成本微秒级。它守的是**设计意图不被悄悄改掉** —— 有人把预检挪到真实仓库里

源码"那条混进归因前提),这条就会红。

**层 C —— `isolated_copy` 的真实行为。** 直接调 `MUT.isolated_copy(tmp)`,
断言副本里 `.git` 与 `__pycache__` **不存在**、`pair.py` 与
`tests/conformance/run.py` **存在**。成本 **0.03s**(实测)。
这是层 B 的行为对证:源码断言说"ignore 里有 `.git`",行为断言说"副本里
真的没有 `.git`" —— 少任何一层都能被绕过。

**规模:** `mutation_check.py` **+4~6 行**(一个纯函数加一处调用点改写);
`test_mutation_tooling.py` **+40~50 行**(3 条测试,14 → 17 条);套件耗时
**+0.03s**(47.5s → 47.5s,实测不可辨)。

**一条必须一并付的后续成本:** `fingerprint()`(`:377-386`)哈希的是
`pair.py` 加 `tests/conformance/*.py` 全部,**包含 `mutation_check.py`
自己**。所以层 A 与这三条测试一旦落地,缓存的 `baseline` 指纹立刻失配,
需要跑一次默认路径刷新(约 70s)。这不是缺陷,是既有设计,但排期要算进去。

**若不接受动 `mutation_check.py`(连抽纯函数都不许)**,退化方案是只做
层 B 加层 C:纯测试侧、0 行产品代码、+0.03s。守不住判定真值表 —— 但那是
`main` 里的一行 `if`,漂移风险低于"同构条件被悄悄改掉"。

### 2. `MAX_CACHED = 1` 与缓存里实际抓手数漂移

三方口径一致:`tests/conformance/mutation_check.py#MAX_CACHED`(值为 1)、
紧挨它上方那段设计注释、`docs/contributing.md:71-74` 的"每个变异点只记**一个**抓手"。
但实测 `tests/conformance/mutation-cache.json` 里 70 条的抓手个数分布是
`{1: 46, 2: 9, 3: 7, 4: 8}`,即 **24/70 条有 2~4 个抓手**,与"只记一个"不符。

**成因:** `MAX_CACHED > 1` 的时代留下的历史数据。

**不会自愈:** `:661` 的写回条件是
`if status == "caught" and note != "缓存命中"`,快路径命中时 `note` 正是
"缓存命中",于是 `fresh` 保持 `dict(cache)` 原样;而只要 catcher 还有效就
一直命中,所以永远走不到重写那一行。实测印证:`ea5344e` 那次刷新
`git diff --numstat` = `1 1`,只有 `baseline` 一行变,catchers 一字节未动。

**影响不致命:** `loaded`(`:422-423`)校验的是"请求了几个就跑了几个",
多记几个只会让失效判定更严格 —— 更容易回退跑全量,不会漏抓变异。代价是
白跑,不是假绿。

**推荐处置:一次性归一化**,把每条 catchers 截到 `[:1]` 再写回,随后重跑一次
`mutation_check.py` 默认路径自证。重跑本身就是验证:若某条截断后留下的那
一个抓手不再抓住它的变异,快路径会自动回退跑全量并重写该条
(`:496-499` 加 `:661`),输出里会出现"缓存已失效,重建";全绿且零回退就说明
70 条截断后依然成立。

**备选:** 放宽 `:661`,让命中时也按 `MAX_CACHED` 重写 —— 会自愈,但把
"快路径命中说明缓存已经是对的"这条注释里的前提改掉了,而且要把 24 条一次
刷齐就得跑全量。

### 6. `cmd_handoff` 收尾处两个 `if` 无互斥,同屏打印相反指令

`handoff` 收尾处有两个**独立的、非 elif 的** `if`:

- `if full_failed:` 打印门禁绿但全量红的横幅,里面写着
  **不要告诉人类"完成"**;
- 紧随其后的 `if plan_all_done(root, cfg):` 打印"PLAN 里的工作项已全部
  完成。项目结束。"与"请向人类报告完成,不要继续轮转。"

于是"最后一个工作项完成 + 全量红"那一次交接里,agent 会在同一屏先读到
不要告诉人类完成、五行后读到请向人类报告完成,而退出码是收尾那句
`2 if full_failed else 0` —— 也就是 2。**两条指令互相否定,退出码站在
前者那边。**

**为什么它在严重度序里仅次于第 1 条:** `pair.py` 是**活的分发物** —— 它随
wheel 与 `pair init` 扩散到消费项目,不像本仓文档只影响这里。一个照着
屏幕办事的 agent 有一半机会挑错那条,而挑错的方向正好是本项目最怕的
那个:向人类宣布"完成"。

**修法:** `:1799` 改成 `if plan_all_done(root, cfg) and not full_failed:`,
并给 else 分支补一句:全量红时项目算不算结束由人类决定。

**本轮不改的理由(人类裁决 4):** 未授权改 `pair.py`。任何 `pair.py` 改动
都会让 `tests/conformance/mutation-cache.json` 的基线指纹失配,得重跑
约 70 秒并追加一次缓存提交。文档侧已在 `docs/design-philosophy.md` 的
"完成有明确定义"那段与 `docs/command-reference.md:129` 加了限定句,
说明那句提示是 **PLAN 维度**的结论、全量红时以退出码 2 与"不要告诉
人类完成"为准。**代码侧矛盾先于本轮存在**,本轮只是把它写成了无条件
规则 —— 限定句消除的是本轮引入的那部分。

### 8. `mutation_check.py` 里解释归因前提的那段注释说得过强

那段注释写的是:预检的失败集"为空则两条路径的 rc≠0 都**必然**由变异
引起"。成立需要的条件比"必然"多:

- 预检是**一次**采样 —— 一个副本、一个时刻;
- 而 `check_one` 之后要在 70 个**另建的**副本里各跑一次;
- 运行器还不同:预检用并行 `run.py -j <jobs>`(在
  `tests/conformance/mutation_check.py#precheck_no_baseline` 里),而
  `check_one` 的判定用串行 `unittest`(快路径 `unittest -q <ids>`,回退
  路径 `unittest discover -f`);
- `loaded` 校验的是"请求了几个就跑了几个",挡不住"同一个
  测试在预检副本里绿、在某个 `check_one` 副本里红"。

所以一个负载敏感或时序敏感的测试完全可以预检绿、某个副本红。此时
rc≠0 **不是**变异引起的,却会被记成 `caught` —— 高估了测试集的拦截力,
而且这条结论还会被写进缓存、当以后的快路径依据(`:661-664`)。

**成立的是:**"在测试确定、环境不变的前提下可归因",不是"必然"。

**修法:** 降级注释措辞并把前提写出来。它不改行为,但一句过强的注释会
让后来者以为这里不需要再复核 —— 而第二道闸的全部合法性正挂在归因
可靠这件事上。

> 「开工前校验的产物与退出码」。有差异那条路径上 `git commit` 同样不带路径,

### 17. `setup_verified` 一旦为真就永不复位，契约改了也不会要求重读  ✅ 已解决(第五轮 W13)

`cmd_verify_setup` 结尾把 `state["setup_verified"]` 置为 `True`,而**全仓
没有任何一处把它置回 `False`**。`claim` / `handoff` / `status` 三处都只读
它。于是:

**第三轮结束后契约新增了三节(术语、文档改动要带理由、冻结文件改成带声明
才放行),而 `setup_verified` 仍然是 `True` —— `claim` 会直接放行,
没有任何机制要求任何一方读过那三节。**

第四轮的计划里写着"开工前重跑 `verify-setup`",但那是**散文规则**,
正是这个项目一向不信任的那种。这道门是协议自称唯一会致命的失败模式
(契约歧义)的主要防线,而它在契约变更之后自动失效。

**修法:** `contract_file` 的 blob sha 变了就把 `setup_verified` 置回
`False`。状态里已经有 `contract_sha` 这个字段,但它的生命周期绑在工作项上
(`claim` 时记、完成时清),要另存一个"上次通过校验时的契约 sha"。
和开放条目 12、13 同属 `verify-setup` 的一组缺陷,建议一起做。

> **落地时与上面的修法不同(第五轮 W13 加,原文保留)**:没有把 `setup_verified`
> 置回 `False`。唯一能发现"契约变了"的时机是 `claim` 的拒绝路径,而那是 `die`;
> `status` 只读、`whose-turn` 承诺始终 exit 0 —— 塞一个写入者会让只读命令产生提交、
> 撞上"状态文件任何未提交改动一律判篡改"。实际做法是**按角色**记下校验时契约的
> **工作区内容** sha(`setup_verified_contract`),`claim` 现场比对。
> 见契约「校验与沉淀的有效期」。

### `mutation-cache.json` 的基线指纹失配  ✅ 已解决(原第 9 条,`ea5344e`)

原缺陷:缓存的 `baseline` 是 `2b25c4be0bd9ae2b`,而 `fingerprint()` 算出来
是 `65deef448105619a` —— 失配,快路径一直用不上;而 `--no-baseline` 会被
`2a32b5f` 新加的预检闸拒掉,所以失配**不会自愈**。唯一的刷新入口是默认
路径:`run_baseline()`(`:571`)跑绿之后执行 `:589` 的
`save_cache(fingerprint(), load_cache()[1])` —— 只刷指纹、原样沿用旧
catchers;`:663-664` 的写盘条件带 `verified`,而 `verified` 在指纹失配时
是 `False`。

**最终事实(`ea5344e`):**

- 指纹 `2b25c4be0bd9ae2b` → `65deef448105619a`,与当前树的 `fingerprint()`
  相等。
- `catchers` **一个字节未动**:`git diff --numstat` = `1 1`,70 个键、与
  `MUTATIONS` 的双向差集 0/0、`old` 串失配 0 处。所以**这 70 条"变异点 →
  抓手"的映射是原样沿用旧缓存,不是这一轮重新验证过的** —— 走的是 `:589`
  那条路径,`load_cache()[1]` 就是把旧 catchers 原封不动取出来再写回去。
- 70 个变异点全部 caught,**零条走回退全量**("缓存已失效,重建"与"首次
  全量"均为 0 处),结论行 `全部被测试抓到。测试集确实有拦截力。`
- 实测:基线 44.3s、变异阶段 26.0s、整条命令 70.4s(8 进程、缓存全命中)。

**为什么拖到这一轮才刷得动:** 默认路径要求基线先全绿,而基线被下面那条
环境依赖锁在 265/266。`6f7afe0` 修掉那个依赖,基线第一次在本机 266/266
全绿,这条的前置条件才成立。

**原条目里两处表述已过期,订正在此:**"在真实终端(全局 git 身份可用)跑"

### `test_v1_shipped` 的环境依赖  ✅ 已解决(原第 10 条,`6f7afe0`)

`test_开工前校验只卡在契约审查结论那一步`(`:64`)在没有 git 身份的机器上
必红,把基线钉在 265/266,并因此锁死上面那条的刷新入口。

**病灶不是"env 被剥离"。** 6 组受控实验:在
`{"PAIR_ROLE": "dev", "PATH": "/usr/bin:/bin"}` 这个剥离 env 下,四条注入
身份的路径**全部 rc=0** —— `git -c user.name=… -c user.email=…`、
`GIT_CONFIG_GLOBAL` 指向含身份的临时文件、样板仓库的 `.git/config` 里写
仓库级身份、`HOME` 指向含 `.gitconfig` 的目录。

**病灶也不是沙箱。** 升级权限后的只读探测,沙箱内外逐项一致:`hostname` 与
`hostname -f` 都返回 `Mac`;`scutil --get HostName` = `not set`;
`socket.getfqdn()` = `Mac`(不含点);`getaddrinfo` 的 `AI_CANONNAME` =
`mac`;`/tmp` 里新建的临时仓库跑 `git commit`,沙箱外同样 rc=128。

**真正的根因是一条链:** hostname 不是 FQDN → git **主动拒绝**从
`username@hostname` 自动推导 email(它拼出 `xbase@Mac.(none)` 然后拒绝用)
→ 各级配置又没有任何 `user.*` 兜底(`git config --list --show-origin` 里
零条 `user.*`;`/etc/gitconfig`、`/opt/homebrew/etc/gitconfig`、
`/usr/local/git/etc/gitconfig` 三个系统级文件均不存在;`~/.gitconfig` 存在
但只有两个 credential 段)→ 任何 commit 永久 rc=128。这是这台机器的持久
状态,不是环境波动。

**一并订正两处旧结论:**

1. "在真实终端里应当通过"—— **错**。本机真实终端同样红,因为
   `scutil --get HostName` 就没设置过。
2. 第五轮交接时给的"选项 b:`GIT_AUTHOR_*`/`GIT_COMMITTER_*` 环境变量
   前缀"作为让基线变绿的手段 —— **不成立**。实测它对**直接调用**
   `make-demo.py` 有效,但 `tests/conformance/test_v1_shipped.py:73@c210ba6`
   传的是整个 `env=` 字典
   (**整体替换**,不是合并),环境变量到不了 `pair.py`。只有仓库级配置
   (已采纳)或全局配置才行。

**同源铁证(照抄既有约定的依据):** `tests/conformance/harness.py:204@d6bc8cf`
与 `examples/make-demo.py:83@d6bc8cf` 的
commit message `"chore: 装上结对协议"` **逐字相同**,git 命令序列同为
`init → (config) → add -A → commit`。harness 就是 make-demo 的测试镜像,
只是它多写了身份(`:200-201`)—— **这正是缺陷本身**:镜像的一半有身份,
另一半没有。

**最终采纳的方案:** 在 `make-demo.py` 里加 `ensure_identity(target)`
(`:22-60`),`git init` 之后、`add`/`commit` 之前调用(`:80-84`),写仓库级
`user.name=conformance` / `user.email=conformance@test`,取值照抄
`tests/conformance/harness.py:204-205@8cc32c8` 与 `:376-377`。一处改动解决
两级失败,因为 `.agents/skills/pair-protocol/scripts/pair.py:2855@e742a67` 的 `cwd=root`
来自 `repo_root()`(`git rev-parse --show-toplevel` 从进程 cwd 求得),
而 `tests/conformance/test_v1_shipped.py:73@c210ba6` 的 `cwd=str(proj)` 就是 make-demo 的输出目录;仓库级身份既不依赖 `HOME`
也不依赖环境变量,所以能穿过那处 env 剥离。

**两处有意偏离既有约定:**

- **条件式,不是无条件。** 探测用 `git var` 的退出码,只在探测失败时才写
  (`6f7afe0` 当时只探 `GIT_AUTHOR_IDENT` 一条;`72ab252` 把它扩成
  `GIT_AUTHOR_IDENT` 与 `GIT_COMMITTER_IDENT` 两条,任一失败就写 ——
  理由见 `docs/contributing.md` 的身份兜底那段)。harness 无条件是
  可接受的 —— 它的目录来自 `mkdtemp`
  (`:198`)、由 `addCleanup` 注册 `shutil.rmtree`(`:206-207`、`:323-325`),
  生命周期完全在测试进程内;而且测试要的就是不受宿主机影响的确定身份。
  `make-demo.py` 不同:它面向用户,产出目录可能被长期留存,无条件写假身份
  会**静默把用户后续所有提交错误归属**,比响亮地 rc=128 更坏。
- **没有照抄 `commit.gpgsign false`**
  (`tests/conformance/harness.py:206@8cc32c8` 有、`:377` 没有)。
  理由与代价见开放条目第 3 条。

**验证:** 266/266 全绿(此前 265/266)。三组反向验证确认条件式真的是

author 仍是人类注入的那一个;两个 ident 都注入时兜底身份 0 条、人类身份
完整保留。

### P0-5 必须拆成四步,否则一个工作项做不完

它包含新阶段机、提案目录、签字、批准命令、额度、`report` 指标 —— 按两轮
实测的**每工作项约 10 回合**,整条塞进一个工作项会失控。拆法:

| | 内容 | 能否独立 |
|---|---|---|
| **D1** | 提案目录与新路径类别(`proposal_paths`) | **能** —— 不碰阶段机 |
| **D2** | `discuss` 阶段的进入与退出、工作项挂起与恢复 | 依赖 D1 |
| **D3** | 双方签字、人类一条命令批准、提升为 PLAN/CONTRACT 改动 | 依赖 D2 |
| **D4** | 额度(死锁闸同构)与 `report` 的 discuss 频次 | 依赖 D2 |

**D1 值得先做而且能立刻还债**:它正是那个"提案目录不能直接进
`shared_paths`"的坑的解法(那个键被五处逻辑依赖,并进去会让"写了一份提案"
被算成"异议落到纸面"),同时给 P0-7 里推迟的 `artifact_paths` 一个统一的
落点 —— 到那时"副产物"与"提案"是同一类问题的两个实例,可以一起设计。

**注意这与"P0-5 不能拆小"不矛盾。** 那句话说的是**不能跳过它** ——
P0-6/P1-9/P1-11/P1-15② 想绕开 discuss 单独做,都得先把签字批准那套机制
建一遍,那就是把 P0-5 做了只是没有名字。这里说的是**它自己内部要分步**。

### 每轮装 2–3 个工作项

两轮实测:`docs/dogfood-run-2.md` 记的**每工作项约 10 回合**(含打回)。
所以一轮 2–3 项约 20–30 回合,与前两轮的实际节奏一致。上面的分轮就是按
这个预算切的,不是按主题凑的。

### 几条排序理由(保留)

**关于"开发过程中不能出现卡住":** 两轮实测,6 次打回里 **4 次是协议在
正确工作**(各发现一处真缺陷),只有 2 次是机械性的;人类 3 次介入里 2 次
机械性。**决定性的卡住必须保留** —— 目标若是"永不卡住",它会先卡不住那
4 次真缺陷,而"看起来完成了其实是废的"正是这套协议最怕的东西。

**为什么第三轮那两条排最前:** 它们是唯一"不依赖任何设计决定"的一组 ——
纯粹是配置覆盖面、文件分类与引用形式的缺陷,证据是四条决策记录。而且
**在它们落地之前,后面每一轮都会继续踩同样的坑**:这两轮已经为此烧掉一次
dev 的 impl 回合、一次 tester 的 spec 回合,以及四次人类手工介入。

**P1-12 编号是 P1 却排最前**,因为本文件的编号按"不做会让协议核心主张站不住"
排,而它不动核心主张;但它的成本/收益比是全表最高的一条。

**P0-1 的优先级在两轮实证后继续下调。** 两轮四次打回**没有一次是红绿发现的**:
两次是评审读代码读出来的,两次是手动变异跑出来的。用例级红绿对"契约条款
没有测试守着"和"用例看起来在测其实测不到"这两类**天然失明**,而它们是
全部四次打回的共同形状。
