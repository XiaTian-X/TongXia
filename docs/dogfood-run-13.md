## 两次打回:都是"测试看起来在守、其实分不出对错"

与第七、九轮反复出现的形状相同,这次两次都由 dev 在 review-test 里用错误实现挖出来:

- **W1**:`tests/test_slugify.py:25` 的 `slugify("a \t\n b")`,tab 与换行两边都有普通空格 —— 只把空格当分隔符、
  把 tab 与换行当标点丢掉的实现也得 `"a-b"`,全套 7 条照绿。tester 补了"7 个空白字符各自作唯一分隔",
  其中 `\x1c`、`\x1f` 是它**自己多加的**:按 `str.split()` 算空白却不在 `string.whitespace` 里,
  用 `string.whitespace` 实现的版本因此也会红 —— dev 自己也没想到那一种错法。
- **W3**:测试分不出契约规定的 `str.lower()` 与 `str.casefold()`。dev 把实现换成 `casefold()`,全套照绿;
  两者在 296 个字母数字上结果不同(`"Straße"` 该得 `"straße"`,`casefold` 给 `"strasse"`;`ς` 该保留,`casefold` 变 `σ`),
  而 W1、W3 的输入里一个都没有。tester 补了 `Straße`、`ß`、`ς`、`µ`、`ſ`、大写 `ẞ`。

**两次都走了第六轮 W17 的捷径**:只涉及测试的打回、契约没变,提交正文是 `phase=spec -> review-test`,
跳过了重写实现与审实现两步。dev 第一次以为要重走实现,实际不用。这是 W17 在独立运行里第一次被真实触发。

## 交给人类的一件事:NFC 会把某些字母拆开,而契约丢掉拆出来的组合符

tester 在 W3 挑出、dev 在复审时同意,两边都**有意没写进测试**:

- `slugify("क़")`(U+0958)得 `"क"` —— U+0958 是 NFC 的组合排除字符,NFC 把它**拆**成 `क` 加组合符 nukta
  (U+093C,类别 Mn),而契约规定"其余非字母数字字符直接丢弃",组合符被丢掉,**结果变成了另一个字母**。
  编排者核实属实。
- `slugify("q" + U+0301)` 得 `"q"` —— 没有预组合形式,重音被丢掉。第九轮也挑出过这一类,当时判为契约锁死、照原样冻结。

两者都是契约"先按原字符判定、其余丢弃"的直接推论。但后者只是少了装饰,**前者改了字** ——
对印地语这类文字的用户是真实的错误。更合理的规则是"紧跟在保留字符后面的组合符一起保留",
这会改变 slugify 的核心行为,样板契约与测试都要跟着改。**建议进路线图,作为样板契约的缺陷。**
