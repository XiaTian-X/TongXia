# 第一次真实运行:用本项目结对开发本项目

> 2026-09。工作项取自 [improvements.md](improvements.md) 的 P1-4
> (`status` 注入落盘)。**目的不是把功能做出来**,是看协议在真实使用里
> 会不会自己把自己卡死,以及两个 agent 会不会互相点头。

## 结论先说

协议**跑得起来**,而且在最该起作用的地方起了作用:两次打回都是真缺陷,
都精确到行,都附了复现步骤。但它也**在一条主路径上把自己锁死了一次** ——
那次死锁锁住的是一个正确的评审决定,没有真跑一轮绝不可能发现。

功能只完成了三个工作项里的第一个。**产出主要不是代码,是结论。**

## 数字

| 指标 | 值 | 说明 |
|---|---|---|
| 打回率 | **40%(2/5)** | 判定 `ok`,不是互相点头 |
| 每工作项回合数 | 10 | 偏高,但主因是中途撞了协议死锁,不是工作项切太大 |
| 协议级真缺陷 | 2 | 一个死锁、一个解析 bug |
| 协议级观察 | 3 | 见下 |
| 决策条目 / 完成工作项 | 8 / 1 | 与"产出主要是结论"一致 |

**这些数字有一半是脏的。** tester 是独立会话,dev 是协议的起草者本人 ——
5 次评审里 tester 做了 3 次。"独立的两个 agent 会以什么频率互相打回"
这个问题**一个样本都没拿到**,它仍然是这个项目最大的未知。

## 两个真缺陷

### ① 评审以"覆盖不足"打回,会把自己锁死在 spec

`review-test` 打回后回合退回 `spec`。当打回理由是"这处修复没有回归测试守着"时,
tester 要补的那条测试**按定义是绿的** —— 修复已经落地了。而 `feature` 的
`spec` 要求 RED。于是这条完全正当的路径无解:不能伪造失败(项目信条反对)、
不能改 PLAN 里的工作项类型(冻结文件)、不能打回(`changes` 只在评审阶段
和 `impl` 异议时解析)。

**这不是设计缺失,是一条已有规则漏接了入口。** 红绿豁免早就在,注释里
那句"异议之后紧接着的 spec 回合"逐字描述了这个处境,缺的只是
`state["after_dispute"] = bool(is_dispute)` —— `is_dispute` 只在 `impl` 阶段
为真,`review-test` 的打回走的不是那条。

修法(`989672c`):任何打回都置位,标志改名 `after_rebound`,
**并且只豁免 RED 不豁免 GREEN** —— `cover` 的 `spec` 期望 GREEN,
而 `cover` 同样有 `review-test changes → spec` 这条边,整个置空会让红着的
`cover` 过关,而"全程绿"正是它的全部纪律。

### ② 契约里的 markdown 示例被当成小节标题

契约用逐字节示例锚定格式(这是正确做法)之后,`contract_sections` 把示例里的
`# 回合简报` 当成了契约小节,同一份契约被判"小节重名",`claim` 直接拒绝。
修法(`0745971`):围栏内容换成**等量空行**(删除会让偏移量错位,`依据` 会读错)。

## 三条观察

- **空转的 impl 回合。** `review-test changes → spec → impl → review-impl`
  在"打回理由纯粹是覆盖不足"时会强制绕经 dev 一趟,而 dev 无事可做。
  理论上可以在"自打回以来 dev 路径没有改动"时从 spec 直接回 review-test,
  但要新判定,而这条路径有多常见还不知道。**记着,没动。**
- **人类介入会破坏补偿检查的前提。** 见 [INSTALL.md](../INSTALL.md)
  的「人类介入的纪律」。
- **`每工作项回合数` 这个指标在协议自身出问题时会误导人。** W1 走了 10 个交接,
  读起来像"工作项切太大",实际是中途撞了死锁。`report` 没法区分这两者。

## 最值钱的一条:两次打回都不是红绿发现的

- 第一次:tester **读** `render_brief` 读出契约偏离(`item_type` 为空时写出裸 ID)
- 第二次:dev 把那处修复**改回去跑了一遍**,发现 230 个测试全绿 —— 手动变异检查

协议的红绿信号**一次都没抓到这两个问题**。它们是被"评审必须逐行给证据"
这个格式逼出来的:要填 `--checked` 就得真去读代码,而读代码才看得见这两类。

这直接改变了 [improvements.md](improvements.md) 的排序依据:
**用例级红绿(P0-1)对"契约偏离"和"修复没测试"这两类天然失明**,
而这两类是本轮全部的真实产出。

## 两个 agent 的表现(定性)

值得记下来的几处,因为它们不是脚本能强制出来的:

- tester 一次交六条用例,**每个会变的字段各配一条能打死常量实现的反例**,
  并在笔记里说明"只留一条正常路径用例等于允许实现返回一份常量"
- tester 在评审里**预先反驳了 dev 可能的辩解**("终端头部也是这么写的"),
  并给出为什么不成立
- tester 承认**自己的测试没抓到那个 bug,是读代码读出来的**,
  并说明评审回合只读、改完下一轮补
- tester 发现自己的产出被人类提交走、补偿检查因此拦住它之后,
  **拒绝写一条凑数的测试去过检查** —— "那正是这条检查要防的东西的镜像"
- tester **拒绝为了让打回率好看而制造第三次打回**,理由是烧掉死锁闸这道保险丝
- 双方都在 `--uncovered` 里如实列了没覆盖的面,没有一次写"无"

## 还欠着什么

**一次两边都独立的运行。** 这一轮 dev 是协议起草者,它对契约的理解、
对边界的熟悉都不具代表性。真正要回答的问题 —— 两个都没参与设计的 agent
会不会互相点头 —— 仍然没有样本。
