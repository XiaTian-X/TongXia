# 故障排查

> 症状 → 原因 → 处理。按发生频率排。
> 命令细节见 [command-reference.md](command-reference.md),
> 规则依据见 [protocol-spec.md](protocol-spec.md)。

## 接入阶段

### `init` 说"基线不是全绿,拒绝初始化"

**原因** `impl` 阶段"测试必须 GREEN"这条不变量依赖基线全绿。基线本来就红,
协议要么直接卡死,要么那条不变量形同虚设。

**处理** 先把现有测试修绿,再重跑 `init`。这不是洁癖,是不变量的前提。

### 全新项目:测试目录是空的,但 `init` 说不绿

**原因** 空测试目录往往不算绿。`python3 -m unittest discover` 在没有任何用例时
会报 `NO TESTS RAN` 并非零退出;`go test ./...` 在没有测试文件时也可能如此。

**处理** 先放一条必过的冒烟用例,基线才成立。
参考 `examples/demo-project/tests/test_smoke.py`。

### `init` 说"探测不到测试命令"

**处理** 手工创建 `.pair/config.json` 填入 `test_cmd`,再重跑 `init`。
格式见 [protocol-spec.md §7](protocol-spec.md#7-配置-schema)。

### `verify-setup` 报"以下文件同时属于两个角色"

**原因** `roles` 的路径集合有交集。这是**最严重的配置错误** ——
零冲突保证的全部来源就是两方路径不相交。

**处理** 多半是同目录布局少了负模式。Go 的 `dev: ["**/*.go"]` 会同时匹配
`foo_test.go`,必须写成:

```json
"dev": ["**/*.go", "!**/*_test.go"]
```

`!` 开头是负模式:一个路径属于某角色 = 命中至少一个正模式且不命中任何负模式。

### `verify-setup` 报"工作项指向的契约小节不存在"

**原因** PLAN 里每个工作项都必须有一行 `对应契约:docs/CONTRACT.md → <小节名>`,
且小节标题要真实存在。

**处理** 核对标题文字是否完全一致(包括标点)。

### `verify-setup` 一直卡在"还差最后一步"

**原因** 它要求你通读契约,把认为有歧义的条款写进
`docs/reviews/setup-verification-<角色>.md`,至少 120 字。这一步脚本代替不了。

**处理** 认真写。没有歧义就明确写"无歧义"并说明**逐条核对了什么** ——
空泛的一句"看过了"既过不了字数,也没有价值。

### `claim` 说"尚未通过开工前校验"

**处理** 让结对的另一方跑 `verify-setup`。存量项目想先跳过可以把
`require_setup_verification` 设为 false,但这是在关掉唯一一道针对
"唯一会致命的失败模式"的门。

### `claim` 说契约在你上次校验之后变过

**原因** 开工前校验按角色记下"那一次读的是哪一份契约"(比的是工作区内容)。
契约之后被改过 —— 包括人类改了还没提交的 —— 你那一份就不作数了。每个角色各记
一份,对方重跑不能替你解锁。存量项目刚升级上来、状态里还没有这份记录时,
也会这样提示一次。

**处理** 通读改过的契约,更新你那份结论,重跑 `verify-setup`。`status` 在这种
情况下也会给一句不阻断的提示;`whose-turn` 不受影响。

## 回合中

### agent 不知道自己是谁 / 脚本说无法确定角色

**原因** 角色解析按 `PAIR_ROLE` → `.pair/whoami` → git 分支名 `pair/<角色>`
的顺序找,三者都没有就停下。

**处理** 按拓扑选一种:

```bash
PAIR_ROLE=tester <agent 的命令>       # 拓扑 A:同目录,两个终端
echo tester > .pair/whoami            # 拓扑 B:分离工作副本
git switch -c pair/tester             # 拓扑 B 的另一种写法
```

拓扑 B 还要在 `config.json` 里开 `"sync": true`。

### agent 没激活技能,直接开始写代码

**原因** 渐进式披露意味着 agent 自己判断要不要加载 SKILL.md。
入口文件里的激活器是硬命令,但没有硬保证。

**处理** 按顺序排查:

1. 确认它到底有没有读到 `SKILL.md` —— 直接问它。
2. 直接让它调用技能(Claude Code 里是 `/pair-protocol`),
   或者让它读 `.agents/skills/pair-protocol/SKILL.md`。
3. 确认 `.claude/skills/pair-protocol` 软链接存在。Windows 上无管理员权限时
   CLI 会退化成桩文件,桩文件里写着真源路径,agent 需要多跳一步。
4. 确认对应工具的入口文件在(`AGENTS.md` / `CLAUDE.md` / `GEMINI.md` /
   `.cursor/rules/` / `.windsurfrules` / `.clinerules` /
   `.github/copilot-instructions.md`)。

### 两个 agent 都说"不是我的回合"

**原因** 状态在 `.pair/state.json` 里,不在对话里。多半是有一方没 pull 到
最新提交(拓扑 B)。

**处理** 两边都跑 `status`(sync 模式下它会自动 pull)。
仍然对不上就看 `git log` —— 最后一次交接的 body 里写着 `phase=X -> Y`。

### `handoff` 说"以下改动越界"

**处理** 撤销越界改动。如果你确信对方的代码有问题:

1. 把问题写进 `docs/reviews/`
2. 在评审回合用 `handoff changes "..."` 打回,**由对方自己改**

**不要"顺手修一下"** —— 那会让对方下一回合看到无法解释的 diff。

### `handoff` 说"spec 阶段结束时测试必须是 RED,现在是 GREEN"

**原因** 两种可能:没写新用例;或者写了个本来就能通过的用例。

**处理** 失败的测试才是有效的规格。如果你本来就是在为**已有行为**补测试,
那这个工作项应该标成 `[cover]` 类型。

### `handoff` 说"impl 阶段结束时测试必须是 GREEN,现在是 RED"

**处理** 看 `.pair/.last-test.log`。还没弄绿就不要交接。

**例外:如果你认为测试本身写错了** —— 不要照着错误的断言写实现,走异议流程:

1. 在 `docs/reviews/` 写清楚:哪条用例、和契约的哪一条矛盾、应该改成什么
2. `pair.py handoff changes "测试与契约矛盾,详见 docs/reviews/<文件>"`

回合退回 tester 的 spec 阶段。**这条路径豁免红绿检查**,
但异议必须写成文件 —— 对方看不到你的对话,不写下来等于没提。

### `handoff` 说"评审记录只能追加"

**原因** 你改动了一份**已经提交过**的评审记录(顶层 `.md`)。改一行、删一行、
删整份、改名都算 —— 它是双方共识的凭据,被无声改写之后没有任何检查会说话。
W14、W15 各发生过一次:第二次评审整份覆盖上一版,逐段对契约的表格就此消失。

**处理** 同一阶段走第二次就新建一份:拒绝文案里给的那个名字
(`<工作项ID>-<阶段>-2.md`)就是本回合该写的。要补充上一版,往**末尾追加**。
`verify-setup` 的契约审查结论同理。

**如果这份改动不是你做的,不要撤销、不要改名 —— 告诉人类。** 评审目录是共享路径,
人类和对方都写得了它。

### `handoff` 说"你删除了已有测试"

**处理** 确有正当理由(比如该用例已被更好的用例完全覆盖)就显式声明:

```
pair.py handoff "说明" --allow-deletion "删除理由"
```

理由和被删文件会写进提交记录,对方评审时必然看到。
**这不是放行,是强制留痕** —— 决定权仍在评审的对方手里。

**改名也算删除。** `git mv` 会被看成旧路径删除 + 新路径新增 —— 否则把一条红的测试挪进评审目录,套件就绿了、删除检查却看不见。整理测试文件时照样带 `--allow-deletion` 写明理由。

### `handoff` 说"你修改了 .pair/state.json"

**原因** 协议状态由脚本维护,手工修改等于伪造回合归属。

**处理** 已自动还原为上次提交的版本。重新跑 `status` 确认真实回合。
如果你认为状态不对,告诉人类,不要自己动手。

**注意** `claim` 之后会立即提交 state,所以正常流程里它始终是干净的。
如果你没动过它却被判篡改,检查是不是有别的工具(格式化、pre-commit hook)
碰了它。

### `handoff` 说"本项是 cover 类型,但你这一回合没有新增或修改任何测试"

**原因** cover 类型全程绿,红绿不变量抓不到空手交接,所以单独检查。

**处理** 真的写测试。

### cover 回合里新写的测试变红了

**这不是失败,是你发现了一个真实缺陷。**

**处理** 告诉人类把它改成 `[bug]` 类型的工作项,由 dev 来修。
**不要在 cover 回合里放宽断言让它变绿** —— 那是在掩盖缺陷。

### `handoff` 说"[refactor] 的实现回合必须交出考古记录"

**原因** 重构回合里 tester 要判断"行为有没有被悄悄改掉",可它手上测试全程是绿的
(绿的测试按定义没抓到问题),契约写的是目标而不是现状。做过考古的是你。

**处理** 在 `docs/notes/<工作项ID>.md` 写三个小节,每节正文至少 40 字:

```markdown
## 现状考古
## 我保留了哪些契约外行为
## 我不确定的地方
```

### `handoff` 说"你往 DECISIONS.md 写了内容,但它不构成一条决策条目"

**原因** 解析不出来的东西 `status` 永远召回不到,等于没写 ——
而你会以为自己记录了。

**处理** 按格式写:

```markdown
## <工作项ID> — <标题>
- 理由:…
- 已否决:…
- 影响路径:…
```

三个字段缺一不可,单条不超过 1500 字符。

**如果这只是 `init` 刚铺下的骨架** —— 让人类先把它提交进去。

### `handoff` 说"你改动了 DECISIONS.md 里已经写下的内容"

**原因** 决策记录是追加式的。已有条目是双方共识的凭据,改它等于伪造共识。

**处理** 要推翻旧结论,**追加**一条新条目说明为什么推翻。旧的留着。

### `handoff` 说"工作项要完成了,但它的笔记还没被处理"

**原因** 笔记是工作项级的,这一项关掉之后没有任何回合会再读到它。
现在是它变成长期资产的唯一时机。

**处理** 二选一:

1. 追加一条决策到 `docs/DECISIONS.md`
2. 显式声明没有可沉淀的:
   `pair.py handoff approve "摘要" --checked "…" --uncovered "…" --no-decision "为什么没有"`

### `handoff` 说"契约在这个工作项期间被改过,但没有对应记录"

**原因** `claim` 时记下了契约的 blob sha,完成时比对发现变了。
契约变更是重新推导代价最高的事 —— 此后每个回合都会拿改过的契约当理所当然,
而改它的理由谁都看不到了。

**处理** 追加一条决策,写清楚原来是什么、为什么不行、改成了什么。

### 同一工作项被打回 3 次,协议停了

**这是设计。** 把双方分歧写清楚,交给人类裁决。

**不要试图绕过**(比如改 `state.json` 里的计数器 —— 会被篡改检测拦下并还原)。

人类裁决之后,通常是修契约或者把工作项拆小。

### `approve` 被拒:必须交出检查清单

**原因** `approve` 要求两个参数,缺一即拒。

```bash
pair.py handoff approve "摘要" \
    --checked "你具体检查了什么" \
    --uncovered "你知道还没被覆盖到的是什么"
```

**处理** 把刚才实际做的检查写进 `--checked`。想不出还有什么没覆盖,
`--uncovered "无"` —— 那是一句被记录在案的明确主张,不是沉默。

**为什么** 空手通过是这套协议唯一会致命的失效方式:两个 agent 互相点头,
红绿全对,而没有任何缺陷被发现。脚本查不了内容,但结构逼你写出检查了什么。

### `changes` 被拒:打回必须具体到位置

**原因** 理由里(或本回合写进 `docs/reviews/` 的文件里)没有 `路径:行号` 引用,
或者引用的路径对不上任何真实文件。

**处理** 指到具体位置:`src/auth.py:42 对 test@example.com 特判`。
路径相对仓库根,详细意见写进 `docs/reviews/`,理由字段只放摘要。

**为什么** 对方看不到你的对话。指不出位置的意见它无从下手,
来回两轮就撞上死锁闸。

### `claim` 被拒:契约小节的依据不可断言

**原因** 那一节的 `依据` 是 `已有文档 …(待核实)` —— 从老文档抄来的线索,
没人核实过它还成不成立。

**处理** 先开一个 `[cover]` 工作项:tester 写特征测试建立事实,同时把契约草案
写进 `docs/reviews/`。人类定稿之后,依据改成 `人类定稿` 或 `考古观察@<sha>`,
这一项才能开工。

**为什么** 老文档写"返回 null"而实际代码抛异常时,tester 会照它写断言、
dev 会以为发现了 bug 去改行为 —— 整条链每一步都合规,结果是线上炸。
详见 [brownfield.md](../.agents/skills/pair-protocol/references/brownfield.md)。

### `claim` 被拒:[refactor] 必须声明保护它的测试

**处理** 在 PLAN 里那个工作项下面加一行 `- 保护测试: tests/<对应目录>`。
路径要真实存在,而且必须落在 tester 的路径下。还没有覆盖就先开一个
`[cover]` 工作项补上。

**为什么** 重构全程是绿的,而绿的测试按定义没抓到任何问题。那片代码本来就
没有测试时,"绿"什么都不证明,`review-impl` 只能凭 diff 猜。

### `handoff` 说 [cover] 必须交出特征测试记录

**处理** 在 `docs/notes/<工作项ID>.md` 写两个小节,每节正文至少 40 字:

```markdown
## 行为来源
## 我冻结了哪些可疑行为
```

**为什么** 特征测试会**把缺陷一起焊死** —— 你照着现状写断言,而现状里可能就有
bug,并且 cover 全程是绿的,红绿不变量抓不到。对方在 `review-test` 要回答的
正是"这行为是有意的,还是我们刚把一个缺陷变成了规格"。

### `handoff` 说改动在本轮范围之外

**原因** `config.json` 里配了 `scope`,而你动了它之外的文件。

**处理** 撤销那些改动。确实需要动范围外的代码,把理由写进 `docs/reviews/`
并告诉人类 —— **扩大范围是人类的决定**,不是你顺手能做的。

**为什么** 存量项目最危险的不是结构不合适,是蔓延:改一个计费 bug,
顺手动了三个公共工具类。

### 工作项完成了,但退出码是 2:全量套件红

**这不等于失败,但也不等于完成。** 门禁套件(收窄过的 `test_cmd`)是绿的,
范围之外有东西红了。

**处理** **不要告诉人类"完成"** —— 报告这件事,由人类决定是扩大范围、
开一个新工作项,还是接受它。详情见 `.pair/.last-full-test.log`。

### `handoff` 说"你没有改动任何测试",可我明明写了

**原因** 这条检查按**工作区改动**判断。如果人类在你这一回合期间提交过东西
(尤其是 `git add -A`),你的产出会被一起提交走 —— 它确实存在,但已经不在
工作区,检查读成"你什么都没干"。

**处理** 跑 `git log -1 --stat` 看你的文件是不是已经在别人的提交里。
是的话,**不要为了过检查补一条凑数的测试** —— 那正是这条检查要防的东西的镜像。
把情况告诉人类,由人类决定是回退那次提交,还是认可你这一回合的产出。

**给人类的纪律** 介入时只 `git add` 自己改的文件,别用 `-A`。
见 [INSTALL.md](../INSTALL.md) 的「人类介入的纪律」。

### `handoff` 说评审目录里的文件名对不上任何工作项

**原因** 评审目录顶层的 `.md` 要以某个工作项 ID 开头(`W1-*.md` 或 `W1.md`),
或者是固定名 `setup-verification.md` / `setup-verification-tester.md` /
`setup-verification-dev.md` / `baseline.md` / `contract-change-<ID>.md`。

**处理** 改成规范名。`status` 每回合会直接告诉你这一轮该写哪个文件名。

**但先确认那个文件是不是你写的。** 人类在结对期间往 `docs/reviews/` 放了文件
却没提交,就会算到你头上 —— 这种情况**不要改名、不要删**,告诉人类。
见 [INSTALL.md](../INSTALL.md) 的「人类介入的纪律」。

### `handoff` 说提异议要写进 `<ID>-dispute.md`

**原因** `impl` 阶段用 `changes` 打回测试,必须写这份文件,三个小节:
`## 哪条用例` / `## 和契约的哪一条矛盾` / `## 应该改成什么`,每节至少 40 字。

**为什么这么严** 这条路径**豁免红绿不变量** —— 全协议只有它豁免。
换来的代价就是把话说清楚:对方看不到你的对话,指不出是哪条、矛盾在哪,
它无从下手,来回两轮就撞死锁闸。

### `handoff` 说 `考古观察@<sha>` 的 sha 找不到

**原因** 那个 sha 在本仓库不存在。`考古观察` 是三档依据里唯一**可被脚本校验**
的一档,靠的就是这个 sha —— 编一个,这一档就只剩标签。

**处理** `git rev-parse --short HEAD` 取当前的。它记的是"我读的是哪个版本的代码"。

### `verify-setup` 说结论里没点到某些小节

**原因** 契约审查结论要**逐节**过一遍,每个被工作项引用的小节名都得出现。
把契约整段粘进 ``` 围栏不算 —— 围栏内容会被剥掉。

**处理** 一节一节写。每节问:返回值精确到能写断言吗?错误条件穷举了吗?
边界(空、超长、null、并发)写明了吗?有没有两种合理解读?

**能力边界** 这条只保证覆盖面,不保证消歧 —— 「以下小节均无歧义:A、B、C」
仍然过得去。真正判断契约含不含糊的只有人。

### `verify-setup` 说要声明有没有参与契约起草

**处理** 带上 `--drafter` 重跑,二选一:

```
pair.py verify-setup --drafter other   # 我没参与契约起草
pair.py verify-setup --drafter self    # 我参与了,这份结论的证明力因此打折
```

**不要在结论正文里写这句话** —— 脚本不看措辞,只看参数。声明会写进提交正文,
对方在 `inbox` 里必然看到。

**为什么** 起草人审自己写的东西看不见自己的盲区。这道门守着协议自称唯一会
致命的失败模式,读结论的人有权知道是谁写的。

**为什么是参数不是搜措辞** 早先这条是在结论里搜「参与|起草|撰写」。那样两头
落空:「本结论作者未介入契约的编写」这种正确说法被拒,而正文里随便一个
「参与」(哪怕说的是参与实现)就放行。见 [ADR-024](design-decisions.md)。

## 交接与同步

### `handoff` 成功了但退出码是 2,提示推送失败

**这等于没交接。** 提交只在你本地,对方在信道上什么都收不到。

**处理** **不要告诉人类"已交接"**,报告推送失败让人类处理:
网络、权限,或者对方推了新提交需要先 pull。

### 拓扑 B 下两边内容对不上

**处理** 确认 `config.json` 里 `"sync": true`。开了之后 `status` 会先
`git pull --rebase`,`handoff` 会在提交后 `git push`。

### 构建副产物被判越界

**原因** dev 跑一次 `npm install` 改了 lockfile 就被判越界是不合理的。

**处理** 把这类路径放进 `ignore_paths`,它们完全不参与边界检查:

```json
"ignore_paths": ["package-lock.json", "**/*.lock", "dist", "build"]
```

**代价:两个角色都能悄悄改它们且不留痕。只放真正的副产物。**

## 质量问题(脚本抓不到的)

这些没有报错,但比报错更值得警惕。

### 两个 agent 一直互相 approve,从来没打回过


**这是手段层最该警惕的失效模式。** 打回率接近 0 说明评审在走过场 ——
两个 LLM 互相点头会让两份努力合起来仍是废的,危及最终交付,所以协议在结构上
防它。但它是保障交付质量的手段,不是项目的目的。

**排查**
1. 读几条 `approve` 的理由。有没有具体到文件和行号?"看起来不错"这类
   空话说明评审没有真的发生。
2. 工作项是不是切得太大,以至于评审者没能力细看。
3. 契约是不是太模糊,以至于没有可争的东西。

**注意:`--checked` / `--uncovered` 只能保证 approve 有结构,保证不了它有内容。**
引用一个真文件配一个假行号也过得去 —— 脚本把敷衍的成本从零抬到了"必须真的打开过
文件",但没有消灭它。**这一条仍然要靠人眼看提交记录。**

**规则依据** `rules.md` 规则 6:approve 必须带 `--checked` / `--uncovered`,
changes 必须指到 `路径:行号`。

### 测试全绿但功能是错的

**排查方向**
- **dev 硬编码蒙混:** 换一组符合契约但没出现在测试里的输入,这段代码还对吗?
  不对就是作弊,评审时必须打回。
- **tester 断言了实现细节:** 断言私有方法名、内部调用次数、日志文本,
  会把测试变成变更探测器 —— 实现稍作重构就红,但没有任何真实缺陷被发现。
  **这比没有测试更糟**,因为它训练双方忽略红色。
- **契约漂移:** tester 测 `login() -> token`,dev 写
  `authenticate() -> Session`,两边各自都"对",合起来是废的。
  这是唯一会致命的失败模式,靠 `verify-setup` 的歧义审查在开工前拦。

### agent 说"我没看到那条决策"

**排查** 决策条目的 `影响路径` 字段是检索键。`status` 只注入与本回合主体路径
相干的条目 —— 写漏了路径,那条结论就等于不存在。

检查那条决策的 `影响路径` 有没有覆盖本回合实际改动的文件。

### 工作项做不完 / 回合数失控

**原因** 多半是工作项切得太大。判断标准:小到一个回合写三五个用例就覆盖完。

"实现用户系统"太大;"密码哈希用 bcrypt,cost=12"才是一个工作项。
