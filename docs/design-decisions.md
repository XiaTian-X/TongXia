## ADR-001 用测试的红绿作回合信号,不用 LLM 判断

**背景** "这一回合做完了没"必须有一个答案。

**决策** spec 回合结束时测试必须 RED,impl 回合结束时必须 GREEN,
由 `handoff` 跑测试用退出码判定,不合规拒绝提交。

**理由** 模型说"我做完了"不可证伪,而且模型有强动机说这句话。
测试的红绿是二值、可复现、跨模型一致的。它还顺带判定了另一件事:
tester 交出来的必须是一条**会失败**的测试 —— 一条恒过的断言在 spec 回合
会被直接拒绝,而这正是"看起来干了活、实际什么都没验收"最常见的形态。

**代价** 依赖基线全绿、依赖测试跑得完、依赖 harness 能执行 shell。

**否掉的方案**
- *让一个第三方 LLM 当裁判* —— 引入第三个不可证伪的判断,还多一份成本。
- *靠 diff 大小 / 文件数启发式* —— 与"做完了没"没有因果关系。

**相关** MetaGPT 的 executable feedback、AgentCoder 的 test executor 同源。

**已知不足** 判定粒度只有整体 0/非 0,不知道"哪一条红了"。见 improvements P0-1。

## ADR-002 写权限按目录/glob 切分,不用锁也不用 worktree

**背景** 两个 agent 改同一个仓库,冲突怎么办。

**决策** tester 只能写 `tests/`,dev 只能写 `src/`;越界文件在 `handoff` 时
被逐条列出并拒绝提交。两个角色的路径集合不得有交集。

**理由** 冲突不是被解决的,是**不可能发生**的。不需要锁、不需要 merge 策略、
不需要 worktree,两个 agent 可以共用一个工作目录 —— 而且天然保证两人看的是
同一份代码。

**代价** 布局必须能切分。Rust 文件内单测因此不支持(见 ADR-011)。

**否掉的方案**
- *git worktree / 独立容器*(container-use、Conductor、Crystal 那一类)——
  它们解决的是"N 个 agent 做 N 件不相干的事",隔离靠复制工作区。
  本协议是"2 个 agent 做同一件事",切分命名空间更便宜。
  worktree 拓扑保留为可选(`sync: true`),不是默认。
- *文件锁 / 提交顺序约定* —— 需要活性检测和超时,复杂度陡增。

## ADR-003 通信只走 git,不传对话

**背景** 两个 agent 怎么交换信息。

**决策** 唯一信道是 git 提交,加仓库里三个位置:`docs/reviews/`、
`docs/notes/`、`docs/DECISIONS.md`。`inbox` 是收件箱。

**理由**
1. 传对话记录会衰减(MetaGPT 称之为"传话游戏")。
2. 从仓库现状重新推导恰好是 agent 擅长的,也比携带越来越长的历史便宜。
3. git 是每个 harness 都会用的东西,不引入新运行时、服务或端口。
4. 顺带解决持久化:崩溃、换机器、隔一周继续,状态都在仓库里。

**代价** 延迟高(一回合一次交接);对方的即时思路完全丢失,只剩写下来的部分 ——
这也是记忆层存在的原因。

**推论** push 失败等于没交接。`sync` 模式下 `handoff` 显式检查 push 结果,
失败时退出码 2 并要求 agent 报告"推送失败"而不是"已交接"。

**否掉的方案**
- *共享消息队列 / MCP 消息总线* —— 引入新组件,且不解决持久化。
- *把对方的 transcript 传过去* —— 成本高,且会让两边推理趋同(见 ADR-009)。

## ADR-004 协议以 Agent Skill 形态随仓库分发

**背景** 怎么让"任意两个第三方 agent"都受同一套约束。

**决策** 协议打包成一个 Agent Skill 目录,复制进目标项目即接入。
`.agents/skills/` 是跨客户端惯例,`.claude/skills/` 用软链接指向同一份真源。
另铺各家入口文件作为硬激活器。

**理由** Agent Skills 是已被广泛采用的开放格式(Claude Code、Codex、Cursor、
Gemini CLI、Copilot、VS Code、Goose、OpenCode、OpenHands、Amp、Junie、Kiro、
Roo Code 等),渐进式披露让协议正文不常驻上下文。不绑定任何厂商。

**代价** 技能激活不是 100% 可靠 —— 渐进披露意味着 agent 自己判断要不要加载。
入口文件里的激活器是硬命令,但没有硬保证。某个 agent 没按协议走时,
第一件事是确认它到底有没有读到 SKILL.md。

**否掉的方案**
- *做成一个 orchestrator 应用*(the-pair 那样)—— 要求用户改用它的 app,
  与"任意两个 agent"直接冲突。
- *只写一份 AGENTS.md* —— 全部约束退化成 prose,强制力归零(见 ADR-005)。

## ADR-005 规则能编码的一律编码,不能编码的强制留痕

**背景** 不同模型对同一段 prose rules 的遵守程度差别很大。

**决策** 边界、红绿、回合归属、删测试、状态篡改、决策格式等全部编码进
`pair.py` 的拒绝分支;"评审要有实质"这类编不了的,退而求其次做到
**强制留痕**(`--allow-deletion "理由"`、`--no-decision "理由"`、
契约歧义结论 ≥120 字)。

**理由** 凡是"靠模型自觉"的规则,在跨 harness 场景下强制力趋近于零。
留痕不是放行,是把决定权交回人类,并保证有东西摆在他面前。

**代价** `pair.py` 变成一个 1.8k 行的单文件,拒绝路径比正常路径还多。
为此需要变异检查来防止防护悄悄失效(见 ADR-012)。

**否掉的方案**
- *全靠 prose*(BMAD 那样)—— 换个模型遵守程度就变。
- *用 hook 实时拦截*(TDD Guard 那样)—— hook 是 harness 特化的,
  与"任意两个 agent"冲突。交接点校验是唯一跨 harness 可保证的时机。

## ADR-006 CLI 不含任何协议逻辑

**背景** bootstrap CLI 需要初始化项目,而 `pair.py` 也有 `init`。

**决策** CLI 只做两件事:复制协议目录 + 建软链接,然后调用**刚复制过去的**
`pair.py init`。构建时协议目录被原样打进 wheel,CLI 不复制、不改写内容。

**理由** 一旦 CLI 里出现协议逻辑,它就会和 skill 漂移 ——
而防漂移正是这个项目从头到尾在做的事。

**代价** CLI 能给的错误提示很薄(它对项目一无所知)。

**推论** 同一条约束适用于任何未来的适配层(MCP server、GUI、CI 集成):
必须是纯转发。

## ADR-007 工作项类型换掉整条流程,而不是加开关

**背景** 补测试(cover)和重构(refactor)天然没有 RED 阶段,
套用 feature 的"先红后绿"会直接卡死。

**决策** PLAN 里的 `[类型]` 标记决定**整条阶段序列和红绿纪律**:

| 类型 | 阶段序列 | 红绿 |
|---|---|---|
| `feature` / `bug` | spec → impl → review-impl → review-test | spec=RED,其余=GREEN |
| `cover` | spec → review-test | 全程 GREEN + 必须真的写了测试 |
| `refactor` | impl → review-impl | 全程 GREEN + 必须交考古记录 |

**理由** 跳过阶段会丢掉一方的对抗价值,所以被跳过的角色靠**评审回合**保留 ——
`cover` 里 dev 只评审"这测试能否发现回归",`refactor` 里 tester 只评审
"行为有没有变"。这样存量项目也能用同一套协议接入。

**代价** 三条流程要各自维护转移表和不变量,一致性测试要覆盖三遍。

**否掉的方案**
- *加一堆 `--skip-red` 之类的开关* —— 开关会被滥用,而类型标记写在 PLAN 里,
  人类看得见、评审时对方也看得见。

**衍生规则** `cover` 回合里新写的测试变红了不是失败,是发现了真实缺陷 ——
应当告诉人类改成 `[bug]` 类型,**不得**放宽断言让它变绿。

## ADR-008 记忆分两层,召回挂在 status 上

**背景** 两个 agent 每回合都是新来的,不共享对话也不共享各自工具的记忆。

**决策**
- `docs/notes/<ID>.md` —— 工作项级,无格式,记**负空间**(试过什么没成、
  否掉了什么、哪里拿不准)
- `docs/DECISIONS.md` —— 项目级,四字段受校验,追加式
- 召回点挂在 `status`:轮到你时自动注入笔记全文 + 相干决策条目

**理由** 各家 agent 的私有记忆格式和召回机制不一样,统一不了,也不该去统一 ——
**你能统一"写什么",统一不了"什么时候被读出来"**。`status` 是协议强制的第一条
命令,也是唯一能跨 harness 保证会被执行的时刻。**存了没人读等于没存。**

文档天然记录正空间,而重构和排查里值钱的知识几乎全在负空间,
没有任何常规文档形态会承载它 —— 所以专门开一个位置,并把成本压到最低。

**代价** 注入会吃上下文,因此设了硬上限(笔记 3000 字符、决策 2000 字符 /
最多 5 条、单条决策 1500 字符)。`影响路径` 是检索键,写漏了那条结论就等于不存在。

**否掉的方案**
- *接一个向量库 / 外部记忆服务* —— 引入新组件,而且召回时机仍然不可控。
- *把所有东西都写进 DECISIONS.md* —— 会长到没人读,而它每次 status 都要被读一遍。

## ADR-009 决策条目追加式,且故意没有"分析"字段

**背景** 决策记录写完之后能不能改。

**决策** 已写下的条目不得修改,要推翻就追加一条说明为什么推翻;
改动历史会被 `handoff` 检测并拒绝,与手工改 `state.json` 同级。
条目只有三个字段:`理由` / `已否决` / `影响路径` —— **没有"分析"**。

**理由**
- 已有条目是双方共识的凭据,改它等于伪造共识。"我们曾经这么想过、
  后来发现不对"本身就是最值钱的那类信息。
- 只共享事实和裁决,不共享推理过程。**两边共享同一条推理路径,
  就更容易想到一块去,而互相点头正是这套机制从头到尾在防的事。
  记忆不同不是缺陷,是对抗性的来源。**

**代价** 文件只增不减,长期会变长。缓解:单条 1500 字符上限,
注入时按相干性过滤且最多 5 条。

**外部支持** 多 agent 辩论研究发现共享推理会导致从众翻转与共识偏置。

## ADR-010 人类是时钟,agent 不自动唤醒对方

**背景** 交接之后谁去叫另一个 agent。

**决策** 不做。每次交接后需要人到另一个终端敲一句。

**理由** 这条现在是限制,但它顺带保证了三件事:每回合有一个天然的观察窗口;
跑飞的成本有上界;契约由人类维护这件事有了执行的时机。

**代价** 不能全自动。想全自动可以在 handoff 后用 headless 模式拉起对方 ——
但先把手动流程跑顺,自动化会把每个还没暴露的设计缺陷放大成事故。

**外部支持** the-pair 用 20 轮预算 + 人类闸门达到同样效果;
辩论研究显示轮次越多准确率越低。

**已知不足** 死锁闸只管"同一工作项打回 3 次",没有全局回合预算。
见 improvements P1-2。

## ADR-011 Rust 文件内单元测试不支持

**背景** `#[cfg(test)] mod tests` 与实现在同一个文件里。

**决策** 明确不支持,在 README、INSTALL、SKILL 里都写清楚。

**理由** 目录切分物理上不成立,glob 也救不了。这是 ADR-002 的必然推论,
不是实现偷懒。

**代价** 排除了一部分 Rust 项目。

**迁移路径** 把测试移到 `tests/` 集成测试目录。

**否掉的方案** *块级 diff 检查*(允许同文件,但 tester 只能改 `#[cfg(test)]`
块内、dev 只能改块外)—— 需要 Rust 感知的分析器,成本远高于收益,
而且会在协议里引入第一个语言特化组件。

## ADR-012 一致性测试扮演作弊的 agent,并用变异检查验证它自己

**背景** 怎么知道那些拒绝分支真的还在拦人。

**决策**
- `tests/conformance/` 扮演作弊的 agent:抢回合、篡改状态、越界写、
  评审夹带私货、删测试、空手交接、伪造决策 —— 断言 `pair.py` 拦得住。
- `mutation_check.py` 逐个拆掉 `pair.py` 里的防护,确认每一条都有测试能发现
  它消失了。

**理由** **一个恒真的测试集比没有测试更危险** —— 它会让人以为强制力还在,
而执行层可能已经什么都不拦了。全绿本身证明不了什么。

**代价** 改动强制逻辑后要跑两遍;新增防护时必须在 `MUTATIONS` 里补变异点,
否则那条防护就是没有保障的。

## ADR-013 只有两个角色,不加第三个评审者

**背景** 要不要加一个独立的 critic / reviewer 角色。

**决策** 不加。

**理由**
- Adversarial Review 的实验里 **3 个 agent 打赢了 5 个 agent 的基线** ——
  结构比数量重要。
- 《Talk Isn't Always Cheap》发现辩论中正确→错误的翻转多于反向;
  一个 agent 被其他人反对时最容易翻供,与对错无关;弱 agent 会拖垮强 agent。
- 两方结构没有"多数压少数"的孤立压力。**这是特性,不是妥协。**

**代价** 没有第三方来打破僵局 —— 所以死锁闸把僵局交给人类。

**例外的可能** 如果将来要加,只应是**只读的 critic**(审计评审本身,
不参与产出),且必须先验证它不会引入从众压力。

## ADR-014 评审证据用参数强制,不解析散文

**背景** `architecture.md` 的强制力分布表长期标着「评审有实质 ❌ 只有 prose」。
`handoff` 只校验裁决理由非空,而 `approve "看起来不错"` 是非空的 ——
这是协议里靠职业操守占比最高的一处,恰好守着最重要的那道门。

Adversarial Review 把这个失败模式命名为 **false-consensus**:
双方在没有充分证据的情况下收敛到一致。

**决策** 三条一起做:

1. `approve` 必须带 `--checked` 与 `--uncovered`,缺一即拒
2. `changes` 的理由或本回合的评审文件里必须有一处 `路径:行号`,且路径真实存在
3. 评审阶段的简报从**负向禁止**("禁止只说看起来不错")改成**正向要求**
   ("先找问题,交出至少一处你找到的问题")

**理由**
- 用参数而不是解析理由里的关键词:脚本一旦开始猜中文措辞,换个说法就绕过了,
  而且会把协议绑死在一种语言上。参数是结构,结构查得准。
- 与 `--allow-deletion` / `--no-decision` 同一手法:不是放行,是**强制留痕**。
  两段内容都进提交体,对方在 `inbox` 里必然看到。
- 第 3 条单独看最不像"强制",但它是三条里**唯一有实证支撑其有效性的** ——
  Adversarial Review 里真正扭转 false-consensus 的,是一次显式要求异议的
  prompt 改动,不是更多的禁令。只加检查不改指令,反而会诱发"为了过检查而编造引用"。

**代价**
- 每次 approve 多写两段。这是最危险的那个时刻,值这个成本。
- **脚本查得了结构,查不了内容。** 引用一个真实文件配一个假行号仍然过得去。
  这条不消灭敷衍,只是把成本从零抬到"必须真的打开过文件"。剩下的靠
  `pair.py report` 的打回率暴露 —— 见 ADR-015。

## ADR-015 健康度报告只观测,不设门禁

**背景** ADR-014 之后仍然有一件事不可观测:两个 agent 是在认真对抗,
还是在合规地走过场。人类唯一的信号是逐条读 commit。

**决策** 新增只读命令 `pair.py report`,从 git log 统计打回率等指标。
**退出码始终 0** —— 它是仪表盘,不是门禁。

**理由**
- **打回率接近 0 是"互相点头"唯一的量化证据**,而这套协议存在的全部理由就是防它。
- 不设成门禁:强制"必须打回 15%"会直接制造为了达标而编造的异议,
  比它要治的病更糟。这一类判断只能交给人类。
- 纯读 git log,不新增任何状态 —— 交接提交的前缀与 body 里已经有全部数据。

**代价** 指标能被刷。一个想过关的 agent 可以制造无意义的打回。
但那需要它主动做一件多余的事,而敷衍的本性是省事。

**样本门槛** 少于 5 次评审时不下任何结论 —— 三次评审算出的打回率没有意义,
报一个假精确的数字比不报更糟。

## ADR-016 契约小节必须写「依据」,老文档不能当断言依据

**背景** 接入现有项目时,`docs/CONTRACT.md` 的内容常常是从老文档抄来的。
而存量项目文档的头号病症是**过时**,它的错误方式极其危险:

> README 写"找不到返回 null",实际代码抛异常。
> tester 照文档写断言 → 红 → dev 以为发现了 bug → 改了行为 → 线上炸。

这条链上**每一步都符合协议纪律**:红绿全对,评审也挑不出毛病。
双方都在拿一份错的规格当权威,而协议里没有任何一环会发现。

**决策** 每个被工作项引用的契约小节必须写一行 `- 依据:`,三档:

| 值 | 可断言 |
|---|---|
| `人类定稿` | ✅ |
| `考古观察@<sha>` | ✅ |
| `已有文档 <路径>(待核实)` | ❌ |

`verify-setup` 与 `claim` 都查。不可断言的小节上开不了 `feature`/`bug`/`refactor`,
唯一出路是先做一个 `[cover]` 工作项建立事实、由人类定稿。

**理由**
- 契约是冻结文件,等级只能由人类抬升 —— 这是"契约漂移是唯一会致命的失败模式"
  那条设计的直接推论,不开新口子。
- **不做成 mode 开关。** 新项目的契约同样该记下它凭什么可信;
  `CONTRACT_SKELETON` 里预填 `- 依据: 人类定稿`,新项目照骨架写就零成本。
  见 ADR-017。

**代价** 人类可以把 `依据` 填成"人类定稿"而其实没真核实。脚本查不了这个 ——
它只能保证这句话被明确说出来过,而不是默认。

## ADR-017 不做 greenfield/brownfield 模式开关

**背景** 接入现有项目要加的那几条机制(契约依据、cover 的特征测试记录、
refactor 的安全网、scope、收窄门禁套件),第一版计划全部用
`"mode": "greenfield" | "brownfield"` 门控、默认关闭,理由是存量仓库零成本升级。

**决策** 不做 `mode`。每条机制都是普适的,默认值让新项目零成本。

**理由**
- 确认没有实际项目在用,"零成本升级"这个理由本身就不存在了。
- 去掉门控之后被迫回答一个之前绕过的问题:**这些机制里哪些是真的只对现有项目
  成立?** 逐条查下来一条都不是。`cover` 在任何项目里都是"给已经能跑的行为补
  测试","我是不是把缺陷一起焊死了"这个问题一模一样;新项目的契约也该记下依据。
- **`mode` 会分裂协议的语义。** 同一个 `claim` 在两种模式下行为不同,意味着
  SKILL.md、rules.md、protocol-spec.md 每处都要写"brownfield 时……"。
  而项目身份是会漂的:新项目上线第二天就是存量项目。

**顺带改掉的一条:** `refactor` 的安全网从"`依赖覆盖: W3`(指向已完成的 cover
工作项)"改成"`保护测试: <路径>`(指向真实测试目录)"。前者只在存量场景成立,
而且脚本只能验证那个 ID 已勾选,验证不了它跟本次重构有任何关系;
后者两边都成立,**而且脚本能真的验证它存在、且属于 tester**。

**代价** 新项目要在契约骨架里多一行 `依据`,`cover`/`refactor` 工作项要多写
一节笔记或一行 PLAN。都是一次性的、可模板化的成本。

## ADR-018 评审证据优先于用例级红绿(第一次真实运行的实测结论)

**背景** `improvements.md` 原本把 P0-1(测试结果从布尔值升级到用例级)
排在 P0-2(评审必须带证据)前面,理由是"回合信号取自程序"这条核心主张
只兑现了一半。

**第一次真实运行推翻了这个排序。** 那一轮产出两个真缺陷,**两个都不是
红绿发现的**:

1. 契约偏离(`item_type` 为空时写出契约没有的第三种形态)—— 评审**读代码**读出来的
2. "打回换来的修复没有测试守着" —— 把修复改回去跑了一遍,230 个测试全绿

**决策** P0-2 先做(已落地),P0-1 后移,并在文档里写明它的能力边界。

**理由**
- 用例级红绿回答的是"哪条测试红了"。而上面两类缺陷发生时**没有任何测试是红的** ——
  第一类是实现与契约不符但测试没覆盖到,第二类是覆盖本身缺失。
  更精细的红绿信号对它们**天然失明**。
- 真正把这两条逼出来的是"评审必须逐行给证据"这个格式:要填 `--checked`
  就得真去读代码,而读代码才看得见这两类。

**代价** P0-1 仍然有它的价值(spec 阶段"红的那条正是你这回合写的"、
over-implementation 检测),只是不再排第一。

**样本量的诚实说明** 这个结论来自**一轮、两个缺陷**,而且那一轮的 dev 是
协议起草者本人。它足以推翻一个基于推理的排序,不足以当成定论。
见 [dogfood-run-1.md](dogfood-run-1.md)。

## ADR-019 自动驱动是可选项,而且判定一条都不搬进驱动器

**背景** ADR-010 定了"人类是时钟,agent 不自动唤醒对方",但也留了口子:
"想全自动可以在 handoff 后用 headless 模式拉起对方"。
第一次真实运行之后,来回敲键盘被点名为最大的操作摩擦。

**决策** 做 `scripts/drive.py`,**默认不开**。同时给 `pair.py` 加一条只读命令
`whose-turn`,一行输出 `turn <角色>` 或 `stop <理由>`。

**理由**
- **驱动器里零协议逻辑。** "轮到谁""要不要停"都是协议判断。让驱动脚本自己去
  读 `state.json` 猜,它就成了协议的第二个实现 —— 和 CLI 那条约束同源,
  同样有测试扫描关键词钉着。
- **通信仍然只走 git。** 驱动器不传内容,只决定叫谁。人类手动搬运对话内容
  才是真正违反设计的做法(那会让两个 agent 看见彼此的推理,而记忆层整个是
  按"看不见"设计的)。
- **人类闸门保留。** 协议说停、进程非零退出、连续两回合没进展、超过回合预算,
  四种情况一律停下。

**代价** 自动驱动会消灭每回合的观察窗口,而第一次真实运行里最值钱的两个发现
都来自人在中间看了一眼。所以文档里明确建议:**先手动跑顺,再开自动。**

**一条硬纪律** 驱动器绝不碰 git。结对期间任何人提交东西都可能把某一方停在
工作区里的产出提交走,而「打回之后必须真的动了测试」按工作区判断,
会把它读成"你什么都没干"。这条也有测试钉着。

## ADR-020 文档规范:强制只加在零成本的地方,风险按触发频率分配

**背景** agent 产出的文档治理极不均匀:`DECISIONS.md` 有四字段和追加式保护,
而 `docs/reviews/` 曾经零治理 —— 没有命名、没有形状,`approve` 甚至可以不产出
任何文件。而那里恰恰是评审的一手证据。

**决策** 加五条强制:评审目录命名、异议三小节(必须存在)、契约变更四小节、
契约审查逐节点名 + 作者声明、考古 sha 真实。**不给评审记录规定必填小节。**

**理由:填模板的风险随触发频率线性放大。**

| 强制 | 频率 | 风险 |
|---|---|---|
| 命名、sha | 每次,纯机械,没有"内容"可敷衍 | 零 |
| 契约审查结论 | 每个项目一次 | 极低 |
| 异议、契约变更 | 罕见 | 低 |
| **评审记录形状** | **每个工作项至少两次,全协议最高频** | **风险全在这里** |

所以前四类直接加,评审记录只管命名 —— `--checked` / `--uncovered` 已经在逼出
实质,再规定必填小节,最可能的结果是"## 我检查了什么\n代码看起来没问题"。

**命名这条是先生成、再校验。** `status` 每回合直接打印该写哪个文件名,
拒绝分支自然没人撞 —— 能生成的就别校验,这和"能编码的一律编码"是同一条信条
的另一面,而且它不消耗 agent 的注意力预算。

**代价与已知边界**
- 逐节点名只保证**覆盖面**,不保证消歧。`architecture.md` 里
  「契约不含糊 | ❌ 只有人类」那一行因此原样留着 —— 把它划掉就是
  ADR-012 说的"让人以为强制力还在",只不过发生在文档上。
- 契约变更四小节**按文件名触发**,换个文件名就绕开了。要真强制得加显式 flag。
- 小节名很短时,正文里任意一次提及都算点名。

**退回条件(事先写死,不是"看着办")** 如果以后给评审记录加了必填小节,
判据是:**在 ≥5 次评审的窗口里,`## 我检查了什么` 的正文中位长度短于它伴随的
`--checked`,即判定该强制退化成了重复,回退。** 一个数字,照 ADR-015
"把不可观测的东西变成只读指标"的手法办,不设门禁。

## ADR-021 契约模板按「接口面」切,不按项目类型切

**背景** `CONTRACT_SKELETON` 硬编码了函数级形状(`函数名(参数: 类型) -> 返回类型`、
参数约束表、抛出)。库项目合适,HTTP 服务、CLI、数据管道、UI 全得现编 ——
而"现编"正是文档规范要消灭的东西。

第一版方案是按项目类型发六份模板(library / service / cli / pipeline / ui / generic)。
**评审推翻了它。**

**决策** 发一份**小节形状菜单**,挂在契约小节上,不挂在项目上。

**理由**
- **按项目类型切会立刻碰壁**:批处理作业十有八九本身就是 CLI;服务也要写幂等性。
  说明那不是几种项目,是若干组正交字段被打包成了几个套餐。
- **一个仓库同时有服务和 CLI 是常态**,按项目类型切时它必须二选一;
  按接口面切,这个问题根本不存在 —— 端点小节用端点形状,命令小节用命令形状。
- **`--kind` 在运行时无处安放。** 规则 4 的「什么算可观测」按接口面不同,
  而 tester 读契约小节时需要那个键。写进 config 就成了持久化的模式开关,
  **直接撞 ADR-017**(mode 会分裂协议语义,而且项目身份是会漂的 ——
  一个库长出 CLI 是常态)。挂在小节上,键就在读者已经打开的那一页。
- **协议里已有先例**:`依据` 就是逐小节的字段。契约形状没理由比它粗一个量级。

**顺带定死的一条硬线(渲染视图)** 契约只能用无障碍树的语言(role + 可访问名)、
URL、发出的事件来描述。`getByTestId('submit-btn')` 能过**全部**机械检查 ——
它是渲染结果、不是内部 state —— 而 testid 是纯实现细节,那条测试就是规则 4
点名要禁的变更探测器。不写死这条,每一个 UI 结对都会滑向 testid 耦合。

**代价** 人类写契约时要自己选形状,没有"一键生成整份骨架"。
换来的是不用为每种新场景发一版模板 —— 漏一种只影响一个小节。
