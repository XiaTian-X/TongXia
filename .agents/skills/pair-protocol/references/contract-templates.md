# 契约小节的形状

按需加载。人类写 `docs/CONTRACT.md` 时抄这里。

## 按接口面选,不按项目类型选

一份契约里不同小节用不同形状是**常态**,不是例外:一个仓库同时有 HTTP 端点
和 CLI 命令太普通了。所以这里发的是**小节形状菜单**,不是六份整文件模板。

按项目类型切会立刻碰壁:批处理作业十有八九本身就是 CLI;服务也要写幂等性。
说明那不是几种项目,是**若干组正交字段被打包成了几个套餐**。
而且协议里已有先例 —— `依据` 就是逐小节的字段,契约形状没理由比它粗一个量级。

**每个小节都要有 `- 依据:` 那一行**,取值见 [brownfield.md](brownfield.md)。

## 进程内调用(函数、方法、类)

```markdown
## <这一节讲什么>

- 依据: 人类定稿

### `hash_password(pw: str, cost: int = 12) -> str`

**行为** 正常路径下做什么。

**参数约束**

| 参数 | 类型 | 约束 |
|---|---|---|
| `pw` | str | 非空;长度 ≤ 1024 |

**返回** 精确到字段和类型。

**错误**

| 条件 | 抛出 |
|---|---|
| `pw` 为空 | `ValueError` |

**边界** 空、超长、null、并发。**没写的,tester 不许假设。**

**不做** 明确不负责的事 —— 这一栏拦的是 dev 的过度实现。
```

## 网络端点

```markdown
### `POST /v1/sessions`

**鉴权** 需要什么,缺了返回什么。

**请求** Content-Type + 字段表(名、类型、必填与否、约束)。

**响应**

| 状态码 | 何时 | 响应体 |
|---|---|---|
| 201 | 创建成功 | `{id: str, expires_at: int}` |
| 409 | 已存在活跃会话 | `{error: "..."}` |

**幂等性** 同一请求重放会怎样。**这一条最常被漏掉。**

**副作用** 写了什么、发了什么消息。

**不做** 不负责的事。
```

## 进程调用(CLI)

```markdown
### `mytool sync [--dry-run] <路径>`

**行为** 正常路径下做什么。

**参数** 名、必填与否、默认值。

**退出码**

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 2 | 参数错误 |

**stdout** 形状(逐行?JSON?),以及**它算不算契约的一部分**。

**stderr** 什么情况下写、写什么。

**落盘** 创建/修改了哪些文件。

**不做**
```

## 数据产物(表、文件、schema)

```markdown
### `daily_revenue` 表 / `out/*.parquet`

**输入 schema** 字段、类型、可空性。

**输出 schema** 同上。

**转换** 每个输出字段怎么来的。

**幂等性** 同一批输入跑两次的结果。

**重跑** 部分失败之后重跑会怎样。

**失败语义** 坏行是丢弃、隔离,还是整批失败。

**不做**
```

## 消息消费

```markdown
### 消费 `order.created`

**消息 schema** 字段与约束。

**处理** 做什么。

**投递保证** 至少一次 / 恰好一次;**重复投递会怎样**。

**乱序** 收到过期消息怎么办。

**幂等键** 用哪个字段去重。

**毒消息** 反复失败之后进哪里。

**不做**
```

## 渲染视图(UI)

**这一份有一条硬线,先读完再写。**

```markdown
### 登录表单

- 依据: 人类定稿

**可见内容** 用**无障碍树的语言**描述:
`role=textbox name="邮箱"`、`role=button name="登录"`。

**URL** 这个视图对应的路径,以及跳转去哪。

**事件** 交互发出什么(提交了什么请求、触发了什么回调)。

**状态转换** 提交中 / 失败 / 成功各自呈现什么(仍用无障碍树的语言)。

**不做**
```

**硬线:契约只能用 role + 可访问名、URL、发出的事件来描述。
凡是不能用这三样指认的,就不在契约里,也就不许断言。**

**视觉外观、布局、快照、`data-testid` 一律不属于可观测行为。**

理由:`getByTestId('submit-btn')` 能过**全部**机械检查 —— 它是渲染结果、
不是组件内部 state、`handoff` 会放行。而 testid 是纯粹的实现细节,
那条测试就是规则 4 点名要禁的**变更探测器**:改个 testid 测试就红,
而没有任何真实缺陷被发现。快照测试是这个失效模式的极端形态,同样过得了全部检查。

无障碍树是唯一一种"用户真的能感知、而且改实现不会无故变"的锚点。

## generic

不确定属于哪一种时用这个,但**尽量别停在这里** —— 越泛的模板越容易写出
含糊的契约,而契约含糊是这套机制唯一会致命的失败模式。

```markdown
### <名字>

**行为** / **输入** / **输出** / **错误** / **边界** / **不做**
```

## 什么算「可观测行为」——按接口面不同

规则 4 说 tester 只能断言契约里写明的可观测行为。**规则不变,清单随接口面变:**

| 接口面 | 可观测 | 明确不可观测 |
|---|---|---|
| 进程内调用 | 返回值、抛出的错误、持久化的状态、对外部系统的调用 | 私有方法名、内部调用次数、中间变量 |
| 网络端点 | 状态码、响应头与体、副作用 | 内部路由结构、中间件顺序 |
| CLI | 退出码、stdout/stderr、落盘的文件 | 内部函数分层 |
| 数据产物 | 输出 schema 与内容、幂等性 | 中间表、执行计划 |
| 消息消费 | 副作用、ack/nack、幂等表现 | 消费者内部状态机 |
| 渲染视图 | 无障碍树、URL、发出的事件 | 组件 state、DOM 结构、testid、快照、样式 |

**日志在大多数项目里不可断言** —— 它是给人看的,不是接口。
如果你的项目真的把日志当产品(可观测性平台),那就把它写进契约,
而不是默认可以断言。
