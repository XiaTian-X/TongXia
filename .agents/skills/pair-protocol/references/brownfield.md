# 接入一个已经存在的项目

按需加载。你在一个**代码结构已经固定、只有零散文档**的仓库里结对时读这里。

这里没有"存量模式"这种东西 —— 下面每一条机制在新项目里同样生效,
只是现有项目更容易撞上它们。

## 一句话:契约的方向是反的

新项目是 **契约 → 测试 → 代码**:人类先写规格,tester 照规格写断言。

现有项目唯一可行的方向是 **代码 → 测试 → 契约**:代码是唯一的事实来源,
而它的行为大部分没有被任何文档正确记录过。

所以接入一个现有项目时,`docs/CONTRACT.md` 不是一次写完的,是**一节一节长出来的**,
而每一节的出生方式决定了它能不能被拿来写断言。

## 老文档只能当线索

存量项目文档的头号病症是**过时**,而它的错误方式极其危险:

> README 写"找不到返回 null",实际代码抛异常。
> tester 照文档写断言 → 红 → dev 以为发现了 bug → 改了行为 → 线上炸。

这条链上**每一步都符合协议纪律**:红绿全对,评审也挑不出毛病。
双方都在拿一份错的规格当权威,而协议里没有任何一环会发现这件事。

所以契约的每个小节必须写明它凭什么可信:

```markdown
## 计费周期换算

- 依据: 人类定稿
```

| `依据` | 含义 | tester 能据此断言吗 |
|---|---|---|
| `人类定稿` | 人类逐条确认过 | ✅ |
| `考古观察@<sha>` | agent 读过代码、跑过代码之后写下来的现状,并记下当时的 commit | ✅ |
| `已有文档 <路径>(待核实)` | 从老文档抄来的线索 | ❌ |

`verify-setup` 与 `claim` 都会查。**不可断言的小节上开不了 `feature`/`bug`/`refactor`**——
脚本会告诉你唯一的出路:先做一个 `[cover]` 工作项。

契约是冻结文件,agent 改不了。**等级只能由人类抬升** —— 这不是官僚,
这是"契约漂移是唯一会致命的失败模式"那条设计的直接推论。

## 标准节奏

```
[cover]  建立事实         tester 写特征测试 + 起草契约小节到 docs/reviews/
   ↓
人类定稿                  把草案并进 CONTRACT.md,依据改成「人类定稿」
   ↓
[refactor] / [feature] / [bug]     现在才能在这块地基上动工
```

不要跳过第一步。跳过它,你就是在拿一份没人核实过的规格开工。

## `cover` 回合:你在建立事实,不是在抄文档

`cover` 是唯一可以断言**契约里还没有的行为**的场景。代价是 `handoff` 会要求
你在 `docs/notes/<ID>.md` 里交出两个小节:

```markdown
## 行为来源

你怎么确认它当前就是这样的:读了哪段代码、跑了什么、看到了什么输出。
契约里没写这条行为时,这就是断言的唯一依据。

## 我冻结了哪些可疑行为

看着像 bug、但你照原样固化进测试的行为。没有就写"没有,逐条对过契约"。
```

**第二节是要害。** 特征测试的固有风险是**把缺陷一起焊死** —— 你照着现状写断言,
而现状里可能就有 bug。而且红绿抓不到它:cover 全程都是绿的。

对方在 `review-test` 要回答的问题也因此变了:不再是"这断言合不合契约",
而是 **"这行为是有意的,还是我们刚把一个缺陷变成了规格?"** 你不写,它无从判断。

如果新写的测试**变红了** —— 那不是失败,是你发现了真实缺陷。
告诉人类改成 `[bug]` 类型,由 dev 来修。不要放宽断言让它变绿。

## `refactor` 回合:先证明有网

PLAN 里的 `refactor` 必须声明保护它的测试:

```markdown
- [ ] **R1** [refactor] — 把计费换算拆出来
  - 对应契约:`docs/CONTRACT.md` → 计费周期换算
  - 保护测试: tests/billing/
```

`claim` 会查这个路径真实存在、且落在 tester 的路径之下。

理由:重构回合全程是绿的,而**绿的测试按定义没抓到任何问题**。那片代码本来
就没有测试时,"绿"什么都不证明,`review-impl` 只能凭 diff 猜 ——
这是协议唯一 police 不了的场景。

脚本验证不了那些测试真的覆盖了你改的代码(和 `对应契约` 一样,它只能验证
指向的东西存在)。**这是对 PLAN 的强制约束,不是覆盖率验证。**

## 结构固定?那就切范围,不动结构

现有项目的代码结构不能改,但可以圈定本轮能碰的范围:

```json
"scope": ["src/*/java/com/acme/billing/**"]
```

范围外的改动一律被 `handoff` 拒。存量项目最危险的不是结构不合适,
是**蔓延** —— 改一个计费 bug,顺手动了三个公共工具类。有了 `scope`,
"要不要扩大范围"变成人类的显式决定,而不是 agent 的顺手。

评审目录(`shared_paths`)与记忆层永远豁免:它们是散文,不是代码。

## 老套件红着、或者慢得没法每回合跑

**门禁套件可以收窄,但它必须是绿的。**

```json
"test_cmd":      "pytest tests/billing",   // 门禁,必须绿,不变量全押在它身上
"full_test_cmd": "pytest"                  // 只在工作项完成时跑一次,只报告不阻断
```

全量套件红时,`handoff` 仍然成功(范围外的代码这对结对本来就无权修,
阻断等于死锁),但**返回码是 2**,并要求你报告而不是宣布"完成"。

在 `docs/reviews/baseline.md` 写明放弃了哪些用例、为什么。
**这不是把"绿"放宽,是缩小它的范围并留痕。**

## PLAN 不是从零规划

现有项目通常已经有 issue tracker、TODO、需求列表 —— 不是白纸,是**粒度不对**。
人类的活是从既有清单里挑本轮范围内的,重切成"一个回合写三五个用例就覆盖完"。

## 最后:`影响路径` 是你留给这个遗留系统的索引

`docs/DECISIONS.md` 每条的 `影响路径` 字段是检索键。今后谁要动这些路径,
`status` 会自动把这条结论摆到他面前。

在一个没人完全理解的老系统里,这份索引最终可能比这轮改的代码更值钱。
写准写全。
