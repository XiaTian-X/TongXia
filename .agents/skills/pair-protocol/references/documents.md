# 文档规范

按需加载。你要往 `docs/` 写任何东西之前读这里。

**一句话:文档的种类由协议决定,不由项目领域决定。** 契约小节的形状会随
接口面变(见 [contract-templates.md](contract-templates.md)),但"有哪几种文档"
是固定的 —— 每一种都因为协议的某个需要而存在。

## 总表

| 文档 | 谁写 | 什么时候 | 规范名 | 脚本拦不拦 |
|---|---|---|---|---|
| `docs/PLAN.md` | **人类** | 开工前 | 冻结 | 格式、类型、`对应契约` 行 |
| `docs/CONTRACT.md` | **人类** | 开工前;变更需双方同意 | 冻结 | 小节存在、`依据`、重名 |
| `docs/notes/<ID>.md` | 当前回合持有者 | 随手 | 由脚本推导 | 只在 `refactor` / `cover` 查小节 |
| `docs/DECISIONS.md` | 双方 | 四个强制时刻 | 固定 | 四字段、长度、追加式 |
| `docs/reviews/<ID>-*.md` | 评审方 | 评审回合 | `<ID>-` 开头 | **命名** |
| `docs/reviews/<ID>-dispute.md` | dev | `impl` 阶段提异议 | 固定 | **必须存在 + 三小节** |
| `docs/reviews/contract-change-<ID>.md` | 任一方 | 发起契约变更 | 固定 | **四小节**(按文件名触发) |
| `docs/reviews/setup-verification.md` | 结对的一方 | 开工前一次 | 固定 | 长度、**逐节点名**(作者声明是参数,不写在文件里) |
| `docs/reviews/baseline.md` | 人类 | 收窄门禁套件时 | 固定 | 两小节;缺失只警告 |
| 提交正文里的四段 | 双方 | 见下 | —— | 非空、结构 |

最后一行容易被忘:`--allow-deletion`、`--no-decision`、`--checked`、`--uncovered`
是 agent 产出的、进 git 的、**对方必读**的文字,只是它们不落文件。
`--checked` / `--uncovered` 的强制力有一半正来自"它进提交正文,对方在 `inbox` 里
必然看到" —— 所以**它们必须自包含,不能只写「详见某文件」**。

## 哪半是脚本拦的,哪半靠你

照 `architecture.md` 那张强制力分布表的写法,这里也说清楚:

| 规则 | 强制方式 | 失效条件 |
|---|---|---|
| 评审文件命名 | 脚本拒绝 | 改代码 |
| 异议三小节存在且够长 | 脚本拒绝 | 每节写满 40 字废话 |
| 契约变更四小节 | 脚本拒绝(**按文件名触发**) | 换个文件名 |
| 契约审查逐节点名 | 脚本拒绝 | 「以下小节均无歧义:A、B、C」 |
| 起草人身份声明 | 脚本拒绝(**`--drafter` 参数**,不搜措辞) | 声明了但不当回事 |
| 考古 sha 真实存在 | 脚本拒绝(git 说了算) | 用一个真 sha 但没真读代码 |
| **评审意见有没有实质** | ❌ 只有 prose + 对方评审 | 双方都敷衍 |
| **契约到底含不含糊** | ❌ 只有人类 | 人类偷懒 |

最后两行是真实边界。**逐节点名只保证覆盖面,不保证消歧** ——
它挡得住"通篇没提任何一节",挡不住"每节都提了、每节都说没问题"。

还有一处已知的松:小节名很短时(比如 `## X`),正文里任意一次提及都算点名。

## 模板

### 评审记录 `<ID>-<阶段>.md`

```markdown
# W1 review-impl(tester → dev)

裁决:approve

## 我检查了什么

具体到行。"看过了没问题"不算 —— 写你实际打开了哪个文件、验证了什么。

## 未覆盖

你知道还没被覆盖到的东西。真想不出就写"无",那是一句被记录在案的主张。
```

同一阶段第二次评审用 `-2`。**别改写上一份** —— 那是已经进过提交记录的证据。

### 异议 `<ID>-dispute.md`(dev 在 impl 阶段打回测试)

```markdown
## 哪条用例

指到文件和行。

## 和契约的哪一条矛盾

引契约的原话,说明为什么两者不可能同时成立。

## 应该改成什么

具体的修改建议,不是"改对就行"。
```

**这条路径豁免红绿不变量 —— 全协议只有它豁免。** 换来的代价就是把话说清楚:
对方看不到你的对话,指不出是哪条、矛盾在哪,它无从下手。

### 契约变更请求 `contract-change-<ID>.md`

```markdown
## 现在的契约是什么

## 为什么不行

具体到会导致什么错误行为。"不够优雅"不是理由。

## 提议改成什么

## 影响哪些测试和实现
```

对方在自己的回合里必须在**同一份文件**追加「同意」或「反驳」。
只有请求没有回应,人类就是拿单方面材料去改契约 —— 那仍然是契约漂移,
只是这次有纸面。

### 契约审查结论 `setup-verification.md`

```markdown
# 契约审查结论

## <契约里的每一个被引用的小节名>

返回值精确到能写断言吗?错误条件穷举了吗?边界(空、超长、null、并发)
写明了吗?有没有哪句话可以有两种合理解读?
```

**必须逐节点名。** 把契约整段粘进 ``` 围栏不算 —— 围栏内容会被剥掉。

**起草人声明不写在这份文件里,它是命令参数**(见
[ADR-024](../../../docs/design-decisions.md)):

```
pair.py verify-setup --drafter other   # 我没参与契约起草
pair.py verify-setup --drafter self    # 我参与了,结论证明力打折
```

声明进提交正文,对方在 `inbox` 里必然看到 —— 和 `--allow-deletion` /
`--no-decision` 同一手法。为什么要问:起草人审自己写的东西看不见自己的盲区,
而这道门守着协议自称唯一会致命的失败模式,读结论的人有权知道是谁写的。

### 基线说明 `baseline.md`

```markdown
## 放弃了哪些用例

## 为什么
```

配了 `full_test_cmd` 就意味着门禁套件被收窄过,**红绿不变量的覆盖面被缩小了**。
这份是"缩小到哪里"的唯一留痕。没有它,以后没人知道当年绿的是哪一半。

## 为什么评审记录不规定必填小节

`--checked` / `--uncovered` 已经在逼你写出实质,而且它们进提交正文。
再给评审文件规定必填小节,风险是把好评审变成填模板 ——
**而评审是全协议触发最频繁的动作,填模板的风险全集中在这里。**

所以现在只管命名。这条以后可能会变(见 `improvements.md`),
但要变得有证据:`pair.py report` 会盯着评审文本的长度分布,
退回条件事先写死在 ADR-020 里,不是"看着办"。
