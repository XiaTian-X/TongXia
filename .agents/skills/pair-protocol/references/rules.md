# 硬性规则详解

按需加载。`handoff` 拒绝你的时候、或者你要写评审意见的时候读这里。

## 1. 目录边界

`handoff` 会跑 `git status --porcelain` 并逐个文件比对 `.pair/config` 里的
路径白名单。越界文件会被逐条列出并拒绝提交。

**被拒了怎么办:** 撤销越界改动。如果你确信对方的代码有问题,把问题写进
`docs/reviews/`,在评审回合用 `handoff changes` 打回。**不要自己动手改。**
你以为的"顺手修一下"会让对方下一回合看到无法解释的 diff。

## 2. dev 不许改测试

一条都不行。包括:改断言、改测试数据、`skip`/`xfail` 标记、删除用例、
"临时"注释掉。

**测试写错了怎么办:** 这是有正式出路的,不要硬着头皮实现一条错的断言。

1. 在 `docs/reviews/` 写清楚:哪条用例、和契约的哪一条矛盾、应该改成什么
2. `pair.py handoff changes "测试与契约矛盾,详见 docs/reviews/<文件>"`

回合会退回 tester 的 spec 阶段,由 tester 修测试。

**这条路径对红绿不变量豁免** —— 你正是因为测试写错、弄不绿才打回的,
拿"必须 GREEN"卡你等于逼你照错误断言写实现。但异议**必须写成文件**:
对方看不到你的对话,不写下来等于没提,`handoff` 会拒绝。

边界仍然生效:你只能写 `docs/reviews/`,不能顺手把测试改了。

## 3. 不许硬编码蒙混

以下都算作弊,评审时**必须**被打回:

- 针对测试输入特判(`if input == "test@example.com": return True`)
- 返回写死的期望值而没有真实逻辑
- 把逻辑塞进只在测试环境生效的分支
- 捕获所有异常并返回测试期望的默认值

判断标准:**换一组符合契约但没出现在测试里的输入,这段代码还对吗?**
不对就是作弊。

## 4. tester 不许断言实现细节

只能断言 `docs/CONTRACT.md` 里写明的可观测行为:返回值、抛出的错误、
持久化的状态、对外部系统的调用。

**禁止断言:** 私有方法名、内部调用次数、调用顺序、日志文本、
中间变量、类的内部结构。

原因:这类断言会把测试变成变更探测器——实现方稍作重构测试就红,
但没有任何真实缺陷被发现。这比没有测试更糟,因为它会训练双方
忽略红色。

**契约里没写的边界情况不能凭空假设。** 你觉得该有,就走契约变更流程,
不要直接写成断言。

## 5. 一回合一个用例

一次提交 20 个失败用例会让 dev 无法定位、无法最小实现、无法有效评审,
直接退化成"批量生成代码"。

一组紧密相关是可以的:比如同一个函数的正常路径 + 空输入 + 越界输入,
三条一起提。判断标准:**dev 能不能用一次连贯的实现让它们全绿。**

## 6. 评审必须有实质

`pair.py handoff approve` 和 `pair.py handoff changes` 都强制要求附理由,空字符串会被拒。
**评审回合同时是只读的**——只能写 `docs/reviews/`,夹带任何代码改动都会被拒绝。
但脚本拦不住"看起来不错"这种废话——这是你自己的职业操守。

**approve 时至少写明你实际检查了什么。** 比如:
> 检查了 hash 函数无特判、cost 参数取自配置而非常量、
> 空密码路径抛的是契约里写的 ValueError。未覆盖:超长密码,下轮补测试。

**changes 时必须具体到行。** "实现有问题"不是评审意见,
"`src/auth.py:42` 对 `test@example.com` 特判,换任意其他邮箱就会失败"才是。

详细意见写进 `docs/reviews/`,`handoff` 的理由字段只放摘要。

## 7. 状态文件不可篡改

`.pair/state.json` 记录当前阶段、工作项和打回计数。它**只由 `pair.py` 写**,
时机是边界校验通过之后、提交之前。

`handoff` 和 `claim` 开头都会检查它在工作区里有没有被改动过。改动即视为
伪造回合归属:自动还原为上次提交的版本,并拒绝本次操作。

这不是可以商量的。改这个文件能让你抢到不属于你的回合、清掉打回计数绕过
死锁闸——也就是让整套协议失效。如果你认为状态不对,跑 `status` 看,
然后告诉人类,不要自己动手。

## 8. 删除测试要显式声明

删掉一条已有测试等于悄悄缩小验收范围,而且如果整体仍然是红的,红绿不变量
抓不到它。所以 `handoff` 会单独检测 `tests/` 下的删除并拒绝。

确有正当理由(比如该用例的断言已被新用例完全覆盖)时显式声明:

```
pair.py handoff "说明" --allow-deletion "删除理由"
```

理由和被删文件会写进提交记录正文,对方在 `inbox` 里必然看到。
这不是放行,是**强制留痕**——决定权仍在评审的对方手里。

## 9. 工作项类型决定纪律

PLAN 里 `- [ ] **W1** [类型] — 标题` 的类型标记不是装饰,它换掉整条阶段序列
和红绿不变量。省略则为 `feature`。

### `feature` / `bug` —— 先红后绿

四阶段全走。spec 必须交出 RED,impl 必须交出 GREEN。这是默认纪律,
**修 bug 是它最好的场景**:tester 写一条复现缺陷的失败测试,dev 修绿。

### `cover` —— 为已有行为补测试

跳过 impl,只有 spec → review-test。全程 GREEN,因为被测行为本来就是对的。

正因为全程绿,红绿不变量抓不到"什么都没干就交接",所以 `handoff` 单独检查
**这一回合必须真的新增或修改了测试文件**。

**dev 在 review-test 回合的核心问题只有一个:这条测试真的能发现回归吗?**
一条永远为真的断言(`assertIsNotNone(result)`)在 cover 场景里毫无价值,
必须打回。判断标准:如果实现被改坏,这条测试会不会红?

**如果新写的测试变红了**,说明发现了真实缺陷。这不属于 cover 的范围 ——
告诉人类把它改成 `[bug]` 类型,由 dev 来修。不要在 cover 回合里放宽断言
让它变绿,那是在掩盖缺陷。

### `refactor` —— 不改行为地重构

跳过 spec,只有 impl → review-impl。全程 GREEN。dev 重构,tester 评审。

dev 碰不到 `tests/`(边界保证),所以测试不可能被削弱。**tester 的评审价值
在于判断这次重构有没有悄悄改变行为** —— 尤其是测试没覆盖到的那些行为。
发现覆盖缺口就记下来,之后开一个 `[cover]` 工作项补上。

## 契约变更流程

实现到一半发现 `docs/CONTRACT.md` 的接口设计有问题,这是**正常且预期的**。
硬着头皮实现一个错的契约,比停下来改契约代价大得多。

1. 在 `docs/reviews/` 写变更请求,必须包含:
   - 现在的契约是什么
   - 为什么不行(具体到会导致什么错误行为)
   - 提议改成什么
   - 影响哪些已有测试和已有实现
2. `pair.py handoff changes "契约变更请求:<摘要>"` 打回。
3. 对方在自己的回合评估,同意或反驳,写进同一份 `docs/reviews/` 文件。
4. **双方都同意后,由人类修改 `docs/CONTRACT.md`。**

agent 不能自己改契约文件,这是刻意设计的。契约漂移——tester 测
`login() -> token`、dev 写 `authenticate() -> Session`,两边各自都"对"、
合起来是废的——是这套机制唯一会致命的失败模式。

## 死锁保护

同一工作项累计被打回 3 次,`handoff` 会拒绝继续轮转并要求交给人类。

触发时不要试图绕过(比如改 `.pair/state.json` 里的计数器——那会被篡改检测拦下并还原)。把分歧双方的立场写清楚,交给人类裁决。

## 10. 记忆:写下来,和被读出来

你和对方每一回合都是新来的:看不到彼此的对话,也不共享各自工具的记忆。
文档解决不了这件事 —— 文档记的是**正空间**(现在是什么),而重构和排查里
值钱的知识几乎全在**负空间**:试过什么失败了、否掉了什么、哪里踩过坑。

所以协议里有两个位置,分别对应两种寿命:

| | `docs/notes/<ID>.md` | `docs/DECISIONS.md` |
|---|---|---|
| 寿命 | 工作项级,项一关就没人再读 | 项目级 |
| 格式 | 无,随手写 | 四个必填字段,受校验 |
| 内容 | 负空间:试过什么没成、哪里拿不准 | 结论与裁决 |
| 写法 | 想写就写 | 追加式,不能改历史 |

**不要复述 diff。** 对方能看到 diff,看不到的是你为什么走了这条路。

### 召回挂在 `status` 上

`status` 在轮到你时会自动注入:本工作项笔记全文 + 影响路径与本回合相干的
决策条目。这不是可选的礼貌,是设计:**存了没人读等于没存**,而 `status` 是
协议里唯一强制、且每个 harness 都会跑的时刻。

所以 `影响路径` 字段要写准写全 —— 它是检索键。今后谁要动这些路径,
这条结论就会被摆到他面前;写漏了,它就等于不存在。

### 追加式不是洁癖

已经写下的条目是双方共识的凭据。改它等于伪造共识,和手工改
`.pair/state.json` 同级,`handoff` 一样会拒绝。

要推翻旧结论,**追加**一条新条目说明为什么推翻。旧的留着,因为"我们曾经
这么想过、后来发现不对"本身就是最值钱的那类信息。

### 为什么单条限 1500 字符

这条结论此后**每一次** `status` 都会被读一遍。一份没人读的长文档比没有
文档更糟——它会让人以为知识已经沉淀了。超长会被 `handoff` 直接拒绝,
压缩到结论和理由本身,过程不要写进来。

同理,条目里**故意没有"分析"字段**。只共享事实和裁决,不共享推理过程 ——
两边共享同一条推理路径,就更容易想到一块去,而互相点头正是这套机制
从头到尾在防的事。你们记忆不同不是缺陷,是对抗性的来源。

### 四个强制时刻

其余时候想写就写,这四处不写会被拒绝:

**① `refactor` 的实现回合必须交出考古记录。**
三个小节:`## 现状考古` / `## 我保留了哪些契约外行为` / `## 我不确定的地方`,
每节都要有实质内容。

理由是这个:重构回合里 tester 要判断的是"行为有没有被悄悄改掉",可它手上
测试全程是绿的(绿的测试按定义没抓到问题),契约写的是目标而不是现状。
真正做过考古的是你 —— 你读了老代码,知道哪里可疑。不写下来,对方只能凭
diff 猜,而 `review-impl` 就退化成走过场。

**② 同一工作项第二次被打回。**
来回两次说明这不是笔误,是真实分歧。第三次会撞上死锁闸交给人类,而人类
到时候需要看到你们到底在争什么。(第三次不再要求写 —— 那时该说的已经
说完了,再要一份文档只是噪音。)

**③ 契约在工作项期间被改过。**
`claim` 时记下了契约的 blob sha,完成时会比对。契约变更是重新推导代价最高
的事:此后每个回合都会拿改过的契约当作理所当然,而改它的理由谁都看不到了。

**④ 工作项完成、而它的笔记还有内容。**
笔记是工作项级的,这一项关掉之后没有任何回合会再读到它。要么晋升成一条
决策,要么显式声明没有可沉淀的:

```
pair.py handoff approve "理由" --no-decision "为什么没有"
```

声明进提交记录,人类看得见。和 `--allow-deletion` 一样,这不是放行,
是强制留痕。

### 记忆层不是新的写权限口子

`docs/notes/` 和 `docs/DECISIONS.md` 两个角色都能写,评审回合也能写 ——
它们是散文,不是代码。但边界一条都没放松:评审回合夹带代码改动照样被拒。

另外,记忆层**不属于** `shared_paths`。异议举证("提了异议就必须写下来")
认的是 `shared_paths` 下的文件 —— 如果笔记也算数,那条防护就会被随手写的
笔记满足,等于被静默削掉。`verify-setup` 会检查你有没有把它们配重叠。
